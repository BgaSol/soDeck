# SoDeck 在线升级功能规划

日期：2026-10-20
状态：功能规划，尚未实现
依据：当前工作区代码、现有 GitHub 发布脚本与公开 Release，以及 Tauri 2 官方 Updater 文档。

## 1. 意图与目标

用户希望继续沿用“发布 GitHub 新版本并附带安装包”的方式，让已安装 SoDeck 的用户在 App 内发现新版本、查看更新说明、下载并安装，减少反复打开 GitHub、挑选平台和手动覆盖安装的步骤。

推荐默认体验：自动检查、轻量提醒、主动下载、确认后安装。SoDeck 是远程工作台，更新不能突然中断用户的远程工作。

成功标准：发布者正常发布一次版本，受支持安装方式的用户可以从 App 内完成升级；配置与历史保留，安装前明确处理活动任务和未保存内容，失败后有可理解的处理入口。

## 2. 现状与可复用能力

| 项目 | 已确认的现状 | 对规划的影响 |
| --- | --- | --- |
| 应用技术 | Tauri 2 + React + TypeScript + Rust | 优先接入官方 Updater，Rust 统一协调更新状态 |
| 当前版本 | 本地配置为 0.1.1；检查时 GitHub 最新正式 Release 为 v0.1.1 | 已发布旧版没有升级入口，需一次手动安装新基线版本 |
| 发布链路 | tag 触发检查、跨平台构建、上传草稿、验证附件、公开 Release | 在现有链路增加升级产物、签名与清单 |
| 安装格式 | Windows x64 EXE / MSI、macOS arm64 / x64 DMG、Linux x64 DEB / AppImage | 依据运行平台、构建架构与安装格式选择升级策略 |
| 关于入口 | 点击品牌打开关于窗口，当前展示名称、版本与描述 | 适合增加检查更新入口与版本状态 |
| 系统设置 | 已有外观、终端复制粘贴和开发者设置 | 增加软件更新区，沿用现有界面风格 |
| 多窗口 | 主窗口、独立 SSH、编辑器、日志、容器终端等 | 检查和下载全应用只执行一份，状态跨窗口同步 |
| 退出保护 | 已统计终端、日志、未保存文件、文件任务、Docker 操作与端口转发；后端负责清理退出 | 安装必须复用并加强退出协调，不能直接调用安装后退出 |
| 数据兼容 | 服务器数据库有结构检查及不兼容重建入口，尚不能据此保证任意跨版本自动迁移 | 在线升级必须明确兼容范围，不能把重建数据库作为升级默认步骤 |

## 3. 第一版功能范围

### 3.1 入口与信息

在现有“关于 SoDeck”窗口增加当前版本、更新状态和“检查更新”。发现新版后提供“查看更新”，进入同一个软件更新区域。

在“系统设置”增加“软件更新”区，包含：

- 当前版本、可用新版本、发布日期。
- 最近一次检查时间与结果；失败时显示最近成功检查时间，避免把失败显示为已是最新。
- 更新摘要，必要时展开完整说明；提供打开 GitHub 版本页面的入口。
- 根据状态显示检查更新、下载更新、安装并重启、稍后、重试等操作。
- “自动检查更新”开关，默认开启；关闭后仍可手动检查。

独立 SSH 窗口可以查看更新状态，通过“前往主窗口更新”聚焦主窗口；安装确认统一放在主窗口。避免多个窗口分别弹出升级对话框。

发现新版本时，在品牌或设置入口提供小型更新标记；每个版本最多主动显示一次非模态提醒，不抢终端焦点。

### 3.2 检查规则

建议初始参数：启动完成后延迟约 30 秒，在距最近成功检查超过 24 小时时检查；长期运行时每 24 小时检查一次。手动检查不受该间隔限制。

检查失败使用有上限的退避，建议 15 分钟、1 小时、6 小时；不高频重试，不因离线阻塞启动。自动检查失败只记录状态，用户主动检查失败时展示原因与重试入口。

只接收正式稳定版，只提示严格高于当前版本的更新，按语义版本比较。草稿、预发布和旧版本不进入稳定更新通道。用户自行安装了更高版本时，不提示降级。

支持“稍后提醒”和“跳过此版本”。跳过仅抑制该版本的自动提醒，手动检查仍能看到它；更新的版本正常提醒。

### 3.3 下载体验

用户点击“下载更新”后后台下载，可继续使用终端和其他功能。关闭更新界面不停止下载。

展示已下载大小和进度；服务器没有提供总大小时显示“已下载 xx MB”，不制造百分比。下载失败提供重试与手动下载入口。

第一版不承诺跨进程缓存、暂停续传、断点续传或差分下载。退出 App 可以终止正在进行的下载；重新打开后可重新下载。页面关闭后仍保持下载状态，这与应用退出后的恢复分别处理。

下载完成并验证通过后进入“已准备好”，提供“安装并重启”和“稍后”。不因下载结束而自动安装，不在普通退出时偷偷安装。

### 3.4 安装前工作保护

点击“安装并重启”后，后端重新获取全应用活动状态，列出受影响工作及跳转入口：

| 工作状态 | 第一版处理 |
| --- | --- |
| 有未保存的远程文件 | 阻止安装，提供返回编辑器处理；保存或用户在原编辑器明确放弃后才能继续 |
| 正在上传、下载、rsync 或 Docker 文件传输 | 等待完成，或回任务面板手动取消后再安装 |
| Docker / NetBird 等管理操作正在执行或结果待确认 | 阻止安装，先完成操作或核对结果；退出客户端不等于远端操作停止 |
| 活动 SSH / 容器终端、日志窗口、资源监控 | 提示将断开或停止接收，用户确认后统一关闭 |
| 活动端口转发 | 明确提示转发与其业务连接将中断，用户确认后关闭 |
| 待处理的非运行任务 | 提供查看入口并说明影响，根据任务类型确认后继续，不清除任务记录 |

确认到安装之间设置应用级安装准备状态，阻止新建连接、启动任务或新增编辑，避免检查后又产生工作。后端再次核验状态，完成清理、落盘后才交给安装器。

应从现有 `quit_app` 提取可复用的关闭准备流程，使“普通退出”和“升级安装”共用清理逻辑，但各自执行最后一步。不能直接复用会执行 `app.exit(0)` 的命令后再期望当前进程继续启动安装。

准备失败时取消安装并解除全局阻止状态，显示具体原因；已经断开的连接不声称能够自动恢复。安装器接管后的系统权限确认和失败，通过下次启动核对结果。

### 3.5 升级后反馈与数据

更新前记录目标版本与更新阶段。下次启动读取实际运行版本，确认达到目标后仅展示一次“已更新到 vX.Y.Z”。仍是旧版本时显示“上次更新未完成”，提供重试和手动安装。

升级保留服务器配置、认证设置、主机指纹、主题、终端偏好及已持久化的历史。保持应用标识和数据目录稳定，不重新初始化用户数据库。

第一版基线采用兼容现有数据格式的升级。之后若涉及数据库结构变更，必须增加版本化迁移与迁移前一致性备份，验证失败可恢复；不自动重建或清空数据库。备份文件需要保持原有访问保护，不上传服务器凭据。

不承诺重启后恢复 SSH 进程、传输或端口转发；需要保留的是已保存数据与可重连配置。自动回滚及完整工作区恢复不纳入第一版。

## 4. 平台支持与上线顺序

功能设计覆盖当前发布矩阵，但应分别验证每一种安装方式后开放安装按钮。

| 平台与安装方式 | 推荐升级行为 | 上线要求 |
| --- | --- | --- |
| Windows x64 NSIS EXE | App 内下载、校验、确认后启动对应安装器并重启 | 第一优先验收，验证用户级与需提权安装、取消安装、路径与数据保留 |
| Windows x64 MSI | 验证同格式升级后开放 App 内安装；完成前提供更新提醒和对应 MSI 手动下载 | 不默认将 MSI 用户转成 NSIS；明确安装来源识别和 Windows Installer 升级关系 |
| macOS arm64 / x64 | 下载对应构建架构的应用升级归档，替换后重启 | 两种架构分别验证，确认应用位置、写入权限以及当前签名方式的实际表现 |
| Linux x64 AppImage | 下载签名 AppImage，替换后重启 | 验证当前文件可写、文件权限、运行环境与启动入口 |
| Linux x64 DEB | 检查新版并提供对应 DEB 下载和手动安装入口 | 第一版不自动提权替换包管理器管理的安装文件 |
| 开发运行或无法识别的安装来源 | 显示版本信息；不开放自动安装 | 开发调试不误装正式包，未知来源给出手动下载 |

Tauri 官方文档区分了升级产物：Windows 可复用 MSI / NSIS 安装器，macOS 使用应用归档，Linux 使用 AppImage。因此不能仅凭“Release 已有安装包”就直接接通所有平台。其签名验证也是必需环节。[1]

安装来源识别是实施前的重点验证项。以应用构建架构选择产物，避免只按物理 CPU 判断，例如 Intel 构建在 Apple Silicon 的兼容运行情况。第一版允许某种安装格式先采用手动兜底，但界面必须明确说明支持范围。

当前发布说明明确尚无 Windows 商业代码签名及 Apple Developer ID 签名/公证。[2] 更新包签名用于验证更新来源；系统平台签名与公证另有用途。接入 updater 签名不会自动消除系统安装提示，macOS 的分发体验须通过实际打包升级验证。

## 5. 发布端方案

推荐采用“GitHub Releases + 静态更新清单 + Tauri Updater”，第一版无需自建升级服务器。官方支持静态清单及 GitHub Release 附件形式的更新源。[1]

在现有 Release 中新增：

- `latest.json`：版本、日期、更新说明、各更新目标的下载地址和签名内容。
- 与升级目标对应的签名文件。
- macOS 额外的应用升级归档；其他平台按选定格式复用正式产物。

清单下载地址固定到具体版本 tag 和文件，不让已开始的下载随最新版本改变。Windows 两种安装格式需要不同目标映射，不能在同一个平台键中任意选取 EXE / MSI。

现有附件收集与校验逻辑严格要求固定文件列表，必须同步修改 `release-assets.mjs` 和 `publish-release.mjs`，不能只在 workflow 多传几个文件。

推荐发布顺序：

1. 校验 tag、源码版本与发布策略。
2. 在各平台完成既有检查、构建及升级产物签名。
3. 汇总全部产物，生成统一更新清单与文件校验表。
4. 校验版本、架构、安装格式、签名对应关系、附件数量与更新说明。
5. 上传草稿并核验附件；任一必要产物失败则保持草稿，不影响旧版本检查。
6. 全部通过后公开 Release，并确认 stable 的 latest 指向本次允许发布的较新版本；历史维护版本不能意外替换稳定通道。
7. 对公开清单和目标下载地址进行检查，用真实旧版验证一次升级。

签名私钥放在 GitHub Actions Secrets，并离线保管恢复副本；客户端仅携带公钥。发布签名过程只在可信版本发布上下文运行，不向普通 PR 构建开放私钥。私钥丢失或轮换必须有单独方案。

更新说明增加面向用户的新增、改进、修复和注意事项，App 内优先展示简明摘要。清单和 GitHub 发布说明从同一份版本说明生成，避免两处文案分叉。

默认更新源使用 GitHub Release 的稳定清单地址，产物仅来自配置的可信来源。考虑 GitHub 下载重定向，不把合法 CDN 重定向误判为异常；发布说明以安全的文本或受限 Markdown 展示。

## 6. App 内部职责建议

### 后端

新增应用级更新管理模块，统一负责检查、版本判断、更新对象、下载进度、错误映射、安装准备和结果记录。使用单一运行任务和状态广播，避免多窗口重复下载与重复安装。

后端封装 updater，前端不能提交任意下载地址、任意执行路径或绕过安装前检查。安装命令仅允许主窗口发起，符合当前主窗口管理全应用退出的模型。

更新偏好沿用 `system_settings.rs` / `settings.json`；运行状态与更新结果记录单独管理，避免每个下载进度都写配置文件。新增字段要兼容已有设置文件。

### 前端

增加复用的更新状态订阅和软件更新区，在关于窗口与系统设置展示相同状态。当前版本以运行应用信息为准，并由发布检查保证打包与界面版本一致。

更新错误分为：网络不可用、更新清单异常、当前安装方式不支持、下载失败、签名验证失败、安装准备受阻、安装权限或安装器失败。每类错误给出具体操作，详情允许复制但不包含认证数据。

### 状态与按钮

| 状态 | 主要显示 | 可用操作 |
| --- | --- | --- |
| 未检查 | 当前版本、检查时间 | 检查更新 |
| 检查中 | 正在检查 | 禁止重复检查 |
| 无更新 | 已是最新版本 | 再次检查 |
| 发现新版 | 目标版本、日期、更新说明 | 下载更新、稍后、跳过 |
| 下载中 | 大小与进度 | 关闭面板继续使用 |
| 已准备好 | 更新已下载并验证 | 安装并重启、稍后 |
| 安装准备受阻 | 需要处理的具体工作 | 前往处理、重新检查 |
| 安装中 | 正在安装，请等待 | 不再接受重复安装 |
| 检查或下载失败 | 失败原因 | 重试、手动下载 |
| 签名验证失败 | 无法确认更新来源 | 拒绝安装、重新下载、查看发布页 |
| 仅支持手动更新 | 新版本与安装方式说明 | 下载对应安装包 |

## 7. 第一版不包含的内容

强制升级、静默自动安装、预发布频道、差分更新、断点续传、自动降级回滚、自定义任意更新源、自动选择第三方镜像，以及升级后自动恢复全部远程工作，留到有明确需求再设计。

下载慢或 GitHub 不可达时提供超时、重试和手动下载安装。若目标用户后续证明需要镜像，再引入自有可信下载源，沿用相同签名校验。

## 8. 实施阶段与交付物

1. **验证与发布基础**：确认各安装方式识别方案；配置更新签名；扩充产物、清单和发布校验；用连续两个测试版本完成 Windows NSIS 实际升级验证。
2. **App 内完整体验**：实现后台检查、关于/设置入口、更新说明、下载状态、忽略偏好和跨窗口同步；接入退出协调、任务阻止和升级结果确认。
3. **平台与异常验收**：验证 Windows MSI、macOS 双架构、Linux AppImage；不满足安装条件的格式先显示手动入口；验证网络、签名、权限、任务和数据保留场景。
4. **正式启用**：发布首个具备 updater 的基线版本，说明现有用户需手动安装一次；后续正式版本按新链路直接推送更新。

上述阶段是建议实施顺序，不代表已经完成。具体发布日期与版本号由下一次发版确定，不预先占用 0.1.2 等版本号。

## 9. 验收标准

- 新稳定版发布后，支持升级的旧版能发现更高版本；没有更新、被跳过、检查失败能清楚区分。
- 选择正确系统、构建架构及安装格式；没有匹配产物时提示不支持，不误报已是最新。
- 检查与下载不影响 SSH 工作；关闭设置后进度继续，其他窗口状态一致。
- 所有窗口只能共享一份下载和安装任务，重复点击不产生重复安装。
- 未保存文件、未完成传输、管理操作和结果待确认状态按既定规则阻止安装；安装准备期间新增工作会被拒绝。
- 活动终端、日志和端口转发的中断经过明确确认，失败的准备步骤不继续安装。
- 网络中断、错误清单、缺包、错误签名与权限问题显示明确结果；不执行未通过验证的文件。
- 升级前后的服务器、凭据、主机指纹、设置与历史一致；不兼容数据格式有明确迁移或拒绝策略。
- 只有新版本实际启动后才报告升级成功，安装取消或仍运行旧版不能误报成功。
- Release 必要附件不齐或校验失败时维持草稿；旧版本检查不受影响，已公开附件不可覆盖。
- 测试以真实打包的相邻版本升级为最终依据；组件和状态测试补充覆盖版本比较、异常状态、并发安装与安装前检查，浏览器模拟不替代安装验证。
