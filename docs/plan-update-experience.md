# 核心与插件更新体验改版规划

2026-11-06。状态：已实施，实际验证与未完成的平台验收见 [实施记录](implementation-update-experience.md)。依据当前更新代码、设置页面及 `AGENTS.md` 的产品边界整理。

## 想解决的用户问题

用户希望 SoDeck 像一个完整的桌面工具：打开就能知道是否有更新，在一个地方完成更新，最后按自己的工作节奏重启。日常维护不应要求逐个进入插件详情、读仓库字段、判断多个相近按钮，也不应打断服务器连接、终端或文件任务。

这次改版的目标是同时改善操作路径和页面层级：让名称、版本、状态、下一步动作成为主体，把更新来源和进程信息留给需要排查的人。沿用现有工作台的配色与控件语言。

## 现状与原因

本次通过代码和文档核对现有行为；未在本轮启动桌面应用或连接真实发行源，不把页面草案当作实际更新验证。

| 现状 | 对用户的影响 | 代码依据 |
| --- | --- | --- |
| 设置的“应用更新”仅展示核心，插件更新在各自详情 | 更新多项需要切页、选插件、逐项检查和下载 | `src/views.ts` 的 `settings`、`detail`、`appUpdates` |
| 启动读取更新状态，没有触发自动检查 | 必须主动找更新入口，才知道是否有新版 | `src/main.ts` 的 `start`；`src/core.ts` 的单项更新命令 |
| 官方插件区也展示已安装插件，下方又有已安装列表 | 同一个插件重复出现，页面长，安装与维护混在一起 | `src/views.ts` 的 `officialPlugins`、`plugins` |
| 列表主要显示 ID 和运行状态，没有可更新版本 | 日常判断依赖点进详情 | `src/views.ts` 的 `pluginRow` |
| 详情同时展示更新、启停、ID、API、平台、路径、进程和来源表单 | 日常动作与诊断字段同权重，界面像配置工具 | `src/views.ts` 的 `detail`、`sourceFields` |
| 部分插件提供“更新并重启”“仅下载”，核心提供“下载”“安装并重启” | 同类动作语义不统一，逐项更新容易引向多次重启 | `src/views.ts` 的 `updateControls` |
| 更新说明直接以滚动 `pre` 展示，页面叠加多个有边框区域 | 说明难扫读，边框竞争，设置弹窗空间利用差 | `src/shell.css` 的插件布局和 update 样式 |
| 更新错误共用页面级错误和 toast，`UpdateView` 只有一个通用 error | 批量处理时难指出哪一项失败、该重试检查还是下载 | `src/main.ts` 的 `pluginAction`；`src-tauri/src/updates.rs` |
| 核心更新对象和已下载字节仅保存在内存中 | 普通关闭再打开会失去核心下载准备；后续检查也可能清空已下载状态 | `src-tauri/src/desktop_updates.rs` 的 `CoreUpdater`、`discover` |

现有底层已经具备独立发版、正式版发现、本机平台/API 主版本检查、插件包校验、暂存、重启切换和初始化失败回退。应在这些机制上改进体验。

## 推荐的信息结构

设置继续使用当前应用内面板，导航调整为“插件”“更新”“外观”“应用与数据”。不为了这次改版改变整个工作台的导航或引入独立设置窗口。

### 更新页：唯一的集中维护入口

- 页头：标题“更新”、一句摘要、最近检查时间、次级“检查更新”、主要“下载全部更新”。有选择时主要动作改为“下载所选（N）”。
- 内容按“可更新”“已准备好”“检查失败或需要处理”“已是最新”“手动管理”组织；无内容的组不显示。
- 核心用“SoDeck”显示并标明“应用”；插件使用实际名称并标明“插件”。两类使用相同的行结构，后台仍各自更新。
- 每项只展示名称、当前版本 → 可更新版本、状态和一个主要动作；更新说明从该行展开。
- 有多个可更新项时提供复选框，默认选择全部可直接更新项；单项时不增加选择操作。
- 不在更新页展示未安装的官方插件；它们不是用户待维护的项目。
- 没有可更新项时显示“已是最新”，仍提供最近检查时间和手动检查入口。存在检查失败时改为“部分项目检查失败”，不能显示“全部最新”。

### 插件页：安装与启用管理

- 默认是已安装插件的完整行列表，取消常驻的空详情栏。
- 每行展示名称、用途、当前版本、当前运行状态及期望启用状态。开关改变配置后标明“重启后启用/关闭”，不假装进程已变化。
- 有更新时行内出现“可更新至 x.y.z”和“更新”快捷动作；操作与更新页共用状态和任务。
- “添加插件”打开固定官方插件选择层，同时提供“从本地目录添加”。已安装官方插件显示“已安装”，不再在主列表上方重复展示。
- 首次在线安装使用“安装并启用”，下载完成后显示“重启后启用”；不安装到一半就出现正式登记。
- 详情在当前设置内容区内打开，有明确返回；保留名称、开关、说明、日志入口。更新说明可展示，更新操作复用更新页组件。
- 来源只显示简短摘要，例如“BgaSol/soDeck”或“手动管理”；编辑仓库与标签前缀须主动展开“更新来源”。原有自定义来源完整保留，不根据官方同 ID 擅自改写。
- ID、API、目标、路径、入口、PID 和实例标识收入“技术信息”。移除记录继续沿用关闭并重启后的限制与保留文件规则。

### 应用级提示

- 主窗口“设置”入口附可更新数量或待重启标记，便于发现；不要给工作台增加一排常驻下载按钮。
- 设置导航“更新”同步显示数量。数量只包括可直接下载的新版本，不把失败、手动管理或待重启重复算作更新。
- 设置底部保留一条统一的待重启区域，跨插件页和更新页显示；点击可展开待应用清单。
- 下载和准备阶段的状态跟随核心任务；关闭设置、切换服务器、重新打开设置，不丢任务和进度。
- 更新发现以入口标记和去重消息为主。自动检查失败留在更新页，不弹出连续错误 toast，不把普通网络失败当作应用运行故障。

## 完整的操作流程

### 发现更新

1. 应用完成首屏初始化后，再延迟约 10 秒检查核心及有明确来源的已安装插件；不阻塞启动。
2. 建议默认每天自动检查一次，并提供“自动检查更新”开关。使用持久化的最近检查时间，避免频繁重开反复请求。
3. 设置打开后先展示缓存；无结果或超过检查间隔时后台刷新。手动“检查更新”立即触发一次检查。
4. 持续运行的应用在到达间隔时检查；主进程统一调度，多窗口不重复运行。
5. 同一批检查按仓库共享 Releases 列表请求，继续按各自标签前缀挑选版本；缓存只是节省请求，不把全仓库 Latest 当作每项最新版。
6. 未安装官方插件在用户进入安装流程时才发现版本。无来源的本地插件不发网络请求。
7. 失败时保存上次成功结果和时间，明确标记本次失败；遵守限流与重试等待，不不断自动重试。

### 下载与准备

1. 用户点击“下载全部更新”即可开始，默认不立即重启。也能取消部分选择或单独下载。
2. 批量任务是若干独立单项操作，建议最多同时下载 2 项，其余显示“等待下载”；不创建跨核心/插件的发布事务。
3. 页面展示每行进度；总摘要展示“已准备好 2/3 项”，只有全部大小已知时才计算总字节百分比。
4. 没有 Content-Length 时展示已下载大小和不定进度，不编造百分比。
5. 下载完成还需校验和准备。不能在网络进度到 100% 时就宣称更新已完成。
6. 核心和启用/本次启动加载过的插件准备好后标明“重启后应用”；完全关闭且资源已清理的插件直接更新登记，不启动、不强加重启。
7. 一项失败不影响其他项完成。失败行说明阶段和原因，提供“重试”；批量重试只处理失败项。
8. 第一版不添加暂停、断点续传或自动后台下载。用户退出时沿用现有更新进行中保护，给出具体原因；任务结束后可正常退出。

### 一次重启

1. 已准备好更新和插件启停变更合并为一个待应用清单。
2. 唯一的主要动作是“重启并应用（N）”，覆盖核心安装和插件切换，不逐行提供“更新并重启”。
3. 下载/准备仍进行中时重启入口不可用，并说明“等待下载和准备完成”；失败项不阻止已经准备好的项目在用户决定后应用。
4. 用户点击时复用现有服务器/工作区退出检查，展示将结束的实际连接、终端、文件任务或未保存内容。提示整合在退出流程，不叠加更新专属的多轮确认。
5. 取消退出检查时保持连接和已准备状态。允许退出后才停止插件，并由 Tauri 官方 updater 安装核心。
6. 核心安装失败要显示失败并保留可重试的包；不显示“已成功应用”。插件启动失败保留既有旧程序回退和日志。
7. 应用重开后展示实际运行版本与结果。只有确认当前版本已切换才清除待应用状态。
8. 不承诺重启恢复远程连接或任务；与现有产品约定一致。

## 状态与文案

状态是界面和错误行为的约定，不引入复杂发行状态机。

| 状态 | 行内文案/信息 | 动作 |
| --- | --- | --- |
| 未检查 | 尚未检查 | 页头统一检查 |
| 检查中 | 正在检查 | 单项检查去重；已有准备结果仍显示 |
| 最新 | 已是最新 · 当前版本 | 无主要行按钮 |
| 有更新 | 当前版本 → 新版本 | 下载更新；有多项时可选中 |
| 排队 | 等待下载 | 不接受重复入队 |
| 下载中 | 百分比或已下载大小 | 不重复检查/下载该项 |
| 准备中 | 正在校验和准备 | 不提供重启 |
| 已准备好 | 新版已准备好 · 重启后应用 | 统一重启入口 |
| 关闭插件已更新 | 已更新至新版本 · 已关闭 | 保留开关，不要求重启 |
| 检查失败 | 暂时无法检查；保留上次结果和时间 | 重试检查 |
| 下载/准备失败 | 下载中断、空间不足或包校验失败 | 重试下载；详细错误可展开 |
| 不兼容 | 新版要求核心 API x，或暂无本机架构包 | 说明原因，不允许选择下载 |
| Linux DEB 核心 | 使用系统安装方式更新 | 打开发行下载页，注明当前架构和 DEB；插件更新照常 |
| 无来源 | 手动管理 | 到插件详情配置来源/本地管理 |

准备状态优先于检查结果；刷新失败不能擦掉已经下载好的核心或已暂存的插件。缓存候选的下载仍要验证来源、清单、目标和包，不能直接相信旧的“可更新”标记。

## 页面视觉方案

推荐使用当前浅色/深色的克制列表结构，并适配已有多巴胺主题。视觉重点是整齐、清楚、少重复。

- 一个页头、一段摘要、一组列表、一个待重启区域；不堆叠统计卡片和大图标。
- 项目行约 72–88px；图标约 32px。名称为第一层，版本与状态第二层，来源和技术字段第三层。
- 设置内容采用约 24px 主间距和 12–16px 行内间距；按钮尺寸、描边和字重复用 `src/ui.css` 与 `src/themes.css`。
- 列表只使用必要的横向分隔线；主按钮在页头或待重启区。单项动作使用次级按钮，避免所有插件都争抢注意力。
- 浅色/深色使用现有紫色强调；多巴胺保持奶油底、粉色导航、黄色主动作和 2px 结构线，减少重复黑框。
- 更新说明默认收起，展开后使用可读段落/列表。第一版可安全分段显示纯文本，避免为 Markdown 渲染新增生产依赖。
- 主设置页只保留一个主滚动区域；不同时滚动插件列表、插件详情与更新说明三个区域。
- 720×480 小窗口下导航可缩为顶部切换，动作换行；125%/150% 显示比例和主题切换不隐藏关键操作。焦点、滚动位置、来源草稿及展开内容在进度刷新时保留。
- 使用原生按钮、开关、复选框及明确的状态文本。键盘能完成选择、下载、展开说明、返回和重启；颜色不独自承担状态含义。

会话中的页面草案用于看布局和点击路径，示例版本与更新说明不是已发布版本信息。

## 实现安排

按完整可验收的用户行为分步提交。整体发布时应把前两步一起交付，避免只改善颜色或只增加按钮。

### 第一阶段：集中处理一次更新

- 增加更新页面，整合核心和已安装插件；建立共用的行组件、选择、摘要和展开说明。
- 增加“检查全部”、有限并发的批量下载、行内重试，以及共用的待应用清单。
- 重启复用原有退出检查和安装入口；统一文案，去掉逐项下载后直接重启的捷径。
- 修正准备状态被重复检查覆盖的问题，批量跳过已准备好项。
- 验收重点：核心加两个插件在一个页面下载，部分失败可独立重试，准备完成后只重启一次。

### 第二阶段：默认可发现、插件管理清楚

- 自动检查、主进程去重、检查缓存及限流处理；主窗口与设置导航显示统一更新提示。
- 已安装插件改为列表；“添加插件”承接官方安装与本地目录，详情折叠来源及技术信息。
- 插件行“更新”复用第一阶段流程；关闭设置不取消下载，多个窗口看到一致状态。
- 三个现有主题、小窗口、显示比例和键盘访问一起验证。
- 验收重点：不用逐项手动检查；同一个已安装官方插件不重复出现；常用操作不需要看技术表单。

### 第三阶段：下载结果保留和异常体验

- 核心下载由内存字节改为应用数据下的临时包与最小恢复信息，正常关闭后可再次打开继续应用；完成后清理缓存。
- 技术验证先确认 Tauri 官方 updater 的恢复、重新验证签名和安装路径。恢复流程必须继续使用官方验签，不直接把落盘缓存判为可信的 ready；确需重新读取发行元数据时明确显示验证状态。
- 缓存损坏、来源变化、平台变化或候选版本变化时重新验证或失效；不会默默安装另一个包。插件继续复用已经持久化的 pending update。
- 优化重新打开后的结果反馈、核心安装失败重试和插件回退展示；不扩展到插件数据迁移回退。
- 验收重点：关闭再开不重新下载已完整保存的核心包；缓存损坏可恢复；实际安装结果与页面一致。

### 代码落点

- `src/views.ts`：保留设置导航、外观和应用信息。更新页面及插件管理达到现有规模后分别放入 `src/updates.ts`、`src/plugin-settings.ts`，避免继续扩大一个模板文件。
- `src/main.ts`：接入操作和入口提示；任务权威状态放核心，前端只保留选择、展开和草稿。
- `src/core.ts`：补充批量操作、最近检查时间、错误阶段和待应用项目的数据。现有单项命令可兼容保留。
- `src-tauri/src/updates.rs`：批量检查/下载调度、仓库请求共享和错误分类；沿用单项锁、校验及暂存。
- `src-tauri/src/desktop_updates.rs`：准备状态保护、核心包缓存和官方 updater 恢复；核心安装仍走现有正常退出路径。
- `src-tauri/src/core.rs`、`storage.rs`、`model.rs`：只增加必要的检查偏好、时间及缓存记录，旧配置使用默认值迁移。
- `src/ui.css`、`themes.css` 与局部页面样式：复用主题和控件，仅提取两个真实页面共同使用的更新行/通知区域。
- 同步 README、产品文档、分发文档、既有在线更新说明和本规划的实际实施结果；规划阶段不改写已有“已实现”记录。

## 验收清单

1. 首屏显示不等待更新网络请求；自动检查关闭后不再调度后台检查，手动检查仍可用。
2. 主进程一天内自动检查去重；多窗口同一时刻请求不会重复下载同一项，同仓库批次共享列表发现请求。
3. 核心、启用插件、完全关闭插件、无来源本地插件、已暂存插件及不兼容版本同时存在时，数量、选择和操作都准确。
4. 批量下载中关闭设置或切换服务器后，任务继续，重新打开可见准确进度。
5. 一项断网或校验失败，其余项仍准备成功；重试只处理失败项，旧程序与原数据保留。
6. 更新准备好后重复检查、检查失败及多窗口刷新不覆盖准备结果。
7. 启用插件下载期间旧进程继续服务；完全关闭插件更新不启动进程，且不单独产生待重启。
8. 重启清单包括核心、插件版本切换和启停变更；有下载/准备任务时禁止重启；有失败项时允许用户应用成功项。
9. 有真实连接、终端、文件任务或草稿时退出检查有效；取消重启保留所有准备结果和当前工作。不要为更新新造另一套退出判断。
10. 核心安装失败可重试，新插件初始化失败恢复旧程序，页面展示真实结果，不出现假成功。
11. 核心缓存完整保存后正常关闭重开可继续应用；损坏包必须拒绝，仍由官方 updater 验签。
12. Linux DEB 不提供无效的核心应用内安装按钮；同机插件在线更新不受影响。
13. 官方安装失败不登记半成品；已有相同 ID 的本地记录不被官方安装覆盖或改来源。
14. 浅色、深色、多巴胺及 720×480、125%/150% 显示比例下布局、状态和键盘操作有效；刷新不夺走焦点或来源草稿。
15. 稳定复现的准备状态丢失及单项错误覆盖问题先复现，再增加对应的回归测试。

实施后运行 `npm run check`、`npm run scripts:test`、`npm run test`、`npm run build`，并将必要的更新页面交互回归纳入现有 UI 检查入口。网络、包校验、暂存和回退使用现有本地 HTTP 夹具扩展集成测试，不依赖真实 GitHub 的即时状态。

正式交付按 `docs/distribution.md` 使用 GitHub Actions 和 Releases。Windows x86_64/ARM64、Linux x86_64/ARM64、macOS ARM64 分别验证原生实际包启动/退出、核心升级及独立插件重启切换；Linux 另验证 DEB 说明。核心打包入口仍不依赖业务插件构建，相关组合验收独立执行；各目标结果按实际记录，不增加全平台联动发布门禁。

## 保持的边界与风险

- 核心与插件独立版本、独立 Release、独立安装包。统一页面和批量操作不要求它们同步发版。
- 当前基本检查只表达 API 主版本及本机目标，不足以判断未来新增能力的最小核心版本。遇到明确不兼容先说明并禁止下载；核心更新后重新检查。不在这次改版引入依赖求解器或声称任意新版组合都能预先安全安装。
- 不添加插件市场、插件签名链、插件授权审批、发布批次或分层确认。核心签名维持 Tauri updater 必需机制。
- 默认后台检查会引入网络请求；通过延迟启动、每日节流、仓库复用和可关闭偏好约束请求量。GitHub 不可达时保持应用可用。
- 核心缓存恢复是本规划的主要技术验证点；不能只改前端而声称关闭后可继续安装。先证明官方 updater API 路径，再交付这一行为。
- 插件回退只保证旧程序，不承诺插件数据迁移回退。重启会结束当前远程工作，不能用“无感更新”误导用户。
- 预计复用现有 Tauri、Rust 下载/校验库与前端原生能力，本规划不申请或引入新的生产依赖。
