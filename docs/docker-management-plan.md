# Docker 常用操作补齐规划

评估日期：2026-10-17。代码基线：`2fe3c62` 及当前工作区。

本文件保留 2026-10-17 的功能盘点与实施建议，下文“当前／未实现”均指该评估基线。用户确认后已实施四批代码，实际交付及验证边界见 `docker-management-implementation.md`；本文件不作为当前完成状态的依据。

## 1. 结论与产品目标

目前 Docker 已具备对象浏览、日志排查和进入容器的能力，最明显的缺口是容器生命周期管理，以及能解释容器为何异常的详情。建议首先让用户完成“找到容器 → 查看原因 → 启动／停止／重启 → 确认结果”这一完整流程，再扩展镜像、部署和资源清理。

沿用 SoDeck 的 SSH 工作区定位：通过已有的已验证连接路径管理远程 Docker，复用日志、文件编辑和端口转发能力。界面保留右侧“监控 / Docker”与 Docker 内部列表、详情结构。

## 4. 分批交付与完成条件

### 第一批：容器常用管理与必要详情（P0）

交付启动、停止、重启、删除已停止容器，以及这些操作依赖的 inspect 数据与后台任务机制。详情首屏展示状态、健康、退出原因，端口、网络与挂载以分组展示。

- 运行中容器显示停止、重启、日志、终端；已停止容器显示启动、日志，删除放入更多菜单。窄侧栏按空间收起次要操作。
- 操作只锁定当前容器的互斥管理动作；查看日志、返回列表和操作其他容器保持可用。
- 后端提交前复核实际状态，不能只依赖约 15 秒周期刷新的前台列表；后台、慢查询和断线时数据还可能更旧。
- 删除明确说明容器可写层会丢失，默认不附加 `--force` 或 `--volumes`；不能把容器删除显示成可撤销操作。[S3]
- 停止与重启须识别 `AutoRemove`：由 `--rm` 创建的容器退出时可能被删除，不能统一宣称“停止一定可恢复”。此类容器显示特殊提示并单独验证操作行为。[S2]
- 命令结束后立即定向刷新详情和共享列表，完成状态同时显示运行状态与健康状态。启动成功不等于服务已健康。

完成条件：同一服务器开两个窗口时状态与进行中操作一致；重复点击不会重复提交；对象被外部删除、断线、无权限和状态改变均有可解释结果；操作不会占用主终端。

### 第二批：排障效率与镜像管理（P1）

交付完整配置分组、逐容器 stats／进程、暂停恢复等补充管理操作，以及镜像拉取、Tag 和删除。

- stats 仅在相应详情可见时订阅，同一连接与容器复用采样；初始建议约 5 秒更新，可在实测开销后调整。停止容器显示“不适用”，查询失败保留最后数据并标记过期。[S4]
- 显示 CPU 时明确统计口径，不将容器数据直接套用服务器的 0–100% 图表；网络与磁盘 I/O 累计值和速率分开。环境变量默认隐藏，详情缓存及错误记录不持久化明文配置。
- 镜像拉取支持名称、Tag 或 Digest；展示真实的阶段／分层进度，无法获得总进度时不显示虚构百分比。首版使用远端已有的 Registry 认证环境，不新增账号管理。[S5]
- 镜像操作区分移除一个 Tag 与删除镜像实体。同一镜像可以有多个 Tag，不能把每一行都当成独立镜像。[S6]
- 删除前查询引用关系，首版不暴露强制删除镜像。引用列表用于解释，最终仍以引擎执行结果为准。
- 从端口详情创建转发草稿：预填经核对的宿主地址与发布端口，交给现有转发编辑器完成；不是直接拼接浏览器 URL。
- 从 Bind Mount 定位文件前确认路径属于当前 SSH 服务器；外部引擎路径只展示与复制。需要扩展当前仅接收 serverId 的转发窗口入口，已有代码不能直接完成全部预填。

完成条件：拉取任务在关闭对话框或切换标签后仍可查看；鉴权失败、网络中断、同 ID 多 Tag、被停止容器引用等场景有明确行为；镜像操作后所有订阅窗口更新。

### 第三批：Compose 与创建容器（P1）

这批拆成两个独立子功能，建议先实现 Compose，再实现简单创建容器表单。

**Compose：**

- 探测 `docker compose` 可用性，通过 `compose ls --all --format json` 与容器标签发现现存项目；没有插件时保留容器浏览能力。[S7]
- 发现项目与能够执行项目命令分开：执行前确认项目名、工作目录、按顺序排列的配置文件、env 文件和 profiles。标签可能不完整，需支持从远程文件树选择／关联配置；不扫描整个服务器查找文件。
- 首版先支持“启动已有容器／停止／重启”。“部署／应用配置／更新镜像”使用独立入口，并显示涉及服务和预期重建范围；普通 restart 不应用 Compose 配置变更。[S8][S9]
- 更新流程为拉取 → 展示目标镜像与服务 → 应用配置／重建 → 查询运行与健康结果。使用后台模式，避免把服务生命周期绑在交互窗口上。[S9]
- 支持在已有文件编辑器打开 Compose 配置；保存后由用户显式执行部署。项目关联需独立保存，避免 Down 后因容器消失而丢失入口。
- Down 使用“停止并移除项目”文案，预览容器和网络；首版不附带删除卷。后续若支持 `--volumes`，必须单独列出其覆盖的命名卷和匿名卷；外部卷不属于该选项删除范围。[S10]
- 项目日志先提供按服务打开现有日志窗口的入口；多服务合并时间线后续再做。重建后的新容器使用新 ID 建立日志来源，保留旧来源档案。

**创建容器：**

- 从镜像详情进入，支持名称、发布端口、环境变量、Bind Mount／已有 Volume、网络、重启策略；Command／工作目录等放入高级区域。
- 提交前展示目标引擎与配置摘要。首版使用已有镜像，缺失时引导先拉取，创建成功后定位新容器。
- 处理名称占用、端口冲突、挂载不满足和创建后启动失败；只创建成功但未运行时保留对象并显示失败阶段，禁止自动删除后重试。
- Compose 管理的容器修改重启策略等配置时提示配置归属；优先通过项目配置实现持续变更。

完成条件：可管理停止的项目；配置文件不存在、缺少 env、远端插件不支持所选参数等情况在执行前解释；重启与更新镜像的行为有不同验收用例；同名重建不误连旧窗口。

### 第四批：空间、卷、网络与批量维护（P2）

- 增加 `system df` 空间概览，展示镜像、容器、卷和构建缓存占用／可回收估计；镜像共享层使逐行大小之和不能直接当作真实释放量。[S11]
- 卷和网络先交付列表、详情及引用关系，再增加创建／删除及网络连接管理。
- 清理按停止容器、悬空镜像、未使用网络、卷、构建缓存分别入口，不以一个“全部清理”按钮承接所有范围。Docker 的 image prune 与 system prune 范围不同，必须分别解释。[S12][S13]
- 候选预览不是原子快照：提交前重新核对对象身份与引用。首版优先删除明确选中的对象；若候选变化，应更新预览，不能在确认后扩大范围。
- 批量任务显示每个对象的成功、失败或结果待确认，不宣称整体事务或一键回滚。
- 容器文件复制与镜像导入导出复用传输任务的反馈方式，但需要单独适配 Docker 数据通道。明确区分本机、SSH 服务器和 Docker 引擎宿主，不能直接把当前 SFTP 当作容器文件系统。

完成条件：删除失败不自动升级为强制操作；清理结果显示实际删除项和实际释放量；复制中断保留可解释的任务状态；Volume 数据删除始终是独立选择。

## 5. 实现前需要固定的技术规则

### 5.1 把只读采集与管理执行分开

现有 `src-tauri/src/remote_read.rs` 对单次查询设置 6 秒超时、stdout／stderr 各 2 MiB 上限。它适合监控采集，不能直接承接 stop、pull 和 Compose：Docker 未指定停止超时时，Linux 容器默认宽限可达 10 秒，且可有更长配置。[S1]

新增 Docker 管理执行器，使用独立 SSH 连接、结构化操作参数、流式输出及操作级 deadline。停止宽限时间与客户端等待超时分开，客户端 deadline 要覆盖宽限及额外开销；无限等待配置需单独处理。监控继续保持现有有界查询。

### 5.2 目标身份、并发与多窗口

- 请求绑定已验证连接身份、监控实例代次、engineGeneration、Endpoint 和完整对象 ID；后端从会话解析身份并校验，不能信任前端传来的 Endpoint 就直接执行写操作。
- 容器名称用于展示，完整 ID 用于执行；同名重建不能自动替代目标。
- 后端按连接身份、Endpoint、对象 ID 对互斥管理操作串行化；增加 operationId／requestId 去重。同一容器的 start／stop／restart 互斥，日志读取仍独立。
- Compose 任务与所涉及容器的管理操作互斥；批量和清理任务明确锁定范围。不同连接别名指向同一引擎时不能假定已实现全局互斥，仍须处理引擎侧冲突。
- 当前前端 `actions` 只处理组件内打开日志／终端的忙碌状态。新任务由 Rust 管理并推送快照，多窗口共享；标签迁移只转移查看状态，不重新提交命令。
- 成功后使相关缓存失效并触发共享刷新；旧引擎或旧连接代次的回包不写入当前页面。

### 5.3 结果确认与断线语义

建议任务状态：等待执行 → 执行中 → 核对结果 → 成功／失败／结果待确认。

SSH 断线或客户端超时并不能证明远端命令没有生效。已提交的修改不能自动重试，尤其是 restart、创建、删除和重建；恢复连接后先查询原 ID／任务目标。无法证明执行结果时保留“结果待确认”，由用户决定下一步。

关闭详情、对话框或切换标签不等于取消后台任务；“取消”仅在能说明实际终止范围时提供。应用退出时显示进行中的管理任务；退出后不自动重放命令，也不承诺远端操作会同步停止。若后续引入持久化任务记录，只保存脱敏目标、阶段和结果。

### 5.4 参数、权限与兼容性

继续使用当前账号权限，沿用逐跳主机指纹验证。新增管理接口只接收允许的操作枚举与类型化参数，经校验和 shell quoting 后构造命令；不新增任意 shell 字符串 IPC。

首先记录 Engine／CLI／Compose 的能力和版本信息，遇到不支持的参数隐藏或说明对应功能。首版沿用现有可用的 Unix socket／DOCKER_HOST 范围，不把尚未支持的 context TLS／SSH 宣称为完整支持，也不为完成操作自动 sudo。

### 5.5 与现有 UI 设计稿的衔接

现有设计稿的列表／详情、主操作区、更多菜单和确认框方向可以复用，但本规划补充以下功能约束：

1. 普通 stop 会在宽限期后使用强制终止；AutoRemove 容器停止后还可能被删除，确认与文案应考虑这些实际行为。[S1][S2]
2. 镜像行代表一个引用，移除 Tag 和删除实体应分开处理。[S6]
3. 补齐创建容器与重启策略设置，避免镜像拉取后仍无使用入口。
4. Compose 启动已有容器、重启、应用配置和更新重建分别表达；项目文件关联是管理前提。
5. 拉取进度与取消能力取决于执行器实际可观测性，不预设一定能拿到总百分比或回滚。
