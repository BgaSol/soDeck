# 外置插件基础功能实施计划

日期：2026-11-05。状态：待实施；本轮仅编写计划，没有修改应用和构建流程。

当前基线是已经发布的核心 v0.1.0：Hello 窗口、五目标原生打包和包内启动退出检查均已通过。下一次交付建议为核心 v0.1.1，以及独立版本的 Hello 插件 v0.1.0。

## 1. 本轮交付目标

用户安装核心后，下载并解压一个独立插件包，选择目录即可加载；能查看插件运行状态、日志和重要消息；可以立即卸载、重新加载，核心保持可用。

本轮实现插件管理、进程生命周期、日志、消息、Hello 示例插件和独立打包。SSH、终端、文件、Docker、NetBird、网络代理及插件业务视图在后续迭代接入。运行中的核心不会加载旧版数据库和凭据。

完成标准：

1. 没有任何插件，核心也能安装、启动和退出，默认进入插件管理。
2. 选择正确平台的 Hello 插件目录，无须重启核心即可加载；列表显示名称、版本和运行状态。
3. 插件启动后写入一条普通日志并发布一条重要消息，二者在各自页面中可查到来源和时间。
4. 点击卸载后进程停止，列表变为未加载，原插件文件和数据仍保留；随后可再次加载。
5. 插件异常退出或启动失败，核心显示具体原因，可以重试；已经接收的日志和消息仍能查看。
6. 退出核心时关闭插件；重新打开后保留目录记录和消息历史。本轮重新启动后由用户手动加载插件。
7. 核心与 Hello 插件各自生成五目标发行包，不需要用户安装 Rust、Node.js 或 Python。
8. v0.1.0 可覆盖安装为 v0.1.1；升级结果与数据保留的实际验证范围分别记录。

## 2. UI：沿用旧版布局与视觉

参考旧版的 [插件设置](reference-v2/plugin-settings.png)、[工作台](reference-v2/workbench-light.png) 和 [连接首页](reference-v2/connection-light.png)。采用单窗口，保留紧凑顶部工具/标签栏、列表与详情分区、浅灰面板、细边框、紫色选中与焦点反馈。

按用户最新要求：去掉独立系统标题栏；应用状态和设置固定在右上角，点击后弹窗查看。进一步的布局推断是把应用管理内容收进浮层，让主窗口以未来的服务器和插件工作区为中心。本轮把“弹窗”理解为应用内浮层，打开和关闭时不新建系统窗口、不重建工作区。

旧版插件设置通过勾选、应用和重启生效。本轮使用立即执行的加载/卸载按钮，不继承设置草稿、候选版本和待重启状态。

顶部约 40–44px，一行同时承载页面/未来服务器标签、拖动区域、全局入口和窗口控件，不额外放一条带 SoDeck 标题的系统栏。当前只有工作台页面标识，不加入尚未实现的连接和终端按钮。取消原计划底部重复展示的应用版本、运行插件数量和全局状态条；未来具体工具需要的连接、目录等业务状态在对应工作区表达。

建议窗口初始 1100×720，最小 720×480。主窗口首轮只提供简洁欢迎页，插件管理统一放在右上角“设置 → 插件管理”中，欢迎页不设置管理插件按钮或独立插件管理导航。加载没有业务视图的 Hello 后，继续显示通用工作台，不为 Hello 编写专用工作区。

Windows/Linux 的最小化、最大化/还原、关闭按钮与顶部内容融为一体；macOS 的原生红黄绿控件融入顶部左侧，状态与设置仍在右侧。使用 Tauri 的平台窗口能力，保留拖动、边缘缩放、双击空白最大化/还原和系统快捷键。按钮、输入框和标签交互区不能被误判成拖动区。跨平台差异在核心窗口适配层处理。

### 2.2 入口与浮层

| 入口 | 展示方式 | 内容与操作 |
| --- | --- | --- |
| 右上角应用状态 | 锚定按钮下方的状态浮层 | 当前 App 状态、插件数量、存储状态、最近异常、查看日志 |
| 右上角设置 | 居中设置对话框 | 左侧分类，右侧内容；插件管理、外观、应用与数据 |
| 右上角消息 | 消息对话框，入口显示未读数量 | 全部/未读、消息详情、已读、来源和重复次数 |
| 状态中的查看日志 / 插件详情中的查看日志 | 日志对话框 | 按来源、级别、时间和文本筛选，暂停/继续显示、复制记录 |

这些入口切换的是应用级浮层，主工作区、插件进程和未来的服务器会话继续运行。任意时刻只有一个应用级浮层，进入日志等目标时替换当前浮层，不堆叠多层弹窗。

状态浮层建议宽 420–480px、右侧对齐触发按钮；设置对话框建议约 900×600px，上限为当前窗口的 90% 宽和可用高度。小窗口时分类改为紧凑导航，内容内部滚动，关闭按钮始终可见。

### 2.3 应用状态浮层

这里的系统状态指 SoDeck 自身，界面名称采用“应用状态”。平时入口只显示正常、需关注或状态不可用，并用文字配合状态点；普通已读/未读消息不直接决定健康状态。

首轮数据全部来自已实现的核心管理模块：

- 应用版本、运行平台与架构、启动时间和运行时长。
- 运行中、正在启动/停止、异常插件的数量与对应详情入口。
- 日志与消息存储是否可用，应用数据目录。
- 当前仍需处理的运行错误；已处理的历史错误保留在日志/消息中，不让状态永久告警。
- 查看日志与复制简短状态信息。

状态读取失败明确显示不可用，不能填入假的正常状态。CPU/内存和网络流量不作为本轮采集前置条件；后续有实际采集时注明范围，例如核心进程或全部应用进程，不能混称系统整体占用。SSH、隧道等状态等对应能力实现后再接入。

顶部摘要优先通过已有生命周期与存储事件更新。状态浮层打开时按需刷新运行时长和详情，关闭后停止详情轮询。增加一个只读的核心状态快照接口，不建立独立监控框架，也不将此接口混入插件 API。

### 2.4 设置与插件管理

设置采用旧版的左侧分类、右侧表单布局，放在应用内对话框中。第一轮只展示真实可用项：

- 插件：名称、ID、版本与文字状态；详情包含路径、API、平台、启动时间和最近错误；提供加载目录、加载/重试、卸载与查看日志。
- 外观：跟随系统、浅色、深色三个主题选择，选择后立即保存；失败时恢复原设置并显示原因。
- 应用与数据：版本、应用数据目录、日志位置及复制路径等基本信息。

插件管理的列表/详情结构沿用前述旧版参考；宽度不够时单栏切换并提供返回按钮。左侧插件列表约 240–280px，设置分类栏保持紧凑。不引入拖拽停靠、多窗口和通用设置草稿协调器。

空列表提示“尚未加载插件，选择已解压的插件目录开始”。加载失败时，在插件详情中保留原因与重试入口；不只闪过一条提示。没有匹配的筛选结果与没有任何数据使用不同文案。

卸载只停止运行，不删除目录记录。按钮旁说明“保留插件文件和数据”。“移除记录”仅对未运行的插件可用，也不会删除磁盘文件。切换页面、关闭详情或暂停日志显示都不会停止插件。

设置使用即时生效的明确操作，不显示全局应用/确定按钮。关闭设置不撤销已经完成的插件操作，也不会中断正在进行的加载/卸载；操作结果继续反映到核心状态与消息中。

### 2.5 浮层交互与可用性

- 状态浮层从右上角入口出现；点击外部、再次点击入口或 Esc 可关闭，关闭后焦点回到入口。
- 设置、日志、消息有清楚标题和关闭按钮，Esc 可关闭；模态内容保持键盘焦点范围，关闭时恢复原工作区焦点。
- 弹窗显示不暂停后台插件或会话，不新开一套核心状态。窗口控件与系统关闭操作仍正常工作。
- 即时消息提示不遮住右上角状态、设置和窗口控件，也不抢输入焦点。
- 动效简短克制，弹出与收起方向一致；减少动态时直接切换或短淡入淡出，不引入弹簧动画依赖和玻璃材质要求。

### 2.6 视觉规则

- 沿用旧版的正文约 13px、按钮约 32px、输入框约 36px、控件圆角约 8px、4/8/12/16/24px 间距；错误详情和日志使用系统等宽字体。
- 浅色采用旧版浅灰白与紫色，深色使用同一套语义颜色变量；默认跟随系统，可在设置选择。本轮不增加主题编辑器、多巴胺主题配置或字体下载。
- Windows、Linux、macOS 优先使用各自系统字体，不把旧版 Windows 字体栈直接套给所有平台。
- 操作开始立即显示“正在加载/正在卸载”；状态同时有文字与颜色。长路径和错误详情允许换行或展开复制。
- Tab 可遍历控件，Enter 激活按钮，焦点可见；消息即时提示不抢焦点。验证中文输入、文字缩放和减少动态设置。
- UI 只显示核心返回的运行状态。操作后重新读取状态，实时事件用于触发更新，页面重新进入时重新获取快照。

## 3. 加载、卸载与故障恢复

### 3.1 插件状态

| 状态 | 含义 | 可用动作 |
| --- | --- | --- |
| 未加载 | 有目录记录，无运行实例 | 加载、移除记录 |
| 正在加载 | 已开始启动，等待初始化完成 | 等待结果，禁止重复加载 |
| 运行中 | 初始化已成功，核心正在管理进程 | 卸载、查看日志 |
| 正在卸载 | 已要求停止，等待进程和资源退出 | 等待结果，禁止再次加载 |
| 失败 | 启动、协议或运行异常 | 查看原因；完成清理后可重试 |

同一个插件 ID 同时只允许一个实例。重复点击在界面和核心两端都要被合并或拒绝。不同目录出现相同 ID 时明确指出已登记目录，用户卸载后可以选择新目录替换记录；不启动两个同名实例。

### 3.2 加载流程

1. 点击“加载插件目录”，打开系统目录选择器；取消选择不改变现有状态。
2. 核心读取目录根部的 plugin.json，做本节约定的基本检查；清单无效时显示错误，不留下假运行记录。
3. 保存有效目录记录，创建新的实例标识，记录启动日志。使用可执行文件路径与参数数组启动进程，工作目录为插件根目录。
4. 通过标准输入输出完成初始化。成功后才显示“运行中”；建议初始化超时为 5 秒，超时后清理实例并显示失败。
5. 核心持续读取 RPC、诊断输出和进程退出事件。重启应用后恢复目录记录，实际运行状态重新从未加载开始。

已登记目录被移动、删除或替换时重新检查并给出原因，不能阻止核心启动。首版只管理用户明确选择的目录，不递归扫描硬盘或安装目录，不监听文件变化自动重启。

### 3.3 卸载和退出流程

1. 先进入正在卸载，停止接受该实例的新业务请求。
2. 发送 shutdown 请求，建议给插件 3 秒自行收尾；随后关闭通信并回收实例持有的核心资源。
3. 超时则终止实例及其受管理的子进程，等待确认退出。Windows 使用进程 Job，Linux/macOS 使用进程组，系统差异收在核心适配层。
4. 清理完成后标记未加载，保留插件目录、插件数据、日志和消息。若进程仍未结束，保持失败状态并允许重试停止，不能提前显示卸载成功或允许重复启动。
5. 主窗口关闭即执行应用退出：停止所有实例，做有界日志刷新，然后结束核心；本轮不引入托盘常驻。

异常退出时由核心记录退出码和最近错误，回收该实例资源，状态变为失败，并发布一条来源明确的核心重要消息。首版由用户点击重试，不自动循环重启。用户主动卸载与异常退出必须区别记录。

等待初始化或停止响应时不持有全局生命周期锁，RPC 读取也不能被某个请求处理阻塞。停止过程中仍在限时内接收收尾日志，避免插件等待日志响应、核心等待插件退出形成互相等待。

当前没有 SSH、PTY 或代理资源，本轮验证进程、管道和已注册任务的清理；端口和连接回收在相关能力真正实现时增加对应测试，不提前搭空资源框架。

## 4. 插件包与通信约定

### 4.1 首个运行形式

Hello 使用原生 Rust 可执行程序，核心和插件分进程，以换行分隔的 UTF-8 JSON-RPC 2.0 通信。用户只需要解压和加载，不需要另外安装语言运行时。后续插件可采用其他实现语言，只要提供可运行入口并遵循协议。

标准输出仅用于 RPC，标准错误由核心接收为诊断日志。协议结构与错误码维护一份规格；若两端共用 Rust 类型，放在一个不依赖 Tauri 的小型协议库中，不扩展成多语言 SDK 或代码生成系统。

包结构：

```text
hello-plugin/
  plugin.json
  bin/
    sodeck-hello.exe       Windows
    或 sodeck-hello        Linux / macOS
```

Windows x86_64 包的清单示例：

```json
{
  "id": "sodeck.hello",
  "name": "Hello 插件",
  "version": "0.1.0",
  "apiVersion": "1",
  "target": "x86_64-pc-windows-msvc",
  "entry": "bin/sodeck-hello.exe"
}
```

每个归档只带一个目标的原生程序，入口相对插件根目录解析。加载前只检查必需字段和版本格式、入口存在且属于该目录、API 主版本匹配、清单目标与本机匹配、插件 ID 未重复。操作系统返回无法执行时展示原始原因。没有权限清单、签名信任链、市场审核或穷举兼容矩阵。

### 4.2 本轮 RPC

| 调用方向 | 方法 | 内容 |
| --- | --- | --- |
| 核心 → 插件 | initialize | 传入核心 API 主版本及该插件的数据目录；收到成功响应后进入运行中 |
| 核心 → 插件 | shutdown | 要求停止并退出，按卸载超时收尾 |
| 插件 → 核心 | logging.write | level、message、可选 fields；来源由核心补充 |
| 插件 → 核心 | messages.publish | title、body、level、可选 notify 和 dedupeKey；成功持久化后返回消息 ID |

RPC 保留请求 ID、明确成功/失败响应及超时。无效方法或参数返回具体错误；协议损坏导致无法继续通信时结束当前实例并保留原因，不拖垮核心。协议帧建议上限 64 KiB，接收队列有界；超量日志合并记录丢弃数量。数值属于实施起点，可根据真实测试调整，不做用户配置中心。

核心为每次加载生成 instanceId，为接收的数据附加 pluginId、instanceId、receivedAt；不采用插件自行声称的来源。API v1 后续新增可选字段保持兼容，破坏性变化增加主版本。

### 4.3 Hello 插件行为

初始化完成后，写入一条“Hello 插件已启动”日志，发布一条 notify=true 的“Hello SoDeck”重要消息，然后等待卸载；收到 shutdown 后写入停止日志并正常退出，输入管道关闭时也结束进程。

核心不判断 sodeck.hello 这个特定 ID，也不为它添加专属页面和演示按钮。当前的插件详情、日志和消息内容都是核心界面，分别从设置或右上角入口打开。未来终端/文件需要的插件视图接口，在真实业务开始时单独设计。

## 5. 日志与重要消息

### 5.1 日志

- 核心自动记录加载请求、启动成功、初始化失败、主动卸载、强制结束与异常退出；插件可提交 debug/info/warn/error 日志。
- 每条保存接收时间、来源、实例、级别、正文和可选字段。标准错误按诊断记录保存，普通 error 日志不会自动弹出重要消息。
- 使用核心数据目录中的 JSONL 文件。初始上限建议单条 8 KiB、单文件 10 MiB、保留 5 份；达到容量后轮转，截断/丢弃数量有明确记录。
- 页面默认展示最近 500 条，筛选后仍使用有界结果。先按保留文件查询，不建立数据库索引、链路追踪或日志检索服务。
- 页面暂停只暂停实时展示，后台继续记录。重开页面读取核心数据，不依赖前端内存充当日志仓库。
- 落盘失败时保留有界内存回退并显示一次明确提示；不递归写错误日志，也不阻塞插件卸载和应用退出。

### 5.2 重要消息

- 消息等级为 info/success/warning/error；独立于日志。发布成功即进入消息中心，notify=true 时额外显示约 5 秒的应用内提示，默认不弹出即时提示。
- 消息中心保存已读状态，重启后可继续查看。首版建议最多保留 1000 条，采用有界 JSON 文件和原子替换写入。
- 同一插件、相同非空 dedupeKey、5 分钟内重复的消息合并，更新内容与接收时间、累计次数；新一次事件可重新标记未读，合并期间不反复弹提示。不传 dedupeKey 则作为独立消息。
- 点击即时提示进入对应消息详情，标记已读；来源入口定位到插件管理，即使插件已卸载也能查看原消息。
- 内容按纯文本呈现。消息写入失败时返回失败，不声称已保存；核心提供可理解的存储错误提示。首版不接入系统通知权限、消息中间件或跨插件工作流。

## 6. 数据与代码边界

使用当前 com.bgasol.sodeck 应用标识对应的系统应用数据目录，通过 Tauri 路径接口获取，不能写死开发者路径：

```text
应用数据目录/
  preferences.json              主题等已经实现的应用设置
  plugins.json                  已选择的外部目录记录
  messages.json                 消息及已读状态
  logs/                         核心统一日志
  plugin-data/<plugin-id>/       插件专属数据
```

插件程序仍在用户选择的外部目录，不复制进核心安装目录。路径与实例元数据由核心管理；插件数据与核心配置分开。坏配置给出明确错误并保留原文件，不静默覆盖为全新数据，不建立多代自动迁移框架。

建议前端使用 TypeScript + Vite，负责类型检查与静态资源构建，先用原生 DOM 实现工作区壳和应用级浮层。按内容与窗口壳拆文件，设置中的插件视图和日志视图复用同一实现；统一的核心调用入口负责前后端通信，业务视图不操作本地进程或文件。按钮、状态、颜色和间距复用少量 CSS，不从旧版搬入整套组件包。

Rust 按插件清单、进程管理、RPC、日志、消息和路径适配拆模块；main.rs 只组合启动与退出流程。同一个状态只有一个核心所有者，前端不维护另一套“以为已经运行”的状态。

初步目录职责：

| 目录或模块 | 职责 |
| --- | --- |
| src/main.ts、src/core.ts | 界面启动、核心调用与事件接收 |
| src/shell/ | 一体化顶部栏、窗口控件、应用级浮层切换 |
| src/views/ | 应用状态、设置、插件、日志、消息内容 |
| src/styles/ | 颜色、控件及布局 |
| src-tauri/src/plugins/ | 清单、实例状态、进程及 RPC |
| src-tauri/src/logging.rs、messages.rs | 核心保存、查询与事件 |
| src-tauri/src/app_status.rs | 汇总已有管理模块的只读状态快照 |
| src-tauri/src/platform/ | 路径和进程管理中的实际系统差异 |
| plugins/hello/ | 独立原生插件、独立版本及锁文件 |
| scripts/ | 已实现的检查、打包和集成检查入口 |

### 6.1 依赖建议

计划阶段不安装或修改依赖。实施所需新增项限定为下表，按实际使用固定版本并提交锁文件：

| 依赖 | 用途及维护情况 | 替代方案 |
| --- | --- | --- |
| TypeScript、Vite（开发依赖） | 官方持续维护的类型检查和前端构建工具 | 继续纯 JS；异步状态与接口约束较弱 |
| @tauri-apps/api | Tauri 官方前端调用和事件 API | 全局注入接口；类型与模块边界不如官方包清楚 |
| Tauri 官方 dialog 前后端插件 | 系统原生目录选择器 | 手工粘贴路径；或逐系统手写选择器，维护成本更高 |
| serde、serde_json 的直接声明 | Rust 常用且持续维护的序列化库，目前已在 Tauri 的锁文件依赖图中；用于清单、RPC 和存储 | 手写 JSON 解析与编码，容易出错 |
| 必要的 windows-sys / libc 目标依赖 | Microsoft Windows 绑定与 Rust 生态基础系统绑定，用于 Job/进程组，按平台编译 | 手写系统 FFI，增加不必要的底层维护 |

目录选择器的 Tauri 应用窗口调用配置属于桌面壳自身配置，不转化为 SoDeck 插件权限声明或授权界面。本轮不引入数据库、React、通用插件 VM、第三方进程管理框架和自动更新依赖。

## 7. 独立打包与发行

核心继续使用现有 Package SoDeck 工作流和应用版本入口；增加前端构建后，仍从 npm run build 进入，安装包只含核心及自身运行资源。Hello 不进入核心安装器、默认依赖或核心发布前置步骤。

Hello 使用自己的清单版本、独立 Cargo 工程和锁文件，增加独立手动工作流。构建入口与工作流同时实现，不在本次文档提交中加入不存在的命令。

| 目标 | 核心 | Hello 插件 |
| --- | --- | --- |
| Windows x86_64 / ARM64 | 各自原生 .exe 安装器 | 各自原生程序的 .zip |
| Linux x86_64 / ARM64 | 各自原生 .deb | 各自原生程序的 .tar.gz |
| macOS ARM64 | 原生 .dmg | 原生程序的 .tar.gz |

Unix 归档保留入口执行位；macOS 产物完成正常的本地签名处理，实际下载后的系统来源限制与正式分发签名情况如实说明，不增加插件信任体系。

插件工作流默认生成 Artifact；需要分发时可选择一个普通 Release 标签并自动附加插件包。插件更新只运行插件工作流，不重打核心，也不要求专门的插件标签命名制度。首个 Hello 包可以附在核心 v0.1.1 的 Release 中，但仍是独立下载和独立版本。

核心和插件的五个构建目标分别完成、分别上传，某个失败不取消其他目标。维持当前“标签生成 Release 草稿，明确发布后在普通列表可见”的流程；版本说明写清核心包与插件包的用途和下载方式，交付状态区分草稿和已发布。

## 8. 实施顺序

按四个完整主题实施，每一步先通过对应验收，再进入下一步；中间提交不要求反复运行全部五目标打包。

| 顺序 | 实施内容 | 当步验收 |
| --- | --- | --- |
| A：界面与构建 | TypeScript/Vite、一体化无独立标题栏的窗口壳、右上角状态/设置/消息入口、应用内浮层、主题设置、系统目录选择 | 拖动/缩放/窗口控件正常；浮层开关、键盘焦点、窄窗口和主题可用；本机仍能打包安装 |
| B：插件运行 | 固定清单及 RPC v1，进程生命周期、目录记录、Hello 初始化/退出、失败与重试 | 外部程序可加载、卸载、再次加载；重复点击、初始化超时、进程崩溃和退出清理有明确结果 |
| C：日志与消息 | 两个核心接口、存储、页面筛选/已读、即时提示和边界处理；Hello 实际调用 | 来源和实例正确；日志不自动变通知；消息重启保留；插件故障后记录仍在 |
| D：独立交付 | Hello 五目标打包、包内集成检查、核心 v0.1.1 覆盖安装、发布说明 | 核心与插件独立下载；五目标实际产物能完成加载到卸载；安装升级结果准确记录 |

A 只提供明确空状态或开发预览，不把模拟插件列表当成真实运行状态。B、C 使用测试进程覆盖异常，不给产品加入专用“模拟崩溃”按钮。D 完成后再进入 SSH 和真实业务插件。

## 9. 必要验证范围

以正常路径及最可能导致“核心卡死、状态虚假、资源残留”的异常为重点：

| 检查 | 预期 |
| --- | --- |
| 核心安装包无插件启动 | 工作台与右上角入口可用，各浮层可打开，退出正常 |
| 无独立标题栏与跨平台窗口控件 | 拖动、边缘缩放、最小化、最大化/还原、关闭和系统快捷键正常；点击按钮不触发拖动 |
| 状态/设置/消息浮层切换 | 工作区保留，插件继续运行，关闭恢复焦点，窄窗口不遮住关闭入口 |
| 应用状态与主题设置 | 状态来自真实核心快照，错误不会伪装正常；主题更改持久化且重开应用保留 |
| Hello 正常加载 → 日志/消息 → 卸载 → 再加载 | 实例标识更新，旧进程结束，文件与历史保留 |
| 同一插件重复点击或相同 ID 来自另一目录 | 不产生并行重复实例，提示当前目录 |
| 清单无效、入口缺失、API/目标不匹配 | 明确失败原因；其他插件和核心可用 |
| 初始化超时、进程崩溃、shutdown 不响应 | 状态与实际进程一致；按限时清理；日志可查且能重试 |
| 插件创建一个测试子进程 | 卸载后受管理的进程组/Job 内子进程一并退出 |
| 日志快速输出、帧超限与轮转 | 内存和磁盘有上限，界面可响应，不生成通知风暴 |
| 消息发布、去重、已读后重启 | 消息与状态保留，来源/次数正确，提示不重复刷屏 |
| 数据目录不可写 | 清楚反馈保存失败，卸载和退出仍可完成 |
| 正常退出核心 | 所有运行插件清理，重新启动不显示假运行状态 |

自动检查以清单/RPC 的针对性测试和真实子进程集成测试为主；界面关注点击后实际状态和消息持久化，不用大量只验证实现细节的单元测试。

交付时在五个原生 Runner 分别使用实际核心包与相应 Hello 归档完成一次组合验证。此验证任务独立于核心打包和插件打包，不建立版本组合矩阵，也不作为核心发行包生成的前置门禁。无插件的核心启动检查继续保留，不能只测试带插件的情形。

纯文档变更只检查文档差异；编码阶段运行格式、类型、相关测试和构建，已通过且未受后续改动影响的检查不反复重跑。

## 10. 升级验收与明确边界

核心标识保持 com.bgasol.sodeck。先安装已发布 v0.1.0，再退出并安装 v0.1.1，检查应用被替换、快捷入口和卸载信息正常、界面展示新版本。Windows 优先在本机真实操作，其余平台按原生环境分别记录验证方式与结果。

v0.1.0 尚无插件目录记录和消息历史，所以这次升级不能证明这些新数据跨版本保留。本轮另外用 v0.1.1 的真实数据验证退出重开及同版本覆盖安装后仍存在；后续 v0.1.1 → 下一个正式版本时再补真正的业务数据跨版本验证，不为制造证明而引入候选激活和复杂发布流程。

本轮尚不交付插件业务 UI、自动加载/自动重启、在线安装/更新、自动数据迁移、系统通知、插件市场、权限审批、完整诊断平台。UI 使用旧版的视觉语言与已验证交互，不复制旧版巨型入口、配置协调器和发布机制。

开发完成后的交付说明只需要给出：实际变更、相关检查结果、核心与插件下载链接、两三步加载说明、平台运行范围，以及尚未验证的升级或系统分发限制。
