## 1. 独立更新：重启 App 后生效

### 1.1 明确采用的更新模型

**插件有自己的版本号和发布包，运行中的 App 固定使用启动时选定的版本。插件更新仅准备新包，统一在 App 重启后启用。**

例如：核心为 `2.0.0`，终端为 `1.1.0`，Docker 从 `1.2.0` 更新到 `1.2.1`，NetBird 仍为 `1.0.0`。只下载 Docker 包；本次运行继续使用 `1.2.0`，App 重启后使用 `1.2.1`，无需重新发布核心安装包。

不实现运行中的模块替换、旧新插件运行实例交接、跨版本 PTY 转交或为了更新保存完整运行内存。开发环境的代码热刷新不属于正式插件更新能力。

T-028中安装、启用、停用和更新均完整重启后运行；停用插件候选仅暂存，重新启用并重启时才执行初始化。卸载不在本次范围，不将本方案解释为已支持卸载。

### 1.2 更新流程

```text
发现兼容版本
  → 下载到暂存目录
  → 强制校验完整性、包结构与兼容性，评估可选签名状态
  → 记录“已准备，重启后生效”
  → 当前版本继续运行
  → 用户正常退出并重新启动 App
  → 启动阶段先读取启用偏好，仅验证并初始化本次启用集合的候选；停用候选继续暂存
  → 成功后提交激活记录并进入正常运行
```

核心负责以下规则：

1. 插件按 `pluginId/version` 保存不可变包，不覆盖运行中使用的文件；整个 App 使用一个受锁保护的激活记录。
2. 完整性清单必需且文件精确匹配；签名可选，无签名允许加载并在设置提示。未知签名来源可加载但不标为已验证；已知错签/畸形签名拒绝。签名绑定清单与内容，哈希不证明发布者身份；实际执行字节必须来自同一已验证快照。
3. 解包限制路径、大小和文件数量，拒绝目录穿越、符号链接越界或清单与包内容不一致。
4. 安装前检查核心版本、API、能力及平台要求；按 P-14 不读取权限清单、不做新增能力授权或权限扩大审批。
5. 下载失败、校验失败或空间不足保留当前可用版本。准备更新不影响当前会话和后台任务。
6. 不因更新准备完成而强制关闭 App。退出前沿用未保存内容和活动任务的处理流程；重启会断开本次运行的连接。
7. 启动时先完成包验证、私有数据迁移和初始化检查，再进入正常运行。初始化和迁移阶段不执行远端业务动作，这是所有插件一致的阶段契约，不是按插件能力授权；调用核心同样留痕。
8. 激活记录、迁移状态和恢复日志应能够在中断后恢复。待启用包无法启动时，使用兼容的旧包和启动前数据，或禁用故障插件后进入核心界面；不能陷入整机启动循环。

建议插件中心显示：已安装版本、已准备版本、兼容性、失败原因，以及统一的“重启后应用更新”入口。一次重启可以应用多个已准备插件包，但应先检查整个目标集合；不增加插件权限页面。

### 1.3 数据迁移与回退

- 插件设置和业务数据使用独立命名空间及 schema 版本，与核心数据库结构分开演进。
- 迁移在启动阶段对本地事务或数据副本执行，失败时保留上次可用版本。迁移阶段只定义本地数据操作契约，不承载远端业务执行，避免回退本地数据却无法撤销远端操作；不引入插件授权表。
- 提交激活前的失败，可以恢复启动前的包选择和数据快照；进入正常运行后产生了新数据，不能简单覆盖旧快照。此时降级需有兼容 schema、明确的反向迁移或可审阅的恢复方案。
- 插件回退不撤销已经在服务器上执行的操作，也不能保证恢复已断开的远端会话。
- 卸载默认保留还是删除插件私有数据，应在对应产品任务中确定；核心服务器、凭据和用户隧道不属于插件私有数据。

### 1.4 与核心更新的关系

核心安装包仍走独立的应用升级流程。插件包在应用数据目录中管理，出厂插件可以随安装包附带；二者都使用相同的插件包校验和兼容检查。

新核心启动时，依据自身实际版本重新选择兼容的插件集合。为新核心下载的插件不能提前在旧核心中启用；旧插件不兼容时提供兼容版本或暂时禁用，不能强行加载。

插件激活记录的原子提交不等于操作系统安装器和插件数据库能够跨系统事务回滚。核心升级失败的恢复需要单独验证，不能用插件回退机制承诺完整 App 降级。
