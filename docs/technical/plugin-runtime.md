# 插件包与运行方案

更新日期：2026-10-24 · 修订：r2 · 状态：候选方案，待原型验证与详细规格；尚未实施。

本文件记录插件包、运行容器和隔离的候选方案。独立 WebView、QuickJS 及每插件独立进程仍需按[技术选型流程](README.md)比较和验证，不能因为已有方案描述就直接成为其他规格的实现前提。

## 1. 插件包与运行环境

### 1.1 插件包包含界面和业务逻辑

建议每个插件发布一个带清单和签名的版本包，例如 `.sodeck-plugin`。格式名称为拟定值，具体封装在原型阶段确定。

```text
plugin-package/
  manifest.json          # 身份、版本、入口、权限、扩展点及兼容要求
  ui/                    # 编译后的 HTML、JavaScript、CSS 和资源
  worker/                # 编译后的插件业务逻辑
  migrations/            # 插件私有数据迁移逻辑，可选
```

业务逻辑建议用 TypeScript 开发并编译为 JavaScript，通过受控 SDK 调用核心。Docker 和 NetBird 的命令构造、响应解析、状态机与操作编排随插件包发布。

前端依赖随插件构建打包，不要求插件共享外壳某个 React 实例；SDK 的运行协议、主题令牌和扩展点保持版本化。插件发布时不运行任意安装脚本，也不现场下载 npm 依赖。

**独立更新的边界是已安装核心提供的能力。** 如果插件需要一种核心尚不具备的协议或原生能力，必须明确要求相应的核心版本。插件系统不能让任意新原生能力凭空出现。

### 1.2 先确定要求，再分别选择业务与视图容器

桌面外壳与核心仍以 Tauri 2 + Rust 为候选，外壳和官方插件 UI 以 React + TypeScript 为候选。插件的业务执行环境、视图容器和进程粒度分开决策；独立更新本身不要求每个插件必须占用独立进程。

候选运行方案需要证明：界面与业务逻辑可以随插件包更新；核心能够识别真实调用者并控制能力访问；视图显示与任务、资源生命周期可以分别管理；故障实例能够停止或隔离，核心仍可提供资源管理入口。[产品总览](../product.md)已确定首阶段 Windows、首期官方插件；同时运行数量、后台行为及资源预算在具体实验中明确。

业务运行方式的比较范围：

| 候选 | 值得验证的理由 | 主要代价与需证明的部分 |
| --- | --- | --- |
| Rust 宿主内嵌受限 JS 引擎，如 QuickJS 类方案 | 可以只开放受控 SDK；宿主可随核心发布 | npm 依赖兼容、异步调度、终止能力与内存限制；进程按插件分配还是共享，需根据故障范围和开销判断 |
| Web 执行环境，如受控 WebView 中的 Worker | 复用 Web 平台能力和前端构建工具 | 可用依赖范围、面板关闭后的存活方式、原生桥接身份、平台差异及资源占用 |
| 随核心分发的其他 JS 运行时辅助进程 | 可能降低部分依赖迁移成本 | 默认本机能力和分发体积通常更大；必须证明权限能满足要求，只有 SDK 包装不能构成隔离 |

视图容器的比较范围：

| 候选 | 值得验证的理由 | 主要代价与需证明的部分 |
| --- | --- | --- |
| 独立 WebView，作为优先验证项 | 可为视图分配受控入口，界面包与外壳分开 | 嵌入布局、焦点、输入法、多视图开销及平台实际权限边界 |
| 其他受限 Web 容器，按实际平台可行性评估 | 可能降低多视图资源开销 | 必须说明共享的信任与故障范围、如何防止伪造调用身份；iframe 或共享页面不能自动视为插件隔离 |

上述是比较范围，不要求为所有候选建立完整实现。先用官方资料和最小实验排除不满足要求的方案；只有影响选择的剩余问题进入原型。不得为了保留某个候选而静默降低权限、故障或产品要求。

通信采用有类型和版本的契约；流数据使用有界且带背压的通道，详见[协议方案](plugin-protocol.md)。这些行为约束不依赖具体 JS 引擎。

若采用扩展宿主，其二进制随核心安装和更新，独立更新的插件主要是脚本与 Web 资源。首期建议不加载插件自带的任意 Rust 动态库或原生可执行文件，避免将跨平台 ABI 和签名问题带入每个插件的发布流程；这一范围需与产品决定保持一致。

应用自定义插件与 Tauri 自身的 Rust 插件是不同层次。Tauri 原生插件可以帮助核心实现能力，但不能把“下载一个 Tauri 插件包”直接当作 SoDeck 的运行时扩展机制。

若采用脚本运行时，v1 中写在 Rust 里的 Docker、NetBird 等业务适配需要迁入插件，现有测试场景可复用，但实现不能全部原样搬入。需要原生库或 WASM 的插件在出现具体需求后再评估，不因架构可扩展就提前建设。

### 1.3 需要验证的隔离边界

不将插件 JavaScript 直接 `import` 到拥有完整权限的外壳页面中。Tauri 官方说明，Linux 上无法区分嵌入 iframe 与其窗口发起的请求，因此不能把外壳中的 iframe 单独当作原生权限边界。

插件视图只获得必要的桥接入口。核心同时校验真实调用来源、插件实例、授权范围和资源所有权，不能只依赖清单中的声明或前端传来的 `pluginId`。业务运行实例即使没有显示视图，也必须具有可信的通道身份。应用自定义命令同样纳入校验，避免绕过插件网关。

独立进程与 WebView 可以提供部分故障隔离和权限收敛，不等于完整的操作系统恶意代码沙箱；WebView 是否共享渲染进程也取决于平台。共享容器即使低权限，也不自动具备插件之间的隔离能力。首期只做官方插件；签名机制按更新方案验证，第三方扩展另行评估运行时、权限和分发政策，不能以官方插件实验通过推断其安全性。
