# 插件包与运行方案

更新日期：2026-10-25 · 修订：r7 · 状态：候选比较及 v1 迁移依据；T-003 已实现独立 QuickJS 进程与 raw Wry 视图，实际验证与限制见[桌面结果](../tasks/T-003-desktop-results.md)。

本文件记录插件包、运行容器和隔离的候选方案。独立 WebView、QuickJS 及每插件独立进程仍需按[技术选型流程](README.md)比较和验证，不能因为已有方案描述就直接成为其他规格的实现前提。

## 1. 插件包与运行环境

### 1.1 插件包包含界面和业务逻辑

建议每个插件发布一个带清单和签名的版本包，例如 `.sodeck-plugin`。格式名称为拟定值，具体封装在原型阶段确定。

```text
plugin-package/
  manifest.json          # 身份、版本、入口、扩展点及兼容要求
  ui/                    # 编译后的 HTML、JavaScript、CSS 和资源
  worker/                # 编译后的插件业务逻辑
  migrations/            # 插件私有数据迁移逻辑，可选
```

业务逻辑建议用 TypeScript 开发并编译为 JavaScript，通过统一 SDK 调用核心。按 P-14，SDK 不分配插件权限，核心对每次调用自动留痕。Docker 和 NetBird 的命令构造、响应解析、状态机与操作编排随插件包发布。

前端依赖随插件构建打包，不要求插件共享外壳某个 React 实例；SDK 的运行协议、主题令牌和扩展点保持版本化。插件发布时不运行任意安装脚本，也不现场下载 npm 依赖。

**独立更新的边界是已安装核心提供的能力。** 如果插件需要一种核心尚不具备的协议或原生能力，必须明确要求相应的核心版本。插件系统不能让任意新原生能力凭空出现。

### 1.2 先确定要求，再分别选择业务与视图容器

桌面外壳与核心仍以 Tauri 2 + Rust 为候选，外壳和官方插件 UI 以 React + TypeScript 为候选。插件的业务执行环境、视图容器和进程粒度分开决策；独立更新本身不要求每个插件必须占用独立进程。

候选运行方案需要证明：界面与业务逻辑可以随插件包更新；核心能够识别真实调用者并记录每次调用；视图显示与任务、资源生命周期可以分别管理；故障实例能够停止或隔离，核心仍可提供资源管理入口。[产品总览](../product.md)已确定首阶段 Windows、首期官方插件、无插件权限分配；同时运行数量及资源预算在具体实验中明确。

业务运行方式的比较范围：

| 候选 | 值得验证的理由 | 主要代价与需证明的部分 |
| --- | --- | --- |
| Rust 宿主内嵌 JS 引擎，如 QuickJS 类方案 | 宿主可随核心发布，统一接入核心调用和记录 | npm 依赖兼容、异步调度、终止能力与内存限制；进程粒度根据故障范围和开销判断 |
| Web 执行环境，如受控 WebView 中的 Worker | 复用 Web 平台能力和前端构建工具 | 可用依赖范围、面板关闭后的存活方式、原生桥接身份、平台差异及资源占用 |
| 随核心分发的其他 JS 运行时辅助进程 | 可能降低部分依赖迁移成本 | 本机能力和分发体积通常更大；须证明核心调用可统一记录、故障及资源能回收 |

视图容器的比较范围：

| 候选 | 值得验证的理由 | 主要代价与需证明的部分 |
| --- | --- | --- |
| 独立子 WebView，作为比较项 | 可为视图绑定调用来源，界面包与外壳分开 | 当前 Tauri 多 WebView 涉及 `unstable`；还需验证布局、跨窗口迁移、焦点、输入法、开销及桥接来源识别，资料依据见第 2 节 |
| 其他 Web 容器，按实际平台可行性评估 | 可能降低多视图资源开销 | 必须说明共享的运行与故障范围、如何准确归因调用；iframe 或共享页面不能自动视为故障隔离 |

上述是比较范围，不要求为所有候选建立完整实现。先用官方资料和最小实验排除不满足要求的方案；只有影响选择的剩余问题进入原型。不得为了保留某个候选而静默降低逐次留痕、故障处理或其他产品要求。

通信采用有类型和版本的契约；流数据使用有界且带背压的通道，详见[协议方案](plugin-protocol.md)。这些行为约束不依赖具体 JS 引擎。

若采用扩展宿主，其二进制随核心安装和更新，独立更新的插件主要是脚本与 Web 资源。首期建议不加载插件自带的任意 Rust 动态库或原生可执行文件，避免将跨平台 ABI 和签名问题带入每个插件的发布流程；这一范围需与产品决定保持一致。

应用自定义插件与 Tauri 自身的 Rust 插件是不同层次。Tauri 原生插件可以帮助核心实现能力，但不能把“下载一个 Tauri 插件包”直接当作 SoDeck 的运行时扩展机制。

若采用脚本运行时，v1 中写在 Rust 里的 Docker、NetBird 等业务适配需要迁入插件，现有测试场景可复用，但实现不能全部原样搬入。需要原生库或 WASM 的插件在出现具体需求后再评估，不因架构可扩展就提前建设。

### 1.3 工作台对视图容器的要求

产品 P-15 至 P-18 及 [F-CORE-004](../core/workbench.md)决定了宿主必须统一支持停靠面板、中央 Tab/双区域、独立窗口与托盘。每个视图只需支持自己声明的形式；业务实例的存活不依赖主窗口或某个渲染表面可见。

- 先验证“保留逻辑视图和会话、迁移或重建渲染表面”。不假定现有框架支持 WebView 无损跨窗口搬移，也不能通过每次弹出都重建连接掩盖不满足行为要求。
- 宿主协调来源绑定、挂载代次、焦点和输入转交；失败恢复源位置。旧表面不能继续发出有效输入，目标未就绪不能关闭源视图的业务资源。
- 分别测量多视图/窗口开销、独立窗口与主窗口的故障关系、隐藏表面的流预算、中文输入法、不同缩放比例和拖动落点。浏览器中实现的分屏不构成原生窗口通过的证据。
- 主窗口“×”收起到托盘时保留 App 与独立窗口；从托盘恢复或明确退出要在真实宿主验证。独立窗口共用核心、插件激活版本和资源管理，不创建另一个自治 App。
- 先实现菜单路径证明迁移契约，再验证直接拖动的实际原生边界；若跨窗口拖动受限，在实验结果和后续界面方案中说明，不能声称已经支持。

具体业务运行粒度、容器选择、视图状态传输和数值预算仍待实验决定。已支持位置、窗口模式与视图状态 schema 的兼容处理纳入插件更新验证；不能仅验证网页能打开。

### 1.4 来源识别、调用记录与故障边界

保持外壳和插件明确的模块及运行实例边界，避免直接导入外壳内部实现。选型需验证各平台是否能从通信通道识别来源；iframe 或共享页面本身不能证明调用归因准确，也不能自动证明故障隔离。

插件视图和业务实例经统一桥接访问全部已公开支持的核心接口，无能力授权表。核心核对真实来源、实例和资源状态并记录调用，不能依赖前端传来的 `pluginId` 记账。业务实例即使没有显示视图也要绑定来源；自定义命令不得绕过统一调用记录。

独立进程与 WebView 可提供部分故障隔离，具体进程共享取决于平台；本方案不以限制插件能力或恶意代码沙箱为目标。首期只做官方插件，包签名与完整性按更新方案验证。未来插件来源扩大时另行设计，不在当前实现中预置另一套授权体系。

## 2. 工作台技术可行性：资料核查

核查日期：2026-10-25。本节结合官方文档、布局库维护者资料和 v1 已实现的窗口迁移及历史原生测试；读取官方 Rust API 时版本为 Tauri 2.12.5。没有安装依赖或运行 v2 样例，本轮没有重跑 v1 原生测试；既有证据和 v2 尚需验证的增量分别记录。

### 2.1 Tauri 提供哪些部分

| 能力 | 已查证的支持与限制 | 对 SoDeck 的影响 |
| --- | --- | --- |
| 多个原生窗口 | [WebviewWindow](https://v2.tauri.app/reference/javascript/api/namespacewebviewwindow/) 创建独立窗口，不要求 `unstable` Cargo 特性 | 独立插件窗口有直接基础能力；工作区归属、加载内容及会话交接由我们实现 |
| 托盘 | [System Tray](https://v2.tauri.app/learn/system-tray/) 提供图标、菜单和事件 | 可实现收起、恢复和明确退出；隐藏主窗口与资源清理仍需按产品契约编排 |
| 窗口几何恢复 | [Window State](https://v2.tauri.app/plugin/window-state/) 保存/恢复窗口位置和大小 | 不负责服务器工作区、Tab、插件状态或业务会话恢复 |
| 单窗口内多个子 WebView | [Window::add_child](https://docs.rs/tauri/latest/tauri/window/struct.Window.html#method.add_child) 是桌面多 WebView API，需要 `unstable`，位置/大小需宿主管理 | 不能当作现成的停靠布局引擎；布局、遮挡、焦点、缩放与故障范围都要验证 |
| 将 WebView 移到另一窗口 | [Webview::reparent](https://docs.rs/tauri/latest/tauri/webview/struct.Webview.html#method.reparent) 已提供；未启用 `unstable` 时，涉及 `WebviewWindow` 的拆分/重挂会报 `CannotReparentWebviewWindow` | 有原地迁移的候选路径，但不能据此承诺所有插件视图无损搬移；完整工作台不应只依赖该路径 |

官方窗口及子 WebView 创建文档还注明 Windows 同步命令/事件处理中的死锁情形，建议使用异步命令或独立线程创建。实验需遵守对应调用方式并验证快速重复打开/关闭；这不是 Tauri 无法创建多窗口的结论。

Tauri 提供原生窗口和 Web 容器，IDEA 式工具栏、Tab、停靠、双区域布局仍由前端及工作台适配层完成。Tauri 自身的桥接配置属于宿主实现，不能据此重新加入已取消的 SoDeck 插件能力审批。

### 2.2 可比较的前端布局库

| 候选 | 维护者资料列出的能力 | 需要验证的适配 |
| --- | --- | --- |
| [FlexLayout](https://github.com/caplin/FlexLayout) | React Tab 组、边缘工具区、可拖动分隔条、布局模型、主题、浮动面板及浏览器弹出窗口；MIT | 与侧边工具区需求较接近，优先作匹配度比较；限制至两个中央区域、apple-design 外观、插件容器和原生窗口适配仍需实现 |
| [Dockview](https://dockview.dev/) | Tab、分组、停靠、分屏、浮动、弹出窗口与布局保存；支持 React 等 | 对比布局事件和定制能力；当前区分 MIT 包及商业 Enterprise 功能，按选定版本的功能/许可证核对，不把全部网站示例视为免费包能力 |

FlexLayout 的[弹出窗口文档](https://github.com/caplin/FlexLayout/blob/master/docs/popout-windows.md)明确说明其使用 React Portal，代码仍在主窗口 JS 上下文运行；跨 document 的控件可能需要重新挂载，主窗口后台运行还涉及定时器节流。这种浏览器弹出机制不能直接当作 Tauri 独立 `WebviewWindow` 已验证方案。Dockview 的浏览器弹出功能同样需验证与原生窗口模型的兼容，具体实现不能凭名称推定。Dockview 包与功能范围见[许可及功能表](https://dockview.dev/docs/overview/licence)。

布局库负责展示布局；SoDeck 的逻辑视图 ID、服务器上下文、迁移事务和资源关系仍由核心工作台持有。库的模型是布局投影/交互输入，通过适配层提交核心，不形成另一套互相修改的权威状态。插件只依赖 SoDeck 视图契约，不直接依赖某个布局库的内部模型。

### 2.3 建议的验证取舍

技术上可行；常规侧栏、Tab 与分屏有现成基础。v1 已实现并具有原生测试证据的窗口迁移、连接连续性和失败恢复见第 2.4 节，不能把它们统称为尚无实现依据的新技术问题。v2 的增量是将已有工作区/终端迁移抽象为插件视图契约，并验证新容器的输入焦点、输入法、调用归因及故障恢复。

建议沿用 v1 的普通 Tauri 原生窗口与快照/会话交接思路，在 SoDeck 工作台适配层接入插件视图；布局部分先核对 v1 已有工具栏和布局逻辑，再比较 FlexLayout 与 Dockview 是否能补足通用停靠和双区域需求，不默认整体替换。弹出时创建独立 `WebviewWindow`、恢复视图、目标就绪后提交归属是已有实现路径。主窗口内插件使用何种 Web 容器仍需独立比较，不直接导入插件内部实现。

连接/PTY 由核心持有，业务状态由不依附 Tab 组件的插件业务实例持有；视图重新挂载不意味着重建连接。原生子 WebView 加 `reparent` 保留为另一比较路径，是否采用由 `unstable` 接口代价、交互、资源开销及实测决定；不再把“每视图一个子 WebView”作为未经验证的优先结论。

按 P-19，把已有迁移路径接入实际终端插件，再覆盖停靠、Tab、双区域、弹出/返回、失败恢复及托盘。v1 原生测试中的会话 ID、shell 数量、输出连续性和失败回滚作为迁移回归基线；新增插件来源、视图状态版本、重新挂载和独立更新兼容检查。中文输入法、多屏缩放及新容器真实 PTY 行为在本批按受影响范围补验。既有拖动/菜单入口优先评估复用，不默认延期跨窗口移动；具体方案见 [T-003](../tasks/T-003-core-terminal.md)和[实施技术建议](first-terminal.md)。

保存结果明确包含：部分冻结回滚不重连；目标原生窗口在接收前销毁时回滚且不创建新 shell；整体拆出保持会话 ID 和 shell 数量；移回继续使用原后端连接；连接与断开终端混合迁移；零终端工作区往返不创建隐含 PTY；终端历史不重复创建会话。

v1 的迁移单位是服务器工作区及其终端/工具快照。v2 的单个通用插件视图、独立业务实例和资源租约是新的抽象，需适配及回归，不能直接声称全部 v2 插件已通过测试；同样不能把底层窗口机制当成需要从零证明。普通原生窗口迁移不依赖 `tauri/unstable`，v1 另有启用该特性的 `plugin-probes` 实验功能，不能混作这条已验证路径的必要条件。

这一依据修正了此前“跨窗口移动只是新增推断、应先延期”的建议：它是 v1 的已有能力及用户认可的参考，v2 应优先承接实现思路和测试资产，再明确插件化增量。是否沿用具体实现代码由 v2 的模块、身份与资源契约决定，不整体照搬 v1 的业务耦合。
