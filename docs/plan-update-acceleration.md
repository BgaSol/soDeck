# 更新下载与多地址加速：功能设计及代码整改方案

整理日期：2026-11-09。状态：已实现，验收见[实施记录](implementation-update-acceleration.md)，本轮发行见 [v0.18.0](releases/v0.18.0.md)。本文覆盖需求、用户行为、失败处理、代码整改与验收。发布规则继续按[分发文档](distribution.md)，设计方法参考[功能设计方法](plan-feature-design.md)。

## 1. 需求理解与完成条件

用户明确希望：准备多个地址，允许在设置中手动追加；GitHub 无法访问时，仍能通过其他地址下载。结合此前要求“全流程都可以被加速”，本方案将范围定义为：

- GitHub Actions 与 Releases 继续负责发布，客户端根据网络情况选择访问线路。
- 首次使用即可自动处理 GitHub 访问失败，无须用户先寻找节点。
- 官方插件名单、首次安装、核心和插件的更新检查、清单复查、包下载都支持备用地址。
- 用户可追加自己维护或更适合当地网络的地址，控制启用状态与自定义地址顺序。
- 某个地址失败后自动尝试其他地址；所有可用线路失败或达到请求时限才显示失败。
- 下载到的仍是同一组件、版本和平台的包，通过原有校验后才进入待应用状态。
- 设置保存、多个窗口、后台检查、正在下载、下载失败和重启恢复采用同一套规则。

据此推测，用户最在意的是日常使用不中断、无需反复手工选线路，以及内置地址失效后能够自行补充。这里的自定义地址按 GitHub HTTPS 加速前缀设计，例如 `https://mirror.example/` 转发 `https://mirror.example/https://github.com/...`。界面会说明这一格式；普通网页或只存放一个 EXE 的下载页不能承担完整自动更新。

代表验收场景：GitHub API 与附件下载均不可达，第一条备用线路也失败，第二条成功；用户仍能看到官方插件、安装插件、检查全部更新、下载核心与插件，最后沿用原有统一重启流程应用。

## 2. 现状与已确认问题

目前 `ReleaseClient::github()` 固定使用 GitHub API，`main.rs` 的名单、安装、单项/批量检查和下载入口多处直接创建该客户端。`updates.rs` 的清单与插件包直接请求原始 URL；`desktop_updates.rs` 则另由 Tauri updater 再读清单、下载核心包。

本次公网实验已验证元数据及五平台核心、四插件各平台包可以经过公共代理读取和下载，同时实际复现了以下问题：

| 问题 | 影响 | 本方案处理 |
| --- | --- | --- |
| ghfast.top、ghproxy.net 拒绝 GitHub API | 文件可下载，检查版本和插件名单仍会失败 | 内置能力区分 API 与文件请求 |
| 多条 gh-proxy 线路出现 GitHub API 限流 | 首页可访问、某次请求成功不能证明整个流程可用 | 按请求类型切换并短期避开失败地址 |
| 缓存不按 `Accept` 区分 blob 响应 | 原始插件 JSON 可能变成 GitHub Base64 包装响应 | 兼容两种有效响应，不依赖缓存正确区分请求头 |
| 核心另走 Tauri 的 HTTP 下载 | 只改 API 或插件下载仍会留下核心直连 | 核心和插件统一下载，保留官方验签与安装 |

上述实验不是长期可用性保证，也不是本方案代码的验收。不同节点可能共享运营方、缓存与上游配额。

## 3. 用户功能与设置

在“设置 → 软件更新”增加可展开的“下载与网络”区域，复用现有设置页面和主题。日常更新按钮及批量处理保持当前交互。

| 设置/操作 | 行为 |
| --- | --- |
| GitHub 无法访问时自动使用备用地址 | 默认开启；关闭后新任务只使用原始发行地址 |
| 内置地址列表 | 展示名称、地址、API/文件支持范围；可启用/停用，地址本身只读 |
| 添加地址 | 名称可选，HTTPS 前缀必填；支持编辑、启用/停用和删除 |
| 自定义地址排序 | 用“上移/下移”调整；启用的自定义地址排在内置地址之前 |
| 测试地址 | 只测试选中地址，分别显示 API、插件信息和文件读取的结果及时间 |
| 保存 | 校验并原子落盘；保存后的配置用于新接受的任务，进行中任务继续使用其配置快照 |

输入草稿在更新进度刷新、窗口缩放和主题变化时保留。多窗口同时编辑采用配置修订号检查；过期保存返回当前配置并保留本窗口草稿，提示重新读取后再保存。

“测试地址”是可用性诊断，不能自动安装或下载整个安装包，也不是启用地址的前置审批。测试会读取真实发行 API、插件目录及一个插件声明、更新清单；读取包时最多取前 64 KiB，未完整下载的包明确显示“未验证完整包”。若地址不遵守 Range，达到读取上限后关闭响应。限流显示“API 当前限流”，格式不支持显示“API 不支持”，两者不混为永久失效；结果与时间只作为本次诊断。

更新项目显示必要状态，例如“正在使用备用地址下载”“地址连接失败，正在尝试下一个”。当前地址和各次失败原因放在可展开详情中；成功切换写普通日志，不逐次弹出通知。网络失败保留缓存候选和已准备好的包，沿用当前单项重试入口。

## 4. 内置地址与地址契约

初版准备以下七个地址。表中的 API 支持是用途配置；公网实验覆盖范围单独注明，发行前仍须复验。

| 默认顺序 | 加速前缀 | 请求范围 | 本轮证据 |
| --- | --- | --- | --- |
| 1 | `https://axisnow.gh-proxy.org/` | API、文件 | 完整链路及全部更新包曾成功，复查出现限流和缓存格式变化 |
| 2 | `https://v4.gh-proxy.org/` | API、文件 | 元数据及 Windows x86_64 核心/四插件包成功，出现限流 |
| 3 | `https://v6.gh-proxy.org/` | API、文件候选 | 版本、目录树与核心清单成功，其他步骤待复验 |
| 4 | `https://gh-proxy.org/` | API、文件 | 版本、插件信息和清单成功，出现限流 |
| 5 | `https://gh-proxy.com/` | API、文件 | 版本、插件信息和清单成功，出现限流 |
| 6 | `https://ghfast.top/` | 文件 | 清单成功；API 明确拒绝 |
| 7 | `https://ghproxy.net/` | 文件 | 清单成功；API 明确拒绝 |

首批不加入本轮连接超时的 `cdn.gh-proxy.org`。文件专用地址跳过版本、Trees、Blobs 等 API 请求，参与清单、归档及包下载。未来新增或调整内置常量随核心版本交付；用户追加地址无需升级核心。

地址规范：

- 仅接受绝对 HTTPS URL；允许部署路径，例如 `https://mirror.example/github/`。
- 禁止 URL 中携带用户名、密码、查询串或片段；前缀规范化为一个结尾 `/`。
- 去除首尾空白，按规范化地址去重，检查与内置地址重复。
- 自定义地址最多 10 个，单条 URL 最长 2048 字符，名称最长 64 字符；达到上限明确提示。
- 代理目标必须是已识别的 GitHub API、附件或 Raw URL。其他供应方的原始 HTTPS 包地址继续按当前方式请求，不套用 GitHub 前缀。
- 原始路径、查询串和百分号编码保持原义，前缀只添加一次；从源码生成的原始 URL 是唯一比较与缓存依据。
- 保留当前系统代理行为，不借用服务器 SSH/SOCKS 会话、不修改操作系统代理配置。维护者 Token 和服务器凭据不随请求发往加速节点。

自定义地址默认尝试 API 和文件两类请求，诊断结果供用户判断。某次 API 限流只影响短期尝试顺序，不能把自定义地址永久改成文件专用。

## 5. 选择、超时与失败处理

### 5.1 请求顺序

没有失败记录时，先请求原始 GitHub 地址。发生可恢复失败后，按“启用的自定义地址 → 支持该请求类型的内置地址”尝试。

核心短期记录 API 与文件两类线路状态。同一批操作中已失败的直连不必在每个插件上重等一次；该类型最近成功的备用地址优先，其他地址保持用户/内置顺序。失败地址默认冷却 5 分钟，限流参考 `Retry-After`，上限 15 分钟；状态只放内存。冷却到期后的下一项新任务重新探测直连，使 GitHub 恢复后可以恢复优先使用。

单个资源请求内，每个候选地址最多尝试一次，移除现有“同地址重试 × 地址列表”的叠加。优先使用未冷却的地址；它们全部失败后，在剩余预算内依次重探测冷却的备用地址，仍冷却的直连放最后。这样清单失败不会把一个仍能下载包的节点排除到最终失败之外；全部地址冷却时也只有一轮有界尝试，不把功能永久锁死。

请求参数初始值：连接期限 3 秒，元数据单地址总期限 8 秒，单次元数据请求的全部地址总预算 45 秒；文件响应首包期限 8 秒，读取连续无数据 20 秒后切换，每次下载总期限沿用 600 秒。重定向跳数和重试均计入相应预算。数值作为代码常量与可控测试输入，不增加用户调参表单。

总预算可能在全部地址尝试完之前到期，错误详情必须记录已尝试数量及“达到请求时限”，不能写成“全部地址均不可用”。后续重试仍优先未冷却的地址，使剩余地址有机会被尝试。

### 5.2 失败矩阵

| 事件 | 行为及终点 |
| --- | --- |
| DNS、连接、TLS 错误、连接重置、请求超时 | 记录当前线路失败，尝试下一地址；保留证书验证 |
| API 限流、429、服务端 5xx | 冷却该类型线路，直接切换；不在前端等待长时间限流倒计时 |
| 403 不支持该 API、HTML/登录页、JSON 格式错误 | 当前线路无法完成此请求，切换并记录原因 |
| 清单或包 404 | 尝试同一原始资源的其他地址；不在下载过程中改版本 |
| 正确的空发行列表/没有适用新版本 | 按现有规则结束检查；不把“没有更新”视为网络失败 |
| ID、版本、核心 API 或平台不符合要求 | 按现有业务校验结束，显示原因；不通过切换线路放宽条件 |
| 下载中断、完整字节数或哈希/签名不匹配 | 关闭响应和临时文件，清理失败副本，再尝试下一线路；固定原候选和校验信息 |
| 写盘失败、空间不足、解包或安装失败 | 按本地失败结束；换网络地址无助于解决，不反复重下 |
| 所有候选失败或预算耗尽 | 单项失败并可重试；其他批量项目继续，已准备项不受影响 |
| 任务被现有退出/重启流程取消或失效 | 停止新增请求，清理未完成临时文件；资源释放后才结束 Operation |

HTTP 状态与格式判断只属于线路读取；拿到符合预期的数据后才执行发行/组件业务校验。候选确定后，切换线路仅重取同一原始资源，禁止在包下载失败时顺带选择另一版本或另一组校验值。

下载切换从零重新下载，初版不跨节点拼接 Range 分片。进度重置时显示“重新下载”，校验完成之前不登记新插件目录或核心 ready 状态。响应过大仍按已有元数据/包/解包上限拒绝；这种拒绝不能触发无限循环。

加速请求若重定向到 GitHub 原始域名，客户端将目标重新放入当前代理前缀，或把该地址判为不能代理；不能悄悄回到失败的 GitHub 直连。其他 HTTPS CDN 跳转有界跟随，继续校验 scheme、URL 凭据与跳数。普通直连允许 GitHub 官方附件 CDN 的既有跳转。

## 6. 归属、并发、恢复与不变量

| 对象 | 唯一管理者 | 创建、结束与持久化 |
| --- | --- | --- |
| 网络配置与修订号 | 核心 Store | 保存成功才替换，沿用 preferences.json；旧文件缺省迁移 |
| 内置名单 | 核心更新网络模块 | 代码常量；用户只保存停用项 |
| 线路成功/冷却记录 | 核心更新网络模块 | 跨任务共享，API/文件分开；重启丢弃，配置改变清理相关记录 |
| 任务配置快照、候选次序与请求 | 已接受的更新 Operation/检查批次 | 接受时固定；关闭、取消或完成时释放 |
| 输入草稿与地址测试展示 | 当前设置窗口 | 刷新不覆盖；迟到测试结果按配置修订号和本次输入标识丢弃 |
| 包临时文件 | 当前下载任务 | 每次尝试独立管理；验证成功后才进入正式缓存/准备流程 |
| 候选与已准备缓存 | 原有 UpdateState/CoreUpdater | 保存原始来源与 URL，沿用既有恢复、离线验签和重启应用规则 |

网络请求、下载与验签不持有 Store、UpdateState 或线路状态锁；读取状态和提交结果使用短临界区。已有同组件去重、批量下载并发上限 2、后台自动检查频率和 Operation 收尾继续使用。

关键不变量：

1. 备用地址只改变传输线路，候选的组件、版本、平台和期望哈希/签名不因线路改变。
2. 设置修改、停用或删除地址不会擦掉已校验包；新任务只使用已提交的新配置。
3. 下载返回成功必须意味着完整接收、校验、必要落盘已经完成，HTTP 200 或测试首页成功不能代替。
4. 重试期间旧 `.part` 不得与新线路字节拼接，不能注册半成品或提前停掉正在运行的插件。
5. 模块停止或父 Operation 失效后，迟到响应不得创建新的下载尝试或登记 ready/插件记录。
6. 永久失败只在当前项目显示；公共线路失败不影响远程连接、工作台或其他已准备项目。

重启恢复使用缓存里的原始 `raw_json` 和 URL 恢复官方 updater 对象。包已完整准备时离线验签；包未完成时由下一次下载任务读取新的网络配置，重新选择线路。新内置名单不会因旧 preferences 文件缺字段而被禁用；未知的旧停用 ID 无害保留。

## 7. 代码整改方案

### 7.1 网络与配置

新增 `src-tauri/src/update_network.rs`，职责限定为 GitHub 更新资源的地址构造、候选选择、失败分类、期限/重定向、读取及文件下载。核心和插件已经是两个真实调用者，可以在此集中共同规则；不把它扩展成远程协议框架。

建议最小数据结构：

```rust
// 以下为方案形状，不是已提交实现。
struct UpdateNetworkPreferences {
    revision: u64,
    fallback_enabled: bool,
    disabled_builtins: Vec<String>,
    custom_mirrors: Vec<UpdateMirror>,
}
struct UpdateMirror {
    name: String,
    prefix: String,
    enabled: bool,
}
enum RequestKind { Api, File }
```

`Preferences` 增加 `update_network`，使用 serde 缺省值向旧配置兼容，默认自动切换开启、自定义为空、内置全部启用。内置能力与顺序由常量定义，不把整个内置表复制进用户文件。

Store 增加网络设置校验、修订号比较和原子保存；只修改该字段，保留同时保存的主题与自动检查设置。通过 `AppCore::release_client()` 这样的单一工厂读取已保存配置快照，注入共享线路状态；继续保留显式直连测试客户端和隔离回环测试入口。

业务层需要获取结构化失败种类而非解析中文错误字符串。只在更新网络模块定义足够表达网络、响应、校验、本地 IO、取消的最小错误类型；最终到现有命令边界再转用户信息。

### 7.2 ReleaseClient 与插件名单

`ReleaseClient` 继续负责仓库、发行、组件与清单业务，网络模块负责传输。迁移以下读取到共同入口：

- Releases 分页，保留原来的稳定版本、draft/prerelease 与 API/平台规则。
- 官方仓库 Trees 与 Blobs。
- 更新清单读取和 `validate_candidate` 复查。
- 插件包下载，保留 SHA-256、大小、解包与注册校验。

官方 blob 查询优先使用普通 GitHub JSON 格式；读取时兼容直接的插件声明和 `{encoding:"base64", content:...}` 包装响应。包装数据去除 Base64 允许的空白后解码，检查编码、声明大小、解码上限并解析同一个 OfficialPlugin。固定 blob 路径及已有 ID/来源检查继续使用。

Base64 可复用当前直接依赖 russh 公开重导出的 `russh::keys::ssh_encoding::base64::{Base64, Encoding}` 或 Base64Reader。只使用其编码工具，无须 SSH 会话；不自写解码器，也不为这项功能新增生产依赖。该公开接口已经从本机锁定版本源码核对。

`ReleaseClient` 的发行缓存保存经过验证的业务结果，并按原始仓库键复用；线路失败要先完成本请求内的地址切换，再向批次返回错误。缓存和清单比较使用原始 URL，不保存代理拼接 URL。

### 7.3 核心更新：统一读取，保留官方 updater

推荐把核心的 HTTP 请求也纳入共同传输入口，避免分别维护 reqwest 与 Tauri 下载两套切换循环。

1. 核心候选发现通过 ReleaseClient 完成并保留原始清单 JSON；下载前通过同一网络入口复查组件、版本、平台 URL 和签名，禁止放宽校验。
2. 使用已经存在的 `updater_builder().restore_update(raw_json)` 从已读取清单构造官方 Update。取代当前 `discover` 内再次发起网络的 `.check()`；保留 Tauri 版本比较、目标选择和 signed-version 检查。
3. 核心与插件共用有界文件下载实现。每次尝试写 `.part`，核心由官方 `Update::verify` 校验完整文件，插件由原有 SHA-256 校验；校验失败以固定的原期望值尝试下一线路。
4. 核心验证成功后沿用 `package.bin`、metadata.json 和 ready 状态。既有 `verify_ready`、`verify_for_close` 与 `Update::install` 保留；实际安装继续使用官方 updater，签名实现不另写。
5. 保留缓存原始 `raw_json`。重启恢复不需要访问加速地址；不保存临时线路或把加速 URL 写回发行来源。

公共下载实现接受验证回调，确保“选择地址 → 下载 → 完整校验”属于同一次尝试；校验成功后交由各调用者做解包、注册或安装。核心 read_package 的已有 512 MiB 上限及插件归档上限继续执行，避免引入不受限下载。

## 8. 回归与交付条件

默认测试使用隔离回环服务，控制失败地址、响应头、延迟和中断，不依赖公共服务当时的状态。HTTP 回环例外只能由已有 test-fixtures 显式注入，用户配置继续只接受 HTTPS。

| 验收范围 | 必须证明 |
| --- | --- |
| 配置与输入 | 旧 preferences 可读取；HTTPS/path 规范化、去重、上下限、禁用、排序、保存失败、多窗口冲突均正确 |
| 默认直连 | GitHub 正常时不访问备用地址；关闭自动切换后只直连 |
| 全链路切换 | API 与附件直连均失败，备用 1 失败、备用 2 成功，完整名单、安装、核心与插件检查/下载成功 |
| 能力分类 | 文件专用地址不接收 API；自定义地址可作为有效后备；HTML、API 限流、404/5xx 能正确分类 |
| blob 缓存 | 同 URL 两种 Accept 顺序交错、缓存返回两种响应，均能取得同一插件声明；错误 Base64/大小拒绝 |
| 包与来源 | 原始 URL/查询编码不变；代理重定向不绕回 GitHub；中断切换清理旧字节；坏哈希/签名不进入准备状态 |
| 并发与退出 | 两项批量更新不重复等待坏直连；改设置不改变已接受任务；任务失效后不发下一请求/登记结果 |
| 恢复 | 更换/删除地址后旧候选仍可重试；已准备核心离线验签；失败缓存保持；插件重启切换仍正确 |
| 设置 UI | 名单管理、添加/编辑/删除、排序、保存冲突、单地址诊断、草稿保留、三主题、小窗口与键盘可完成 |
| 五平台 | 五个正式系统/架构分别编译、打包，验证实际包启动/退出及更新下载；ARM64 使用原生产物 |

实施时运行相关 `npm run check`、`npm run scripts:test`、`npm run test`，以及 `npm run ui:production:test -- --updates-only`。核心原生打包采用[开发指南](development.md)中的平台命令和现有五平台工作流；相关源码结果与包验收都记录确切提交，公网测试作为额外专项明确记录日期、地址、跳过项。修改前先为实际复现的缓存格式和线路失败增加回归。

## 9. 实施顺序与文档影响

1. **闭合读取与线路切换。** 引入网络模块和偏好，迁移版本、名单、清单全部入口，加入可控切换及 blob 回归。
2. **闭合核心和插件下载。** 共同文件下载、失败副本清理、Tauri 本地构造/验签、候选复查和重启恢复一起完成。
3. **交付用户设置。** 自定义/内置名单管理、顺序、修订冲突、诊断与状态呈现，覆盖单项/批量/后台所有调用点和 UI 回归。
4. **原生验证与记录。** 运行相关源码、实际前端和五平台包验收，更新受影响文档后通过既有流程发布。

每个提交只包含一个完整主题；整体功能只有上述范围一起完成才能标为已交付。实施后更新 usage 的用户操作、development 的相关验收入口、distribution 的客户端线路说明和对应核心版本记录，并新增实施记录及索引。GitHub 发布工作流、插件独立版本、核心唯一版本来源、插件启停/升级重启规则继续遵守原约定；根 README 的稳定首页无需因普通下载功能细节而追加记录。

已知限制：公共节点数量不等于独立运营保障；限流和缓存可能同时影响多个地址。第三方代理是发行传输的一部分，核心签名能验证核心包，插件现有 SHA-256 主要验证包与清单的一致性；本功能不追加插件授权或签名发布体系。自定义地址为同样的 GitHub 转发契约，其他类型镜像需要真实用例后另定适配。实际实现、已执行与尚未完成的验收见[实施记录](implementation-update-acceleration.md)。
