## 1. 提交方案

用户喜欢所提供参考图的风格和配色，明确“深浅色依旧可以自由切换”，随后要求“按照这个设计方案，结合apple-design，重构一下项目整体的样式”。整体方向已明确；本次把此前意图讨论补全为可实施的具体规格和测试。

1. **一套视觉语言、两套完整主题**：浅色为灰白层次、深色为蓝灰层次，共用蓝紫重点色及少量粉橙渐变。正文实色，品牌/空态适度彩色点缀，菜单和弹窗轻阴影；所有色值仍独立定义。
2. **整体覆盖**：主窗、工作区窗、独立终端窗、两层 Tab、文件侧栏、终端、服务器选择/编辑、认证、已打开页面、插件/资源/记录与错误空态全部整理。现有业务与窗口模型保持。
3. **运行中切换**：“应用 → 外观”中选浅/深，立即应用并保存；所有当前版本表面更新。建议首次默认深色，终端跟随全局；本次不增加跟随系统或终端独立主题。系统高对比优先。
4. **公共样式重构**：新增公开 `@sodeck/ui` 的基础变量、控件样式与少量通用呈现组件，外壳与插件独立打包消费；清理外壳累积覆盖，业务样式留在各插件。排版、密度、圆角、焦点、图标与控件反馈统一。
5. **apple-design 落点**：清晰层次、系统字体、按下即时反馈、空间一致性、可中断且克制的动效、减少透明/动态和高对比。Windows窗口行为保持原平台约定；模糊仅用于有实际同层背景的局部表面，不对原生插件区域做视觉变换。
6. **交付**：分层检查、真实 Windows/隔离Linux验证、浅深截图及独立本地开发包。开发包使用新目录，保留既有工作区和旧包；不包含 Git 提交、推送、发布或安装器。

具体色板见[主题 r3](../standards/theme.md#12-t-011-双主题配色方案)，尺寸和材质见[UI r9 §2.2](../standards/ui.md#22-t-011-整体样式方案)，交互、失败语义和测试见 F-CORE-012。以上建议作为一份方案整体确认，方案内技术细节由 AI 自主处理。

### 3.2 公开契约和兼容

已按确认方案采用 API/SDK 4.3.0，能力 `ui.theme.live.v1`，主题数据schemaVersion 2；传输RPC v1和workbench整数API 4保持。开发交付标识核心2.0.0-dev.7、终端0.6.0、文件0.3.0，公共UI为1.0.0。

`ui.theme.get`按协商能力返回v1/v2，旧调用的字段集合及类型保持原样；新`ui.theme.preference.get`和`ui.theme.select`只在新能力中出现。`ui.theme.select`接受绝对明暗值及预期字符串修订，不接受任意CSS或文件路径。新能力表示兼容，不增加插件权限或授权弹窗。

主题选择成功提交后，经`app.theme.v1`最新状态发布。state-feed仍复用既有方法/能力，新增契约仅向明确请求者返回App scope；既有`workspace.directory.v1`、`view.presentation.v1`快照保持原形状。SDK按contract检查target/scope/objectId，不能放宽为任意对象；外壳owner由真实窗口id和运行代次绑定，未声明新能力的旧插件不能收到陌生主题推送。

主题的字符串修订和已有v1数值revision分开适配；兼容投影中的数值必须在安全整数范围，不用JS浮点比较新协议修订。核心提交序列及原有feedEpoch各守自己的语义。主题加载/偏好/事件接口及错误按F-CORE-012编写契约样例和测试；旧字段规则不因v2而放宽。

每个文档只有一个主题订阅，多React消费者读取SDK当前快照；文档销毁主动释放，窗口/绑定销毁由宿主兜底清理。隐藏表面保留轻量主题订阅以保持一致，不重新激活文件I/O。新挂载必须先拿到权威主题再显示，注入的旧bootstrap上下文不能覆盖更高修订。

旧插件仍可运行，但没有实时应用能力；保持挂载时主题到下次自然挂载，外观页明确提示。不得为了满足色彩一致而重启PTY或强制重建旧插件；本轮双新插件必须实时一致。兼容矩阵由AP-07验证。
