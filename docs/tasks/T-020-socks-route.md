## 1. 本次方案

用户原意：现有 SSH 连接允许通过 SSH 跳板，希望增加通过 SOCKS 代理的方式，并先完成理解、功能设计和代码设计。

用户本次澄清已固定两种能力的边界：

- **SSH 跳板是主机隧道代理**：SoDeck 要 SSH 登录跳板主机，确认主机指纹并使用该主机的 SSH 转发能力；跳板需要主机账号/密码或私钥，但不创建跳板 PTY。
- **SOCKS5 是网络代理**：SoDeck 只连接 SOCKS5 服务并发送 CONNECT，不进入代理主机，不确认代理主机指纹，不使用 SSH 账号/私钥，不创建代理工作区；最终目标仍独立进行 SSH 指纹和登录。

本次建议采用三种互斥访问方式：直接连接、SSH 主机隧道、SOCKS5 网络代理；暂不实现 SSH 与 SOCKS 混合、代理链或系统代理自动发现。这是范围建议，不是用户已明确排除混合，也不是协议不能组合。用户明确要求“不用再考虑任何旧的兼容”，本次代码方案取消旧路由/API/schema兼容，所有官方消费者一次性升级。

本次实施覆盖已确认的功能规格、核心代码设计、认证/资源/UI 边界及 SK-01～09 测试，交付独立 Windows 开发包。设计阶段未运行的验证仍需实施后逐项记录。

## 3. 源码核实与设计结论

| 位置 | 现状 | 重新规划后的处理 |
| --- | --- | --- |
| `crates/core/src/route.rs` | 路径枚举只表达 direct/sshJump，节点都假定为 `Server` | 用单一 `AccessPath` 替换，明确 `hostTunnel` 与 `networkProxy`，不建立跨类型通用图 |
| `crates/core/src/route_store.rs` | 服务器跳板通过旧引用和多级解析管理 | 新库使用有序 `jumpServerIds`；网络代理只引用一个 `proxyId`，依赖索引分开 |
| `crates/core/src/ssh.rs`、`ssh/transport.rs` | 每个路径节点都建立 SSH session，已有 direct-tcpip bridge | 主机隧道保留原逻辑；SOCKS 只建立 TCP、完成 CONNECT，再把流交给最终 SSH session |
| `contracts/connection-route-v2.schema.json` | 旧 schema 只表达 SSH 路由 | 删除现有 v1/v2 兼容层，不实施上一版拟议 v3，建立 API 5 单一 `connection-route.schema.json` |
| `crates/core/src/secrets.rs` | 秘密按 server ID 存放 | 增加独立 SOCKS proxy namespace，禁止代理凭据与 SSH 凭据串用 |
| `server-dialog.tsx`、认证事件 | 当前表单和挑战以 SSH 服务器为中心 | 三项互斥访问方式；SOCKS 独立代理管理和独立认证挑战，不显示主机登录语义 |

已读取并使用 `apple-design` 技能；本次落点是渐进展开、即时反馈、稳定焦点、清楚的节点语义和减少动态/高对比验证。设计阶段仅更新方案；实施及实际验证见结果记录。

## 4. 实施顺序与关口

0. 先在隔离环境验证 TCP → SOCKS5 CONNECT → `set_tcp_stream` → 目标 SSH；包含分片/SSH banner 交接、认证、取消、释放和错误阶段，通过后再推进全量重构。
1. 用 API 5 单一契约和 `AccessPath` 替换旧路由类型、生成文件及官方消费者。
2. 建立数据库 v6 的 `connection_paths`、`socks_proxies`、依赖索引和代理秘密 namespace。
3. 实现 SOCKS5 有界协议状态机和独立单元测试。
4. 将 SOCKS 路径接入目标连接管理器、认证、快照/复用及计量。
5. 将现有多级 SSH 接入新的 `hostTunnel`，完成纯 SSH 回归。
6. 接入代理管理、认证挑战、错误/状态 UI，统一升级终端、文件和网络插件。
7. 运行真实 SOCKS/SSH、Windows 原生、契约、资源和独立目录包验证。

如果第 0 步只能依赖外部 `ssh`/ProxyCommand、远端 helper 或把代理伪装成 SSH 主机，则停止实现并重新提交技术方案。
