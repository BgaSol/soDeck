## 1. 最新需求与理解

收尾回归细化（2026-10-27，原确认范围内）：以持续响应而非有限文件验证 64 条 TCP 流全程存活 60 秒；16 条流停读 10 秒后恢复。补充超长规则列表按 32 KiB 动态分页、停止后立即启动的迟到回执隔离、过期路径分页不覆盖新路径、检查超时后不保留迟到 probe 结果、上游非法 HTTP 字段返回 502 的回归。以上保持已确认的预算、交互与错误语义。

并发缺陷修复：64 条流曾触发宿主既有的 32 个未决 RPC 上限，状态 ACK 失败导致规则停止，而旧统计仍显示连接数。因此负载用例必须同时断言规则为 ready、核心连接数和后续真实请求；旧“64 流/控制 p95”单项不能作为完整通过。插件增加全实例共享的有界调用调度，普通调用、状态/回执查询和清理分别保留并发额度，总在途不超过 24，不扩大宿主既有上限、不绕过审计。

吞吐基准实施：NT-08 的“相同配置原生 TCP→direct-tcpip”以同工作区 `ssh2`/OpenSSL 库和 debug 构建的最小本机 TCP 转接程序作为正式基线，隔离一跳 SSH、同凭据/目标/64 MiB、三次中位数；基线直接复制数据，不经过插件、审计或核心调度。Windows OpenSSH 命令行对照另存，不与该相同库基线混称。早期 OpenSSH 对照在 QEMU TCG 下存在约 1.0/1.8 秒两档波动，失败证据保留，不删除或写成已通过。

实施细化（2026-10-27，原确认范围内）：组状态订阅补充可用路径数和实际接入连接数，插件据此驱动接入/断线恢复，不持续创建空 accept 操作。组流量按 listener 接入方向统计，避免两端重复计数。启动/手动恢复复用工作台命令与逐跳身份对话框，网络路由操作使用同一命令身份；等待身份处理期间关闭暂停的 listener，保留可取消的组和挑战。协议测试覆盖提前响应、100 Continue、跨目标流水线与握手尾部；这些是既有 NP-07/NT 流程的实施细节，不改变范围。

公开接入细化：`ui.servers.edit({serverId})` 仅向视图所属窗口请求展示既有核心服务器编辑器，不保存或复制连接数据；作为原方案“编辑服务器连接”入口的实现。网络强停回执返回 `affectedGroups` 与 `cleanupPending`，全局操作查询不带 scope，带 scope 的原操作严格匹配原归属。两者均补契约和相应原生/资源测试。

用户明确要求：“以插件的方式实现两个功能：一个是实现点对点的端口转发，允许跨多机器；一个是实现将目标机器的局域网映射到我本地的某个端口，用于 http 和 socks 的代理。”当时要求理解、推测目的并重新整理需求；后续实施授权已在本节登记。

需求目的推断：把分散在不同网络和多层访问路径后面的资源接到本机，兼顾只能连接固定地址的客户端与支持代理的浏览器/工具。用户不希望手工在多台机器配置一串转发命令，也不希望每访问一个网站都新建转发规则。

| 功能 | 用户预期 | 典型链路 |
| --- | --- | --- |
| 点对点端口转发 | 一个入口映射到一个指定服务，普通客户端直接连接入口 | 本机 `127.0.0.1:13306` → SSH A → SSH B → SSH C → C 可达的数据库 `10.10.1.223:3306` |
| HTTP/SOCKS 内网代理 | 一个本地端口作为远端网络入口，目标由客户端请求指定 | 浏览器配置 `127.0.0.1:10808` → SSH 路径 → 最终节点 C → 请求中的 `10.10.1.223` 或其他服务 |

两项都纳入本次。推荐一个“网络隧道”插件内的两个模式，分别维护配置与测试，复用核心路径和资源。是否一个或两个插件包是组织建议；两功能均插件化、Windows/Linux SSH 主机、v1 只看功能和 v2 重做界面是明确要求。

用户已明确选择“经过多台 SSH 主机中转，入口在本机”。跨多机器确定为多层 SSH 中转，本次不提供远端监听入口；至少需用 A/B/C 三个 SSH 节点验证两个插件功能真实经过完整路径。每条规则明确本机入口、经过的机器、最后从哪台机器访问目标。目标服务不必是 SSH 服务器，可能在最后节点本机或它可达的其他机器上。

“局域网映射”用 HTTP/SOCKS 代理表达：覆盖最终节点实际可访问的多个服务，域名由最终节点解析（客户端需提交域名）。TCP 代理不等于自动为全部应用增加网段路由，UDP/广播/ICMP/VPN 不自动纳入。

实现建议通过已有 SSH 服务提供传输：本机处理 HTTP/SOCKS 请求，最终 SSH 节点创建目标连接，无需额外远端代理进程。用户以本机 `10.100.77.166`、最终 SSH 主机 `192.168.1.16`、远端网页主机 `192.168.1.18` 再次确认访问方向；随后答复“好的，那我就放心了，你再确认一下功能设计”。本轮据此复核功能，不要求用户再次选择实现术语，不将该答复记为编码批准。具体链路及前置条件见[F-PROXY-001 §1.1](../plugins/proxy/features/network-proxy.md#11-用户具体场景与连接位置)。

### 1.1 v1 两种模式的源码复核

用户提醒“v1 提供了两种代理方式”后，重新核对相邻 `soDeck` 工作区和本仓库 `origin/master`（`436cad2`，v1.0.2 发布说明提交）。相邻工作区当前为 `codex/plugin-platform` 且存在未提交工作；另外核对 master 的模型和表单，避免将该工作区增量当作发布基线。下列核实是读源码，不是本轮运行验证。

| v1 模式 | 配置和使用 | 实际分支 | 本次关联 |
| --- | --- | --- | --- |
| 固定端口转发 `PortForward` | 规则预设目标 IP/端口；例如本机 `18080` 映射到远端网络的 `10.10.1.223:80`，浏览器直接打开 `http://127.0.0.1:18080` | `Service::target()` 返回固定目标，worker 直接将客户端 socket 交给 `ForwardCore` | 可用于单服务，也可映射一个已经存在的远端代理端口；自身不解析代理请求 |
| 内网代理 `NetworkProxy` | 规则选择 SSH 节点和本地入口；浏览器设置代理 `127.0.0.1:10808` 后仍访问 `http://10.10.1.223`，换目标无需改规则 | 本机识别 HTTP/SOCKS5，请求解析出的目标经 connector 进入 SSH `direct-tcpip` | 对应用户本次主场景，应作为插件功能规划依据 |

两者共用 SSH 传输和资源机制，但用户操作、目标来源和本机协议处理不同。此前只用“本地代理/SSH 通道”解释容易混淆，这里以 v1 实际模式名为准。当前核实的“内网代理”分支没有通过 curl 部署、启动远端 HTTP/SOCKS 程序；“远端部署代理再固定映射”是另一种组合方式，不能写成该分支既有实现，也不能据此否认用户可能自行部署过代理。

源码定位（相对 v1 工作区）：

- `src/PortForwardEditor.tsx:200`：两个用途选项；`:255` 明示内网代理的同端口 HTTP/SOCKS5 及逐请求目标。
- `src-tauri/src/port_forwarding/model.rs:19`：`PortForward { target_host, target_port }` / `NetworkProxy` 两种类型。
- `src-tauri/src/port_forwarding/worker.rs:273`：本机监听；`:454` 起分别进入代理协议或固定目标转发。
- `src-tauri/src/port_forwarding/proxy/mod.rs:248`：SOCKS5/HTTP 分派；`http.rs:108`/`:151` 及 `socks5.rs:77` 取请求目标并打开通道。
- `src-tauri/src/port_forwarding/proxy/connector.rs:207`：将目标提交给通用转发；`src-tauri/src/ssh_transport/forwarding.rs:295` 调用 `channel_direct_tcpip`。

## 3. 明确要求、建议与待决边界

明确：两项功能插件化；两项入口均在本机，端口转发经过多台 SSH 主机中转；远端是 SSH Windows/Linux；参考 v1 功能，重做 v2 界面。本次不增加远端监听入口。

建议：一个插件两个模式；端口转发先表达固定 TCP 目标，内网代理同端口支持 HTTP/HTTPS CONNECT/SOCKS5 CONNECT；两种功能共用多层 SSH 路径；多规则并行、逐规则启停、状态、检查、配置保存、异常与清理；入口默认本机回环，代理端口默认建议 10808 且可改。

本轮完整建议：

1. 插件QuickJS worker持有HTTP/SOCKS及规则，核心新增通用net.*原语；控制JSON、正文有额度二进制流，固定转发/CONNECT/SOCKS握手后原生splice。UI只显示状态；业务可独立更新。
2. 核心复用T-013路径/身份，但网络数据物理池与终端/文件分开；每池按需至多4成员，纳入既有全链预算。目标open超时隔离draining成员，其他有效流继续，新请求可使用健康成员，容量耗尽明确报错。
3. 一个独立插件、每服务器一个管理视图；配置/运行快照分开，实际listener检查、关闭/退出核心兜底、默认手动恢复和可选有限自动恢复。恢复时当前路径修订变化进入需要处理，不悄悄换出口。
4. API/SDK建议4.7兼容增量，旧DTO/旧插件保持；首版插件0.1.0，真实更新/坏包验证和三插件Windows独立开发包一并交付。最大运行数/缓冲/协议边界和测量门槛已写入核心r6，不由实现临时无界扩展。

没有需要用户选择Rust模块名等内部事项；实际隔离Windows测试环境需在实施中建立，若环境不足必须保留未完成，不用模拟代替真实平台。新需求/架构或产品范围变化仍按文档流程更新确认。

暂不主动加入系统代理接管、PAC、VPN/TUN、UDP、自动服务发现、跨 App 驻留或生产发布。远端代理自动部署不是本轮默认前置，但如实际方案需要必须解释平台依赖、生命周期与回收。
