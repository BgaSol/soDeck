## 1. 本次目标与授权

用户先提出“完整的，不应该仅仅局限于日志调试”，明确包括用户操作事件、重要事件上报，以及未来AI插件读取信息定位问题；随后认可统一记录/关联/查询的理解，并要求“设计一下核心应该提供哪些能力”。本轮授权为能力设计与必要文档维护，不包含应用、原型、测试或构建代码，不包含Git提交/推送。

本稿提出统一事件、操作关联、历史查询/统计、可补读订阅、重要问题生命周期、诊断快照/指标/证据包、统一留存/健康以及插件接入。当前调用审计继续是可靠性基线；未来诊断消费者通过公开接口，既不绕过P-13做插件命令互调，也不增加P-14禁止的插件权限审批。

包含：核心服务语义、候选公开接口、身份/数据/生命周期/失败边界、留存建议、功能测试与既有设计衔接。

本轮不包含：诊断界面视觉/交互稿、最终代码修改方案与schema、实际AI插件/模型调用、外部遥测上传、通用自动修复/工作流引擎、远端正文录制。这里限定的是本稿设计与交付，不将整体目标缩减为仅调试日志。

## 3. 核实、影响与兼容

2026-10-27只读核实：Core::record/Store保存调用开始和结果；调用列表支持筛选及保留清理；worker console置空、stderr丢弃；网络插件保留200条运行内存诊断，文件插件有私有诊断状态。实际API版本由contracts/capabilities.rs定义，核实时为4.7.0；T-015预定4.8的实施独立进行，不能因本稿提前声明新的能力已可用。

影响边界：

- 核心负责采集/存储/查询/问题/证据公共服务，领域服务负责事实和恢复依据。
- 宿主绑定来源、代次和操作上下文，SDK提供声明式上报和有界消费；正式业务日志逐步替换空console。
- 三个当前插件后续各自补充采集点与业务字段规格；普通业务事件随包独立更新，核心不导入它们的私有实现。
- calls.list旧返回形状保留，以统一记录服务提供兼容投影；审计向新存储切换时只有一个权威数据源。
- state feed继续表示最新状态，可靠历史另设feed；诊断历史不用于传递业务命令。
- P-52数据库不兼容即备份重建保持；旧calls保存在旧库备份，不自动迁移。不同数据库epoch与已失效服务器标识在诊断中可识别。
- T-015任务已有其他会话的实施记录，本稿不改变其授权、任务状态或实现内容；最终衔接以实施时的工作区和有效规格为准。
