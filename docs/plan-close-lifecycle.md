# 关闭、退出与重启的完整生命周期设计

设计日期：2026-11-08。状态：实现已进入整改分支，本轮验收与未完成项见[实施记录](implementation-close-lifecycle.md)，尚未发布修复。方法见[功能设计方法](plan-feature-design.md)。

本方案细化[组件 UI 设计第 6 节](plan-component-ui.md#6-生命周期关闭与移动)的统一关闭要求。当前可调用协议仍以[插件 API](plugin-api.md)为准，本文定义新宿主命令与阶段，具体实现与验收差异见实施记录。

基于当前核心 0.11.0 源码 `752410e` 的逐文件修改、接口迁移、锁与资源结束确认、实施顺序和测试落点，见[详细代码整改方案](plan-close-lifecycle-coding.md)。其中补充了所有组件设置草稿参与关闭，以及安装器在途时不能把监视超时当作可安全重试的边界。

## 1. 目标与范围

用户可以在多个窗口中同时运行终端、编辑文件、传输文件、使用网络隧道和后台系统状态，然后关闭页面、工作区、窗口或退出/重启应用。所有入口具有一致的保存、取消、释放和失败语义。

完成条件是：目标资源确已收尾，目标生命周期结束，迟到请求不会让它复活；取消关闭时仍保留可继续使用的对象和正确的业务状态。系统状态等后台组件的增加不要求核心为插件 ID 编写退出特例。

本次涵盖正常关闭、取消、保存失败、清理失败、重复请求、跨窗口输入同步、后台挂载、连接/移动与关闭的竞争，以及宿主/插件异常退出的收尾。沿用可信插件模型、独立发行、重启应用启停配置和现有平台适配，不引入插件权限或审批、通用工作流引擎、持久事务数据库、自动恢复远端会话或新的生产依赖。

## 2. 现状与证据边界

前次故障排查参考 `97b6b1d` 及 2026-11-08 当时的工作区，更新体验等改动当时尚未提交；排查时用户运行的已安装核心为 0.10.0。详细代码整改方案已重新核对后续源码 `752410e`（核心 0.11.0）。这里保留原复现证据的基线，不能把它当成新源码或新安装包的验证结果。

已复现的路径：

1. `Components.close()` 调用 `finishClose`，随后刷新工作区。
2. `ui_close_finish()` 清理视图后删除关闭计划，解除 `frozen()`。
3. `ui_snapshot()` 调用 `reconcile_ui()`，为仍存在的工作区补建后台 view。
4. `shutdown()` 的 `require_closed()` 发现残留 view，返回“请先完成组件页面的关闭确认”。

前次排查使用当时已有的 Windows x86_64 核心与插件测试夹具、临时数据目录和模拟会话：后台声明开启时连续三次关闭后读取快照，均得到一个新建且未显示的 view，关闭计划的 dirty 列表均为空；关闭后台声明的对照保持零个 view。没有操作用户的真实连接，也没有重编译或执行五平台验证。该证据证明重建路径，不是修复验收。

## 3. 对象、归属与结束条件

对象不是一棵简单的插件树：一个插件进程可服务多个工作区，一个连接可被多个能力引用。逻辑视图同时绑定插件实例与工作区 Context；原生窗口是展示归属，移窗不能重新创建逻辑任务。

| 对象 | 管理者与归属 | 生命周期与结束条件 |
| --- | --- | --- |
| 应用 | 核心；Tauri 执行最终退出/重启 | 正常运行 → 关闭中 → 资源停止 → 原生退出/重启；失败保留实际阶段 |
| 插件进程 | 核心进程监督；启停配置单独保存 | 启动 → 运行/失败 → 停止与进程组清理；应用关闭时确认实际进程退出 |
| 连接与连接尝试 | 核心连接服务；固定 Context 和引用关系 | 接受尝试 → 认证/提交 → 使用/断线 → 取消及释放；旧认证结果不可登记到关闭目标 |
| 工作区 | 核心；绑定连接上下文及当前窗口 | 建立 → 使用/移窗/重连 → 关闭中 → 删除；关闭期间不接受新视图或新 Context |
| 逻辑 view | 核心登记身份，插件维护业务状态 | 创建/挂载 → 就绪/失败 → 使用 → 关闭中 → dispose 与资源释放；旧 viewId 不重新挂载 |
| surface/iframe | 宿主前端展示，核心验证窗口与 surface 身份 | 挂载 → 输入同步/展示/隐藏/迁移 → 卸载；卸载不等于销毁逻辑 view |
| 原生任务、流、端口和文件操作 | 对应核心服务；绑定实例、view、Context | 接受并登记 → 运行 → 完成或取消 → 确认收尾/释放；覆盖尚在创建的资源 |
| 草稿及业务结果 | 输入暂存在页面，已同步状态归插件/对应服务 | 输入同步 → 保存/放弃/保留；只有确认保存成功才能据此决定关闭 |
| 关闭操作 | 核心；明确目标和发起窗口 | 准备 → 决策 → 清理 → 收尾 → 完成，或释放前中止、释放后失败待重试 |

## 4. 范围和用户语义

| 用户动作 | 实际范围 | 保留什么 |
| --- | --- | --- |
| 收起侧栏、切换 Tab、最小化 | 改变可见性 | view、连接、任务和后台采集 |
| 关闭终端页、编辑页或弹窗 | 明确的逻辑 view 集合 | 同工作区其他 view、共享插件进程与连接 |
| 关闭服务器工作区 | 工作区的全部 view、在途工作和资源引用 | 其他工作区与仍被引用的共享资源 |
| 关闭子窗口 | 该窗口拥有的工作区与连接尝试 | 主窗口和其他子窗口 |
| 主窗口关闭、系统退出 | 整个应用，包含其他窗口和尚未形成工作区的连接尝试 | 已持久保存的配置；不承诺会话恢复 |
| 普通重启、更新重启 | 同全局退出，最后执行对应重启/安装动作 | 原有更新与配置持久化规则 |

`backgroundOnWorkspace` 声明的逻辑实例随工作区存活。面板收起只隐藏；业务暂停仍由插件提供。它不能被当成普通编辑页销毁后又由后台循环补建，宿主不提供这种自相矛盾的页面关闭入口。该判断基于声明和目标类型，不基于系统状态插件 ID。

关闭一个普通 view 时，可为其所在工作区短暂保留现有变更冻结，避免布局/移窗竞争；资源清理范围仍只包含选定 view。其他工作区继续运行。

## 5. 必须始终成立的规则

1. **一个关闭目标只有一个在途操作。** 核心在短临界区内确定范围并登记操作；覆盖的工作区、窗口和应用创建入口同时看到它。
2. **关闭状态从准备持续到结果确定。** `finishClose` 不能在父对象关闭前解除约束；前端刷新或前端消失不解除它。
3. **资源在接受创建时就可追踪。** 关闭覆盖已登记资源与未完成的创建任务；提交新资源与关闭检查必须互斥。
4. **保存全部成功后才开始释放。** 部分页面保存成功、另一个失败时保留全部页面；成功写入的文件不自动回滚。
5. **已有操作可收尾，新业务不得进入。** 允许既有任务查询/取消/释放和本次明确选择的保存；拒绝新 PTY、监听、采样及普通文件操作。
6. **结果必须匹配当前生命周期。** view、实例、Context、关闭操作及 surface 过期的回复不得重新挂载、登记资源或改变新对象。
7. **隐藏与移窗不改变任务归属。** 展示生命周期不负责开启或终止后台逻辑实例。
8. **关闭完成要有资源证据。** 发出 cancel、移除 Tab、清空列表、收到 dispose 回复，均不能单独作为全部释放的证明。
9. **快照只有读取含义。** 刷新、网络统计、状态页面和定时读取不能新建 view 或重启采样。
10. **结束过程有界且不重放副作用。** 清理超时给出阶段和可重试范围；重试继续收尾，不重新执行保存或已提交的业务操作。

## 6. 核心持有的关闭操作

### 6.1 最小数据与调用边界

演进现有 `ClosePlan`，记录操作编号、发起窗口、目标范围、阶段、固定的参与对象身份、尚未完成的工作和失败原因。最终对象集合由核心解析并验证，前端不再把自己的 view 列表当成清理依据。

核心保存唯一的关闭事实，各入口按阶段查询“能否接受新工作”“是否正在清理”。现有 `Application.exiting` 与 `AppCore.closing` 的职责在迁移时收敛；Tauri 如需避免系统退出事件递归，只保留反映核心最终交接结果的标记，不独立决定业务能否恢复。

宿主内部拟采用以下语义，具体命令名称可在实现时与现有桥接风格统一：

- `prepare(target)`：验证目标、保留范围并返回操作及输入同步参与者。
- 输入同步回报：按操作、窗口和 surface 核对；主窗口目录表单及全部组件设置草稿参加全局决策，沿用各自保存与冲突处理规则。
- `decide(operation, save | discard | cancel)`：提交决定；核心完成后续协调与父对象关闭。
- `status(operation)` / 状态事件：只查询进度，不触发保存、挂载或重试。
- `retry(operation)`：只恢复失败的清理步骤；重复相同请求得到同一操作状态。

前端的职责是展示、禁用受影响输入、完成 flush、提交决定和呈现结果。它不再执行“先关闭组件，再另调关闭父对象”的串联。宿主退出适配器、更新安装器与各资源服务执行各自收尾，由核心操作记录接收明确结果。

保留有界的近期终态记录用于重复响应；活动操作有数量上限，重复点击复用记录，冲突请求直接返回当前操作。实现时设置固定上限及过期回归，不建立跨重启持久化事务。

### 6.2 状态转换

| 阶段 | 允许的操作 | 离开条件与下一阶段 |
| --- | --- | --- |
| 准备 | 只读、受控输入 flush、已有请求收尾；暂停范围内的新创建/移动/重连提交 | 前置检查通过、同步与 beforeClose 得到结果 → 决策；无法确认的内容作为错误列入决定，目标失效/前置失败/取消则中止 |
| 决策 | 等待用户选择；执行本次选择的保存；查询或取消已有任务 | 所有保存成功或明确放弃 → 清理；取消或确定的保存失败 → 中止；保存结果未知则先核实，不进入清理 |
| 清理 | 只读进度、原有任务取消/释放、dispose、连接与进程收尾 | 全部资源达到结束条件 → 收尾；期限内未完成 → 失败待重试 |
| 收尾 | 移除父对象、销毁原生窗口，或安装更新并交接退出/重启 | 目标动作完成 → 完成；动作失败 → 失败待重试 |
| 失败待重试 | 查询详情、重试记录的清理或收尾阶段 | 回到失败阶段，仅继续未完成步骤；保持目标不可新建资源，不自动恢复正常运行 |
| 完成 | 返回既有结果 | 页面/工作区已关闭，或宿主已交接原生退出/重启；真实进程退出由外部原生验收确认 |
| 中止 | 返回取消或失败原因 | 释放关闭保留，后台协调恢复；已经成功保存或已经结束的任务保持真实结果 |

等待用户决定没有自动替用户选择的超时；准备、同步、保存等待和清理等机器步骤必须有截止时间。状态改变只由核心提交，前端显示以其为准。

用户在保存进行中取消关闭时，先停止推进关闭，等待已接受写入得到可报告结果或进入明确的结果未知状态；完成这一收尾前不假装撤销写入、不释放 view。未知结果允许核对、保留/导出草稿或明确放弃，不自动重发远程写入。

### 6.3 完整主流程

1. 在登记关闭范围时检查其他关闭操作及移窗事务。重启还要先做更新忙碌、更新包可用性和现有验签等前置检查；相关更新状态需保留到提交，防止检查后又启动冲突下载。
2. 暂停目标范围新业务接入，收集所有相关窗口的 surface。让每个窗口停止新增编辑输入，排空已有输入并完成 flush；隐藏但已挂载且声明 flush 的页面同样参加。核心先限制拓扑和新资源，仍接收指定 surface 的最后一批同步数据，直到对应 flush 回报被确认；之后才关闭其普通写入入口。不能先用全局 frozen 拒绝同步，再要求页面证明已同步。无 iframe 的后台 view 由插件状态查询参加，不虚构页面确认。
3. 等待准备前已接受的挂载、UI 写入等得到受控结果，再调用 beforeClose 汇总 dirty/busy/error。主窗口目录表单、全部设置草稿与插件页面的决定都完成前，不释放任何一页。超时且无法确认的内容必须明确返回处理或放弃，不自动视为已经同步/保存。
4. 核心执行保存或放弃决定。保存先等待已有阻塞任务收尾，再为需要保存的 view 发出一次 `ui.save`，随后用 `ui.beforeClose`/现有任务状态查询结果；结束后仍 dirty 则报告未完成，不能通过轮询反复提交保存。文件批次、冲突处理和取消复用现有业务协议，等待输入的冲突要明确返回处理途径。
5. 在短临界区内提交“清理中”，保持禁止新资源。停止调度新工作，处理在途创建，再按 view 通知 dispose 并调用各服务取消、等待和释放已有资源。
6. 页面关闭清理选定 view；工作区/窗口关闭继续释放连接引用；应用关闭继续停止插件进程、连接和后台 worker。资源确认后进入收尾，移除目标父对象、销毁窗口，或安装更新并由 Tauri 退出/重启。保留安装是否已经成功等结果，重试原生重启动作不能重复安装。
7. 完成或失败状态由核心统一发布。确认阶段可中止，清理阶段保留未完成项供重试。事件通知失败、前端刷新和窗口重载不影响核心继续收尾。

## 7. 并发、后台与只读快照

### 7.1 创建与结束必须使用同一判断

后台初始化、`ui_attach`、插件请求资源、认证成功提交、工作区创建和移窗提交，都查询同一份核心关闭状态。应用范围还必须阻止尚未拥有工作区的连接尝试落地。

资源请求在受控临界区登记在途身份，释放锁后进行 IO/RPC；返回时在同一状态边界重新检查并提交。关闭可以取消它、等待它或拒绝其结果，但不能遗漏已创建的本地句柄。规定锁顺序并沿用连接提交等既有顺序，不持锁等待插件调用。

资源进入取消后立即停止对新业务提供服务，但保留足以等待、重试和验证释放的归属与结果记录。工作线程实际退出或句柄释放后才删除收尾记录、归还并发预算；不能从 registry 提前删掉对象，再以“列表已空”证明资源结束。

每 view 的生命周期调用保持受控顺序：已发出的 mount/写入先得到结果或确认终止，才允许 dispose 成为最后一步。后台 worker 不得因取消关闭永久退出；暂停新工作和应用最终停止分开表达。

只收到 RPC 超时不代表插件端工作已结束。工作区级关闭若无法确认某 view 已释放，应报告清理未完成并保留重试；不能为了这个 view 杀死还服务其他工作区的共享插件。全局退出按既有进程组/Job 机制有界终止并确认退出。受支持插件仍须遵守 dispose 幂等和收尾契约；分进程不构成沙箱，也不保证任意插件创建的脱离进程都可回收。

### 7.2 接管实例初始化的职责

把 `ui_snapshot()` 中的实例创建、默认初始化和偏好登记转移到核心明确的生命周期协调入口：工作区被接受、插件完成启动、连接 Context 更换、相关布局偏好改变。事件触发协调，后台循环只处理符合运行阶段的实例及挂载重试。

协调提交前重新验证工作区、插件实例、Context 和关闭阶段。只有处于正常运行阶段的工作区才能补建后台实例；默认终端/文件的创建仍只执行适用的初始化策略，不因读取快照或关闭最后一个终端重跑。

状态发布要么已经完成必要初始化，要么明确显示初始化尚未完成；不能要求前端读一次快照来补全核心状态。无后台插件的工作区也必须正常初始化，这需要单独回归。

### 7.3 重复与冲突规则

- 同一个目标重复关闭复用已有操作，不重复保存、dispose 或弹出多份对话框。
- 与尚在准备/决策的操作重叠时，返回当前操作及其位置；先完成或取消原决定，再重发新目标。第一版不自动合并用户决定，也不排队执行过时关闭。
- 工作区清理失败后仍须允许用户退出整个应用。全局退出先关联已有清理操作的未完成项和已完成结果，对其余窗口重新执行完整的同步与保存确认，期间原失败操作暂停单独重试；新增目标同意关闭后，才一次性交接清理执行权并允许停止共享插件。旧操作指向新操作，只有一个执行者；不重新保存或重置已清理目标。全局确认被取消时，只恢复新增目标，原目标仍处于此前的清理失败状态。这只处理全局退出接管收尾的实际场景，不扩展任意范围合并。
- 更新安装失败后的“退出”修改同一操作的最终收尾动作，不从头再关闭一次已停止的应用；重试安装与退出互斥。
- 正在移窗的目标先让已有移动完成或按既有机制取消，再重新解析关闭目标；关闭保留建立后禁止移入、移出以及迟到的移动提交。
- 取消关闭后允许新的合法操作；旧关闭回复不能推动新一轮关闭。通过操作身份和阶段核对隔离。
- 插件内部迟到结果不能取得已失效 view 的核心资源；仅丢弃前端回包不足以视为已经释放它造成的资源。

## 8. 失败处理与期限

| 发生位置 | 对用户的结果 | 生命周期和恢复 |
| --- | --- | --- |
| 更新前置检查失败、目标已变化或存在移窗冲突 | 明确原因，目标尚未释放 | 不启动或中止准备，不改变会话运行状态 |
| 子窗口 flush 超时、页面加载失败、输入无法确认 | 指出服务器/页面和同步失败 | 默认返回处理、保留已知草稿；用户可明确放弃后继续，不能把未知输入视为已保存或永久堵住退出 |
| 用户取消、某页保存确定失败 | 保留全部页面，显示实际保存结果 | 等已接受的保存收尾后恢复；已成功写入内容保持成功 |
| 保存提交后断线、结果未知 | 明确“结果未知”，允许核对/保留草稿 | 不释放、不自动重复提交；用户明确放弃前保持决策状态 |
| 选择放弃并关闭 | 取消任务并报告已有远端结果 | 清理不承诺撤销已经发生的文件写入或远端副作用 |
| dispose 失联、原生资源取消超时 | 显示具体未完成组件/资源类型 | 清理失败可重试；其他工作区保持运行 |
| 工作区清理失败后请求全局退出 | 汇总其他窗口尚未处理的内容 | 保留原清理结果，处理其余目标决定后按全局范围收尾，不能永久以“已有关闭操作”阻断退出 |
| 插件崩溃 | 显示组件失联及已知未保存风险 | 核心回收其拥有的资源；未持久草稿不能承诺恢复，继续关闭需沿用明确放弃语义 |
| 用户界面重载或发起窗口消失 | 正常重载可重新显示操作状态 | 清理继续；准备阶段失去必需输入参与者则失败中止，不因计时自动同意 |
| 原生窗口被意外销毁 | 提示其工作区已中断 | 以核心实际归属回收资源；无法补做消失页面的保存确认；应用其他部分继续 |
| 更新安装失败，旧会话已清理 | 显示安装失败，可重试安装或退出 | 保留现有包及失败记录，不宣称恢复旧终端/采集；阶段继续限制业务创建 |
| 宿主崩溃、系统强杀或断电 | 不保证交互保存和远端子任务终止 | 依赖既有进程组、连接断开、持久化与启动恢复边界；与正常关闭验收分开 |

期限复用现有能力：输入同步保留现有宿主上限；保存协调以现有 125 秒预算为基线，改成操作共享的机器等待截止时间，不能随页数逐页追加；RPC 保留其自身上限；插件停止和连接收尾保留当前 6 秒、3 秒应用阶段预算及进程监督器既有期限。若需要调整数值，在相应用例和实施记录中给出依据。

超时表示本阶段未完成。用户阅读确认框不消耗机器等待预算；取消、重试和日志输出保持可响应。资源数量、并发和队列沿用各服务已有上限。

## 9. 接口兼容、平台与排障

核心与自带前端一起迁移宿主关闭命令，调用处与夹具同批更新。外置插件继续使用 `ui.mount/beforeClose/save/disposeView`、现有 flush、文件任务和会话接口。关闭操作编号首先保留为宿主内部关联，不增加插件权限声明。

旧插件未声明 flush 时沿用现有保证范围，不能宣称取得其仅存在于页面的草稿。需要新增可观察协议语义时，先确定 capability 或 API 版本的兼容方式，再同步实现和文档；不能用默默增加必需字段迫使所有插件同步升级。

保存继续复用核心资源服务中的既有保存/已接受批次入口，按原实例、view、Context 和已接受工作身份判断。普通新任务不能因为参数自称“保存”就通过关闭阶段检查；这是生命周期正确性检查，不是插件授权系统。

统一记录操作编号、范围、阶段、耗时、实例/view/Context 和未完成资源数量；用户看到服务器/组件名称、当前阶段和可执行动作。日志不包含凭据或文件正文，普通日志不自动弹出通知。

Tauri 的窗口销毁、应用退出/重启及 Windows Job/Unix 进程组仍留在核心平台适配层。五个正式目标分别验证实际程序和外置插件的启动与退出；本机测试、交叉编译或浏览器窗口不能代替目标原生验收。核心打包不新增对业务插件构建的依赖。

## 10. 实施落点与顺序

| 完整工作项 | 主要落点 | 交付条件 |
| --- | --- | --- |
| 锁定复现与操作边界 | `component_ui` 测试、workspace UI 夹具 | 确定性复现重建；写出准备/清理/失败、范围及重复操作断言 |
| 迁移关闭协调及全部入口 | `component_ui/close*`、`core.rs`、`windows.rs`、`main.rs`、`components.ts`、`workspaces.ts`、`main.ts`、对应命令与夹具 | 页面、工作区、子窗、退出、普通/更新重启都由同一操作持有到底；旧的先清组件再关父对象路径被移除 |
| 完成后台和在途资源规则 | `component_ui/layout.rs`、`background.rs`、`host.rs`、连接接入、资源归属与各服务 | 快照只读；默认初始化完整；创建/提交与关闭互斥；取消恢复；迟到资源可回收 |
| 验证插件契约与原生收尾 | 现有四插件业务用例、核心生命周期测试、桌面与原生包入口 | 多窗口真实草稿、PTY/文件/端口/采样和进程确认释放；失败及重试有证据 |

这些工作项属于同一个关闭生命周期问题。可以按完整主题提交，但入口迁移和资源规则未闭合前不能宣称已修复或发布一半方案。实施时先检索所有相关调用者，保留并协调工作区已有更新改动；不顺带重写插件业务或发布框架。

实施后更新本方案涉及的组件 UI/插件 API/架构段落与使用限制；在独立实施记录中保留本次版本、测试、跳过范围和风险。当前设计阶段不改写现有协议文档为“已实现”。

## 11. 验收矩阵

| 编号 | 场景与扰动 | 必须证明 |
| --- | --- | --- |
| L01 | 一个隐藏后台 view；关闭时持续读取快照、触发工作区通知 | 清理后没有新 view/挂载/采样，目标正常结束 |
| L02 | 后台关闭中途取消；随后隐藏、显示与再次关闭 | 原 view 可继续使用，采样恢复一次，无重复 worker 或永久停采 |
| L03 | 无插件、无后台插件、默认终端/文件、工作区正在初始化 | 能关闭；正常初始化无需读快照触发；关闭最后终端不重新自动创建 |
| L04 | 两个窗口均有文件草稿，其中一个页面隐藏；服务器表单及未选中的组件设置页有草稿；主窗口退出 | 两窗输入都完成 flush；宿主草稿也参加决定；所有决定完成前没有任何页面被释放 |
| L05 | 部分保存成功后另一页失败、保存中取消、写入结果未知 | 页面保留；成功结果不回滚；取消不谎称撤销写入；未知结果不重放 |
| L06 | 终端输出、文件批次、活动 SOCKS 客户端及系统状态同时运行 | 保存/放弃语义正确；目标 PTY、任务、监听、流和采样释放；其他工作区可用 |
| L07 | mount、资源创建、认证和移窗在可控同步点被关闭打断 | 开始与提交均受约束；迟到结果清理且不能创建新 Context/view/句柄 |
| L08 | 重复点击、重复 decide/retry、重叠关闭、旧操作回包；全局退出接管清理失败的工作区 | 单一有效执行者；不重复副作用；接管前仍处理其他窗口草稿，不永久阻断全局退出 |
| L09 | dispose 超时、连接收尾慢、插件崩溃，随后重试 | 保留正确阶段和未完成项；已完成步骤不重做；不误杀其他工作区共享进程 |
| L10 | 前端刷新/失联、子窗意外销毁、主窗口尚未加载 | 无人持有的关闭保留可收尾；不伪造保存成功；资源按实际归属清理 |
| L11 | 页面、工作区、子窗、系统关闭、退出、普通/更新重启；安装失败改为退出、安装成功后重启失败 | 同一生命周期规则；前置失败不先销毁工作区；安装失败不假装恢复会话，重试不重复已完成安装 |
| L12 | 每个正式目标上的实际包退出/重开，带四类代表性资源 | 本机进程与受管子进程结束，测试端口可重绑、连接关闭；配置保持，远端任务结果按能力边界报告 |

核心竞态测试使用屏障/可控回复安排交错，不通过重复睡眠碰概率。断言覆盖 registry、在途请求、实际进程和端口等结果，不能只断言界面消失或没有错误提示。

优先扩展 `src-tauri/tests/component_ui.rs`、`workspaces.rs`、`lifecycle.rs`，以及 `scripts/test-workspace-ui.mjs` 和现有文件/终端/网络/系统状态业务用例。UI 测试要连接真实核心协调，不能由 mock 永远返回“已关闭”掩盖缺陷。新增插件复用公共契约，再增加自己的业务副作用验收。

按[开发检查范围](development.md#版本与持续集成)运行相关格式、类型、构建、脚本、核心和业务测试；按[分发流程](distribution.md)完成五平台原生验证并记录实际范围。现有版本升级脚本有固定版本预期，不能不更新用例就当作新版本验收。
