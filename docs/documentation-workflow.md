# 文档更新与方案确认流程

更新日期：2026-10-25 · 修订：r3 · 状态：执行规范

## 1. 编码前的顺序

**更新本次文档与测试流程 → 形成可审阅方案 → 用户明确确认 → 编码 → 按流程验证 → 用户验收。**

适用于应用功能、修复、重构、依赖与构建配置、测试代码和技术原型。公共基线及本次功能写细；后续功能保留范围、依赖和待决事项。

只读排查、运行已有检查，以及一次性的只读分析和文档链接核对命令可直接进行。文档整理本身可按用户授权直接推进；新增需要保存复用的诊断工具、测试脚本或原型代码时，先定义范围与测试方法，纳入本次方案。方案确认与产品验收是两次不同的判断。

## 2. 信息各自放在哪里

| 信息 | 唯一维护位置 | 其他文档怎样使用 |
| --- | --- | --- |
| 产品目标、用户决定和待决问题 | [产品总览](product.md) | 架构、规格和任务引用决定编号 |
| 职责、授权与交付 | [开发规范](../DEVELOPMENT.md) | AI 入口保留摘要与链接 |
| 更新顺序、前置条件和记录规则 | 本文件 | 其他规范引用，不复制完整流程 |
| UI、编码和测试的公共细则 | 对应 standards 文档 | 功能说明适用规则及专属差异 |
| 模块职责和依赖方向 | [架构](architecture.md)与[核心能力](core/README.md) | 技术方案描述如何实现这些边界 |
| 技术候选、采用理由与验证依据 | [技术方案](technical/README.md)及必要决策记录 | 不把候选写成核心既定实现 |
| 功能行为、接口、验收及测试步骤 | 单项功能规格 | 插件/核心总览索引链接，任务引用验收和用例编号 |
| 本次方案确认、进度、实测与验收 | 任务记录或轻量变更条目 | 产品、功能和插件索引仅链接来源 |

每个插件都有独立总览，逐项链接功能规格。单项功能的测试流程可与规格合并；长流程可以拆文件并双向链接。实现细节不逐行文档化，会影响行为、契约、资源和验证的决定必须可追溯。

## 3. 更新步骤

1. **读取与核实**：从产品总览进入当前任务，阅读本次相关规则，核对工作区。
2. **记录本次变化**：说明问题、原行为、目标、包含与排除、影响及未决事项；缺陷补复现方法。
3. **更新有效来源**：只修改受影响的规格、接口、测试与索引。公共规则变化先改来源，再处理受影响消费者。已有正确规则和测试可以引用，变更记录仍须先写。
4. **检查方案完整性**：本次目标和可观察结果明确；相关 UI、接口、数据、资源、取消与恢复足以实施；每项功能有准备、步骤、预期、异常及清理流程；依赖和限制已说明。
5. **提交具体方案**：给用户可读的结果摘要、范围、关键取舍、测试方式和文档链接，指出需要决定的事项。记录所提交的修订。
6. **记录用户确认**：以用户对具体方案的明确答复为依据，记录日期、范围、文档修订及原意。阻塞事项解决后，任务进入可开发。
7. **编码与验证**：按确认范围执行；出现变化按下一节处理。测试后填写实际结果和证据，完成必要检查才进入待验收。

文档是草案或技术仅为候选，不自动阻止用户批准范围明确的实验；实验应写清问题、候选、变量、测量方法、通过/失败/停止条件和清理方法。批准实验不等于批准将实验代码作为正式功能发布。

## 4. 确认的范围与开发中变更

一次确认覆盖本次任务的目标、范围、设计约束和验收方法。AI 自主完成该范围内的实现细节、测试和缺陷修复，不为每次代码修改再请求确认。

| 情况 | 先更新什么 | 是否重新确认 |
| --- | --- | --- |
| 新任务或首次实验 | 本次规格、测试、影响与任务 | 是，先提供具体方案 |
| 已确认方案内的内部实现、补充异常测试或修复 | 技术或变更记录、受影响测试；正确需求保留 | 无需重复，记录仍在原范围内的依据 |
| 改变功能范围、既定交互、平台、兼容、权限边界、成本或验收目标 | 有效来源、消费者、测试和任务 | 受影响部分需要先确认 |
| 修正错误测试或过期检查 | 正确需求的依据及回归流程 | 不改变已确认目标时自主修正；改变目标则重新确认 |
| 技术实验发现候选不可行 | 实验结果、替代方案及影响 | 已确认实验允许比较的范围内继续；超出范围先确认 |

变更先落文档再编码。无影响的规格不为满足形式要求重复改写。未获得必要确认时，继续只读排查或无依赖的文档工作，不把沉默、推荐选项、测试通过或文档优化授权当作编码批准。

## 5. 文档状态与任务状态

功能规格只维护文档就绪程度：**草案 → 可评审 → 已替代**。可评审表示本次内容足以判断，不代表获得编码授权。后续修订从草案开始，并保留历史修订引用。

任务维护本次工作状态：

`规划中 → 待方案确认 → 可开发 → 开发中 → 待验收 → 已验收`

- 待方案确认：文档已可评审，等待用户对具体方案作出明确答复。
- 可开发：所需文档、测试与依赖已具备，且用户确认覆盖本次修订。
- 开发中：实施或必需验证未完成；外部条件不足时附具体阻塞。
- 待验收：本次必需工程检查完成，实际入口和证据已交付。
- 已验收：用户明确认可对应规格和实现版本。发布另外记录。

文档类任务不包含应用编码，可在用户授权后直接从规划中进入文档工作，完成检查后待验收。技术决定在技术文档记录候选、验证中、已采用或已放弃；验证通过不自动等于已采用。

产品和模块索引不重复填写任务状态。修改已验收功能时新建本次任务或变更条目，历史验收只适用于原修订；不会因新变更而改写旧版本事实。

## 6. 轻量变更与可追溯性

单点文案、样式或已有规则内的小修复，可在所属功能规格中增加轻量条目，作为本次任务记录，无需另建完整文件。条目至少记录：

- 唯一标识、日期、目标和影响范围。
- 所依据的规格修订和测试用例，新增或变化的检查步骤。
- 本次用户方案确认，或其属于已确认任务内修复的依据。
- 执行后的实现版本、验证结果、限制和验收反馈。

新功能和跨模块工作使用[任务模板](templates/task.md)。技术实验可在任务中合并规格及自己的测试流程，避免同一问题复制多份文档。

修改有效规则时更新修订号；任务引用确切修订，已有 Git 提交时可同时引用提交号，未提交时用文档修订和可辨认的工作区/构建说明基线。同日多次变化仍能区分基线。文档先于编码指先保存有效文档，不要求先创建 Git 提交；文档修改、方案确认或任务完成都不自动触发提交或新建分支。Git 操作统一遵守[开发规范](../DEVELOPMENT.md)第 5 节的明确授权规则。

交付阶段只补充实际结果与证据，不能事后追补本应提前确定的规则，也不能调整预期掩盖失败。接续时以任务记录和实际工作区核对当前基线；已记录的确认无需因换对话再次取得。
