# SoDeck v2 产品与当前工作

更新日期：2026-10-27 · 修订：r69

## 1. 重做的目标

用户明确指出 v1 的主要问题：**模块耦合过高、模块通信混乱、缺少插件概念。**

v2 优先建立清楚的核心与插件边界：公共能力由核心管理，各业务通过公开且有版本的接口调用，插件具有独立的界面、业务逻辑和发布版本。具体结构见[总体架构](architecture.md)。

## 3. 对意图的推断

通信带宽理解（2026-10-27）：从全局到目标服务器再到终端/文件/隧道资源，观察双向速率、累计量、来源、趋势及连接事件；统一客户端视角与计量边界，多级路径不重复相加，实际使用速率与测速分开。用户已认可这一整体方向。T-019 r2据此提交实时计量、跨启动历史、诊断提醒与主动测速四项功能规格及统一界面；核心公共服务/外壳、插件业务的边界保持。具体默认值及T-016衔接为本次推荐方案，尚未逐项确认或实施。

本轮推断（2026-10-27）：用户希望主要空间留给终端，服务器工具从侧栏按需展开，常见创建少填字段，列表优先显示可操作信息，几何/滚动/启动符合桌面习惯。[T-015](tasks/T-015-workflow-polish.md)细化为可评审方案；分组单层、挂载行容量条、关闭按钮保留危险色等为推荐细节，不伪装成用户逐项已确认。

P-45（2026-10-26，用户最新明确范围）：本次以插件方式提供两个功能：①点对点端口转发，允许跨多机器；②把目标机器可达的局域网通过本地某个端口供 HTTP/SOCKS 代理使用。继承 P-44 的 Windows/Linux SSH、v1 只参考功能、v2 界面重新设计。替代 T-014 r1～r3“本次只做内网代理、固定转发后置”的建议，不等于实施确认。

P-45 的需求整理：推荐一个“网络隧道”插件内提供“端口转发”和“内网代理”，分别维护配置类型、行为与测试。端口转发按固定目标转发 TCP；内网代理按客户端 HTTP/SOCKS5 请求动态选择远端目标。用户随后明确选择“经过多台 SSH 主机中转，入口在本机”，固定访问方向为“本机入口 → 多个 SSH 中转 → 最终 SSH 访问节点 → 服务”；本次不包含远端机器监听入口。两种功能复用当前 T-013 已实现的核心多级路径。具体需求和测试见 [T-014 r6](tasks/T-014-network-proxy.md)、[端口转发](plugins/proxy/features/port-forward.md)、[内网代理](plugins/proxy/features/network-proxy.md)。该答复解决需求边界，不等于完整技术方案或编码批准。

P-45 的场景复核（2026-10-26）：用户再次明确本机 `10.100.77.166`，最终 SSH 主机 `192.168.1.16`，浏览器配置 `127.0.0.1:10808` 后访问远端网络的 `192.168.1.18`；认可本机接收代理请求、远端 SSH 建立目标连接的解释，并要求再次确认功能设计。T-014 r6 推荐无需部署额外远端 HTTP/SOCKS 程序，补齐界面、恢复及该场景的隔离验收；协议载体/公开接口仍需完整代码方案。此次功能复核不记录为编码批准，也不使用这些示例地址探测用户网络。

v1 两种模式复核（2026-10-26）：用户要求仔细区分 v1 的两种代理方式。核对相邻 v1 源码及本仓库 `origin/master` 的 `436cad2`，实际模式为“固定端口转发”（`PortForward`，目标预先写入规则）和“内网代理”（`NetworkProxy`，HTTP/SOCKS5 请求逐次指定目标）。两者共用 SSH 转发底层，后者包含本机代理协议处理；当前源码未包含由 curl 自动部署远端代理程序的这条实现。P-44 的浏览器用法对应“内网代理”，不能用固定端口映射替代；证据和区别写入 [T-014 r3](tasks/T-014-network-proxy.md)。这次核实没有扩大为两种模式全部迁入 v2 的编码授权。

P-44（2026-10-26，用户明确需求）：新增代理插件，远端是通过 SSH 连接的 Windows 或 Linux 主机；只参考 v1 功能，界面按 v2 重新设计。用户以“浏览器配置 `127.0.0.1:10808` 代理，再访问 `10.10.1.223`”澄清：应访问到所选 SSH 主机所在局域网的 `10.10.1.223`。访问目标由浏览器地址决定，不能把代理固定为一个服务，也不能误走本机同地址内网。`10808` 是示例端口，本稿建议作为可修改的默认值；此建议不等于用户固定端口要求。
