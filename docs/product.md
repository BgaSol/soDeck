# SoDeck v2 产品与当前工作

更新日期：2026-10-25 · 修订：r11

## 1. 重做的目标

用户明确指出 v1 的主要问题：**模块耦合过高、模块通信混乱、缺少插件概念。**

v2 优先建立清楚的核心与插件边界：公共能力由核心管理，各业务通过公开且有版本的接口调用，插件具有独立的界面、业务逻辑和发布版本。具体结构见[总体架构](architecture.md)。

## 2. 已确定的决定

以下来自用户在 2026-10-24 至 2026-10-25 的明确指令及回答。后续改变时先更新本文件及受影响规格。

| 编号 | 决定 | 对开发的约束 |
| --- | --- | --- |
| P-01 | 核心提供服务器、连接、隧道和端口等公共能力；终端、Docker、NetBird 等作为业务插件 | 业务变化优先由所属插件交付；核心提供可复用原语 |
| P-02 | 插件可独立更新，重启 App 后生效 | 界面和业务逻辑都随插件更新；当前运行不替换版本 |
| P-03 | 先完善本次方案文档，由用户确认后再编码 | 文档完整和方案确认均是编码前置条件；文档维护授权不代表应用编码授权 |
| P-04 | 公共基线和本次功能写细；后续功能保留范围及待决项 | 按近期任务逐步细化，不要求提前写完全部插件功能 |
| P-05 | 优先验证插件架构与独立更新；首条交付按 P-19 使用真实终端 | 将边界、通信、生命周期和版本切换的验证纳入终端交付，不再单独交付样例平台 |
| P-06 | 首阶段在 Windows 验证，结构保留跨平台能力 | 平台能力通过边界封装；Windows 结果不代表 macOS/Linux 已支持，正式首发平台仍待确定 |
| P-07 | 首期只做我们维护的官方插件，保留以后扩展的接口 | 首期不依赖第三方市场或任意原生扩展；保留身份、调用记录、兼容与失败恢复设计，插件调用策略按 P-14 |
| P-08 | 每个插件有独立详细文档，每个功能有自己的测试流程 | 本次规格和测试流程先完成，再经方案确认进入编码 |
| P-09 | UI 设计必须使用 `apple-design` 技能 | 技能使用及验证细则由 [UI 规范](standards/ui.md)维护 |
| P-10 | v2 在原远程仓库中新建 `v2` 分支，建立全新的文档基线提交 | 分支及提交约定见[开发规范](../DEVELOPMENT.md)；应用编码仍需具体方案确认 |
| P-11 | 用户明确退出 SoDeck 时，全部结束 App 持有的连接和隧道；需要后台工作时保持 App 运行 | 首阶段不引入退出后维持资源的独立后台服务；明确保留的运行资源也随 App 退出结束，持久配置可保留 |
| P-12 | 关闭终端或插件面板时，默认结束它创建的会话；需要时由用户明确选择保留 | 关闭仅释放所属会话及使用权，不误关其他消费者的共享连接；保留需有支持的托管、查看及停止能力 |
| P-13 | 第一阶段插件各自调用核心公共能力，暂不开放插件互调 | 不实现插件服务发现、插件间调用或跨插件句柄转交；未来可选服务单独设计和确认 |
| P-14 | 不限制插件调用核心的权限，每次调用必须保留记录 | 全部已启用插件平等调用核心公开且已支持的能力；不做插件权限清单、能力/服务器授权、授权弹窗或权限扩大审批。核心统一记录调用，身份、参数、生命周期和资源有效性检查用于运行正确性 |
| P-15 | 工作台参考 IDEA：侧边工具按钮与可展开面板、中央 Tab、独立窗口；插件声明每个视图支持的展示方式和默认位置，用户在支持范围内移动 | 核心统一承载、移动及保存布局；不要求每个视图支持全部形式，一个插件可贡献多个不同视图 |
| P-16 | 每台服务器有自己的工作区，切换工作区时切换所属工具与页面 | 服务器视图具有明确归属，不能把旧页面原地改成新服务器上下文；布局与会话分开管理 |
| P-17 | 中央区域需要分屏，先支持左右或上下两个区域 | 每个区域可有自己的 Tab；首期不建设任意嵌套分屏 |
| P-18 | 点击主窗口右上角“×”收起到系统托盘，App 和独立窗口继续运行 | 收起不触发 P-11 的退出清理；提供恢复主窗口和明确退出的入口，退出仍结束所有窗口及 App 持有资源 |
| P-19 | 首批直接做核心与实际终端插件，不做测试插件作为前置交付 | 真实 SSH/PTY 纳入第一条可运行流程；用终端自身的独立包验证更新。自动化夹具与故障注入仍用于测试，不建设独立样例插件产品 |
| P-20 | 不显示独占一行的顶部窗口标题栏 | 窗口控制、拖动及平台行为仍需在功能方案中明确；本轮只要求功能设计，不授权编码 |
| P-21 | 服务器列表改为顶部 Tab，并可在新窗口打开、合并回主窗口 | 本轮按“一台服务器一个完整工作区 Tab”提出设计；拆合粒度、关闭规则及多窗口细节见 F-CORE-006，推断不自动成为已确认细节 |

## 3. 对意图的推断

以下是根据上述决定形成的工程理解，用于提出方案，不作为新增产品承诺：

- 一项业务变更应能定位到所属插件，避免修改多个不相关模块才能完成。
- 连接和资源有明确所有者，跨模块调用有明确入口，减少隐式共享状态和任意事件通信。
- 用户关注本次目标、交互、范围和验收；AI 在已确认方案内自主处理技术细节、测试和修复。
- 第一批应交付可用的终端，同时证明插件边界和独立更新；工程验证围绕真实交付开展，避免反复搭建最终不用的样例。
- 工作台应由核心统一提供，插件集中交付业务内容；改变视图位置时保持同一工作上下文，减少重复开页、重建连接及各插件自造窗口体系。
- 独立窗口便于并排或多显示器工作。具体窗口与工作区切换、布局记忆及焦点行为按[工作台设计](core/workbench.md)评审，不把这些推断全部当作已确认细节。
- 本轮将 P-20、P-21 理解为浏览器式的服务器工作区页签：页签与窗口控制共用顶部一行，整份工作区可拆合，内部仍保留插件页面 Tab。只显示已打开工作区、子窗口也支持多个服务器、一个工作区只有一个承载位置等是推荐细节，集中在[功能设计](core/server-tabs.md)，尚待用户评审。
- 用户继续询问终端窗口与插件实例的关系、Tab 改造对插件的影响及核心还需哪些能力。推测其在检验 v2 的插件边界：工作台承载方式变化应由公共契约吸收，插件管理自己的业务和状态，后续工具可复用同一套窗口能力；实例数量、资源开销和故障范围需要明确。当前事实与建议增量见 F-CORE-006 第 6 节；这是对问题的理解，未新增已确认决定，也未授权实施。

推断涉及新的功能、交互、兼容、成本或发布承诺时，必须在本次方案中明确提出并由用户确认。
