# SoDeck v2 产品与当前工作

更新日期：2026-10-24 · 修订：r3

## 1. 重做的目标

用户明确指出 v1 的主要问题：**模块耦合过高、模块通信混乱、缺少插件概念。**

v2 优先建立清楚的核心与插件边界：公共能力由核心管理，各业务通过公开且有版本的接口调用，插件具有独立的界面、业务逻辑和发布版本。具体结构见[总体架构](architecture.md)。

## 2. 已确定的决定

以下来自用户在 2026-10-24 的明确指令及本轮回答。后续改变时先更新本文件及受影响规格。

| 编号 | 决定 | 对开发的约束 |
| --- | --- | --- |
| P-01 | 核心提供服务器、连接、隧道和端口等公共能力；终端、Docker、NetBird 等作为业务插件 | 业务变化优先由所属插件交付；核心提供可复用原语 |
| P-02 | 插件可独立更新，重启 App 后生效 | 界面和业务逻辑都随插件更新；当前运行不替换版本 |
| P-03 | 先完善本次方案文档，由用户确认后再编码 | 文档完整和方案确认均是编码前置条件；文档维护授权不代表应用编码授权 |
| P-04 | 公共基线和本次功能写细；后续功能保留范围及待决项 | 按近期任务逐步细化，不要求提前写完全部插件功能 |
| P-05 | 第一个阶段先验证插件架构与独立更新，再做业务功能 | 用最小实验检验模块边界、通信和版本切换，再形成真实业务流程 |
| P-06 | 首阶段在 Windows 验证，结构保留跨平台能力 | 平台能力通过边界封装；Windows 结果不代表 macOS/Linux 已支持，正式首发平台仍待确定 |
| P-07 | 首期只做我们维护的官方插件，保留以后扩展的接口 | 首期不依赖第三方市场或任意原生扩展；保留必要的身份、权限、兼容与失败恢复设计 |
| P-08 | 每个插件有独立详细文档，每个功能有自己的测试流程 | 本次规格和测试流程先完成，再经方案确认进入编码 |
| P-09 | UI 设计必须使用 `apple-design` 技能 | 技能使用及验证细则由 [UI 规范](standards/ui.md)维护 |
| P-10 | v2 在原远程仓库中新建 `v2` 分支，建立全新的文档基线提交 | 分支及提交约定见[开发规范](../DEVELOPMENT.md)；应用编码仍需具体方案确认 |

## 3. 对意图的推断

以下是根据上述决定形成的工程理解，用于提出方案，不作为新增产品承诺：

- 一项业务变更应能定位到所属插件，避免修改多个不相关模块才能完成。
- 连接和资源有明确所有者，跨模块调用有明确入口，减少隐式共享状态和任意事件通信。
- 用户关注本次目标、交互、范围和验收；AI 在已确认方案内自主处理技术细节、测试和修复。
- 第一轮实验应证明插件边界和独立更新可行，运行容器和技术栈按实测选择。

推断涉及新的功能、交互、兼容、成本或发布承诺时，必须在本次方案中明确提出并由用户确认。

## 5. 后续决定及细化时机

| 事项 | 当前情况 | 何时需要确定 |
| --- | --- | --- |
| 首个具体实验 | 方向已定；实际比较候选、资源指标、步骤及退出条件待写方案 | 实验编码前 |
| 技术栈与插件容器 | Tauri、Rust、React、受限 JS、独立 WebView 等仍是候选 | 对应实验或选型后记录证据；正式采用前同步规格 |
| 第一条业务流程 | 当前建议服务器配置、认证、终端输入输出；尚未确认首期范围 | 架构实验结论后、业务编码前 |
| 默认附带插件 | 尚未确定终端、Docker、NetBird 的默认安装组合 | 插件安装及首发范围设计时 |
| 隧道与端口范围 | 当前建议优先本地转发；远程转发、动态代理待定 | 对应功能规格编写时 |
| 工作区与 UI | 已确定使用 `apple-design`；具体视觉参数、布局和交互待定 | 对应界面方案确认前；实验临时界面单独标明 |
| 退出后的后台资源 | 当前建议随 App 退出；独立守护进程未列入已确定范围 | 资源生命周期方案确认前 |
| 安装、启用、停用、卸载 | 是否统一重启后生效仍待定；更新重启已确定 | 插件管理功能方案确认前 |
| 卸载数据处理 | 默认保留或删除插件私有数据待定 | 卸载功能方案确认前 |
| v1 数据与共存 | 是否导入、迁移范围和兼容方式待定；开发隔离 v1 数据 | 数据导入或首发方案确认前 |
| 正式首发平台与发布 | 验证平台仅先定 Windows；渠道、签名和应用标识待定 | 平台或发布相关任务前 |

v1 各能力的保留、重设计、延期或移除在对应范围讨论时登记。未登记的功能不默认进入首发，也不默认删除。
