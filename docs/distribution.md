# SoDeck 安装、升级与插件分发

## 原则

核心独立安装和升级，业务插件全部外置。使用标准工具完成打包，不自建发布框架，不让插件检查阻塞核心发行。

`npm run build -- --bundles <格式> -- --locked` 生成本机核心发行包，`.github/workflows/build.yml` 负责五目标核心打包与原生测试；`npm run plugin:build` 独立生成 Hello 归档，`.github/workflows/plugin.yml` 只构建插件。`.github/workflows/check.yml` 检查类型、格式和前端构建。实际运行结果另行记录，不把工作流存在视为构建通过。

## 核心安装与升级

| 目标 | Rust target | 第一版发行形式 |
| --- | --- | --- |
| Windows x86_64 | `x86_64-pc-windows-msvc` | `.exe` 安装程序 |
| Windows ARM64 | `aarch64-pc-windows-msvc` | `.exe` 安装程序 |
| Linux x86_64 | `x86_64-unknown-linux-gnu` | `.deb`，可补充 AppImage |
| Linux ARM64 | `aarch64-unknown-linux-gnu` | `.deb`，可补充 AppImage |
| macOS ARM64 | `aarch64-apple-darwin` | `.dmg`，包含 `.app` |

- 安装包只带核心程序、核心界面和自身运行资源，不包含任何业务插件；需要独立宿主程序时，它属于核心运行资源。
- 升级使用标准方式：退出核心，在 Windows 运行新版安装器、Linux 安装新版包、macOS 替换应用。AppImage 则替换应用文件。
- 配置、日志、消息和插件放在安装目录以外，覆盖升级后保留；首次启动没有插件也能进入工作台。
- 第一版不做自动更新服务、TUF 信任链、候选激活、内部发布批次和跨平台原子发布。
- Linux 起步以 Ubuntu 22.04/24.04 LTS 为运行基线；所需系统库和 Windows WebView2 由打包配置及简短安装说明表达。系统签名按平台正常分发需求配置，不另建插件签名体系。

## 插件加载与卸载

1. 下载插件并解压到外部目录，或在界面选择已有插件目录。
2. 打开右上角“设置 → 插件管理 → 加载插件目录”，选择含 `plugin.json` 的目录，核心启动插件。当前 Hello 无业务视图。
3. 点击卸载，核心停止插件、移除其界面并释放它的连接、端口等资源；文件和数据保留。
4. 更新插件时先卸载，替换目录内文件，再加载。删除插件文件可在卸载后手工完成。

插件目录只需清单、入口文件、运行依赖和可选 UI 资源，普通 ZIP 用于下载即可。核心 API 仅做清单格式、入口存在、API 主版本及适用系统架构的基本检查。插件按可信扩展使用，不做权限申请、签名信任链或完整历史版本矩阵。

核心与插件各自维护版本；更新一个插件不触发核心重打包，核心更新也不强制重打所有插件。

## GitHub 流程

- 普通提交：运行与改动相关的检查，不每次全平台打安装包。
- 手动打包：在 Actions 运行 `Package SoDeck`，从各目标的 Artifact 下载，不需要标签或发布配置。
- 发布核心：修改 `src-tauri/tauri.conf.json` 的应用版本，推送普通版本标签（如 `v0.1.0`），同一工作流构建五个目标并把产物上传到同一个 GitHub Release 草稿。
- 各目标独立构建和上传。一个目标失败明确显示为失败，其他成功产物仍可下载；不加全目标联动发布门禁，也不把失败目标说成已经支持。
- 插件需要发布时运行 `Package Hello plugin`，默认只生成 Artifact；填写已有 Release 标签则附加五个独立插件归档，不要求专用插件标签或单独发布状态机。插件版本只修改 `plugins/hello/Cargo.toml`。
- 需要检查实际包的组合时，单独运行 `Verify packaged core and plugin`，填入两次构建的 run ID。该流程不参与核心或插件打包，分别使用五个原生 Runner 下载、安装/解包核心与插件，检查加载、日志、消息、卸载、重载和重启保留。
- 本地和 CI 使用相同构建入口、锁文件和固定工具链。正常路径只需改版本、推标签、下载产物，不让用户手工改多份版本和计算内部批次。

## 必要验证

只关注改动相关的实际结果：核心能安装启动、覆盖升级保留数据、外置插件能加载卸载、卸载后资源释放。业务变化补对应关键检查；纯文档不构建应用。通过的检查不重复跑，不为每个包生成大量证明材料。

五目标分别记录构建和实际运行状态。开发者没有对应设备时如实记录验证范围，不把人工穷举测试变成每次打包的前提。

自动检查：Windows 静默安装 `.exe`、Linux 解包 `.deb`、macOS 挂载 `.dmg`，再在原生 Runner 中运行包内程序。检查二进制架构；`--smoke-test` 使用隔离数据目录，等待前端读取核心并完成工作台渲染后退出并写入完成报告，30 秒未完成或异常退出即失败。组合检查额外传入插件目录，重启验证真实数据保留。Linux 使用虚拟显示器。Windows 组合流程还验证同版本覆盖安装保留数据；Linux/macOS 组合流程验证包内程序与重启，尚不代表已完成系统安装升级。
