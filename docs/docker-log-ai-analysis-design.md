# Docker 日志 AI 分析功能设计

日期：2026-10-20  
状态：设计建议，尚未实现

## 1. 需求理解与产品目标

用户的直接需求是在已有 Docker 日志查看能力上增加 AI 分析。推测主要任务是：容器异常时，快速理解问题、找到原始证据、判断排查顺序，并围绕同一批日志继续追问，减少复制粘贴和反复补充上下文。

优先服务三个场景：

- 服务启动失败、反复重启或接口报错，想知道可能原因及下一步检查。
- 日志很多，想从重复输出中找出异常类型、发生过程及关键变化。
- 对某段堆栈或日志含义不熟悉，选中后让 AI 解释，并追问如何验证。

首版定位为“有原始证据的日志排障助手”。以手动分析为主；持续告警、自动修复、跨容器关联放在后续阶段。这里的优先级是基于现有产品形态的推测，尚不是用户确认的需求。

成功标准：用户可以从一份报告直接回到日志证据，并知道下一步先检查什么；证据不足时，能明确知道缺少什么。

## 2. 当前基础与需要补齐的能力

已核对的代码基础：

| 现有能力 | 对应位置 | 可复用方式 |
| --- | --- | --- |
| 独立日志窗口、范围选择、搜索和上下文查看 | `src/ContainerLogsApp.tsx` | 增加分析入口与侧栏 |
| 日志来源、序号、时间、输出流、分页及快照查询参数 | `src/logApi.ts` | 构建可追溯的分析输入 |
| 本地持久化、归档读取和范围导出 | `src-tauri/src/logs.rs`、`src-tauri/src/log_store.rs` | 后端读取完整分析范围，不依赖前端缓存 |
| 容器状态、健康状态、退出码、OOM、重启次数和状态时间 | `src/dockerApi.ts` | 经身份校验后补充诊断信息 |
| 配置默认遮盖敏感值 | `src/docker/ContainerDiagnostics.tsx` | 延续最少传输的原则，但不能直接把完整诊断文本发送给模型 |
| 系统设置入口 | `src/SystemSettingsDialog.tsx` | 增加 AI 配置分组 |

目前在检查的前后端源码中没有发现模型接入、AI 会话或密钥配置能力，需要新增。

日志前端缓存有条数和字节上限，因此“分析当前筛选”必须由后端按查询条件读取本地归档，不能只发送屏幕上已加载的数据。现有日志 API 中没有容器管理的连接令牌，补充实时状态需要增加来源与有效连接的绑定校验，不能凭容器名称猜测目标。

## 3. 核心使用流程

1. 在日志窗口点击“AI 分析”，在同一窗口右侧打开分析面板。
2. 面板展示分析范围、模型与接收端、是否包含容器状态，以及可选的问题输入框。
3. 点击“开始分析”，固定本次日志快照，后端读取范围、整理上下文、脱敏后发起请求。
4. 面板先展示处理阶段，随后逐步显示报告；日志采集继续运行。
5. 点击报告中的日志引用，在左侧定位并高亮对应日志，支持回到原筛选状态。
6. 用户继续追问，沿用这次快照。需要新日志时，显式点击“加入最新日志”，创建新的分析版本。

首次未配置模型时，在侧栏提供设置入口，保存后保留原来的分析范围。查看分析预览不等于发送日志；“开始分析”是发送动作，不另加重复确认弹窗。

## 4. 分析范围

| 范围 | 行为与用途 |
| --- | --- |
| 已选序号范围 | 已有有效选区时默认选用，适合解释堆栈或某次失败 |
| 当前筛选结果 | 无选区但有搜索或筛选时默认选用；覆盖快照内全部匹配记录，不是当前页 |
| 最近一段日志 | 无选区、无筛选时默认选用；建议以最新有效日志时间为终点回看 15 分钟 |
| 自定义时间范围 | 用户指定故障时间，界面明确时区 |

上述默认值是初始建议，后续可依据真实日志规模调整。离线存档使用日志自身的最新时间，界面展示实际起止时间，避免把历史日志称为“当前最近 15 分钟”。没有可靠时间戳时，明确改用最近 2000 条记录。

选区和筛选结果允许补充相邻上下文，初始建议每个命中片段前后各 20 条并合并重叠区间。对明显多行异常继续补全，直到事件边界或输入预算上限；所有补充记录在预览中计数，可关闭。上下文可以包含筛选条件以外的日志，界面须说明。

预览展示：目标服务器与容器、实际范围、匹配记录数、补充上下文数、实际发送记录数、是否抽样或截断、模型接收端。元数据区分本地目标显示信息和真正发送给模型的字段。

不把“全历史分析”作为默认操作。需要扩大范围时通过时间范围完成，按相同预算与覆盖率规则处理。

## 5. 输出内容与证据要求

报告按以下顺序组织：

1. **结论摘要**：一句话说明最主要的异常或观察结果；可显示“发现异常线索”“未发现明确异常线索”“信息不足”。
2. **主要发现**：合并相同类型错误，显示该范围内的出现次数与首末发生时间。只有完整扫描所得的统计才能描述为全范围计数，抽样统计必须标注。
3. **证据**：每项发现附带可点击的日志序号与时间，展示少量关键原文。
4. **可能原因**：区分直接事实与推测，按证据强弱排序，并列出需要验证的条件。
5. **排查建议**：优先给出具体、可验证的步骤；有必要时展示可复制命令及其目标和用途。
6. **分析限制**：说明未覆盖的范围、数据缺失、状态读取失败或抽样限制。

示例（仅用于说明交互，非真实诊断）：

> 发现应用连接数据库失败，连接被拒绝，可能影响启动。
>
> 证据：#18420 显示连接被拒绝；#18435 显示本次启动失败。
>
> 推测：目标地址或端口错误、目标服务未监听，都可能导致该现象。当前日志不能确认是哪一种原因。
>
> 建议：先核对连接目标，再从应用所在网络验证该端口是否可达。

不输出未经校准的“93% 根因置信度”，也不把没有 ERROR 字样等同于服务正常。错误等级和 stderr 只作为线索，不直接决定问题严重性。

每个引用绑定 `sourceId + seq`，容器状态引用绑定独立的状态快照及采集时间。后端校验模型引用是否来自本次提供的证据；无效引用标记为不可验证，不生成可点击的伪证据。结构校验只能保证引用存在，不能保证推理正确。

## 6. 界面建议

保持现有独立日志窗口。工具栏增加“AI 分析”，序号范围区增加“分析所选”，后者打开侧栏并预填范围。

宽窗口使用左右分栏：左侧日志、右侧 AI。右侧建议默认约 420px，可拖动调整；窄窗口切换“日志 / AI 分析”页签并保留两边状态。引用跳转在窄窗口自动切回日志，并提供返回分析入口。

面板从上到下依次为：

- 目标与范围摘要，可展开调整范围和查看发送内容。
- “重点关注什么？”输入框，可留空；提供“解释报错”“分析启动失败”“总结异常”等快捷问题。
- 模型与接收端、开始/取消按钮。
- 当前报告，包括证据跳转和复制报告。
- 追问输入框，以及“加入最新日志”“历史分析”入口。

分析不停止采集。定位证据时只暂停自动滚动，复用现有行为；用户可随时“跳到最新”。

状态包括：未配置、待分析、准备上下文、请求中、生成中、完成、已取消、失败。取消尽力终止传输，但已发出的请求可能仍产生费用。失败保留范围和问题，让用户主动重试；不进行无提示的整次请求重发。

## 7. 日志整理与大日志处理

首版采用有明确预算的单次分析：

1. 固定来源、查询条件、序号上界和所选范围，防止实时新增日志改变本次对象。
2. 从本地分批读取，尽量恢复多行异常和长行片段；尚未完整写入的记录须标记，不能与已完成记录混淆。
3. 清理纯显示控制符，保留时间、级别、输出流、异常链与稳定证据编号。
4. 对重复事件进行分析层聚合，保留次数、时间范围及代表记录；不修改原始归档。
5. 按模型输入预算计算能容纳的数据，同时预留问题、输出及后续追问空间。
6. 超出预算时保留异常附近、范围开头/结尾、重启附近和分布采样；不能只留下 ERROR 而丢掉前因。
7. 展示覆盖说明，允许用户缩小范围重新分析。

初始可以设置每次最多约 20000 条候选记录并叠加字节上限，最终发送量仍受模型上下文预算约束。任何扫描、聚合、输入截断都要单独标记。存在截断时不得宣称已分析全部历史，也不能保证未选中的区域没有异常。

分块摘要再汇总会引入额外成本及遗漏风险，建议作为后续“大范围分析”模式，并保留摘要到原始证据的映射。

## 8. 容器上下文

首版可提供“附带当前容器状态”选项，仅在有可验证的有效连接时启用。采用字段白名单：镜像标识、运行状态、健康状态、退出码、OOM 标记、重启次数、启动/退出时间，以及该状态的读取时间。

默认不包含完整环境变量、配置原文、挂载宿主路径和连接凭据。健康检查输出或错误文本如需加入，须经过与日志相同的脱敏流程。

历史日志与当前状态分开展示。当前重启次数或当前退出状态不能直接证明历史时间段的情况。状态不可用时继续分析本地日志，并说明缺失；本地存档可在 SSH 离线时分析，但仍需能访问选定的模型服务。

## 9. AI 配置与数据处理

系统设置增加独立 AI 分组，配置连接名称、服务地址、模型、凭据、超时和输入预算，提供不发送真实日志的连接测试。首版实现一个明确约定的接口适配器，通过适配层保留扩展能力；具体协议与供应商在实施前确定，不承诺任意兼容地址都能直接工作。

调用链为：React 面板 → Tauri/Rust 后端 → 用户配置的模型服务。继续沿用桌面客户端直接连接的产品形态，无需新增 SoDeck 中央服务。

API 凭据只交给后端保存和使用，优先使用系统凭据存储；设置页面只展示配置状态，不回显已保存明文。不能因为已有 SSH 密码存储方式就自动复用明文存储方案。

发送前在本地识别并替换常见密码、Token、Authorization、连接串凭据等敏感内容。使用稳定占位符保留同一对象的关联，报告引用仍对应本地原始日志。脱敏无法覆盖所有业务敏感数据，因此提供实际发送内容预览，不宣称完全无泄漏。

日志中的文字一律作为分析数据，不能成为工具调用指令。首版模型没有终端执行工具；建议命令支持复制，不自动执行重启、删除、改配置或日志中出现的命令。

## 10. 追问与历史

每次分析保存分析 ID、来源身份、查询范围、快照上界、覆盖说明、状态快照、模型配置标识、问题、报告及证据映射。报告与追问历史保存在本地，提供删除入口，不重复复制全量原始日志；不把分析文本写入一般调试日志。

追问默认使用同一分析快照及已有上下文。上下文预算不足时提示缩小问题或开始新分析，避免悄悄丢掉关键证据。模型不能假装读取了没有提供的日志。

“加入最新日志”显式生成新版本，界面展示新增范围；最新数据仍遵循脱敏、预算和发送预览规则。关闭侧栏保留本次状态；首版关闭日志窗口时取消未完成请求，已完成报告下次可恢复。程序异常退出后，将遗留的进行中任务标记为中断。

来源使用日志 sourceId 并保留容器 ID 和引擎身份，不以可复用的容器名称关联报告。原始档案被外部删除时，保留报告但提示证据不可用。

## 11. 实现边界与分期

### 第一阶段：可用的手动排障闭环

- 模型配置和连接测试。
- 最近时间段、选中范围、筛选结果、自定义时间分析。
- 固定快照、上下文补齐、预算、脱敏及发送预览。
- 可选容器状态补充；失败降级为仅日志分析。
- 报告、证据跳转、同一快照追问、取消和重试。
- 本地历史、复制报告和显式加入最新日志。

第一阶段可以先完成“配置 → 选区分析 → 引用定位”这条纵向链路用于内部验证，再补齐其余范围与历史功能后交付。

### 第二阶段：提高复杂排障效率

- 大范围分块分析与证据合并。
- 修复前后两个时间段的对比。
- Compose 多容器时间线，注明时钟误差与来源差异。
- 用户选择的额外状态或只读检查结果，作为新的证据加入分析。

### 第三阶段：持续检测

在用户开启、设置检查周期和费用上限后，对新增日志先做本地规则检测，再按需触发模型；按异常类型去重，仅在新异常、显著恶化或恢复时提示。此阶段需要独立考虑后台生命周期、限流和通知，不纳入首版。

自动修复需要单独设计操作授权、目标校验和回执，不作为日志分析的附带能力。

## 12. 建议模块与验收

前端建议增加分析面板、AI 设置和类型化 API；后端按 AI 配置/客户端、日志上下文准备、分析任务和历史存储拆分。原有日志采集和归档仍由现有模块负责，AI 只读取快照。

分析结果采用结构化字段：摘要、发现、证据引用、可能原因、建议、限制；流式展示与最终结构校验分开。存储和网络工作应在后台运行，准备输入和模型请求均能取消。

验收重点：

- 选区、筛选、时间范围均正确；超过前端缓存的数据仍纳入后端范围处理。
- 堆栈、分片长行、重复日志、缺失时间戳和未完成记录有明确处理。
- 请求期间新增日志不改变原快照；加入新日志后显示新版本与范围。
- 引用能够跳转原始记录，无效引用不会被伪装成有效证据。
- 超预算明确展示实际覆盖；未发现异常不被表达为“系统正常”。
- SSH 断线、容器删除和状态查询失败不妨碍对已有存档的分析。
- 历史日志不会被当前容器状态错误归因。
- 密钥不回显，日志脱敏发生在发送前，日志内指令不能触发执行。
- 模型鉴权失败、超时、取消、格式异常和应用重启均有可恢复状态。
- 宽窄窗口、证据跳转后返回、流式结果与实时日志并存时操作可用。

质量验证使用一组已知原因的固定日志样本，例如连接失败、启动配置错误、内存终止线索、正常启动、仅有警告和证据不足。重点评估引用准确性、事实/推测区分和排查步骤的可验证性，不把模型文字与某份标准答案逐字比对。
