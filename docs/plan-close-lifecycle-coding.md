# 核心与组件关闭生命周期代码整改方案

日期：2026-11-08。源码基线：`752410e`，核心配置版本 0.11.0。状态：实现已进入整改分支，验收进行中，结果与未完成项见[实施记录](implementation-close-lifecycle.md)。本文定义代码落点和迁移方式；目标行为、范围及失败语义见[功能设计](plan-close-lifecycle.md)，设计方法见[功能设计要求](plan-feature-design.md)。

## 1. 整改结论与交付边界

现有分进程插件、统一 RPC、资源 Owner/Context、进程监督、连接取消和测试夹具可以继续使用。整改集中于核心关闭状态、资源结束确认、后台初始化以及宿主入口。组件业务算法不随本次整体重写。

交付一个完整问题：**所有关闭入口在同一套生命周期约束下完成输入确认、保存、资源释放和最终动作，刷新与迟到工作不会重新创建目标。** 页面、工作区、子窗口、应用退出、普通重启和更新重启均在本次范围内。

| 范围 | 处理方式 |
| --- | --- |
| 核心关闭协调、创建接入、在途工作、结束确认 | 必改；是修复成立的前提 |
| 宿主跨窗口 flush、服务器表单、组件设置草稿、统一关闭反馈 | 必改；数据确认不能只覆盖当前可见插件页面 |
| 四个插件的生命周期实现 | 必验；只有契约测试暴露缺口时才改相应插件代码并独立发版 |
| RPC 传输、SSH/SFTP、SOCKS 协商、更新包签名、安装器 | 沿用；修改生命周期接入或结果观察，不重做协议和发行框架 |
| 数据格式、凭据保存、会话恢复、插件权限、业务新功能 | 本次不扩展；没有必要的数据迁移或新增生产依赖 |

完成整改前不把中间状态作为修复版本交付，也不通过关闭检查豁免、插件 ID 特例、删除刷新或增加重试次数掩盖问题。

| [catalog 夹具](../src-tauri/tests/fixtures/catalog.rs) | 工作区关闭等路径直接改 `Workspaces`，退出忽略部分结果 | 关闭测试走生产协调器；夹具收尾失败必须可见 |

## 3. 目标代码结构

### 3.1 新增范围

拟新增以下文件；目前不存在，名称是实现约定而非已导出的 API：

| 文件 | 单一职责 |
| --- | --- |
| `src-tauri/src/lifecycle.rs` | 关闭目标、操作阶段、范围保留、接入判断、在途调用/创建的登记、快照及状态转换；由 `AppCore` 持有 |
| `src-tauri/src/lifecycle/close.rs` | 关闭流程执行：准备、决策、保存等待、清理、失败重试、全局接管和收尾交接；按现有资源服务显式调用 |
| `src/close.ts` | 宿主关闭桥：请求关闭、路由跨窗口同步、汇总宿主草稿、显示操作状态和提交决定 |

核心在 [lib.rs](../src-tauri/src/lib.rs) 注册生命周期模块，`AppCore` 初始化它。`component_ui` 保留 UI 定义、布局、surface 和插件 view 数据；不再拥有应用关闭事务。新模块按终端、文件、网络、执行、连接和进程服务显式协调，不建设通用服务注册框架。

### 3.2 既有代码如何归并

| 现有内容 | 最终落点 |
| --- | --- |
| `ClosePlan`、`plans`、全局/范围关闭状态 | `lifecycle.rs` |
| `ui_close_prepare/finish/poll` 的流程控制 | `lifecycle/close.rs` |
| `ui.beforeClose/save/disposeView` 调用与 metadata 更新 | `component_ui/host.rs` 保留基本能力，生命周期执行器负责调用时机 |
| `require_closed()` | 可保留为内部一致性断言；不再作为用户先自行清空组件才能退出的流程前提 |
| `Components.close()/allowExit()` 的对话框与流程 | `src/close.ts`；组件宿主只保留目标 surface 的同步和展示功能 |
| `AppCore.shutdown()` | 拆为受操作保护的资源停止，以及已有基础服务收尾；生产调用不再绕过协调器 |
| 原生 close/restart 命令及窗口事件 | 适配到同一操作；Tauri 窗口/进程动作继续留在 `main.rs` / `windows.rs` |

## 4. 数据与接口设计

### 4.1 核心类型

下面是数据形状示意；实现使用 Rust 枚举及现有身份类型，避免大量可同时为真的布尔字段。

```rust
enum CloseTarget {
    Views { view_ids: Vec<String> },
    Workspace { workspace_id: String },
    Window { window_id: String },
    Application { action: AppFinalAction },
}
enum AppFinalAction { Exit, Restart, InstallAndRestart }
enum ClosePhase {
    Preparing, Deciding, Cleaning, Finalizing,
    Failed, Completed, Aborted,
}
enum CloseDecision { Save, Discard, Cancel }
```

每个 `CloseOperation` 至少包含：

| 字段 | 用途 |
| --- | --- |
| `id`、`revision`、`requested_by`、`target` | 去重、展示快照排序、发起窗口和最终动作 |
| `input_round`、`decision_revision` | 分别识别本次同步与用户确认的内容；普通进度更新不能作废另一个窗口的有效同步回报 |
| `scope` | 核心解析出的工作区、窗口、view、完整 Context、插件实例、连接尝试和宿主参与者身份 |
| `phase`、`failed_stage`、`cancel_requested` | 当前阶段、失败恢复点；取消请求不代表已经取消完成 |
| `participants` | 每个 surface 的同步状态、每个宿主草稿的处理结果、每个 view 的 dirty/busy/error 与保存阶段 |
| `pending_work`、`cleanup_results` | 尚在途的调用/创建及各服务结束结果；不复制文件正文或任务输出 |
| `finalization` | 父对象移除、窗口销毁、安装尝试及重启交接的已完成/在途结果 |
| `adopted_operations` | 全局退出接管失败子操作的引用，保证只存在一个执行者 |
| 阶段截止时间、错误原因 | 有界等待、排障与重试提示；用户等待与机器等待分开 |

草稿值、密码和文件内容继续留在原有保存层；操作快照只携带显示标题、身份、状态和失败原因。保存结果使用 `NotStarted / WaitingExistingWork / Saving / Saved / Failed / Unknown` 等互斥状态，不能只使用 `busy` 推断是否应重新保存。

初始容量建议为 32 个活动关闭操作，其中预留一个全局退出/接管位置；最多 128 个近期终态结果，终态保留 60 秒。活动/失败操作不按 TTL 淘汰；重复请求复用既有操作，满额时拒绝新独立操作。具体常量集中维护并测试，避免分散魔数。

### 4.2 宿主命令

| 拟议命令 | 输入与输出 | 约束 |
| --- | --- | --- |
| `close_prepare` | `{requestId, target}` → 操作快照 | 发起窗口由 Tauri 注入；核心解析目标，不接收客户端提供的“最终资源集合” |
| `close_report_inputs` | `{operationId, inputRound, participants}` → 最新状态 | 按参与者身份/草稿版本分别接受回报；不同窗口同轮回报可以乱序，旧轮次不能完成新同步 |
| `close_decide` | `{operationId, decisionRevision, decision}` → 已接受/当前状态 | 核对用户看到的待处理内容；普通进度 revision 变化不影响决定；重复决定复用结果 |
| `close_status` | `{operationId?}` → 操作/当前窗口相关操作 | 只读，用于丢失事件或前端重载后的恢复 |
| `close_retry` | `{operationId, failedStepId}` → 当前状态 | 只恢复指定的已结束失败步骤；相同重试复用执行者，不重发在途保存和安装 |
| `close_exit_after_failure` | `{operationId, failedStepId}` → 当前状态 | 仅用于安装失败改为退出；局部失败后的全局接管仍走 `close_prepare(Application)` |

事件使用 `core-close-changed`（可读阶段）及定向的 `core-close-inputs`（需要哪一窗口同步）。事件是通知，核心状态是事实；事件丢失后查询可以恢复。所有命令均维持核心 API 的身份、参数、资源状态检查，不构成插件权限机制。

只有主窗口发起全局退出/重启；子窗口的相关操作按现有 `request_main_action` 转给主窗口。窗口关闭和页面关闭按实际窗口归属验证。UI 自带命令可以同版迁移；外置插件 RPC 名称与必需字段先保持现状。

`Views` 校验非空、去重及实际窗口归属；插件发起的集合还受既有同插件/同工作区约束。后台工作区实例不接受普通页面销毁请求，面板收起走隐藏入口。主窗口的 `Window` 目标规范化为应用退出，不能只销毁主窗口而遗漏子窗口。

### 4.3 入口迁移表

| 旧入口 | 新路径 |
| --- | --- |
| `Components.close(workspaceIds, viewId)` | 页面操作直接请求 `Views`；工作区调用者直接请求 `Workspace`，不再调用组件清理后再关父对象 |
| `Components.allowExit()`、`Workspaces.allowExit()` | 全局 `Application` 操作，核心自己收集所有窗口 |
| `workspace_close`、`workspace_close_window` | 薄入口提交目标；移除与旧 `require_closed` 串联的流程 |
| `close_app`、`request_exit`、原生 `CloseRequested/ExitRequested` | 定位或建立同一个操作；仅已交接的最终退出事件允许继续 |
| `restart_app`、`restart(install)` | `Application { Restart / InstallAndRestart }`；检查、清理和安装纳入同一操作 |
| iframe `closeView/closeViews` | 保留原 ticket 回复格式，完成结果由核心操作产生；验证同插件/工作区范围 |
| 夹具和原生 smoke 的 `ui_close_* → shutdown` | 使用生产协调器；测试注入输入结果和最终动作执行器，不跳过核心阶段 |
| 插件异常退出、窗口意外销毁 | 核心强制资源回收路径；记录不可恢复数据边界，不伪造用户的正常保存确认 |

对旧宿主方法只允许临时内部适配，同一个提交组完成调用者迁移后删除。最终不保留两套可被生产入口选择的关闭状态机。

### 4.4 阶段与决定的合法组合

| 当前状态 | 可接受动作 | 必须拒绝或合并的动作 |
| --- | --- | --- |
| Preparing | 同轮输入回报、取消准备 | 未收集完内容前的 Save/Discard；重复 prepare 只返回已有操作 |
| Deciding，尚未保存 | 保存、明确放弃、取消；含未知输入时仅返回处理或明确放弃 | 无法确认输入却声称保存成功 |
| Deciding，保存已开始 | 查询；取消请求停止继续推进，并等待已接受保存的结果 | 重复 Save 不能新建任务；新 Discard 不能中断并冒充已撤销正在提交的写入 |
| Deciding，结果未知 | 核实结果、返回处理或明确接受未知结果后放弃 | 自动重发保存；没有真实结束依据就清空在途记录 |
| Cleaning/Finalizing | 进度查询、真实完成回报 | Cancel 不恢复已释放资源；在途安装/重试不得并发启动第二次 |
| Failed | 重试指定失败步骤，或按规则退出/接管 | 旧步骤的迟到 retry、把已失败清理标成正常运行 |
| Completed/Aborted/已被接管 | 返回终态或新操作位置 | 旧操作编号不能再次执行保存、释放或安装 |

普通快照 `revision` 只用于界面排序。输入回报按轮次和参与者独立去重；决定只在待处理内容实际变化时更新 `decision_revision`。资源进度变化不能导致用户永远提交不了关闭决定。

## 5. 接入控制、锁和在途工作

### 5.1 一个短临界区决定接收与关闭

`AppCore` 持有 `Mutex<Lifecycle>`。它既登记关闭范围，也保护“检查阶段 → 登记在途工作/提交归属变化”的短原子过程。检查后释放锁再做无登记的资源创建仍然不安全。

拟议接入分类如下，分类只表达已有核心能力的运行语义：

| 类别 | 准备/决策阶段 | 清理/收尾阶段 |
| --- | --- | --- |
| 新工作区、重连提交、移窗、view 创建、普通资源创建 | 目标范围拒绝 | 拒绝 |
| 指定 surface 的最后一批输入 | 仅在其 flush 回报完成前允许，并登记在途写入 | 拒绝 |
| 已接受批次继续、已存在任务查询 | 沿用原 Context 和任务身份；按决定继续/取消 | 仅允许查询、取消和释放 |
| 本次关闭选择的保存 | 明确关联操作和原 view/资源，不能由参数自称保存获得通行 | 拒绝新保存 |
| 普通状态、日志、结束通知 | 允许；迟到回复只更新仍匹配的对象 | 允许排障和完成回报，不重新登记业务资源 |

已有 `resource_owner()` 拆分为身份/Context 校验与阶段接入判定。调用者不能依赖一个 `is_closing()` 判断所有行为；读结果、释放旧资源和创建新资源具有不同条件。`session.state.closing` 继续提供兼容的派生值。

插件 `files.request(save)` 由核心按该 view 在当前关闭操作中登记的保存步骤匹配原资源和本次固定 Context，不要求旧插件附加操作编号；同一步重复请求返回原任务。宿主 `save_settings` 可携带内部 `closeOperationId`，由 Tauri 窗口和已选中的设置草稿参与者核对。一般业务调用不携带该关联，继续受正常接入规则约束。

### 5.2 锁顺序与边界

生命周期临界区是相关变更的外层边界。迁移涉及的嵌套路径遵守：生命周期 → 目录/变更互斥 → 连接 entries 或更新状态 → 工作区 → component UI → 具体资源登记表。连接和更新不在同一条嵌套链交叉等待；需要读取其他数据时优先复制后释放原锁。

这份顺序是整改目标，不声称当前代码已经满足。实施时必须逐个检查新接入点：现有 `updates` 持锁后调用 `is_closing()`、`start_enabled` 持有 mutations、网络打开时在 registry 内读取连接、UI 内读取冻结状态等，都不能直接换成会再次取得外层锁的函数。

具体规则：

1. 已持有生命周期 guard 的内部 helper 接收该 guard 或所需状态，不重新加同一把锁。
2. 不持有生命周期、workspace、UI 或 registry 锁等待 RPC、磁盘、网络、worker、用户确认或 Tauri 调用。
3. 下层锁持有期间不回调外层生命周期接口。事件与日志在提交后、释放锁后发送，保留现有 RPC 重入能力。
4. 后台线程先取候选快照，再逐项取得接入登记；不能拿旧候选直接发起 mount。
5. 保存和更新的落盘工作使用“短锁登记操作 → 释放生命周期锁执行 IO → 短锁提交结果”，不要把网络下载或整轮插件启动放进全局锁。

### 5.3 登记范围

必须登记的在途工作包括 `ui.mount/event`、组件数据写入、PTY 打开、SFTP/文件操作、监听绑定、网络连接/复制、命令启动、SSH 认证提交及插件启动。还没有 view 的连接尝试用其已有 attempt/window/server 身份归属，形成 view 后继续使用现有 Owner/Context。

具体服务仍拥有资源细节；生命周期只掌握足以判断范围、在途数量及结果能否提交的身份。任务外层确保正常返回、错误、取消和可捕获的 worker 终止都会报告结果。作用域 guard 只能证明本地 worker 已结束，不能据此宣布远端写入成功或远端进程已经终止。

## 6. RPC 排空与超时后的真实状态

[plugin-client](../crates/plugin-client/src/lib.rs) 的核心调用超时是 4 秒；核心插件请求上限见 [plugins/rpc.rs](../src-tauri/src/plugins/rpc.rs)，当前为 5 秒。因此 `terminal.close`、`files.request(close)`、`net.close` 继续快速返回已接受，核心内部另行确认真正结束。不能把 6 秒以上的清理等待塞入这些响应。

正常 `ui.event` 和重入请求继续并发。关闭采用“停止接收新工作 → 等待已经接受的调用排空 → beforeClose/save/dispose”的阶段边界，不能用每 view 一把锁把所有 RPC 串行化；已有重入与乱序响应回归必须继续通过。

合并初次 mount 只解决后台与 surface 同时初始化同一 view。不能在响应读取线程或重入回调里同步等待自身所属的初始化请求；无法立即复用的初始化重入返回明确的进行中状态，不能通过互相等待造成死锁。

| 位置 | 修改内容 |
| --- | --- |
| `component_ui/host.rs` | 对影响生命周期的调用关联 view/实例/Context 和内部工作票据；结果提交二次校验；同 view 初次 mount 合并，已有实例重挂载仍按协议幂等 |
| `plugins/mod.rs` 的 `Call` / `Instance.request` | 增加内部可观察的发送/完成信息；不把宿主票据作为外置插件的必需字段 |
| `plugins/process.rs` 请求登记与响应匹配 | 区分未发送超时、已发送但结果未知、真实回包、进程退出；调用者超时不能直接等同于插件端已停止执行 |
| `plugins/rpc.rs`、`dispatch.rs` | 保留读写独立、有界队列和停止优先；关闭阶段对新的业务请求使用共同接入检查，结果/日志/释放仍可通行 |

已经发送而超时的生命周期调用保留有界观察记录，收到迟到回包仅完成原票据，不重新更新关闭后的 view；进程确认退出可结束其所有悬挂票据。记录计入现有请求上限，不能因调用者已返回就无限接受更多未知请求。

单工作区关闭遇到无法确认结束的 mount，不能盲目重发 dispose 然后报告成功。保留失败状态和旧身份；全局退出可按进程监督机制结束插件。不能为了释放一个工作区直接停止服务其他工作区的共享插件。

## 7. 各核心资源模块的修改

### 7.1 共同结果约定

保留各服务自己的 registry。统一提供以下最小能力：请求取消、查询本范围未结束项、回收已经结束的记录。关闭执行器显式汇总，不复制各服务的完整状态。

```text
cancel(scope)           请求取消，停止业务接入，保留结束依据
cleanup_status(scope)   返回尚未结束的资源身份及确定错误；只读
reap_closed()           仅回收实际结束且不再需要结果的记录
```

`CleanupProgress` 可共享 pending/failed 的基本结果形状，因为终端、文件、网络已有三个真实用例。等待使用完成通知或有界的状态轮询，最长间隔 100 ms；一个阶段使用共享截止时间，不对每个资源重新追加超时。

业务已结束但用户尚未读取的结果，与关闭中的资源分别处理。关闭会释放结果缓存，普通业务仍沿用自身读取/TTL 规则。资源记录“不可再使用”后，旧句柄允许查询/释放到规定终点，普通读写明确返回关闭状态。

### 7.2 终端

修改 [terminal.rs](../src-tauri/src/terminal.rs) 的 `Terminal`、`Terminals::cancel`、`terminal_open/close`、`run()` 及数据订阅收尾：

- 为终端运行任务提供结束事实与结果；取消后保留记录至 `run()` 已退出并释放通道。
- 在登记 PTY 创建请求时完成生命周期检查，替换“先登记，再次检查，失败就删除”的竞态窗口。
- `terminal_close()` 快速标记取消，重复关闭同一资源返回既有结果；不能提前把收尾记录删掉。
- 结束时关闭输入队列，使排队写入得到明确失败；结束 Replay 输出与 surface 订阅，不能留下等待数据的任务。
- 所有分支先释放 SSH channel/本地引用，再报告本地收尾完成。远端脱离 shell 的进程仍按既有 SSH 语义，不承诺全部杀死。

回归：PTY 打开中关闭、持续输出中关闭、队列有输入时关闭、重复 close、断线和迟到打开结果；检查实际 worker/通道结束以及后续连接仍可用。

### 7.3 文件资源与文件操作

修改 [remote_files.rs](../src-tauri/src/remote_files.rs) 的 `Resource`、`Files::cancel/cancel_pending`、`files_open/control/data`、`start_file_job()`；同步修改 [operations.rs](../src-tauri/src/remote_files/operations.rs) 的批次、输入和后台操作登记：

- 资源保存任务、SFTP 操作、正在进入的本地文件数据流分别计入在途状态，取消 Resource 后仍能观察它们结束。
- `files.request(close)` 快速接受，最终回收目录游标、文件句柄、SFTP 会话引用和本地输入；不依赖 `Drop` 发出异步关闭请求来证明已经结束。
- 保留 `files.request(status/save)` 的兼容语义。保存只允许原资源、原 Context 及本次关闭已登记的保存步骤；完成结果继续记录文档 revision。
- 准备阶段允许已登记批次继续或取消；清理阶段不能再凭 `batchId` 绕过关闭约束启动新的批次工作。
- `files_begin_input/finish_input` 和所有 `op.*` 提交再次核对票据；取消后迟到的输入必须关闭实际文件句柄并处理临时文件，不能只丢弃结果 JSON。
- `unknown` 与确定失败分开。保存/改名已提交但确认丢失时保留结果未知，禁止协调器自动重做操作。

回归：两个编辑器保存部分成功、文件任务等待冲突、批次取消、上传中关闭、本地输入取消、提交后断线、旧 revision 完成回包、临时资源清理。保存语义不能因生命周期改造而退化。

### 7.4 网络监听、流与复制

修改 [network/mod.rs](../src-tauri/src/network/mod.rs)、[runtime.rs](../src-tauri/src/network/runtime.rs)、必要的 [relay.rs](../src-tauri/src/network/relay.rs) 收尾：

- `Listener` 跟踪 accept loop、连接中的流、serve、splice 和 probe 的活动数量及结束事实；流从 serve 移交 splice 时转移跟踪，不能出现“旧 worker 已结束所以全组为空”的间隙。
- `net.listener.open` 在异步 bind 前登记创建；监听 socket 获得后再次检查状态，关闭目标不会短暂发布成 running。
- `Network::cancel` / `net.close` 停止接入并取消子任务，保留 listener 收尾记录；poll 不再把取消中的客户端发布成可协商新连接。
- 所有子任务释放 socket、流和 semaphore permit 后才扣减活动计数；probe 的客户端及去重记录一起清理。
- 操作去重记录对已关闭资源返回已关闭/过期结果，不用同一 operationId 创建替代监听。

回归：监听绑定中关闭、SOCKS 协商中关闭、splice 交接中关闭、持续流量、probe 在途、断线；确认端口能够重新绑定且资源预算恢复。

### 7.5 命令、连接、插件进程与后台 worker

| 模块 | 修改点 | 结束依据 |
| --- | --- | --- |

### 7.6 按关闭范围安排取消与等待

先发取消、再等待结果，不能把所有等待放在取消底层依赖之前：

- **单个 view：**冻结并排空其输入/创建，发 dispose 与资源取消，等待这个 view 的结果；其他 view 的连接和共享插件继续运行。无法确认时保留局部失败，允许之后由全局退出接管。
- **工作区/子窗口：**发出全部目标资源取消，释放其连接引用；对不再服务其他目标的连接发送取消以打断阻塞 IO，再共同等待 view/连接结束。不能等待一个只有断开连接才会结束的任务之后才决定断开连接。
- **整个应用：**停止新调度，发出目标资源取消并尝试有界 dispose；随后执行插件正常停止/进程组收尾、连接取消和 worker 排空，再汇总实际完成。已发送而结果未知的 mount 不得成为“永远不能走到插件停止”的前置条件，进程实际退出可以终结其在途事实。

上述升级仅发生在相应范围已经完成用户决定之后。全局停止不是单个页面的隐式回退。各步骤可以在依赖允许时并行等待，但必须在所有必要结果确认后才进入最终窗口销毁/安装/退出。

## 8. 只读快照与工作区初始化

把 `reconcile_ui()` 拆成职责明确的内部动作：同步已运行插件的定义/默认偏好、初始化新工作区、刷新 Context、确保正常工作区的后台实例。保留已有默认展开、用户布局与实例去重逻辑。

| 触发点 | 应执行的动作 |
| --- | --- |
| 插件初始化成功/失败/停止 | 更新定义可用性；仅在适用阶段建立后台实例，不为既有工作区重跑全部普通启动策略 |
| `accept_connected()` 与生产 `adopt_connection()` 建立新工作区 | 标记待初始化，在核心协调中完成默认布局/view；无需前端读快照 |
| 重连得到新 Context | 更新引用及代次，旧工作不能提交；保持同一工作区的既有业务恢复语义 |
| 用户修改布局偏好 | 保存偏好并更新展示；不把每次偏好修改变成重新执行启动策略 |
| 关闭中止 | 解除本操作保留并唤醒协调；复用原 view，不建立替代实例覆盖草稿 |
| 工作区/插件资源实际结束 | 撤销定义/实例或标记不可用；不因下一次查询重新创建已关闭对象 |

核心状态发布在必要初始化提交之后，或明确携带 initializing 状态。`ui_snapshot()` 仅序列化已提交状态；`workspace_changed()` 主要发布变更，不再通过“某个 view 暂时不在列表里”隐式代替完整清理协议。

核对 `workspace_changed()` 当前各资源取消逻辑，迁移到明确的工作区结束、view 结束、Context 失效和插件失效入口，保留这些安全清理功能。默认初始化要覆盖无插件、插件尚在启动、无后台声明和混合后台/普通插件，避免重演默认终端丢失。

## 9. 宿主输入与未保存内容

### 9.1 跨窗口同步

`src/close.ts` 由每个原生窗口初始化。核心确定参与窗口和 surface；各窗口完成自己的同步再回报。`Components.flush()` 改成接收明确目标和同步轮次，同时保留移窗调用者；移窗与关闭不能同时覆盖同一 surface 的 `flushing` 回调。

同步流程：

1. 核心保留目标拓扑，阻止创建/移窗，通知窗口停止新增编辑输入。
2. 对已声明 flush 的目标 surface 发送现有 flush；允许其最后一批同步和已有 promise chain 完成。
3. 按 surface 回报操作/轮次，核心关闭该 surface 的普通写入通道；全部完成后汇总 beforeClose。
4. 未声明 flush 的插件沿用现有保证范围；未就绪、失联或消失的必需参与者记录“输入无法确认”，不当成同步成功。默认返回处理；用户仍可明确选择放弃这些未同步内容后关闭，不能因为每次准备都失败而只剩系统强杀。无法确认的参与者不能被“保存并关闭”静默跳过。
5. 中止时恢复输入；清理时保留只读进度；完成后卸载 surface。旧 flushed 消息不能完成新的关闭或移窗操作。

修改 `ui_data_writable()`、`ui_event()`、组件数据桥与 metadata 回写检查。必须允许准备阶段受控的最终数据进入，不能先 frozen 再等待同一入口完成 flush。

目标身份失效、更新前置失败等直接中止准备；输入同步/插件状态无法确认则携带明确错误进入决策阶段，由用户返回或明确放弃。没有可交互前端时不能自动替用户决定，按异常退出的能力边界报告。此细化保证数据保护与可执行退出路径同时成立。

### 9.2 宿主草稿

服务器表单和组件设置已经是两个真实参与者，可用一个小型宿主参与接口统一“收集状态、处理决定、恢复输入”，具体表单和保存规则仍留在各自模块。

| 模块 | 具体整改 |
| --- | --- |
| `servers.ts` | 把 `allowExit()` 的状态检查与弹窗决定拆开，检查全部 frames 和保存中状态；保留已有表单的返回/明确放弃行为，不在后台擅自保存带凭据的复杂表单。需要保存时定位原表单，让用户按既有入口处理后重试关闭 |
| `settings.ts` | 增加收集全部 drafts 的接口；保存逻辑提取为按 key 的操作，当前页面按钮复用它。关闭不能只保存 `selected`；隐藏页校验使用已有声明与核心校验，遇到需要原页面处理的错误则定位并中止关闭 |
| `settings.ts` 的保存结果 | 保存到磁盘与应用到运行实例分别报告；本轮随后要退出时，不因已经保存但等待展示应用而重复保存。冲突、校验失败和未知响应保留原 requestId/草稿 |
| `main.ts` | 服务器、设置和插件页面全部完成决定前，不进入任何 view 的 dispose。全局重启也走此路径 |

参加准备的宿主表单只回报标题、dirty/busy、版本和可处理动作，不把密码、设置正文写进生命周期日志。需要用户处理表单的等待属于决策阶段，不消耗输入 flush 的机器等待期限。

### 9.3 页面交互与错误

保留现有保存/放弃/取消用语和键盘交互，显示具体服务器、组件、阶段及未完成原因。清理开始后提供进度和失败重试，不继续显示能够撤销已释放资源的“取消关闭”。焦点返回尚可操作的页面或关闭状态面板。

`status` 查询恢复 UI 状态，重复点击定位既有操作。修复过程不顺带重做主题或整个工作台布局；新增状态必须在三主题、小窗口和键盘操作中验证。

## 10. 原生窗口、重启及更新收尾

### 10.1 原生动作

`main.rs` / `windows.rs` 只执行核心已经到达 Finalizing 的动作，并向原操作回报结果。核心保存父对象移除、窗口销毁、安装、重启交接各步骤的明确结果及当前执行步骤，不能因某一步失败把全部生命周期设回运行中。

在应用 setup 时注册一个内部 finalizer 回调或有界消息通道，直接由原生宿主执行核心发出的 `FinalizeAction`；它与发送给前端的状态事件分开。执行前先登记步骤在途，完成后以 operation/step 身份回报；调度和回报都在释放核心锁之后进行。使用可断开的通道或弱引用避免回调持有自身形成永久引用环。测试注入同一边界的假执行器，生产关闭不依赖前端收到事件后再调用一次退出。

`CloseRequested` 与 `ExitRequested` 的事件防重入标记只反映最终交接是否已获核心允许。`Destroyed` 根据核心实际归属回收资源；正常销毁重复通知不再二次 dispose，意外销毁则记录输入无法恢复的事实。

主窗口尚未加载时也要检查实际参与对象：没有草稿参与者可由核心正常清理启动中的插件；已有参与者失联则按失败边界处理，不能以 `frontend_loaded=false` 绕过已存在的 view 和资源。

### 10.2 更新前置与最终动作

- 重启先检查更新忙碌和包可用性/验签；把“没有冲突更新任务”和关闭范围保留放在同一短接入过程，防止检查后又启动下载。
- 更新检查、下载、准备/替换插件登记及落盘提交都参加应用级在途工作。普通退出先停止接收新更新；已有工作按其可取消性取消或在自身期限内完成，发布目录替换等短提交不能在一半时退出。
- 对 `CoreUpdater` 增加与关闭操作绑定的准备包引用及安装尝试状态，复用官方 updater 验签/安装，不自建安装流程。
- 保存或准备失败释放关闭保留，已下载包仍可使用；清理后安装失败保留“旧资源已停止”的事实，允许重试失败安装或转为退出。
- 安装已成功、重启交接失败时只重试重启；不得因为原准备包引用已清空而重新下载/安装。
- 安装 worker 在途时，超时显示与真实完成分开。官方/系统安装器若不能可靠取消，监视超时只能显示耗时或结果未知，不能清掉在途标记再启动第二次安装，也不能在其改写程序期间按普通失败路径退出。

当前 `resume_after_failed_install()` 清除 closing 的行为随之移除，改为原操作失败阶段更新；保留现有安装错误、包缓存及“需要重启”的用户反馈。新行为在隔离安装测试中验证，不操作用户正在运行的安装目录。

### 10.3 全局退出接管失败的局部清理

只有已经失败、没有正在执行重试 worker 的子操作可以被接管。全局准备先引用它的完成结果并暂停其单独重试，再对其余窗口/草稿正常准备与确认；全部决定完成后，在生命周期临界区一次性转移执行权。

若全局决定取消，只恢复新增目标，原子操作仍保持失败状态。接管后旧操作状态返回 `adoptedBy`，旧 retry/decide 不再执行。系统级插件终止仍须等其他受影响窗口同意，不能由一个工作区失败隐式批准全局丢弃内容。

## 11. 四个插件的适配与兼容验证

| 插件/共享代码 | 保留 | 必须核对；失败时的最小修改 |
| --- | --- | --- |
| 终端 `plugins/terminal/src/main.rs` | PTY 协议、xterm、数据流和原有设置 | mount 去重、重复 dispose、core close 快速接受；晚到 mount 不再创建 view。优先由宿主排空规则解决，不为终端加退出特例 |
| 文件 `plugins/files/src/main.rs` 及任务管理 | 文件原语、批次与冲突、文档 revision | beforeClose 能报告真实阻塞/未知结果；save 仅接受一次，busy 结束后正确清除 dirty；dispose 取消所属任务，晚到结果释放句柄 |
| 网络 `plugins/network-proxy/src/main.rs` | 规则、SOCKS、转发策略 | 管理 view 与规则编辑弹窗的清理范围分开；dispose 不停掉其他工作区规则；快速接受关闭后由核心证实端口释放 |
| 系统状态 `plugins/system-status/src/main.rs`、`scheduler.rs` | 采集算法、周期、趋势、业务暂停 | 关闭中不派发新 Start；取消关闭后继续原 view；已删除 view 的晚到 Start 结果按原票据 release/由核心回收，不复活采集状态 |
| `crates/plugin-client/src/lib.rs` | 四 worker、请求 ID 匹配、4 秒调用上限、shutdown 快速响应 | 不整体改成串行 handler。只有公共协议实现确有缺陷才改 SDK，并扩大对应插件验证范围 |

先验证“新核心 + 当前四插件原包”，再验证需要修订的插件。内部生命周期票据不增加插件必需字段。若现有协议无法表达某项新增可观察语义，先记录明确缺口并采用可选 capability/API 兼容策略，不能以升级核心为由要求无关插件同步升级。

所有 `ui.mount`/dispose 及业务保存的幂等保证要基于真实测试。宿主负责自身调度和核心资源；可信插件自行创建的脱离进程及不可撤销远端副作用，仍按既有产品边界报告。

## 12. 机器等待、重试与可观测性

| 阶段 | 初始预算/策略 | 到期处理 |
| --- | --- | --- |
| surface 输入同步 | 沿用当前 45 秒，所有目标共享截止时间 | 标记无法确认，默认返回处理；只有明确放弃才继续，不自动丢弃内容 |
| 单个插件控制调用 | 保留核心现有 5 秒与 SDK 核心调用 4 秒的协议边界 | 区分未发送、真实错误和已发送结果未知 |
| 已有任务等待与保存 | 操作共享 125 秒机器等待预算 | 保留页面和真实结果；已发写入不自动重放 |
| view 资源清理 | 初始共享 6 秒；结合实际可取消任务回归调整 | 保留 pending 项和取消状态，允许在确认无同一重试 worker 后继续等待/收尾 |
| 应用插件进程停止 | 沿用应用阶段 6 秒及现有监督器内部期限 | 报告实际未退出对象，不能只看 shutdown 回复 |
| 连接收尾 | 沿用应用阶段 3 秒 | 按 `done` 报告未完成，不提前删除引用证明成功 |
| 系统安装器/重启交接 | 使用实际返回与原生结果观察；在途尝试互斥 | 监视超时不是安全重试依据，先确认原尝试已结束 |

用户阅读或处理确认没有自动同意时限。所有后台重试有单一执行者与明确次数/用户触发点；关闭失败不自动反复发保存、安装或远端命令。

统一日志字段：operationId、目标类型、阶段、view/实例/Context、等待资源类型及数量、耗时、失败原因、接管来源。普通阶段日志不弹通知；可操作失败在原关闭 UI 显示，避免每点一次积累一个 toast。

## 13. 实施顺序与提交单元

所有工作在同一整改分支完成；使用 `codex/` 前缀。先确认工作区已有修改，再实施。本方案不创建分支、不提交代码。

### C0：固定基线与回归入口

- 重新构建当前源码夹具，在隔离数据目录重现后台 view 重建，保存本次精确提交与结果。
- 记录当前核心、脚本、UI 和四插件相关测试结果；已有失败与本次新增回归分开。
- 扩展夹具支持可控延迟、晚回复、保存失败和资源结束通知，不操作真实用户服务器。
- 交付条件：能确定性触发错误，测试能观察 view 身份、资源结束及退出结果；不依赖随机 sleep 碰竞态。

### C1：资源取消具备可验证的结束状态

- 按第 7 节修改终端、文件、网络，接入执行/连接/进程既有完成事实。
- 为取消后仍在运行的资源保留状态，清理结束后回收；确保旧关闭 RPC 仍快速返回。
- 每种资源各自完成真实结束与配额/端口复用回归，再继续下一种，不同时把四个模块改到无法定位失败。
- 交付条件：取消不会使资源从观察范围中消失，查询不启动新工作，正常业务与既有协议测试通过。

### C2：统一生命周期范围与接入判断

- 新增 `lifecycle.rs`，实现目标解析、阶段、去重、范围保留、在途登记及核心快照；单元测试直接覆盖状态转换。
- 接入创建、认证提交、移窗提交、插件启动、更新操作与资源登记；完成锁顺序整改。
- 旧关闭计划在过渡期只能映射到同一状态，不能与新模块各自保留一份冻结状态。
- 交付条件：每个被保留目标的新工作和迟到提交均被拒绝或收尾；正常重入及无关工作区不被阻塞。

### C3：后台初始化与快照职责迁移

- 完成第 8 节的生命周期触发点；移动默认初始化、定义同步、后台确保逻辑。
- 快照变成只读，后台 worker 支持关闭暂停、取消恢复与最终停止。
- 交付条件：默认文件/终端、隐藏采样、重连和移窗仍可用；任意次数读取状态不会改变 view 或创建任务。

### C4：关闭协调器与全部宿主入口切换

- 新增核心执行器和 `src/close.ts`；实现跨窗口 flush、服务器表单与全部设置草稿参与。
- 将页面、工作区、子窗口、退出、普通/更新重启、插件请求关闭、原生 smoke 迁到同一操作。
- 实现清理/收尾失败、全局接管、安装单次执行和原生事件防重入；移除旧的串联路径与布尔恢复逻辑。
- 交付条件：所有入口使用同一生命周期事实；保存失败保留页面、关闭取消可恢复、清理失败不会恢复已失效业务。

### C5：插件契约、组合回归与原生验证

- 先用当前正式插件包验证新核心；仅修订暴露真实问题的插件，分别测试与打包。
- 完成全部生命周期用例、代表性多组件组合及五平台实际包验收。
- 交付条件：结果能够对应明确的核心提交和插件版本；代码、协议说明、使用限制及实施记录一致。

C1–C3 可以形成保持既有入口可运行的内部提交；C4 的跨入口切换必须完整。上述是逻辑工作单元，不承诺每项固定一个提交，也不允许为缩小 diff 发布未完成的生命周期。
