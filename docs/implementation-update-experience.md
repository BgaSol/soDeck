# 核心与插件更新体验实施记录

2026-11-06。依据 [更新体验规划](plan-update-experience.md) 实施。代码已落地并提交，随核心 0.9.0 和新版官方插件发行；结果见 [发行说明](releases/v0.9.0.md)，下文保留源码实施时的验证范围。

## 用户可见行为

- 设置 → 更新统一列出 SoDeck 与已安装插件，展示版本、状态、更新说明和每项下一步操作。支持检查全部、默认选择全部可下载项、取消选择、批量下载及逐项重试。未安装的官方插件只出现在“添加插件”。
- 主窗口设置入口与更新导航显示可更新数量；准备完成后显示待重启提示。下载不会自动重启，设置底部固定的统一清单合并核心更新、插件版本切换与启停变更，小窗口也能直接重启。核心安装失败保留包，提供重试安装并重启。
- 首屏完成后恢复核心缓存，再延迟约 10 秒启动后台检查。默认每天检查一次，偏好可关闭；手动检查仍可用。调度和排队由主进程管理，同一时刻的全量检查去重，同仓库同批次复用分页 Releases 列表及读取失败结果，避免不可达仓库被各组件重复请求。
- 检查结果与下次检查时间保存到应用数据。失败检查保留上次结果并显示原因，15 分钟后才允许下一次自动检查；正常结果间隔为 24 小时。网络失败不阻塞工作台，不自动下载。
- 批量下载最多同时处理两项，其余显示等待下载。一项失败后其余继续，失败项可独立重试。下载后还需校验和准备；未知总大小时显示已下载字节和不定进度。
- 插件页只列一次已安装插件，保留启停开关、详情和更新快捷操作。“添加插件”承接官方安装与本地目录。详情折叠更新来源和技术信息，保留自定义来源。启停继续在重启后生效。
- 完全关闭且未加载的插件下载完成后直接更新记录，保持关闭，不增加待重启项。启用或本次启动加载过的插件仍运行旧程序，到重启时切换。初始化失败沿用原程序回退。
- 更新页与插件页复用现有浅色、深色、多巴胺主题。刷新保留选择、来源草稿、详情展开状态、滚动和键盘焦点。
- Windows NSIS、macOS app、Linux AppImage 仍使用官方 Tauri updater；Linux DEB 明确显示系统安装方式和发行下载入口，插件仍可在线更新。

## 核心包缓存与校验

核心更新包位于 `<应用数据>/updates/core/package.bin`，最小恢复信息位于同目录的 `metadata.json`。下载由官方 updater 验签后先写临时文件并同步，再替换正式缓存。核心不长期保留下载包的内存副本。

重开时检查当前应用版本和本机目标，使用固定版本官方 updater 的 `restore_update(raw_json)` 重建更新对象，并调用 `Update::verify` 验证缓存。恢复无需联网。用户决定重启时再次验签，随后复用原有退出检查、插件清理与官方安装路径；安装器也继续执行官方验签。损坏缓存不会被标记为已准备好，用户可重新下载。缓存平台过期或重开确认运行版本变化后清理，不把启动安装器当作实际版本切换。

候选发现缓存不直接作为下载依据：插件下载前重新读取清单并核对 ID、版本、API 和各平台包信息，下载继续使用 HTTPS、SHA-256、路径及入口检查。来源变更使对应候选失效。插件待切换版本继续使用原有持久化记录。

本次未新增生产依赖。`test-fixtures` 启用已有 Tauri 的测试辅助功能，以官方签名测试向量验证实际 updater。Windows 测试程序需要 Common Controls v6 清单；构建脚本仅在该测试功能下补充清单，并让已有 Tauri 资源清单的应用及夹具二进制保留原清单。

## 缺陷原因与回归

已准备好的插件再次检查时，原实现返回“该插件已准备好更新，请先重启应用”，把成功准备当作检查错误。先使用稳定夹具复现，再改为跳过已准备项，状态投影始终以持久化待切换版本优先。回归覆盖重复单项检查与批量检查。

核心原先只把官方更新对象及下载字节放在内存，关闭后失去准备状态。现改为落盘和官方离线验签，测试覆盖正常恢复、损坏包、篡改候选版本、恢复后包被修改。安装失败保留准备状态和安装阶段错误。

全量检查与下载共用主进程任务状态，下载期间不启动自动或手动全量检查，也不能重复入队或重启。任务异常中断释放占用并提供重试。无候选的检查失败也保存并在重开后展示，避免把失败伪装成未检查。

## 更新说明 Markdown 修复（2026-11-06，未发行）

验收行为：核心与插件的更新说明按 Markdown 展示标题层级、段落、列表、强调、引用、代码和表格，网页链接交由核心打开；三种主题及小窗口保持可读，长代码和宽表格在说明内部滚动。

## 官方插件从仓库自动发现（2026-11-08，未发行）

此前名单和发行标签前缀写在核心 `official_plugins.rs` 中，界面的插件图标与排序也按 ID 固定，因此新增官方插件需要修改并发布核心。验收行为改为：同一核心运行期间，仓库新增或移除插件配置后，刷新即更新名单；新 ID 可通过原安装服务安装，不要求修改核心代码。

核心现在通过 GitHub Trees API 读取官方仓库 main，只选取 `plugins/<目录>/release.json`，再按该目录快照的 blob SHA 读取配置。直接复用各插件已有发行配置的 ID、名称和标签前缀，增加可选用途说明、图标与排序字段；不生成集中索引，也不改独立打包、Release 或实际插件清单。核心保留固定官方仓库地址，名单与安装来源在运行时解析。

读取复用现有 HTTPS、超时和响应体大小限制，校验元数据、唯一 ID/标签前缀及目录完整性。成功的完整名单在内存和应用数据目录缓存一小时，手动刷新绕过缓存；请求失败或任一配置无效时保留上次完整名单并提示，无缓存时明确报错，成功空名单才清空列表。移除配置不删除已安装插件、不改其更新来源。缓存使用独立锁，网络请求不占用服务器或更新任务锁。

工作台启动不请求官方名单，进入插件管理后异步读取；等待期间仍可切换设置或使用已有功能。官方列表提供刷新、重试和上次成功获取时间，名称、说明、图标和顺序均来自仓库。安装仍需校验正式版本、API、本机平台、哈希及实际包内容；列表出现配置不等于已发布可安装包。
