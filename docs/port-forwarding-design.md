# SSH 端口转发设计

状态：设计提案，尚未实现。日期：2026-10-16。

功能范围、默认行为及验收基线见 [功能需求](port-forwarding-requirements.md)。本文记录技术实现方案；初始资源预算需通过实际测试确认。

## 1. 产品目标与技术决策

让本机应用通过已配置的 SSH 服务器，访问该服务器能够连接的 TCP 服务。典型目标包括 MySQL、PostgreSQL、Redis、内网 Web 页面，以及只监听服务器回环地址的管理服务。

第一版实现本地 TCP 端口转发，等价于 OpenSSH 的 `ssh -N -L`。沿用 Rust `ssh2/libssh2`，通过 `Session::channel_direct_tcpip` 建立通道，在 Rust 中双向转发字节。服务器无需安装额外代理，账号无需拥有交互式 shell，但需要 SSH 服务允许向指定目标转发。

```text
本机数据库客户端
  连接 127.0.0.1:13306
          │
          ▼
SoDeck 本地监听器
          │ SSH 加密连接
          ▼
已配置的 SSH 服务器 B
          │ 由 B 解析目标域名并发起 TCP 连接
          ▼
db.internal:3306
```

如果 B 配置了跳板 A，路径为：本机 → SSH A → SSH B → 目标服务。A/B 各自核对指纹和认证，沿用已有单层跳板能力。最终的目标服务不是第三个 SSH 跳板，无需保存成服务器配置，也不需要 SSH 账号。

关键决策：

- 隧道归应用后台管理，独立于终端标签和窗口；无需先打开终端。
- 跳板连接与用户端口转发共用 SSH 转发内核；跳板不依赖端口规则、管理窗口或 `PortForwardManager`。
- 每条运行规则持有一套独立 SSH 连接路径，同一规则的多个本地 TCP 连接使用多个 SSH channel。
- 第一版监听本机回环地址；默认 `127.0.0.1`，高级选项允许单独使用 `::1`。
- 目标域名交给最终 SSH 服务器解析，本机不预先解析。
- 自动重连恢复后续连接能力；已中断的 TCP 会话由业务客户端重新建立。
- 状态区分“隧道已启动”和“目标最近一次连接结果”。

暂不纳入第一版：远程端口转发 `-R`、SOCKS5 动态代理 `-D`、UDP、Unix socket、局域网共享监听、系统代理/VPN、应用退出后驻留运行。

## 2. 用户流程与界面

### 2.1 入口与管理窗口

在主工作区全局操作区增加“端口转发”入口，显示运行数量及需处理标记。点击打开单实例的独立管理窗口，再次点击聚焦已有窗口。风格、标题栏和键盘操作沿用现有独立窗口。

服务器选择界面提供“配置端口转发”，预选该服务器。从已连接会话进入时也预选服务器；连接路径在界面中完整展示。无需创建一个空终端来启动转发。

管理窗口包含搜索、新建和规则列表；选中规则可查看详情。每条规则至少显示：

```text
生产数据库                         已启动 · 2 个连接
127.0.0.1:13306  →  db.internal:3306
经由：生产入口机（通过跳板机 A）

[复制本地地址]  [测试连接]  [停止]  [更多]
```

列表显示名称、完整本地地址、目标地址、经由服务器、状态和活动连接数。详情补充连接路径、运行时间、双向流量、最近失败原因和有界事件列表。避免在列表中堆叠曲线。

“复制本地地址”复制实际监听的 `host:port`；详情允许分别复制主机和端口，IPv6 组合地址加方括号。“打开网页”仅用于用户配置了 HTTP/HTTPS 打开方式的规则，使用实际本地端口，不根据目标端口自动猜测协议。

### 2.2 新建规则

| 字段 | 示例/默认值 | 说明 |
| --- | --- | --- |
| 名称 | 生产数据库 | 用户可读名称，不要求唯一 |
| 经由服务器 | 生产入口机 B | 选择已有服务器；展示其跳板路径 |
| 目标地址 | `db.internal` | 从 B 访问的地址；可填域名、IPv4、IPv6 |
| 目标端口 | `3306` | 1–65535 |
| 本地端口 | `13306` | 默认使用用户填写的固定端口，也可选择自动分配 |
| 本地地址 | `127.0.0.1` | 高级选项可改为 `::1`，一次只绑定一个地址 |
| 断线自动重连 | 开启 | 仅对可重试的连接错误生效 |
| 网页打开方式 | 无 | 可选 HTTP/HTTPS，仅生成本地访问链接 |

表单实时展示“本机地址 → 经由服务器 → 目标地址”，底部提供“保存”和“保存并启动”。认证信息复用所选服务器，表单不重复保存密码或私钥。

目标地址输入框下固定说明：“由经由服务器访问；填写 127.0.0.1 表示这台服务器自身。”本地地址不用模糊的 `localhost` 展示，以免 IPv4/IPv6 解析差异造成连接失败。

地址字段只接收主机名或 IP，不接收 URL、路径和内嵌端口；拒绝控制字符、NUL 和超长输入。IPv6 可接受成对方括号并规范化，端口单独填写。目标主机不拼接成 shell 命令。

自动端口使用操作系统 `bind(..., 0)` 分配，并保留该监听 socket；实际端口返回前端。该次运行的自动重连保持同一端口，停止后再次启动可能改变。固定端口冲突明确报错，不自动换端口，也不终止占用端口的其他程序。

### 2.3 运行、编辑与关闭

- 启动同一规则是幂等操作，不会因双击或多个窗口产生重复监听器。
- 初次连接沿用现有逐跳密码、私钥、Agent 和指纹交互。
- 关闭管理窗口或终端标签不停止已经运行的转发；全局入口继续显示运行数量。
- 管理窗口关闭时，尚未就绪的首次启动尝试取消并释放资源；已经运行的规则和它们的后台重连继续。重新认证期间关闭窗口则结束该次认证尝试，保留原规则的“需处理”状态和本地端口。
- 重新连接需要用户介入时显示“需处理”，用户打开管理窗口后继续认证，不在后台自动接受新指纹。
- 运行中的规则保留启动配置快照。名称和网页打开方式保存后立即更新；网络参数和自动重连策略可“保存，下次启动生效”，显示“有修改待应用”，也可“停止并应用”。后一操作结束现有连接并用新设置启动，失败时不自动恢复旧目标。
- 修改底层服务器地址、用户名、认证方式或跳板路径，不改变已经运行的隧道。界面标明“服务器配置已修改，重新启动后生效”；自动重连继续使用当前运行快照。
- 停止会关闭监听器及该规则的全部 TCP 连接。存在活动连接时提示连接数；没有活动连接时直接停止。
- 删除运行规则先明确确认停止及删除；删除已停止规则不影响其他规则。
- 退出应用的现有确认中加入活动转发和连接数，确认后统一停止。第一版重启应用只恢复配置，默认不自动启动。

## 3. 状态与故障语义

### 3.1 规则状态

| 状态 | 行为 |
| --- | --- |
| 已停止 | 无监听器、SSH 连接和运行凭据 |
| 启动中 | 已原子保留本地监听地址，正在建立 SSH 路径 |
| 等待认证/核对指纹 | 展示具体第几跳；可取消，有等待时限 |
| 已启动 | SSH 路径已认证，监听器可将新连接转发至目标 |
| 正在重连 | 保留本地端口；显示次数、原因及下次尝试时间 |
| 需处理 | 认证、指纹或其他需要用户决定的错误，停止自动重试 |
| 启动失败 | 端口冲突、配置错误等；释放本次启动资源 |
| 停止中 | 拒绝新连接、结束通道、释放 socket 与工作线程 |

启动时直接绑定并持有最终监听器，避免“检查端口空闲后再绑定”的竞态。在尚未就绪、重连或需处理期间，若监听器仍保留，对接受到的新连接立即关闭，不排队保存业务数据。初次启动取消、失败或认证超时，释放监听器。

“已启动”不等于数据库登录成功，也不证明目标服务此刻可用。每个实际本地 TCP 连接才创建目标 channel。目标连接失败更新最近结果并关闭该本地连接，不因此关闭整个隧道或其他正常 channel。

### 3.2 测试连接

运行规则提供显式“测试连接”：通过同一 SSH 路径向配置目标打开一个短生命周期 `direct-tcpip` channel，然后关闭，不发送业务协议数据。测试取消和超时由同一通道调度器处理。

显示“从 B 可建立到 db.internal:3306 的 TCP 连接”和测试时间；不显示“数据库认证成功”或“HTTP 服务正常”。目标可能记录本次短连接。第一版不持续轮询目标、不自动探测数据库类型。

### 3.3 错误定位

错误包含规则 ID、运行代次、发生阶段、涉及的 SSH 跳、时间以及服务端可提供的原因：

- 本地端口被占用或地址无法绑定。
- 本机无法连接 SSH 入口，或 A 无法连接 B。
- 某一跳认证失败、Agent 不可用、主机密钥变化。
- SSH 服务拒绝转发，可能涉及 `AllowTcpForwarding`、`PermitOpen` 或账号密钥限制。
- 目标域名解析/连接失败、连接被拒绝、打开通道超时。
- 并发达到上限、通道关闭或连接中断。

仅按底层实际提供的信息分类。服务端只返回通用 channel-open failure 时，显示“无法建立到目标的转发连接”及原始原因，不猜测究竟是权限、DNS 还是防火墙。错误展示不包含凭据或业务内容。

### 3.4 重连

自动重连仅针对该次运行已成功启动后的可重试网络故障，使用带少量随机抖动的 1、2、4、8、16、30 秒退避，上限 30 秒；稳定运行一段时间后再重置退避。用户停止会取消当前尝试和后续计时。首次启动失败释放资源并由用户重试；关闭自动重连的规则在断线后释放资源，显示“已停止 · 连接中断”。

传输层失效时关闭全部旧业务连接，再按已验证的运行路径重建 SSH。重建后仅接收新业务连接，不重放旧数据，不自动重发 SQL 或 HTTP 请求。客户端需要自行重连；结果不明的业务请求由业务客户端处理。

自动重连继续校验原运行身份的指纹。认证失败或指纹变化进入“需处理”，用户继续操作才开启交互流程；配置变化需要显式重启。若重新认证仍沿用原地址和主机身份，可恢复原监听端口上的服务。

显式配置 SSH keepalive 和平台支持的 TCP 活性探测，另设握手、认证、打开通道和关闭操作时限。不能将 `keepalive_send` 返回成功当作收到服务端回复，也不能仅凭业务连接长时间没有数据判断断线。休眠恢复通过实际 I/O、探测结果和操作时限处理；黑洞网络的发现延迟需要三平台实测。

## 4. 后端实现

### 4.1 与现有代码的衔接

现有 `connection.rs` 已提供连接路径、逐跳认证和已验证身份；`ssh_transport.rs::forward` 已使用 `channel_direct_tcpip` 把跳板通道包装为下一跳 SSH 的传输流。后者服务于单条嵌套 SSH 连接，不直接等同于监听多个本地客户端的转发管理器。

本次先从现有跳板实现抽出共享转发内核，再由跳板适配器和端口转发使用。共用通道打开、非阻塞调度、双向缓冲、背压、半关闭、取消和资源释放，不长期维护两套独立的字节泵。认证和路径规划由既有连接层负责。

新增 `PortForwardManager`，放入应用级 `State`，自行管理规则、监听器、工作线程、运行代次和订阅。不要放入 `State.terminals`，不要借助隐藏终端维持连接。

建议模块：

```text
src-tauri/src/ssh_transport/
  forwarding.rs  共享通道调度器，接收已建立的 SSH 连接
  relay.rs       共享双向缓冲、背压、半关闭和结束处理
  jump.rs        通道到下一跳 SSH 传输流的适配及所有权

src-tauri/src/port_forwarding/
  mod.rs         管理器、生命周期和配置协调
  model.rs       规则、运行快照、状态、事件和错误
  store.rs       SQLite 配置存储
  commands.rs    Tauri 命令、调用窗口校验
  worker.rs      SSH 路径建立、本地监听、调用共享转发内核和重连
  tests.rs       状态与真实协议测试

src/
  PortForwardingApp.tsx
  PortForwardEditor.tsx
  PortForwardDetails.tsx
  portForwardApi.ts
  port-forwarding.css
```

现有 `InteractiveProvider` 和 `Interaction` 依赖 `TerminalStream`，需要抽出与终端输出无关的认证事件接收接口。终端用适配器保留当前行为，隧道用独立的认证事件通道。底层连接器返回 `SshConnection + SharedContext`，不启动 PTY、不执行 shell 集成，也不创建终端历史。

可从发起操作的已连接会话获取经后端验证的 `SharedContext`，仅在本次启动的配置和路径与上下文匹配时复用当次运行凭据；仍创建新的 SSH 物理连接并核对每跳指纹。服务器配置已经改变或没有可复用上下文时独立认证，不把旧终端的连接目标当作新配置。不要从其他窗口按前端提交的 identity 任意提取凭据。

### 4.1.1 跳板与端口转发的共同基础

依赖方向明确为：连接路径构建器通过跳板适配器使用转发内核；`PortForwardManager` 调用连接路径构建器获得最终 SSH 连接，然后使用同一转发内核连接业务目标。转发内核只接收已经建立的 SSH 连接、目标地址、本地流和取消信号，不读取服务器配置、不发起路径构建、不调用业务管理器。

| 层次 | 职责 | 共享范围 |
| --- | --- | --- |
| SSH 传输与转发内核 | socket、channel、收发调度、背压、取消、关闭 | 跳板和端口转发共用 |
| 连接路径与认证 | 直连/跳板、逐跳指纹、认证、已验证身份 | 终端、文件、Docker、日志、端口转发共用 |
| 跳板适配器 | 把父 SSH 的 channel 包装为下一跳 SSH 的传输流 | 由每次业务连接路径持有 |
| 端口转发管理器 | 用户规则、本地监听、状态、重连和界面订阅 | 仅用户端口转发功能使用 |

跳板 A → B 的具体过程：建立并认证 SSH A；共享内核在 A 上打开到 B 的 SSH 端口的 channel；跳板适配器通过内部 stream pair 把此通道交给新的 SSH B Session；随后正常执行 B 的握手、指纹检查和认证。复用现有 Unix socket pair/Windows 临时回环配对机制，不为跳板创建用户可连接的持久本地监听端口。

端口转发的具体过程：建立并认证选定路径（如 A → B）；监听用户配置的本地地址；每接受一个客户端，就让最终 SSH B 上的共享内核打开到业务目标的 channel 并转发数据。内核可接收单条内部流或多条外部客户端流，流的来源不改变字节转发规则。

共享代码与独立生命周期同时保留：

- 跳板的内部通道由使用它的 SSH 连接持有，正常结束或取消时随连接释放，不登记为用户端口规则，不在管理窗口提供独立停止操作。
- 用户端口规则由 `PortForwardManager` 持有；停止规则只结束该规则拥有的整套 SSH 路径及其业务连接。
- 第一版不把终端、文件任务和多个规则合并到一个物理 SSH Session；停止一条规则不会切断其他功能的跳板连接。
- 转发内核报告失败并结束失效流，不自动把旧字节流接到新连接。跳板 A 断线后，嵌套的 SSH B 也失效，拥有该路径的业务层决定是否重新建立完整路径。端口规则可重连整条路径，终端继续遵循既有会话重连行为。
- 业务层传入流量归属，保留最终 SSH 层计量和跳板外层不重复累计的口径。共享内核不把内部跳板数据另记为用户端口转发流量。
- 保留现有 `ssh_transport::forward` 的外部行为，可将其逐步改成调用共享内核的适配入口，降低对已有业务的影响。

若先做内核迁移，仍保持当前只支持单层跳板；本次不顺带增加多层跳板或跨业务连接池。

### 4.2 连接与并发模型

一条运行规则对应一个 worker，以及一套独立 SSH 路径。每个本地客户端对应一个 `channel_direct_tcpip(targetHost, targetPort, ...)`，同一规则内复用 SSH 认证和传输。不同规则不共享物理 SSH Session，便于隔离停止、配置变化、故障和流量归属。

最终 SSH Session 由共享转发内核所在的一个 worker 独占，以非阻塞方式调度所有 channel。端口管理层通过消息提交新流或控制请求，不并发读写该 Session。当前连接函数返回时会设置阻塞模式，隧道接管前必须显式切回非阻塞。不能将 Session/Channel 克隆给多个阻塞线程并假定它们可独立运行。

使用跨平台 readiness 等待机制（可选小型 `polling` 依赖）处理监听 socket、本地 socket、SSH 传输 socket 和停止唤醒；根据 `block_directions` 注册需求，并设置最大等待期限。`SshConnection` 需暴露用于 readiness 注册的借用句柄，SSH 传输读写仍只能通过 libssh2，不能另读底层 socket。每轮等待前先推进可执行操作并消化库内已缓存的数据，避免 socket 无新事件时遗漏可读 channel。跳板已有桥接 worker 保留其所有权。避免逐连接每几毫秒轮询造成空闲 CPU 和线程数增长。

调度要求：

- 双向各自有界缓冲，正确处理短读、短写、`WouldBlock/EAGAIN`。
- 某次 SSH 写入在 EAGAIN 后保持底层分配地址、偏移和长度，直到该次调用完成；其他连接的数据不能覆盖待写缓冲。
- 按 Session/Channel API 的挂起状态串行推进 SSH 调用；每轮按连接设置工作量预算，避免大流量连接长期占用调度。
- 同一 SSH Session 同时只允许一个尚未完成的 channel-open 操作，其余请求进入有界队列；等待过程中继续推进可执行的数据转发。
- 本地客户端在 channel-open 挂起期间断开，保留打开操作的归属，结果到达后关闭相应 channel，不把迟到结果交给下一客户端。
- libssh2 的挂起操作若超时且无法安全取消，需要重建整条规则的 SSH 连接；明确报告同规则既有连接会中断。不能假装已取消并复用未知协议状态。
- 本地读 EOF 后先发送完缓冲，再向 SSH channel 发送 EOF，同时继续接收响应。远端 EOF 后发送完收到的数据，再关闭本地写方向。两侧半关闭完成才正常释放。
- 背压只暂停对应方向的新读取，不丢字节。单条业务连接错误通常只关闭该连接；底层 SSH 传输失效才影响整条规则。
- 停止可唤醒所有等待，在有界时间内释放资源。正常 channel 关闭与强制终止分开；强制终止先关闭底层 socket，使后续释放不无限等待。

初始工程预算建议：每规则最多 64 条本地连接（含等待连接），等待打开通道的队列最多 8 条，应用级最多 256 条本地连接；每连接每方向应用缓冲上限 64 KiB。超限快速关闭新连接并给出计数。以上是待压测确认的初始值，libssh2 自身窗口/缓冲和 SSH 跳板也占内存，不能用应用缓冲容量宣称总内存上限。

一条 SSH TCP 连接仍存在共享带宽和传输层队头阻塞；首版不承诺连接间完全性能隔离。数据库连接池和浏览器并发是必须实测的场景。

### 4.3 配置存储与引用

建议使用应用数据目录中的 `port-forwards.sqlite` 保存规则，保持现有 `servers.db` 结构和旧库处理方式。隧道表不复制服务器密码、私钥内容或认证口令。

规则字段：`id`、`name`、`ssh_server_id`、`listen_address`、`listen_port`（NULL 表示自动分配）、`target_host`、`target_port`、`auto_reconnect`、`web_scheme`（可空）、`revision`、创建/修改时间。

运行态字段留在内存：`run_id`、`generation`、配置版本与路径快照、实际监听地址、状态、活动连接数、重连时间、最近错误和计数。规则列表每次订阅先返回完整快照，再发送带序号的增量；界面重建不会重新启动 worker。

跨数据库引用由应用的 `configuration` 协调锁维护：保存规则校验服务器存在，删除服务器检查规则引用，启动/编辑/删除避免竞态。被规则引用的服务器需先修改或删除规则才能删除；活动规则还检查其启动快照涉及的跳板。外部修改或重建服务器数据库后，保留失效规则并提示重新选择服务器，不自动绑定同名服务器。重建数据库前检查活动隧道。

配置更新用 revision 检查，避免多个窗口覆盖新修改；停止完成前不发布新一代运行。认证回答和异步结果均绑定 `rule_id + run_id/generation + challenge_id`，过期消息无法启动隧道或改变目标。

### 4.4 IPC、窗口和退出

提供列出、保存、删除、启动、停止、测试目标、回复认证和订阅状态等显式命令。前端只发送配置和控制操作，业务流量始终在 Rust/socket 层，不经过 Tauri IPC 或 React。

转发管理窗口加入 Tauri capability。后端按真实调用窗口和登记代次校验权限：规则修改及认证在管理窗口处理；主工作区可打开管理窗口并订阅摘要。认证挑战只发给当前登记的交互窗口，普通状态订阅不包含凭据。管理窗口销毁会注销订阅、作废其挑战，运行中的隧道继续。

应用退出先设置 stopping，取消全部启动/重连，再关闭监听器和业务连接，等待 worker 收尾，最后刷新通信账目。不能在终端数量为零时漏掉仍运行的隧道。状态订阅、事件日志和 UI 刷新均有界，数据速率更新约每秒一次即可。

### 4.5 流量与事件

新增 `TrafficPurpose::PortForward` 及对应统计分类，接入现有应用生命周期的通信账目。总体统计延续现有口径：目标 SSH 层实际读写的字节，含该层 SSH 开销，跳板外层不重复累计。

每条规则另记录成功转交的业务字节：本机客户端 → 目标、目标 → 本机客户端。两种口径清楚命名，不相加、不把业务量当网卡流量。成功写入本机 socket 也不等于业务客户端已经消费数据。

事件仅记录启动、停止、断线、重连、认证阶段、目标连接失败和汇总计数；不记录 SQL、HTTP 内容或转发载荷。第一版事件使用每规则最近 200 条内存环形记录，重复错误合并计数，避免每个短连接写入一条长期日志。

## 5. 使用边界

- SSH 加密保护本机至最终 SSH 服务器的路径；最终服务器至目标服务使用目标自身协议。应用可以继续使用数据库 TLS、HTTPS 等端到端加密。
- 本地回环监听允许本机其他进程连接，SSH 认证不代替数据库或 Web 服务自己的账号认证。
- HTTP Host、HTTPS SNI、证书校验和重定向保持业务客户端原行为。依赖内网域名的站点可能需要应用级域名配置；端口转发不改写网页响应或自动关闭证书校验。
- Redis Cluster、MongoDB 副本集等可能向客户端返回其他内网节点地址。只映射一个端口不保证整个集群可用，应使用客户端支持的连接模式、多条明确映射或后续的代理能力。
- 一条规则只能连接固定目标。SOCKS5 若在后续加入，应单独设计域名解析、协议响应、连接限制和浏览器使用流程；它不是本地转发表单上的一个未完成选项。

## 6. 实施顺序与验收

### 第一步：验证底层转发

先从已有跳板字节泵抽出共享转发内核，以单通道适配保持跳板外部行为，完成已有终端、文件、Docker 和日志路径回归；再完成不依赖界面的本地监听 → SSH channel → 测试 TCP 服务链路，验证直连、单层跳板、并发、双向吞吐、半关闭、取消与空闲资源占用。重点验证当前 libssh2 版本的多 channel 挂起/恢复语义，再定最终调度细节。

### 第二步：补齐生命周期

实现独立认证、PortForwardManager、配置存储、运行快照、状态机、重连和应用退出。此阶段要求无需终端也能运行，停止/重启没有迟到结果复活连接。

### 第三步：接入界面

完成管理窗口、规则编辑、服务器快捷入口、复制地址、测试连接、错误定位和全局运行摘要，接入现有通信统计及退出确认。

### 必须通过的验证

| 场景 | 验收结果 |
| --- | --- |
| 既有跳板功能回归 | 终端、SFTP、Docker、日志逐跳认证和传输行为保持正确 |
| 跳板与端口转发同时运行 | 停止规则不影响其他业务；外层跳板不重复计量 |
| 目标域名仅远端可解析 | 本机无需解析，直连及跳板路径均成功 |
| 目标 `127.0.0.1` | 访问最终 SSH 服务器自身服务 |
| 真实 TCP 数据 | 双向字节精确一致，二进制/大流量/短写不丢失 |
| 半关闭 | 客户端发完请求关闭写端后仍能完整收到服务端响应 |
| 并发客户端 | 多个 channel 隔离、无串流，慢连接不饿死其他连接 |
| channel-open 挂起 | 已有连接可继续；取消/超时/迟到结果处理正确 |
| 无 shell 权限账号 | 允许转发时仍可使用，不创建 PTY 或远端进程 |
| 转发权限限制 | 实测 OpenSSH 的 AllowTcpForwarding、PermitOpen 和密钥限制 |
| 本地端口冲突 | 保留其他进程，提示冲突；自动端口确实持有同一 socket |
| IPv4/IPv6 | 绑定、地址复制、目标 IPv6 和 IPv6 不可用时的错误正确 |
| 断网/黑洞/休眠 | 原业务连接结束，退避重连；恢复后新连接可用 |
| 主机密钥/认证变化 | 停止自动重试并需要用户处理，不接受过期回答 |
| 多窗口与标签关闭 | 关闭、刷新、迁移终端和管理窗口不误停运行隧道 |
| 修改配置/重复启动 | 幂等，目标不热切换，旧回调不影响新一代运行 |
| 停止与退出 | 监听器、channel、工作线程和凭据生命周期正确结束 |
| 空闲和压力运行 | 没有随连接历史增长的资源泄漏，CPU/内存符合预算 |

测试分三层：Rust 状态/缓冲测试；隔离 OpenSSH 容器配合 echo、HTTP 和延迟/半关闭测试服务的真实协议联调；浏览器模拟 IPC 的界面测试与 Windows/macOS/Linux 原生桌面验收。现有 Paramiko 跳板 fixture 可补充可控故障，但不能替代真实 OpenSSH 权限和并发行为验证。

## 7. 后续方向

完成本地转发并验证稳定性后，按实际使用需求选择：SOCKS5 动态代理（访问多目标及内网域名）、规则分组与一键启动、可选应用启动时恢复、局域网共享监听、远程端口转发。每项独立设计权限、生命周期和错误行为，不提前把所有模式堆进第一版表单。
