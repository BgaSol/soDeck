# 功能设计方法与完整生命周期要求

整理日期：2026-11-08。状态：设计提案，供后续功能采用；不代表相关实现已经完成。本次实例见[关闭、退出与重启设计](plan-close-lifecycle.md)。既有产品边界以 [AGENTS.md](../AGENTS.md) 和[架构文档](architecture.md)为准。

## 1. 对需求的理解

用户已经明确：功能必须先规划设计；生命周期必须完整；不能随着组件增加不断积累同类缺陷；不能采用只处理当前表现的补丁式修改。

据此推断，用户希望 SoDeck 具备以下特征。这些是对目标的解释，不是用户逐字指定的实现方案：

- **功能交付是完整行为。** 能创建、能使用，也要能取消、失败、恢复、关闭和清理；成功路径跑通只是其中一部分。
- **核心承担稳定的共同规则。** 新插件接入已有连接、资源和生命周期契约，核心不随插件名单不断增加业务判断。
- **交互数量受到控制。** 新组件主要证明自己符合公共契约，不依赖为每两个插件补一组特殊兼容逻辑。
- **设计能直接约束代码和验收。** 对每个状态说明谁持有、何时改变、允许做什么、如何结束；测试证明这些约束，而非仅检查按钮和页面存在。
- **结构调整与问题大小匹配。** 可以为完整问题调整既有职责和调用边界；通用框架、发布流程和生产依赖只有真实需要时才增加。
- **问题可以追踪。** 出错时能知道哪个操作、对象和阶段没有结束，能判断重试是否安全；不会把“请求已发出”显示成“已完成”。

不能承诺以后没有缺陷。设计目标是让共同规则集中、缺陷可稳定复现、一次修正覆盖同类入口，并限制组件增长带来的额外耦合。

## 2. 一次功能设计需要回答的问题

先写用户行为和可验收结果，再确定接口及文件改动。涉及状态、异步或资源的功能至少回答下表；纯展示、静态文案等简单改动可以标明不适用，按影响缩减篇幅。

| 设计内容 | 必须回答 | 可评审产物 |
| --- | --- | --- |
| 场景与边界 | 谁在何种状态下做什么？完成后看到什么？本次到哪里结束？ | 代表场景、范围和明确的完成条件 |
| 对象与归属 | 创建了哪些对象和资源？唯一管理者是谁？引用者是谁？ | 归属表，包括内存对象、异步请求、进程、连接与落盘数据 |
| 生命周期 | 如何创建、就绪、使用、隐藏、迁移、失败、恢复、停止和释放？ | 适用于本功能的状态转换表，区分可见性与实际运行状态 |
| 不变量 | 无论调用顺序怎样，哪些事情都不能发生？ | 可转成断言的规则，例如关闭后旧请求不能登记新资源 |
| 异步与并发 | 重复请求、迟到结果、同时关闭/移动/重连怎样处理？ | 接受请求和提交结果的检查点、去重与取消边界 |
| 失败与恢复 | 每个异步步骤失败后处于什么状态？能否撤销？谁重试？ | 失败处理表、期限与未知结果的处理方式 |
| 接口与兼容 | 哪一层有权改变状态？已有调用者如何迁移？旧插件怎样运行？ | 最小调用协议、现有调用点清单、兼容策略 |
| 验收与交付 | 哪些证据可以证明行为完整？哪些需要真实系统？ | 回归矩阵、实施顺序、源码/界面/原生包验证边界 |

所有会改变状态的入口都要找到，包括用户按钮、系统事件、插件 RPC、后台定时器、故障恢复、更新和测试入口。不能只设计最容易观察到的一条路径。

## 3. 生命周期设计的具体规则

### 3.1 一个事实有一个管理者

核心负责宿主生命周期、连接、资源登记及清理；插件负责业务状态和任务语义；前端负责输入与呈现。前端可以显示“正在关闭”，但不能自行宣布核心资源已经释放。

配置状态、运行状态和展示状态分别表达。例如“已保存为关闭插件”“插件进程仍在运行”“面板未显示”是三个不同事实。插件启停仍按既定规则在重启后生效。

### 3.2 归属要覆盖创建过程

资源在请求被接受时就登记归属，不能等网络连接、进程或后台任务已经创建后才登记。父对象进入关闭阶段后，已有创建任务要么安全完成并被收尾，要么取消并清理；迟到结果不能重新注册到已关闭的父对象。

复用 `pluginInstanceId`、`viewId`、完整 `Context`、请求编号等现有身份。只有现有身份无法区分真实重试或新一轮操作时才增加操作编号，不为每层再造一套身份体系。

### 3.3 为每个退出分支定义终点

成功、取消、失败、超时、连接丢失和进程异常退出都要有明确处理者。发出取消信号不代表任务已经结束，任务结束也不代表所有资源已经释放。

撤销关闭不等于撤销已提交的远程写入。结果未知时保留这个事实，禁止把它当失败后自动重放。资源释放开始后发生错误，应继续清理或明确保留未完成状态，不能假装恢复了原来的会话。

### 3.4 读状态与改变生命周期分开

快照、刷新和绘制读取核心已提交的状态。创建、默认初始化、自动恢复和销毁由生命周期入口触发。读取次数和前端刷新时机不应决定后台任务的生死。

异步操作在开始和结果提交时都核对归属及当前阶段。跨进程等待不持有核心状态锁；最终检查与状态提交通过短临界区完成，不能依赖多个分离的布尔检查避开竞态。

### 3.5 共同规则有共同验收

公共生命周期、资源归属、迟到请求和重试由核心契约测试覆盖；每个插件验证自己的保存、取消、释放和业务副作用。终端、文件、网络、系统状态承担不同代表场景，新增插件复用同一组接入要求。

共享契约不能代替真实组合验收。保留有代表性的多窗口、多组件共同工作场景；出现新的交互关系时再增加专项，不穷举全部插件组合。

## 4. 从方案到代码的顺序

1. **核实现状。** 复现问题，检查实际调用链；分开记录已证实的缺陷、源码推导的风险和尚未验证的情况。
2. **定义完整边界。** 写场景、对象归属、状态转换、不变量和失败矩阵。检查正常使用、后台工作和退出是否采用同一套规则。
3. **检查设计反例。** 主动安排刷新、重复点击、另一窗口操作、断线、保存失败和迟到回包，观察规则是否仍成立。
4. **确定最小实现。** 优先调整现有模块和契约，列出所有调用者、测试夹具、配置及文档影响。未解决关键归属或不可逆边界前不开始依赖它的实现。
5. **实现并证明。** 用可控同步点复现竞态，再实现共同规则；迁移所有入口后移除旧的绕行路径。每个提交解决一个完整主题，跨入口迁移未完成的代码不能作为已完成版本交付。
6. **记录实际交付。** 方案维护目标，实施记录维护本次证据与限制，版本说明维护发布结果；更新受影响文档，避免复制多份验收进度。

## 5. 可复用的功能设计提纲

新建对应 `docs/plan-<功能>.md`，按下面的顺序写清楚即可；表格或图只在有助于理解时使用。

1. 目标、代表场景、本次范围、完成后的用户行为。
2. 现状证据、已知约束、尚未确认的假设。
3. 对象和资源归属、生命周期、始终成立的规则。
4. 主流程、跨窗口/后台流程，以及每个失败、取消、超时分支。
5. 接口、并发与重试、资源回收、持久化、平台和版本兼容。
6. 代码落点、调用者迁移顺序、回归用例和交付条件。

“生命周期已完整”要能回答：每个对象从哪里来、现在归谁、每种结束事件由谁处理、何时确认释放、旧请求之后会怎样。如果其中一个问题只能回答“正常应该不会发生”，方案就还没有闭合。
