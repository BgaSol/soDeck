# SoDeck 本地诊断记录：功能与实现设计

状态：待用户确认；本文只定义实施方案，尚未开发。更新日期：2026-10-21。

## 1. 目标和本期范围

用户要求：只做本地诊断；别人可以快速把磁盘上的日志拷贝给开发者；日志应足够详细，可以回查故障过程。设计确认后才开始开发。

核心交付：**默认记录详细的关键过程，保存在固定目录；整个目录可直接复制，也可一键生成 ZIP；开发者收到后先读摘要，再按操作编号查看完整时间线。**

本期包含记录器、前后端接入、操作关联、异常捕获、磁盘轮转、环境摘要、错误索引、设置入口和本地打包。上传、分享授权、网络接收服务、统计平台、复杂日志阅读界面和远程调试均不在本期。

本版细化并替代先前的本地诊断提案：默认容量建议调整为 100 MiB，以容纳关键阶段记录；诊断使用本地应用数据目录；打包以整次运行的留存文件为单位，优先保证上下文完整。

## 2. 用户怎样把日志交出来

### 2.1 应用可以打开

推荐步骤：**系统设置 → 本地诊断 → 打包日志 → 保存 ZIP → 用户自行把文件交给开发者。**

打包默认选择“最近 24 小时内有活动的运行”，包括这些运行的全部留存分片，以及仍保留的最近一次异常结束运行。可改选“本次运行”或“全部保留日志”。不要求用户理解日志文件或逐个选择模块。

打包完成后显示“已保存”，提供“在文件夹中显示”。若任何选中文件缺失或无法读取，必须标注不完整，不能只显示无条件的成功。

如果不想打包，点击“打开日志目录”，直接复制整个 `diagnostics` 文件夹即可。也能只复制某次运行的整个子目录，但不推荐只拷 `errors.jsonl`，因为它没有完整上下文。

### 2.2 应用打不开

位置固定，在 README 和磁盘目录内的说明文件中记录。采用 Tauri 的 `app_local_data_dir()/diagnostics`；以下是当前应用标识 `com.sshworkspace.desktop`、没有目录覆盖配置时的默认路径：

| 系统 | 默认目录 |
| --- | --- |
| Windows | `%LOCALAPPDATA%\com.sshworkspace.desktop\diagnostics` |
| macOS | `~/Library/Application Support/com.sshworkspace.desktop/diagnostics` |
| Linux | `$XDG_DATA_HOME/com.sshworkspace.desktop/diagnostics`；未设置时使用 `~/.local/share/com.sshworkspace.desktop/diagnostics` |

Windows 用户可把路径粘贴到资源管理器地址栏。设置显示实际解析路径，提供“复制路径”，不在安装目录中找日志。

初始化很早就失败、或正常目录不可写时，尽力使用系统临时目录下的 `SoDeck-diagnostics/<运行目录>/` 保存最小启动线索，并在原生启动错误提示中显示实际位置。临时目录可能被系统清理，不能保证长期保留。两个目录都无法写入时明确告知。

路径依据当前仓库的应用标识及本机缓存的 Tauri 2.12.3 路径实现核对，实施后仍需在三个平台的安装包中验证。

## 3. 磁盘文件设计

```text
diagnostics/
  README.txt
  latest.json
  runs/
    2026-10-21T091500Z_a1b2c3d4/
      summary.txt
      session.json
      events-0001.jsonl
      events-0002.jsonl
      errors.jsonl
      panic.jsonl                  # 仅在捕获到 panic 时产生
    2026-10-21T103000Z_e5f6a7b8/
      ...
```

- `README.txt`：说明整个目录可复制，如何查阅，保留期限和完整性边界，不包含机器真实路径。
- `latest.json`：本地运行索引，只使用相对路径；多实例时列出最近运行及状态，不假定唯一进程。
- `summary.txt`：普通文本摘要，包括应用版本、系统环境、运行时间、正常/未确认结束状态、错误计数、最近错误、记录缺失和已删除分片。开发者先打开它。
- `session.json`：机器可读的运行元数据、格式版本、构建标识、记录策略、当前覆盖区间和计数。周期性原子更新，记录截至哪个事件序号。
- `events-*.jsonl`：完整的已保留诊断记录，每行一个 JSON 对象，UTF-8，可直接用文本编辑器、脚本或本地分析工具读取。
- `errors.jsonl`：WARN/ERROR 的精简索引，包含发生时间、错误码、操作编号和对应事件序号；完整错误链仍在 events 中。重复错误用次数更新事件表示，控制索引大小。
- `panic.jsonl`：独立的、受大小限制的应急记录，不依赖正常日志队列；不承诺能覆盖所有原生崩溃。

文件按运行归档、按大小分片，不按窗口或业务模块散落。每次运行使用随机唯一 ID，短 ID 只用于目录可读性，完整 ID 保存在元数据内。日期使用 UTC 并标明 Z，避免时区和重名问题。

除了事件分片外，其余文件都有独立上限：摘要最多 64 KiB、运行元数据最多 64 KiB、错误索引最多 1 MiB、应急记录最多 256 KiB。所有文件都计入日志区总容量，索引截断时显示计数及时间范围。

**原始目录内的文件从写入时就遵守同一套数据边界，不依赖“导出时才脱敏”。因此直接复制文件夹与使用 ZIP 的内容安全规则一致。**

## 4. 设置界面

```text
本地诊断
自动记录应用运行过程和错误，所有记录仅保存在此设备。

记录状态：正常
当前运行：2026-10-21 17:15:00
已保留：3 次运行 · 18.6 MiB
保留规则：最近 7 天，最多 100 MiB；达到任一限制即清理旧记录
日志位置：<系统实际解析的路径>                       [复制路径]

[打开日志目录]  [打包日志…]  [清理日志]
```

基础记录固定默认开启，独立于开发者模式；不增加分享开关，也不要求普通用户选择日志等级。记录状态包括正常、部分记录丢失、降级到临时目录、记录不可用。

“打包日志”弹出简单范围选择及保存对话框，默认文件名 `SoDeck-diagnostics-20261021-173000.zip`，时间使用用户本地时间，包内明确时区。显示生成进度，允许取消；取消或失败清理未完成文件，成功后原子落到目标路径。覆盖已有文件由保存对话框明确确认。

“清理日志”需确认清理范围：应用管理的诊断文件和诊断暂存；不删除终端历史、容器日志、服务器配置和用户之前导出的 ZIP。当前进程清理后继续记录，当前操作编号保留，并标明此前上下文已清理。

重要错误提示增加可展开的“诊断信息”，可复制操作编号和错误码；不强行在所有普通提示里显示技术字段。异常边界中的兜底界面也保留打开目录和打包入口，只依赖独立诊断状态。

## 5. “足够详细”的具体标准

### 5.1 默认留下关键操作的全过程

首版默认记录业务生命周期、选定模块的内部阶段、结果、关键分支和错误。INFO 记录操作摘要，DEBUG 记录排查所需的阶段细节，WARN/ERROR 记录不同性质的异常。这里的 DEBUG 是明确选择的安全事件，普通发布版本也写入，不需要用户提前开启模式。

不能仅记录 `连接失败`、`操作失败`。至少要知道：

1. 当时的应用版本、构建和系统环境。
2. 用户发起了哪类操作，来自哪个窗口，关联哪次连接或任务。
3. 依次进入哪些阶段，哪些完成，最后停在哪一步。
4. 每阶段耗时、实际超时配置、重试次数和触发重试/取消的原因。
5. 稳定错误码、原生数值错误码、可用错误链和代码位置。
6. 程序之后如何处理：展示失败、保留任务、等待用户、结束连接或允许重试。

### 5.2 必须接入的模块

| 模块 | 本期事件覆盖 |
| --- | --- |
| 启动/退出 | 构建、系统、设置加载、各存储初始化、窗口创建、启动完成、退出开始/结束、上次未确认正常结束 |
| SSH/跳板 | DNS、TCP、跳板通道、SSH 握手、主机密钥核对结果、认证方式与尝试、PTY/shell 创建、连接就绪、中断、取消、重连 |
| 窗口/会话 | 创建、加载、关闭、刷新、迁移开始/提交/回滚、连接归属与代次变化 |
| 文件/传输 | 请求、校验、入队、开始、阶段变化、冲突策略、汇总进度、取消、重试、完成/失败及结果是否已确认 |
| Docker/NetBird/转发 | 检测与关键命令的开始/结束、能力或权限判断、状态变化、失败阶段、执行结果未知 |
| 终端/剪贴板 | 终端会话生命周期；复制/粘贴请求结果、策略判断和大小区间；不记录正文或逐键输入 |
| 历史/容器日志采集器 | 启停、恢复、追赶、队列溢出、落盘/索引失败；不记录采集到的正文 |
| 本地存储/设置/更新 | 读写、迁移、冲突、失败；更新检查/下载/签名校验/安装阶段和耗时 |
| 前端/后端异常 | 已捕获的关键业务错误、全局 JS 错误、Promise 未处理异常、React 异常边界、任务退出、可捕获 panic |

实施按模块逐个接入并勾选覆盖清单。只安装统一记录器不算功能完成；每项至少具有可关联的开始、阶段或决策、终结结果/异常，短查询无需制造无意义阶段。

高频流量有单独规则：终端字节流不记录；资源轮询成功、传输进度等每 30 秒汇总一次，状态变化和首次失败立即记录；重复错误保留第一条完整事件，同组后续按 30 秒汇总次数、最后时间和最后结果。用户独立发起的操作保留自己的结果，不能被后台错误合并吞掉。

### 5.3 事件字段

| 字段 | 含义 |
| --- | --- |
| `schemaVersion`、`tsUtc`、`seq` | 格式版本、接收事件的 UTC 时间、后端分配的进程内序号 |
| `runId`、`processId`、`buildId` | 本次启动、进程和构建；没有持久化设备标识 |
| `level`、`module`、`event`、`message` | 等级、模块、固定事件名、可读的安全摘要 |
| `traceId`、`spanId`、`parentSpanId` | 一次操作、当前阶段与父阶段 |
| `windowRef`、`connectionRef`、`generation`、`taskRef` | 本次运行内的对象别名与连接代次 |
| `stage`、`durationMs`、`timeoutMs`、`attempt` | 阶段、单调时钟耗时、超时设置和尝试序号 |
| `outcome`、`errorCode`、`nativeCode`、`causes` | 结果、稳定错误码、底层数值码和经过白名单处理的原因链 |
| `source`、`stack` | 仓库相对代码位置，以及可获得、已清理的堆栈 |
| `details` | 当前事件类型允许的附加字段，不能任意序列化对象 |

公共环境信息放在 session 中，每条事件仍携带定位所需的 runId/buildId。前端批量事件另保留来源顺序和前端相对时间；后端接收顺序不伪装成真实发生顺序。前后端因果关系靠 trace/span 关联，不能直接相减不同进程的单调时钟。

## 6. 保留诊断价值，同时避免记录工作内容

本地日志会被直接交给开发者，所以从源头采用字段白名单，所有输出文件使用同一策略。

**保留**：认证方式、地址类型（域名/IPv4/IPv6）、解析结果个数、候选序号、跳板层数、权限判断、实际超时、系统错误码、SSH 库错误码、SQL 错误类别、命令模板 ID、远端退出码、字节数量/区间、关键设置的允许字段、代码位置和安全错误链。

**不保留**：密码、私钥、口令、令牌、终端输入输出、剪贴板正文、文件正文、容器/服务日志正文、完整命令、原始 stderr/stdout、完整环境变量、配置/数据库对象、真实服务器名称/地址/账号/路径/指纹、联系信息和设备机器码。

本次运行内生成随机目标/窗口/任务别名，跨事件可关联，真实映射只在内存。既有业务 ID 若编码了地址、路径或身份信息，必须重新映射，不能认为“叫 ID 就安全”。

未知错误也不能简单丢成“未知错误”：保留来源库、类别、数值码、发生位置和阶段；自由文本仅在经过专用安全转换器时记录。无法安全保留的文本标明 `detailOmitted`，不能把正则替换当作唯一保护。

## 7. 实现架构与现有代码衔接

### 7.1 Rust 统一持有记录器

新增 `src-tauri/src/diagnostics/`，建议拆分为：

| 文件 | 职责 |
| --- | --- |
| `mod.rs` | 生命周期、服务状态、类型化事件入口 |
| `event.rs` | 事件 schema、操作/阶段上下文、对象别名 |
| `redact.rs` | 各类错误及字段白名单转换，输出长度限制 |
| `writer.rs` | 有界后台队列、序号、JSONL 写入、轮转、计数 |
| `store.rs` | 运行目录、元数据、目录维护锁、配额、保留期清理 |
| `snapshot.rs` | 刷写屏障、快照范围、打包、取消与清理 |
| `commands.rs` | 状态查询、打开目录、打包、清理、前端事件入口 |
| `panic.rs` | 最小启动缓冲、panic hook、应急文件 |

优先复用现有 `serde_json`、`uuid`、标准库队列、`tempfile`、`rfd`、opener 和 clipboard 插件。增加 ZIP 写入的直接依赖（与当前锁文件兼容，启用必要压缩能力），以及维护目录所需的跨平台文件锁实现。无需接入网络日志 SDK。

记录入口使用类型化 `DiagnosticEvent`，而不是接收任意 `format!("{:?}", object)`。不全局开启第三方库的 verbose 日志，不重定向全部 stdout/stderr，以免业务输出和敏感参数进入文件。

### 7.2 启动与退出

在 `lib.rs::run` 开始安装最小内存启动缓冲和 panic hook；取得 Tauri 路径后，第一时间建立独立 `DiagnosticsState`，早于设置、业务数据库及窗口创建。若正常路径失败，按第二节降级；没有文件前发生的安全启动事件随后补写。

现有 `.run(context).expect(...)` 改成可诊断的失败处理：记录启动阶段、刷新能够写入的文件、用原生错误提示给出实际路径。不能只让发布版在无控制台的 Windows 上退出。

保持现有未保存内容、进行中任务等退出检查；只有实际接受退出后才写结束标记并有界刷写。不能在被用户取消的退出请求上标记正常结束。

日志状态独立于包含服务器数据库的现有 `State`，设置诊断入口和错误兜底尽量不依赖业务初始化成功。

### 7.3 前端统一入口

新增 `src/diagnostics.ts` 及 `src/diagnosticsApi.ts`：

- `main.tsx` 在渲染前安装 `error`、`unhandledrejection` 处理；尽早加载的入口捕获能力需验证，早于入口执行的资源故障标注为覆盖限制。
- `WindowErrorBoundary.componentDidCatch` 记录清理后的异常及组件堆栈，兜底页面保留日志入口。
- 为关键 `invoke` 增加 `invokeDiagnosed` 包装，记录命令名、关联上下文、耗时和安全结果，不记录完整 args/result。
- 对带后台结果的操作，区分“命令已接受”和“任务已完成”，后者由真实任务事件决定。
- 普通前端事件短时批量送入 Rust；异常立即尝试发送。前端队列也有硬上限，发送失败不递归记录自身失败。
- 每个窗口由后端确认身份并分配别名，不相信前端传入的窗口名。控制事件大小、条数和速率；浏览器预览环境明确无本地诊断服务，不伪装已保存。

### 7.4 操作上下文与错误信息

每次用户动作创建随机 `traceId`，通过可选的诊断上下文参数传给后端；后端校验格式及窗口归属，没有上下文时自行创建。内部阶段生成 span。`spawn_blocking` 和 `std::thread::spawn` 显式带入上下文，不能只用线程局部变量。

扩展 `AppError` 的可选错误码/操作编号供界面关联；内部增加不自动序列化到界面的诊断原因结构。保持现有 message 和用户交互兼容，禁止把包含服务器信息的 `AppError::at` 结果原样落盘。

在错误被转换成文字之前保存 `io::Error::raw_os_error`、SSH ErrorCode、SQLite 主/扩展错误码等。当前部分 `AppError::new(kind, error)` 会提前丢失类型信息，重点调用点改用显式转换器；转换器不自动记录错误，终结边界负责写一次，防止层层重复。

在 `connection.rs::connect_metered` 及 `ssh_transport` 的解析、TCP、转发和握手阶段埋点，覆盖交互连接和后台已验证连接。接入现有 provider progress 但不只依赖它：目前它不足以记录所有阶段成功、耗时和原生原因。

### 7.5 拟新增命令

| 命令 | 用途 |
| --- | --- |
| `get_diagnostics_status` | 实际目录、当前运行、占用、保留范围、记录健康状态 |
| `open_diagnostics_directory` | 先请求刷写，再打开固定诊断目录；失败说明，不允许任意目录参数 |
| `append_frontend_diagnostics` | 接收严格校验的前端事件批次 |
| `export_diagnostics` | 原生保存对话框、选择本地运行范围、创建 ZIP，返回实际结果 |
| `cancel_diagnostics_export` | 取消本进程的导出任务 |
| `clear_diagnostics` | 按用户确认执行诊断范围清理 |

清理/导出参数仅接受枚举、后端生成的运行 ID 和任务 ID；不让前端提供任意读取/删除路径。复用现有窗口权限体系，按需补充合法窗口范围，不开放通用文件系统权限。

## 8. 刷写、复制与快照一致性

### 8.1 日常写入

所有窗口汇入同一 Rust 进程的后台写线程。普通事件按批次写入，最长约 1 秒刷新用户态缓冲；WARN/ERROR 请求优先刷新。刷写不放在终端或 UI 主线程中，也不每条都同步落盘。

“写入文件/flush”与“已在物理磁盘持久化”分开：正常后台不能承诺断电不丢；打包屏障、正常退出和应急路径按需要调用同步，但仍受操作系统与硬件限制。

队列建议最多 4096 条且最多 4 MiB，单条普通事件最多 16 KiB（长度按 UTF-8 字节计，截断时保留合法 JSON 和标记）。为重要事件预留队列份额；过载时先合并高频细节，仍无法入队时记录丢弃计数并显示不完整。任何级别都不能无限占内存。

### 8.2 直接从磁盘复制

日志文件以允许其他程序读取/复制的方式打开，需在 Windows 文件共享模式下验证。已关闭分片不再修改；当前分片只追加完整行。复制过程中恰好发生追加，可能得到末尾半行，读取工具需忽略不完整末行，并说明复制时完整性未知。

应用运行时直接拷目录无法保证跨文件原子一致，也可能遇到轮转；因此推荐按钮打包。应用关闭后仍可直接复制整个目录，依靠 events 自身的 runId/seq 分析，不把 latest 或摘要当作唯一事实来源。

### 8.3 按钮打包

1. 后端验证保存范围，选择相关运行，并触发各已连接窗口提交前端缓冲；无响应窗口等待有界超时，写入完整性说明，不挂住导出。
2. 在后端队列插入刷写屏障，等待屏障前的事件写完，关闭当前分片，取得序号及文件范围。之后业务继续写新分片。
3. 锁定快照期间的清理规则，把文件稳定复制到独立的有界暂存区；多进程的活跃日志按已完成行的固定字节边界复制，注明无法保证另一进程的内存缓冲已提交。
4. 按快照截止序号生成新的摘要和清单，再压缩；ZIP 只包含明确列出的诊断文件，附上文件大小、校验和、覆盖区间和缺失信息。
5. 成功后释放快照并清理暂存；失败或取消不保留看似成功的 ZIP。应用重启时清理残留暂存。

导出最多读取 100 MiB 的日志数据，暂存最多约 110 MiB；ZIP 输出计入用户指定目标目录，额外空间在导出前提示/检查。不能假定压缩一定变小。若分配不了空间或选中数据超限，明确提示缩小范围。

元数据、错误索引与应急文件也必须遵守同一快照边界；不能只固定 events 然后复制一份更新更晚的 summary。历史分片已被轮转删除时，清单注明缺失范围。

## 9. 轮转、容量和并发

- 日志保存最近 7 天，总日志区上限 100 MiB，单个事件分片最多约 10 MiB。达到任一条件清理最旧数据；“7 天”不是在高流量下保证保留 7 天。
- 优先清理旧运行。某次运行持续很久时，也要允许删除其中最旧的已关闭分片；保留小体积 session 和缺失范围，不能因为进程一直运行而突破容量。
- 全局配额同时计算摘要、索引、应急文件和分片，为关键元数据/应急记录预留有限空间。
- 每个进程使用独立运行目录和活动锁；目录清理与配额预留采用跨进程维护锁。PID 仅作为线索，不能单凭 PID 判断旧运行是否仍活跃。
- 正在写入的分片和被快照保护的文件不直接删除。无可释放配额时限制新分片/新记录并显示不完整，而不是突破上限；导出完成后恢复清理。
- 文件被外部程序占用、磁盘满或权限变化时按可恢复错误处理，不能使 SSH 等主要功能失败。
- “清理日志”与导出互斥；处理写入队列的清理屏障后开启新分片，避免旧排队事件又被写回。其他实例仍活跃时明确提示需关闭其他实例，不声称已经全量清理。
- 检测目录内的链接/重解析点并跳过，删除及打包均限定在已校验的诊断根目录内；运行锁、临时文件及任意陌生文件不进入导出包。

## 10. 崩溃、启动失败和构建定位

panic hook 尽力写安全错误类别、线程别名、仓库相对位置及有限堆栈。使用独立应急通道/预打开文件，避免依赖可能已被锁住的主队列；应急写入有上限，hook 自己不得再 panic。不无条件输出可能带秘密的 panic payload，也不把所有任务 panic 直接标成整个进程已崩溃。

启动标记用于发现上次未确认正常结束；活动锁仍持有时视为另一个运行实例。强制结束、断电和 native crash 不保证有完整栈，标记名称只用“未确认正常结束”。首版不生成内存转储。

构建中写入版本、Git commit、构建渠道/目标架构及是否工作区构建。后端显式埋点保留仓库相对代码位置；前端异常记录清理后的 bundle 文件名和行列。

为让发布版堆栈可定位，构建流程保留匹配构建的前端 hidden source map，作为开发者构建产物保存，不放入用户诊断包；Rust 可用的符号文件同样按构建归档。未提供相应平台符号时明确标注可还原范围。这里保存的是代码构建产物，不是上传用户日志。

## 12. 验收：用收到的文件证明有用

1. **真实交付路径**：普通安装版、开发者模式关闭。触发一次问题后，另一个用户只按“设置 → 打包日志”操作；开发者仅凭 ZIP 能找到版本、操作、失败阶段、错误码及后续处理。
2. **磁盘复制路径**：不依赖应用界面，复制整个 diagnostics 目录到另一台机器；普通文本工具能读摘要和 JSONL，所有相对引用可解析，没有依赖原机器数据库。
3. **关键故障样本**：DNS 失败、TCP 拒绝/超时、跳板认证失败、目标握手失败、传输取消/失败、设置写入失败、更新校验失败分别检查真实阶段和原生错误信息；不把几种故障都写成同一条泛化消息。
4. **前后端关联**：多窗口、重连、后台任务、窗口迁移下，操作/阶段/连接代次正确；invoke 成功不能伪装后台任务已成功。
5. **敏感数据注入**：将测试密码、Token、地址、路径、剪贴板、终端和文件内容放入潜在异常来源，检查原始目录和 ZIP 全部文件均未泄露；原生码、阶段和代码位置仍然保留。
6. **复制和快照一致性**：持续写入/轮转时打包，检查截止序号、摘要、索引、校验和一致；前端失联、其他实例活跃、历史已裁剪均有完整性说明。手工复制允许尾部不完整但可读。
7. **异常与启动故障**：React 错误、未处理 Promise、Rust panic、业务数据库无法打开、默认目录不可写均得到可用线索或如实的不可记录提示；强制结束只标记未确认结束。
8. **资源与容错**：高频事件、满队列、长时间运行、磁盘满、文件被占用和多实例下，容量有界，日志失败不阻塞主要业务，丢失计数可见。
9. **操作边界**：打包取消/失败、清理、导出磁盘不足不会误删业务数据，不留下被误认作完整的产物；不新增任何诊断网络请求。
10. **平台验证**：Windows 验证安装版固定目录、文件共享复制、原生保存与定位文件；macOS/Linux 验证路径、权限和文件管理器行为。未实际验证的平台明确列出，不用浏览器测试代替原生验证。

设计完成后由用户确认实施范围和默认值；收到确认前，只维护本设计文档。
