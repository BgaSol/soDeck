# SoDeck 本地诊断记录功能设计

状态：功能设计提案，尚未实现。更新日期：2026-10-21。

## 1. 当前需求

当前只建设 SoDeck 自身的本地诊断记录能力。目标是：用户正常使用应用时，自动留下必要的运行线索；出现连接失败、操作异常、窗口错误等问题后，能够通过本机日志判断发生时间、所在版本、相关操作和失败阶段，为后续排查提供依据。

预期流程是：**正常使用并自动记录 → 遇到问题 → 找到对应本地日志 → 关联前后过程 → 分析和修复。**

本期实现范围：自动记录、操作关联、持久化、轮转清理、打开日志目录及本地导出。不建设上传、分享授权开关、发送队列、接收服务和开发者统计平台，也不预先加入相关 SDK 或客户端标识。未来是否分享、分享哪些数据，另行设计。

## 2. 对现有能力的判断

根据此前代码检查，当前已经有容器日志、终端历史、部分业务操作记录、结构化错误和少量控制台输出；尚未发现统一的应用自身运行日志持久化机制。

| 现有位置 | 与本功能的关系 |
| --- | --- |
| `src-tauri/src/logs.rs`、`log_store.rs`、`log_ingest.rs` | 保存远端容器输出，继续作为独立业务功能 |
| `src-tauri/src/terminal_history/` | 保存终端历史，不用作应用诊断记录的数据源 |
| `src-tauri/src/model.rs` 的 `AppError` | 可沿用错误类别、连接跳数和阶段；message 可能带服务器名称和地址，不能直接写入诊断文件 |
| `remote_read.rs`、`system_settings.rs` 的 `eprintln!` | 有局部诊断信息，需要纳入统一的本地记录入口 |
| `src/App.tsx` 的 `WindowErrorBoundary` | 已有错误界面，应补充安全的异常记录 |
| `SystemSettingsDialog.tsx`、`system_settings.rs` | 可承载“本地诊断”入口；记录能力不依赖开发者模式 |

本文件仅调整设计，没有改变现有应用行为。

## 3. 使用体验

### 3.1 默认自动记录

普通安装版启动后就记录必要信息，无需开启开发者模式，也无需先复现一次问题再打开日志。日志保存在本机，跨应用重启保留，直到到期或达到容量上限。

不仅记录最终错误，还记录与其相关的关键阶段及结果。例如连接前的发起操作、跳板认证成功、进入目标握手、等待超时和界面展示失败。

正常使用时不弹出日志窗口，不持续显示调试消息，不要求用户配置日志等级。

### 3.2 系统设置入口

在系统设置增加“本地诊断”区域：

```text
本地诊断
自动记录应用运行状态和错误，帮助排查问题。
记录仅保存在此设备。

记录状态：正常
当前占用：12.4 MiB
保留规则：最近 7 天，最多 50 MiB

[打开日志目录]  [导出日志…]  [清理日志]
```

- **打开日志目录**：通过系统文件管理器打开诊断目录，文件可用普通文本工具读取。
- **导出日志**：选择“本次启动”“最近 24 小时”或保留范围内的时间区间，保存到用户选择的本地位置。
- **清理日志**：确认后清理诊断文件与应用管理的临时导出文件，随后继续记录新的运行事件。
- **记录状态**：正常、部分记录丢失、记录不可用；异常时说明原因，避免让人误以为日志一定完整。

本期以文件查阅为主，不建设复杂的内置日志搜索、问题反馈表单或报告管理中心。临时详细诊断模式也留待基础记录验证后按需增加。

### 3.3 错误关联入口

重要错误提示可展开“诊断信息”，显示错误码及可复制的操作编号，便于在文件中查找。同一操作的前后端事件使用同一个编号；普通用户仍然首先看到可理解的错误说明。

设置中的“打开日志目录”应在服务器数据库初始化异常时尽可能可用；若主界面无法启动，最小启动错误提示提供本机日志位置。若诊断目录本身不可写，如实说明没有保存成功。

## 4. 记录范围

| 类别 | 应记录的信息 |
| --- | --- |
| 启动与环境 | 应用版本、构建标识、系统版本、CPU 架构、可获取的 WebView 版本、启动结果 |
| 生命周期 | 正常退出、上次未正常结束、窗口类型及创建/关闭结果 |
| SSH 与跳板 | 发起连接、直连/跳板类型、认证方式、关键阶段、重试决策、耗时、断线及重连结果 |
| 文件与传输 | 操作类型、任务开始/结束/取消、失败阶段、耗时、数量和大小区间 |
| Docker、NetBird、端口转发 | 关键操作及状态变化、能力检测结果、错误类别 |
| 设置与存储 | 设置读写、本地数据库初始化、历史存储和日志存储的异常 |
| 应用更新 | 检查、下载、校验、安装阶段的结果和错误码 |
| 前端异常 | 全局错误、未处理 Promise、React 异常边界中的安全摘要和可用堆栈 |
| 后端异常 | 关键命令失败、后台任务异常退出、可捕获的 Rust panic |

首次实现优先将启动、前端/后端异常、SSH/跳板、窗口生命周期和本地存储串完整。其他模块至少接入关键操作结果与异常，逐步补充必要的内部阶段；验收时列出已覆盖模块，不把“有统一入口”当作所有模块已覆盖。

正常轮询、数据流和进度刷新不逐条持续写日志。保留状态变化，对重复事件汇总次数，避免重要故障被大量噪声淹没。

首次核对主机指纹、用户取消、正常关闭等属于正常流程。网络中断、认证失败、权限限制和程序内部错误分开分类，不能把所有失败都认定为软件缺陷。

## 5. 日志应具备的上下文

每条结构化记录包含：

- 格式版本、UTC 时间和进程内顺序号。
- 应用版本及构建标识、本次启动编号 `runId`。
- 等级、模块、固定事件名和安全摘要。
- 适用时包含操作编号 `traceId`、阶段、耗时、结果码和重试次数。
- 适用时包含窗口别名、任务别名、连接代次。

一次用户操作从前端发起，经 Tauri 调用到 Rust 执行和结果事件，沿用同一个操作编号。后台任务保留与发起操作的关联。窗口迁移不打断操作关联，重连产生新的连接代次。

耗时使用单调时钟，避免系统时间调整导致负耗时；UTC 时间用于查找，序号辅助判断先后。远端无需安装代理，记录只描述客户端实际观察到的步骤。

例如：

```text
应用版本：0.1.x / build-abc    系统：Windows x64
本次启动：run-...             操作：op-...

INFO   ssh   connect.start              路径=单层跳板
INFO   ssh   jump.tcp.connected         耗时=18ms
INFO   ssh   jump.auth.succeeded        耗时=142ms
INFO   ssh   target.handshake.start
WARN   ssh   target.handshake.timeout   耗时=10000ms
INFO   ui    connection.error.shown     code=SSH_TARGET_HANDSHAKE_TIMEOUT
```

这能确认失败发生在跳板认证之后的目标握手阶段，但不直接证明是远端故障还是客户端问题。无法获得的状态、缺失记录和未还原的堆栈必须明确标注。

## 6. 本地数据边界

即使只保存在本机，也采用字段白名单，只生成排查所需的信息，避免敏感内容进入长期文件或后续导出包。

不记录密码、私钥、口令、令牌、完整环境变量、终端输入与输出、剪贴板文本、文件内容、容器日志正文或完整请求/响应对象。服务器名称、真实地址、账号、完整路径、主机指纹和含业务信息的窗口标题不直接写入诊断文件。

需要区分目标时，用本次启动内的随机别名关联，不落盘保存别名与真实服务器的对照表，不用真实地址的普通哈希作为匿名标识。前端错误提示中的操作编号负责帮助用户找到对应记录。

错误摘要通过明确的类别、阶段和安全模板生成。已有 `AppError.message` 和第三方异常文本不能未经处理直接写入；堆栈去掉用户目录和不可信动态文本，保留可用的函数名、代码位置及构建标识。

诊断不触发额外远端巡检、命令执行或文件读取。已有容器日志、终端历史仍遵循各自功能的保存规则，与本功能独立。

## 7. 保存、导出与资源控制

### 7.1 存储格式

在 Tauri 应用数据目录下新增独立的 `diagnostics/`，采用 UTF-8 JSONL 文件：每行一条记录，方便按编号搜索、用脚本分析，也减少对业务数据库是否正常的依赖。

按时间与大小轮转，文件名不包含服务器、用户名或路径。写入由 Rust 统一管理，各窗口将经过字段校验的事件交给后端，避免多窗口竞争写文件。

只读解析允许跳过异常退出造成的不完整末行，并显示缺失情况。诊断格式带版本，后续新增字段保持兼容，不提前加入上传专用结构。

### 7.2 默认限制

| 项目 | 建议规则 |
| --- | --- |
| 保留时间 | 最近 7 天 |
| 基础日志容量 | 合计最多 50 MiB，与时间限制同时生效，超限移除最旧文件 |
| 单文件 | 约 5 MiB 轮转；单条记录另设硬上限，避免大异常文本撑爆文件 |
| 写入队列 | 后台批量写入，队列条数及字节数都有硬上限 |
| 导出 | 单次压缩包最多 20 MiB；超限提示缩小范围，不静默截断用户选择 |
| 导出暂存 | 合计最多 20 MiB；限制同时进行的导出，完成、取消或下次启动时清理残留 |

数值为设计初始值，实施时用打包客户端验证。用户导出到自选位置的文件由用户管理，不计入应用自动清理范围。

### 7.3 导出内容

导出包只包含选择范围内的应用诊断记录和一份简短说明：格式版本、覆盖时间、涉及启动编号、已知缺失情况，以及必要的版本/系统摘要。

导出时冻结文件范围，后台新日志不会改变已选快照；日志轮转与清理不能破坏正在读取的快照。无法稳定取得内容时明确失败，不生成看似完整的空包。

不打包服务器数据库、完整设置文件、终端历史、容器日志或任意用户文件。导出行为仅写入本机文件，不产生诊断网络请求。

### 7.4 故障与清理

日志写盘失败、目录无权限或队列耗尽时，主要业务继续运行。设置页显示记录不完整，日志系统不得递归记录自身错误而形成无限循环。

队列拥堵时优先保留错误与关键阶段，汇总被丢弃记录的数量；全部容量都耗尽时仍需保持硬上限，不承诺错误记录永不丢失。磁盘恢复后可补记诊断中断的时间范围，但不伪造丢失的事件。

清理要协调写入队列和导出快照，避免删除后又把旧排队记录写回。清理后继续记录新事件，保留当前操作所需的编号并标注上下文已清理。清理不触及业务日志、服务器配置和用户已导出的文件。

## 8. 异常覆盖的实际边界

尽早初始化记录器，覆盖设置与数据库初始化过程；正常退出进行有界的队列刷写，不无限等待。前端全局异常和 React 异常边界、后端关键任务和 panic 分别接入。

记录正常结束标记，下次启动发现未正常结束时写入线索。强制结束、断电、原生崩溃和 WebView 进程退出并不都能被捕获，不能仅凭标记缺失断言是应用 bug，也不能保证最后几条记录一定保存。

发布构建记录可追溯的构建标识；利用可用的 source map 或调试符号还原位置时必须匹配构建。无法还原时如实标记，不把完整原生崩溃栈或卡顿根因分析列为本期承诺。

## 9. 验收标准

1. 普通安装版在开发者模式关闭时仍能自动记录，重启后可以读取保留期内的旧日志。
2. 模拟 SSH/跳板连接失败，前端错误与后端关键阶段能通过同一操作编号关联，日志足以指出失败阶段。
3. 多窗口、后台任务、重连与窗口迁移不会混淆启动、操作和连接代次。
4. 前端异常、可捕获的后端异常、设置/数据库初始化失败分别留下可查询的线索；强制结束只标记异常结束。
5. 使用测试凭据、服务器地址、文件内容、终端回显和剪贴板文本检验所有采集入口，日志与导出包不出现这些敏感值。
6. 长时间运行、大量重复错误、磁盘满和目录不可写时，容量保持有界，记录缺失可见，主要业务仍可使用。
7. 打开目录、导出和清理工作正常；导出范围准确，清理不影响终端历史、容器日志和服务器配置。
8. 与未启用诊断功能的基线比较，不新增诊断网络请求；应用自身的 SSH、更新等既有网络功能不计入这一判断。

本期完成标准是“本机有可读、可关联、有边界的诊断记录”。上传和用户自愿分享作为后续独立需求，不作为本期的依赖或验收条件。
