# 测试流程规范

更新日期：2026-10-25 · 修订：r3 · 状态：执行规范

## 1. 每个功能有自己的测试流程

核心功能和插件功能都要在编码前写好测试流程，保存在该功能规格中或单独文件并相互链接，并作为本次方案交给用户确认。总体验收清单、通用测试规范和“运行所有测试”不能代替功能自己的步骤和预期结果；方案确认流程以[文档更新流程](../documentation-workflow.md)为准。

“功能”按可验证的用户或技术流程划分，不要求每个函数单独建文档。局部文案、样式或修复也应在所属功能中先补充相关检查或回归场景。

## 2. 测试流程的最少内容

| 内容 | 要求 |
| --- | --- |
| 关联 | 功能编号、验收项编号、适用规格日期或版本 |
| 环境 | 平台、运行方式、软件或服务版本、模拟与真实边界 |
| 准备 | 测试数据、凭据引用、服务状态和隔离要求，不在文档放秘密 |
| 步骤 | 可重复执行的操作或明确脚本入口，说明执行顺序 |
| 预期 | 可观察的界面、事件、状态、数据或资源结果，不能只写“正常” |
| 清理 | 停止任务、关闭连接、释放端口、移除临时数据或恢复环境 |
| 执行结果的位置 | 关联任务或轻量变更记录；执行后填写实际环境、日期、命令或操作、结果、证据和限制 |

每条用例有功能内唯一编号，并能对应验收项。脚本尚不存在时写明拟建立入口及覆盖场景，不伪装成可运行命令；必要验证条件尚未明确时，将其列为本次方案阻塞项，不能进入对应编码。

先写细本次要实施的功能及其公共依赖。后续功能只需保留范围、依赖和待决事项，不提前编写未经验证的完整用例。技术原型也有自己的流程和判断标准，可使用同一[功能模板](../templates/feature.md)；结果只支持该原型实际验证的问题。

## 3. 场景选择

每个功能至少有主要成功流程，并评估空数据、边界输入、失败、取消、恢复和重复操作。按实际行为选择，不适用的项目说明原因。

涉及相应能力时还应包括：

- 异步：快速切换、迟到结果、超时、取消后的副作用和重复触发。
- 连接与资源：断线、重连、多会话隔离、视图关闭、工作区结束及资源清理。
- 远端写操作：回执、结果不明、状态核对与重复操作风险。
- 插件：版本和能力兼容、无需授权且逐次留痕、独立构建、更新准备、重启启用及失败恢复；验证内部依赖和公开调用边界，确认普通业务变化可仅更新所属插件的界面和逻辑，核心不增加对应业务专用命令。
- 数据：备份、重复导入、迁移失败、中断和恢复，验证源数据保持可用。
- 界面：功能定义的状态、尺寸、键盘、焦点及真实平台交互。

## 4. 自动化与实际验证

根据风险选择静态检查、单元、契约、界面、集成、原生桌面和安装验证。测试流程说明各层证明什么、覆盖不了什么。

| 层级 | 验证什么 | 适用场景 |
| --- | --- | --- |
| 静态与构建 | 格式、类型、lint、编译与资源打包 | 按语言和变更范围执行 |
| 单元 | 状态转换、校验、解析和关键业务规则 | 规则存在分支、容易回归或需精确断言时 |
| 契约 | 请求、事件、错误、调用记录、资源有效性及版本兼容 | 核心与插件协议、跨语言边界变化时 |
| 界面交互 | 操作流程、异常反馈、快捷键和视觉状态 | 新增或修改界面行为时 |
| 集成 | 真实 SSH/SFTP、数据库、运行实例及服务交互 | 修改对应边界时使用隔离环境 |
| 原生桌面 | WebView、窗口、焦点、剪贴板、输入法、拖拽等 | 修改依赖操作系统的功能时 |
| 安装与升级 | 安装包、启动、升级签名、数据兼容和失败恢复 | 候选版本及发布链路变化时 |

不要求每个功能都新增自动化代码，可以引用已有用例或检查入口；仍需明确本功能的条件、预期和执行结果。可自动复现的缺陷优先补充有意义的回归测试。

模拟 IPC、浏览器、真实 SSH、原生桌面及安装结果分别记录。编译或模拟通过不能代替真实边界验证，WebKit 测试不能代替 macOS 原生验证，跨平台编译通过不能代替各平台安装与运行验证。缺少任务必需的验证时，在任务记录中保留未完成状态、解除条件及可继续工作，不把限制写成通过。

## 5. 流程变化与结果记录

需求或方案变化时，先更新受影响的用例、预期和回归范围，再编码。执行中发现用例遗漏，先补充流程，再修改相关代码和测试实现。失败暴露实现缺陷时保留正确预期，修复后重跑受影响场景。

测试结果使用“通过、失败、未运行、不适用”，记录环境和依据。计划阶段不填写通过；环境受限说明原因和替代路径。结果只在本次任务或轻量变更记录中维护，功能规格保留稳定的测试步骤及结果链接，不再复制一套完成状态。

每次执行关联适用的规格修订和实现版本；尚无版本标识时记录日期、任务及工作区依据。更新了预期或实现后，旧结果只证明原版本，必须标出受影响的待重跑用例。日志、截图、测量及安装产物保存证据路径，不把测试通过写成用户已验收。

模板见[功能规格](../templates/feature.md)，开发状态和完整交付标准见[开发规范](../../DEVELOPMENT.md)。

## 6. 检查入口、回归和验证限制

T-003 已建立以下实际入口，环境、前置和结果见[开发入口](../development-entry.md)与[桌面结果](../tasks/T-003-desktop-results.md)。后续新增检查时须同时维护脚本和本次功能流程。

| 已建立入口 | 用途 |
| --- | --- |
| `npm run check` | TypeScript 类型与依赖边界；不包含格式、完整 lint 或全部测试 |
| `npm run test:contracts` / `npm run test:core` | JS/TS 契约、Rust 核心/宿主/管理器与桌面状态；需外部夹具的 Rust 测试显式另跑 |
| `npx playwright test -c playwright.ui.config.ts` | 浏览器布局及桥契约，使用注入提供者 |
| `npm run test:terminal:native` / `npm run test:updates:native` | Windows 原生与 loopback SSH 协议、真实终端更新；未覆盖的原生人工场景另记 |
| `npm run build` | 前端生产构建；完整桌面构建和安装包命令另说明 |

Rust 检查可由统一入口编排，底层命令必须可追溯。不用空脚本或仅模拟调用充当真实能力检查。

开发中先跑受影响检查，交付完成本次约定回归；整合及发布的检查范围遵循开发规范。通过后不无理由重复同一套检查，只有新改动、失败或未解决问题才扩大或重跑。

验证平台按[产品总览](../product.md)和本次方案确定。当前首阶段在 Windows 验证；保留跨平台结构不要求提前宣称或验证所有平台。环境受限时先尝试已有 CI、隔离环境等可用路径；仍不足则记录具体缺口，不将必需验证默认为用户代做。

性能要求使用具体场景、数据量、并发和测量环境定义，先确定判断标准再测量，不统一规定缺乏依据的性能数字或覆盖率。日志、截图和临时产物存约定产物目录，任务保存路径与结论，临时产物通常不进入源码版本控制。
