# 编码规范

更新日期：2026-10-24 · 修订：r2 · 状态：公共工程规则；语言工具链和具体依赖尚待选型。

## 1. 编码前置条件

先阅读并更新相关规格、技术方案和功能测试流程，由用户确认本次方案后再编码；确认范围内的实现细节自主推进，不逐步请求批准。开发途中改变契约或设计时，先更新文档，并按[文档更新流程](../documentation-workflow.md)判断是否需要重新确认方案。

新增模块、原型、测试与构建配置同样需要先记录目标、边界和验证方法。局部调整采用简短记录，不跳过前置流程。

## 2. 模块与依赖

- 外壳负责展示与通用交互，通过明确服务边界调用能力；核心持有连接、存储和长期运行资源。
- 核心只提供公共协议与资源原语，不导入 Docker、NetBird 等插件业务模型。
- 插件对 SoDeck 内部模块的依赖只能使用公开 SDK、协议和公共 UI 包，不直接读取核心数据库、其他插件私有数据或导入外壳内部实现。第三方依赖可按插件运行环境、打包、许可及维护要求选用，不能借第三方库绕过核心能力和权限边界。
- 插件之间使用公开且有版本的服务；官方插件使用相同的公开通道。
- 按能力和生命周期组织模块；共享代码须有明确复用需求，不顺带扩展功能或进行无关重构。

建议目录和独立构建边界见[技术方案](../technical/README.md)，API 行为见[核心能力](../core/README.md)和[插件协议](../technical/plugin-protocol.md)。

## 3. 接口、类型与命名

- 使用稳定、含义明确的功能、资源和状态名称，同一概念在规格、代码与日志中保持一致。
- 对外请求、响应、事件、错误、版本和兼容范围有明确来源；跨语言契约从同一 schema 生成或校验。具体工具随技术选型确定。
- 外部输入在边界验证，拒绝未知或不合法的状态组合；不靠类型断言掩盖缺失的校验。
- 区分配置、持久化对象、运行实例和资源句柄，不复用同一个标识表达不同生命周期。
- 注释解释约束、原因和非显然行为；公开接口的重要语义保留在规格中。

技术栈采用后，再在本规范补充语言命名、格式化、lint、目录和工具版本，形成可执行规则。当前不声称这些工具已经配置。

## 4. 状态、异步与资源

- 明确状态持有者以及创建、取消、释放和恢复的责任，组件卸载不应偶然决定后台资源是否存活。
- 跨边界请求始终有明确且可校验的调用者身份；服务器、工作区及运行实例代次按操作与资源作用域绑定，必需字段由接口规格定义。全局设置、插件安装等全局操作不强行绑定工作区。
- 持久配置标识、运行实例、访问租约和临时句柄分别建模；临时调用或句柄按其所有者和代次校验，切换或重连后丢弃失效结果，不因一个使用者结束而删除其他使用者仍持有的资源。
- 长操作定义超时、取消、重复操作和迟到结果；释放流程应可重复调用且不误伤其他使用者。
- 流使用有界缓冲和背压，明确截断、丢失及恢复语义；预算和测量方法先写入相关规格。
- 断线后的远端写操作可能结果不明；未经业务核对不得自动重试，不能把 RPC 去重当作远端操作只执行一次。

## 5. 错误、日志与数据

- 错误保留可诊断的原因和上下文，映射为已定义的用户状态，不吞掉失败或用空数据伪装成功。
- 日志关联操作标识及适用的插件、服务器、工作区上下文，避免记录密码、私钥、令牌及其他秘密；凭据使用核心管理的引用。
- 数据格式与 schema 变更先记录兼容、备份、迁移和恢复，验证副本后再使用。
- 开发数据、测试凭据和服务器与 v1 日常环境隔离，不默认使用业务服务器进行验证。
- 不得为掩盖失败而删除或弱化检查、断言及权限校验。原检查本身错误时，先核实正确规格并补充必要的回归流程，再修正检查；涉及方案变化时按文档更新流程处理。
- 模拟实现与占位代码只证明其已声明的验证范围，不能作为完整业务功能的完成结果。

## 6. 检查与交付

每个功能先有可执行测试流程，再按改动选择测试实现和实际操作验证。已有检查可以复用，低影响调整无需新增重复测试；但仍须保存该功能的测试步骤及本次结果。

检查入口、测试分层和完成标准遵循[开发规范](../../DEVELOPMENT.md)与[测试规范](testing.md)。提交前自查边界、失败路径、资源、无关改动和文档一致性。技术选择变化先更新方案和测试要求，再调整代码。
