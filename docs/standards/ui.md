# UI 规范

更新日期：2026-10-24 · 修订：r3 · 状态：公共规则基线；设计方法已确定，具体视觉参数待设计。

## 1. 职责与适用范围

适用于核心外壳、插件面板、独立窗口及公共组件。用户决定视觉和交互方向，AI 负责实现、补齐状态和验证。各功能的页面布局、操作与状态写在其功能规格中，并引用本规范。

新规则或设计变化先按[文档更新流程](../documentation-workflow.md)更新本规范和受影响功能，本次方案经用户确认后再修改界面代码。既有确认范围内的实现不增加逐步确认；方案变化是否重新确认，统一按该流程判断。

### 1.1 必须使用 apple-design

**所有 UI 设计必须读取并使用 `apple-design` 技能。** 此要求覆盖核心外壳、插件面板、独立窗口、公共组件和原型界面的视觉、布局、交互及动效设计；对应实现与设计审查同样依据该技能和已确认规格。

- 开始相关工作前，从当前会话的技能清单定位并读取 `apple-design` 的 `SKILL.md`，按需读取其引用资料；不能仅凭技能名称或记忆代替实际使用。
- 在本次 UI 方案中说明适用的设计原则及具体落点，例如即时反馈、空间一致性、清晰的层次与排版、可中断且克制的动效、可访问性；相关行为写入该功能的测试流程，适用时覆盖减少动态效果、对比度和键盘焦点。
- 结合目标平台适配系统字体、窗口操作、鼠标、键盘和输入法行为。技能中的参数、库和代码示例作为设计参考；本项目的具体视觉参数及技术采用仍由相应规格和选型文档确定。

技能使用纳入既有的文档与方案确认流程：先完善设计和测试流程，经用户确认后再编写 UI 或交互原型代码。临时界面同样使用该技能，并按实验范围明确设计深度。

## 2. 公共视觉基线

颜色、字号、间距和组件规则使用统一来源，插件通过版本化主题协议接入。下面的项目须在对应界面开始编码前明确适用值或设计参考，当前不虚构最终参数。

公共基线随即将实现的界面逐步收敛，不要求先完成整个组件库。插件架构原型可采用范围明确的临时界面，先写清验证所需布局、状态和操作；临时值不自动成为产品视觉规范。

| 项目 | 需要确定的内容 | 当前状态 |
| --- | --- | --- |
| 主题与颜色 | 主题范围、背景层级、文字、边框、强调色、语义色和对比要求 | 待设计 |
| 字体与排版 | 中英文及等宽字体、字号、行高、字重和截断规则 | 待设计 |
| 尺寸与布局 | 间距、密度、圆角、边框、工作区布局、窗口和面板尺寸规则 | 待设计 |
| 公共组件 | 按钮、表单、列表、表格、标签、菜单、对话框和通知的状态与行为 | 随首条流程建立 |
| 动效 | 适用场景、反馈时机、持续时间及减少动态效果的处理 | 涉及后先确定 |
| 插件主题协议 | 令牌名称、注入方式、变更通知及兼容规则 | 待技术验证 |

公共组件已存在时优先复用；出现新变体先更新组件规则，不能在插件内各自解释同一交互。功能专属展示规则留在功能规格，不把业务含义放进全局组件。

## 3. 每个功能必须说明的界面行为

- 入口、主要操作、布局和当前服务器或工作区上下文。
- 初始、加载、成功、空数据、失败、禁用等适用状态；异步或长任务还需说明取消、超时和恢复。
- 操作是否允许重复、进行中能否切换或关闭，以及操作完成或失败后的反馈。
- 键盘操作、焦点进入与返回、快捷键冲突和适用的输入法行为。
- 长名称、大量内容和目标窗口尺寸下的截断、滚动及溢出处理。
- 涉及断线、权限不足、插件缺失或结果不明时，用户看到什么、下一步可以做什么。
- 涉及删除、覆盖、断开或服务操作时，按功能决定提示、确认和恢复方式；不统一追加无依据的弹窗。

不适用项可以说明原因；不能用“统一处理”替代尚未定义的交互。

## 4. 插件与外壳

核心管理工作区和扩展入口，插件通过公开扩展点接入。关闭面板、结束工作区、停止任务和退出 App 是不同操作，界面行为必须对应已定义的资源策略。

插件与外壳遵循相同的公共视觉和交互规则；插件专属布局和业务状态在自己的详细文档中定义。插件更新、安装和启停的具体交互分别遵循已确定规格，其中更新必须重启 App 后生效。

## 5. 界面验证

每个功能编码前写好自己的界面测试步骤和预期结果，按[测试规范](testing.md)选取实际影响的状态、主题、尺寸、键盘、焦点和平台路径。

交付时查看实际渲染，记录环境并提供可查看入口或截图。原型标明模拟数据，浏览器和原生桌面结果分开陈述。设计决定或发现的规格缺口先写回文档，再继续相应实现。
