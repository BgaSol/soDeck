# F-CORE-003：插件核心调用记录

更新日期：2026-10-25 · 修订：r2 · 文档就绪：草案
所属模块：核心调用网关及调用记录服务
关联任务：[T-002](../tasks/T-002-core-design.md)
依据：[产品 P-14](../product.md) · 相关契约：[调用与状态通信](communication.md)

## 1. 目标与范围

用户明确要求不限制插件权限，每次调用核心保留记录。已启用插件可平等使用核心公开且已支持的能力，不建立按插件、服务器或方法的授权表，不要求权限声明、授权弹窗或权限扩大审批。当前插件来源仍按 P-07 为官方插件；本规则适用于插件到核心的调用，不因方法未写进清单而拒绝已支持的调用。

`requires.capabilities` 仅用于版本/可用能力兼容判断，不是运行白名单。能力存在和当前状态允许时，插件可以调用；尚未实现的接口、第一阶段不开放的插件互调、已失效会话仍按契约返回相应错误。

调用记录由核心自动生成，插件无需自己记日志，也不能把记录成功作为可选标记。外壳可使用同样的记录机制并标记调用来源，不能混记为某个插件。

## 2. 保留的正确性检查

- 宿主绑定真实插件 ID、版本、实例及适用的视图；插件不能在参数中冒充其他来源。这用于归因及实例回收，不分配不同能力权限。
- 检查 API 版本、参数、方法是否实现、实例是否仍活跃、资源是否存在及会话代次是否有效。
- 租约属于某个消费者的引用记录。释放自己的租约不会误减别人的引用；对共享资源执行明确的管理操作则按该接口处理并记录影响，不按创建插件判定允许或禁止。
- 公开资源查询与管理接口对插件一致开放。某接口使用不透明句柄时，调用方先取得自己当前有效的句柄，避免引用计数和会话串用；取得句柄不需要用户授权或插件权限检查。
- 核心内部数据库、插件私有实现和未公开字段仍按模块职责封装。默认存储命名空间用于避免键名冲突，不能演变为另一套插件授权表。未提供的原始秘密读取接口不会因本决定自动创建。
- 操作系统权限、SSH 账号认证及远端文件权限属于实际执行环境；错误应如实返回，不把它们改写成 SoDeck 插件权限不足。

功能本身的状态、取消、并发、缓冲限额和发布完整性检查仍适用。限额是统一的运行容量规则，不以某个插件的能力许可为依据。

## 3. 每次调用记录什么

| 字段 | 内容与用途 |
| --- | --- |
| 调用记录 ID | 核心为每次收到的调用分配，独立于调用方请求 ID |
| 时间与版本 | 开始/结束时间、耗时、App 启动标识、核心/API 版本 |
| 来源 | 插件 ID、包版本、实例代次；适用时含视图 ID，由宿主绑定 |
| 请求与操作 | 请求 ID、方法、关联操作 ID；重复请求关联原操作但仍各有调用记录 |
| 目标 | 适用的服务器、工作区、资源 ID 及会话代次，不为全局方法伪造上下文 |
| 输入摘要 | 由具体方法规定的字段摘要、数量或长度；敏感字段只记录存在性或秘密引用类型 |
| 结果 | 已接收/执行中/成功/失败/取消/超时/结果不明；异步调用的受理结果与操作终态分开 |
| 错误与影响 | 稳定错误码、脱敏说明、创建/停止的资源标识；需要时列出受影响消费者 |
| 流摘要 | 流标识、开始/结束、累计字节、截断或异常原因；不保存流正文 |

不把完整密码、私钥、令牌、认证响应、终端输入输出、文件正文或任意命令文本复制到记录。参数使用方法专属的字段清单生成摘要；新方法未定义摘要时只记录方法、目标标识及字段数量，不直接序列化原始参数或错误堆栈。

## 4. 完整性与执行顺序

1. 调用到达网关时绑定实际来源，分配调用记录 ID；格式错误、过期实例和未知方法也要有失败记录。
2. 登记开始事实，进行契约检查，再交给能力模块处理。核心内部继续调用其他模块时保留关联关系，不把一次外部调用误记为多次业务执行。
3. 同步返回记录结果和耗时；异步返回记录操作 ID，后续把完成、取消或未知状态关联到原调用。
4. 重送请求每次都记录，同时通过请求去重规则关联同一操作；记录多次不意味着执行多次。
5. App 中断后，只能把没有完成记录的调用标为中断或结果待核对，不能补写为成功，也不能据此自动重放操作。

每个公开 API 调用均记录，不通过采样省略查询、失败或高频调用。连续流的传输帧若属于同一已建立调用，则记录流生命周期和计数，无须为每个字节创建调用记录；若 SDK 暴露独立的 `write` 等 API，每次调用仍分别记录。

## 5. 存储、查看与故障处理

记录由核心保存到 v2 独立数据目录，与插件可自行写入的诊断文本区分。提供按插件、方法、服务器、时间、结果和操作 ID 查询的核心能力；可进一步关联任务及资源，记录查询自身也通过同一机制留痕，内部追加记录不递归生成调用。

日志轮转、保留时间、容量和查询分页要在实施方案中给出数值。轮转清理应留下可见的保留范围，不能宣称永久保存；插件卸载不默认删除核心调用记录。若提供清理/导出 API，同样对插件一致开放并记录操作，不伪称此设计具备抵御可信插件故意破坏的不可篡改保证。

写入失败不得静默吞掉或虚报“已记录”。建议采用有界待写队列、显式故障状态、恢复后补写，并通过不依赖故障存储的诊断入口显示问题。**持久化时点、磁盘满时是否暂停新调用、队列上限及崩溃丢失窗口仍是实施前待决的技术取舍**，不能把此处的候选处理当作已满足每次留痕要求。后续实验须选定一种方案并验证失败行为；这不建立插件权限审批流程。

具体查询界面在后续 UI 方案中使用 `apple-design`。本次只定义记录内容和服务行为，未设计界面布局。

## 6. 验收与测试流程

验收项：AC-01 所有插件平等调用公开能力，无额外授权步骤；AC-02 每次调用可追踪且来源可信；AC-03 结果、重试、异步与流记录准确；AC-04 秘密不进入记录；AC-05 存储失败不被隐瞒。

准备：真实终端插件、可控核心方法、延迟/失败提供者、临时记录目录及测试秘密标记。表中 A/B 是测试宿主绑定的不同来源身份夹具，无权限清单，不作为产品插件交付；原生实际来源另由终端包验证。持久化及异常使用真实存储边界；本批预算、故障处理及执行入口规划见[终端实施技术方案](../technical/first-terminal.md)。以下均未运行。

| 用例 | 操作步骤 | 预期结果 | 关联 |
| --- | --- | --- | --- |
| LOG-01 | A/B 无权限清单地调用相同已实现方法及服务器；再调用未列入其能力依赖清单、但核心实际支持的方法 | 调用按相同契约执行，不出现插件权限拒绝或授权弹窗，来源分别留痕 | AC-01、AC-02 |
| LOG-02 | 分别发起成功、错误参数、未知方法、执行失败、取消及超时请求 | 每次收到的调用都有独立记录，准确区分执行阶段、错误与结果 | AC-02、AC-03 |
| LOG-03 | A 在参数中伪造 B 的身份，结束 A 实例后重放请求 | 不冒记为 B；旧实例调用无效且有失败记录，不能因句柄字符串相同继续运行 | AC-02 |
| LOG-04 | 重复同一请求 ID，再执行异步操作；查询完成结果 | 重送各留记录但不额外执行；异步受理及终态通过同一操作 ID 可追踪 | AC-02、AC-03 |
| LOG-05 | 输入测试密码、令牌、私钥、命令与流正文标记；触发正常及错误路径 | 可定位方法与结果，记录及导出不含秘密/正文标记，摘要长度受控 | AC-04 |
| LOG-06 | 建立长流并读写，正常关闭与注入截断；若写入为独立 API 再逐次写入 | 流字节计数和关闭原因准确；独立 API 调用均有记录，无逐字节正文日志 | AC-02、AC-03 |
| LOG-07 | 在调用执行中终止 App，重启查询；注入磁盘满或记录存储失效 | 未完成记录不被补写为成功，不自动重放；存储故障显式呈现，按事先选定方案处理新调用和待写记录 | AC-03、AC-05 |
| LOG-08 | 触发约定的轮转，移除临时目录中的终端包（模拟缺失），再从核心查询剩余记录与保留范围 | 按预设容量/时间处理，包缺失不清除记录，查询不产生无限递归；正式卸载流程另随该功能验证 | AC-02、AC-05 |

清理：结束终端插件、身份夹具、流及提供者，恢复存储故障注入，核对未决操作后释放测试资源；保留脱敏证据并删除临时记录与标记。结果写入实际实施任务，不以文档检查代替运行测试。

## 7. 修订记录

### T-003 分页补查（2026-10-25，方案内修复）

LOG-01/08 的记录查看增加同毫秒边界：写入超过两页且开始时间相同的调用，使用服务端返回的不透明复合游标读取下一页，必须无重复、无遗漏；翻页期间新增记录不挤占后续页。继续兼容旧 before 时间筛选。界面提供来源（插件 ID）、服务器 ID、方法和结果筛选、可见保留起点以及“加载更早记录”；改变筛选或刷新从第一页开始，迟到的旧筛选响应不能覆盖新结果。每页最多 100 条，只展示记录摘要。
