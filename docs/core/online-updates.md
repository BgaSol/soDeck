## 1. 目标与本期范围

P-70明确要求：GitHub发布自动打包并发布产物；安装后的应用可拉取GitHub新版在线升级。用户额外希望核心和插件按各自版本分别更新，并允许不可行时放弃此项。核实现有插件版本、不可变包、pending和重启激活后，建议本期实现分别升级，不把插件更新绑定为核心版本更新。

本稿建议Windows x64、NSIS当前用户安装、GitHub公开仓库BgaSol/soDeck；保留跨平台接口。用户已选择自动检查提示、手动下载安装及首期官方插件。其余具体方案仍待整体确认。

| 项目 | 本次建议 |
| --- | --- |
| 自动程度 | 默认自动检查并提示；用户点击下载和安装，不自动执行这两步 |
| 主动操作 | 随时检查、下载选定组件、取消下载、安装选定更新；核心安装并重启，插件安装后完整重启生效；可关闭自动检查 |
| 插件范围 | 首期官方发布源；第三方本地导入及未签名加载保持T-028规则，任意第三方GitHub源另期细化 |
| 更新渠道 | 稳定与预览隔离；开发目录默认不连接正式更新源，不将dev包当正式安装版本 |
| 平台 | 首期Windows x64安装版；便携目录支持提示与手动替换核心，本期不承诺原地在线替换便携EXE |

包含CI、发布清单、更新发现/下载/校验/持久状态、核心安装交接、官方插件单包升级、兼容/数据门禁、设置页及分层验证。排除差分补丁、插件市场、任意原生扩展、第三方源自动注册、自动跨schema迁移、macOS/Linux安装发布和购买Windows代码签名证书。

当前dev.20没有在线升级客户端；用户首次需手动安装带本功能的v2安装包，此后在应用内升级。新安装不自动导入开发目录或v1数据。

## 2. 发布者流程

1. 修改实际变化组件的版本：核心涉及桌面外壳、核心服务、宿主、公共运行资源；插件拥有自己的manifest/package版本。未变化的组件保持原版本。
2. 将已验证代码放在v2分支，推送专用发布标签，例如`sodeck-v2/stable/000001`或`sodeck-v2/preview/000001`。编号是本渠道发布批次，不是核心或插件版本。
3. GitHub Actions核对标签提交属于v2、版本/发布输入及上一批清单；构建变化组件，复用未变化的已发布资产，执行检查，生成并签署完整发布清单。
4. 全部产物就绪后发布GitHub Release。失败保持草稿或失败任务，不让客户端看到半套可更新版本；禁止覆盖已发布标签、版本或资产。

| 本次变化 | 生成/发布 | 客户端更新 |
| --- | --- | --- |
| 仅核心2.0.0→2.0.1 | 新核心安装包和更新签名；插件引用原包 | 只下载核心；已装插件和启用偏好保留 |
| 仅终端0.13.1→0.13.2 | 新终端资源包；核心引用原安装包 | 只下载终端；核心及其他插件不变 |
| 核心及两个插件 | 相应三个新资产 | 分项展示，按兼容依赖准备并在重启切换 |
| 源码变了但组件版本没变 | 校验失败 | 不用相同版本覆盖不同内容 |

一批Release携带完整目录快照，各组件可引用此前不可变Release资产。只更新插件的Release不重新制造同版本核心安装包；发行说明提供当前核心安装包链接，新安装后可独立获取较新的插件。

发布判断按各组件实际构建输入，根锁文件仅因另一个插件版本变化时，不要求核心跟着升版。共享SDK/UI实际被组件使用的代码变化才要求相应组件升版；未被使用的新导出不强迫重打所有包。安装器中的出厂插件版本固定，已有安装器不会因后来的单插件发布而改内容。目录待所有实际资产上传并核验后签署，全部就绪才公开；只有文档变化不产生软件更新。

v1仍使用同仓库，当前默认分支master、公开最新版本v1.0.2。v2标签避免匹配v1的`v*`发布规则，发布时`make_latest=false`；v2客户端按自己的渠道与签名清单发现版本，不读取仓库通用`releases/latest`作为核心版本。不得修改v1的latest.json、默认分支或更新源。

“推送专用标签→自动打包并创建Release”为推荐发布入口。手动先发布一个空Release不作为成功发布；不依赖更改master分支才能运行的新workflow_dispatch入口。具体触发器与隔离见代码方案。

## 3. 使用者流程与界面

新增设置“更新”，显示当前核心、渠道、上次检查、可用版本、下载大小/进度/错误与重启提示；更新说明纯文本或受控链接，不执行Release正文HTML。提供“检查更新”“下载所选更新”“取消下载”“安装所选更新”；核心安装动作明确标为“安装并重启”，已准备插件可“立即重启”。自动检查开关作为设置草稿参与原应用/取消/关闭协调；检查/下载/安装是独立即时操作，取消设置不撤销已准备包。

页面顺序为当前版本/渠道与“检查更新”→自动检查偏好→核心条目→已安装官方插件列表→选中项合计与下载/安装操作。每行区分“当前版本、可用版本、已下载、重启后生效”，失败原因和重试紧邻该行；无更新时显示上次成功检查时间。核心需要一起更新某插件时，先列出依赖及下载总量，由用户明确勾选，不暗中扩大选择；未满足依赖时安装按钮说明原因。渠道由安装版本决定，本期不做应用内稳定/预览切换；ABI、签名密钥、内部状态文件等实现细节不出现在普通操作流程。

插件管理仍是统一入口，在各插件条目旁显示在线可用版本、下载/待重启/依赖原因与单项更新动作；已选定/本次运行/待启用版本保持区分。启用复选框只控制运行，不复用为更新开关。下载/更新状态由核心持有，关闭设置窗口继续下载，不算未保存草稿或被误当成插件导入选择器在途。

自动检查开启时，应用启动不阻塞主窗口；启动后检查已缓存状态，距上次检查满6小时才后台请求；持续运行每6小时检查，带小幅随机错开。关闭自动检查后只允许用户手动触发。手动检查至少间隔30秒；离线、超时、GitHub限流显示原因并退避，不把检查失败写成“已经最新”。稳定渠道忽略预览及v1；同版本不重复下载，不自动降级。

自动检查仅查跟随官方源的已安装插件，不擅自新装未安装插件，不以相同pluginId夺取手动导入包的来源。手动导入覆盖某个官方ID后，该ID转为本地来源，不推荐自动替换；可通过明确的“恢复官方更新”动作核对来源和版本后重新跟随。高于官方版本的本地包不自动降级。

即使手动导入包与官方包字节相同，该动作仍使该ID转为本地管理；来源记录按当前与候选的准确包内容识别。来源或导入提交中断时先核对实际版本，无法证明则保留本地来源。来源存储失败不能先改候选再假称记录成功，报告保存失败，保留旧版本；来源数据损坏时管理页及现有插件保持可用，明确提示修复/重新核对后再安装。恢复官方跟随只改变后续来源，不自动下载安装，不覆盖更高版本或同版本不同内容的本地包。

停用的官方插件也显示可用更新，用户可下载并安装为候选，但不启动worker、provider、数据迁移或远端任务；保持停用，重新启用并重启才激活。失败插件不触发无限自动重试同一候选；显示失败版本和原因，用户显式重试或等待更高版本。

下载完成只产生经过校验的缓存，不写插件pending、不启动核心安装器。用户点击插件“安装更新”才准备候选，完整重启后激活；可选择稍后重启。用户点击核心“安装并重启”，通过所有未保存内容/活动任务关闭检查后才交接安装并重开应用；可以先只安装插件，或只升级满足兼容条件的核心。

插件通过公开更新能力请求下载/安装/重启时，打开核心更新页供用户操作，不把插件请求当成人已点击按钮；检查与查询仍可通过公开能力进行。该规则不新增插件权限表、加载审批或信任弹窗。所有用户安装意图绑定具体组件和计划，重复点击返回同一操作结果；计划变化后重新展示，不能悄悄换成另一个版本。

下载和准备不打断终端、SFTP、监控、隧道。主窗口关闭仍是托盘；正常“退出”、系统关机、强制终止和退出审查取消均不自动安装核心。下载未完成时正常退出取消本次传输，保留已验证文件，清理不完整临时文件；重新启动只核对状态并提示，不擅自续下或安装。用户已点击安装并准备的插件候选仍按T-028在下一次完整启动激活。

apple-design应用：反馈即时、进度与错误就近显示、检查与安装语义清楚、用户掌控重启；复用现有Button/Checkbox/Notice/主题令牌与设置窗口，不增加玻璃效果或强制弹窗。键盘可操作，读屏获取阶段/进度，减少动态时保留静态进度；三主题、大字、窄窗口不挤掉操作。遵守[UI规范](../standards/ui.md)，不在方案确认前制作交互原型。

## 4. 兼容、签名与数据

插件先匹配核心版本、Plugin API、能力、平台和插件数据schema。仅依赖当前核心的更新可独立准备；依赖目标核心的插件先放在更新缓存，不写进旧核心的pending。目标核心成功安装并启动、按实际能力重新验证后才进入插件激活流程。核心安装失败时这些包继续等待，旧核心不能提前执行它们。

应用核心更新前按最新已保存的启用偏好检查目标启动集合：存在不兼容且没有用户选定安装、已下载验证的替代包时阻止应用，说明具体插件；用户可先更新或停用它，不静默停用以强行升级。未应用草稿不作为已停用，关闭审查中保存或其他来源改变插件状态后必须重新规划/核对。停用插件保留包/偏好并标明兼容状况。兼容通过不等于初始化成功；插件初始化失败仍按已有回退/隔离机制处理，核心能够打开管理页。

启动集合优先采用已安装为候选的版本，不能只检查正在运行的旧版本；某插件在本次运行停用、但已保存下次启用时，也纳入目标核心检查。安装更新按实际应用版本比较，插件兼容按明确的核心兼容版本/API/能力判断，二者不混用；便携/单独拷贝EXE不因处于普通运行模式就获得安装版自动替换能力。

本次实现保持core v7、四个观测分区v2。未来目标core、观测集合或激活/偏好/更新持久格式不受当前支持且会触发重建/不可读时，只提示并阻止在线安装，不自动执行重建；需要独立明确确认既有P-52的备份重建后果。不能将二进制回退等同于数据库回退。插件数据schema变化但缺少已实现迁移能力时保留旧版并说明，安装前即拦截，不能谎称已有通用迁移器。

三种校验分别负责：

- 核心安装包使用Tauri updater签名，发布目录使用固定公钥验证的签名清单；自动更新不得绕过。
- 插件资产先核对发布清单中的准确ID/版本/大小/哈希/来源，再走T-028必需的integrity及可选signature规则。官方流水线生成正式签名包。
- 用户手动导入的第三方未签名包继续允许，设置提示即可；不能因为新增在线升级，倒退为全体插件必须签名或新增加载审批。

更新签名与Windows Authenticode证书是不同用途。首期必须有更新签名；没有Windows代码签名证书时如实说明安装界面发布者/SmartScreen状态，不宣称已有受信任Windows发布者。客户端不嵌GitHub令牌，公开下载只向固定GitHub仓库和受控资产CDN发HTTPS请求；不发送服务器配置、凭据或业务日志。

更新文件放在核心数据目录独立updates分区，插件包和数据继续在plugins；安装器不得清理应用数据，默认卸载也保留数据。断网、取消、坏哈希、错签、磁盘不足保留当前可用版本。核心交接有持久记录；安装后靠实际运行版本确认成功，不能以“启动了安装器”宣称成功。安装器中途失败需记录可诊断结果及离线重装入口；本期不承诺任意断电点的整个应用自动回滚。

安装关闭审查取消时保留原连接；通过审查并清理资源后若安装器启动失败，提供原生错误及重新打开当前版本入口，新打开的程序不恢复远端会话、不自动重试安装。新进程确认渠道/应用版本/构建身份后才标记核心升级成功；旧版本再次启动显示“安装未完成”。多个插件分项准备，部分成功明确列出已准备项，不把一次选择描述为跨核心安装器与插件的原子事务。已准备/等待核心的文件不会被缓存容量清理驱逐，空间不足可取消下载或释放未被安装计划引用的缓存。

## 5. 验收标准

- AC-01：专用v2发布标签自动生成完整Release；版本错误或构建失败不得发布可用清单，v1源保持。
- AC-02：安装版能发现对应渠道的更新；核心、插件版本各自比较，下载准确变化组件。
- AC-03：下载与准备不影响现有业务；退出审查可取消，核心交接与重启后激活顺序正确。
- AC-04：本地第三方来源、未签名加载、逐插件启停和全部停用行为保持；核心升级不覆盖插件数据。
- AC-05：跨核心依赖、坏包/签名、失败候选、限流/断网、重复请求及中断均有确定状态和恢复路径。
- AC-06：真实Windows安装A→在线升级B、真实官方插件A→B以及配置/凭据保持有证据；本地夹具、真实GitHub、安装验证分开记录。
