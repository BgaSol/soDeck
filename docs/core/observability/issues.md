# F-CORE-020：重要事件与问题生命周期

修订：r1 · 日期：2026-10-27 · 文档就绪：能力方案可评审，尚未实现
所属：核心问题投影与通知数据服务 · 上级：[总览](../observability.md) · 任务：[T-016](../../tasks/T-016-observability.md)

## 1. 目标与范围

把需要用户关注的异常变为可追踪的问题，提供发生、重复、升级、确认、恢复和再发生的记录。普通日志级别不直接决定打扰用户；不是每条error都弹提示。包含本机问题数据与可订阅通知意图，通知页面、系统toast、声音、邮件/Webhook和自动修复不属于本稿。

## 2. 产生、聚合和恢复

核心内置规则覆盖：应用/存储不可用、插件异常退出、连接持续失败、资源意外停止、更新失败。插件事件描述可声明本插件的problemType、dedup字段、影响对象类型、打开/恢复事件和建议优先级；均为有界声明式数据，没有任意脚本执行或跨插件动作。

| 字段/行为 | 规则 |
| --- | --- |
| issueId、revision、episodeId | 同一问题稳定ID与版本；每次恢复后再发生为新episode，历史不抹去 |
| problemType、origin、target | 命名空间、可信报告者、持久对象及适用运行代次；不同插件/服务器不因错误码相同而合并 |
| occurrenceCount、firstSeen、lastSeen | 每次已提交事件计数，关联首条/末条及可分页的事件范围；重复交付按eventId去重 |
| state、acknowledgedAt/by | state=open/resolved；确认单独存储，确认表示已知悉，不代表已经修复 |
| priority、impact | critical/high/normal与影响资源清单分开；系统不可用、持续影响和普通提醒有不同默认关注度 |
| evidence、relatedIssues | 引用事件/快照和核心验证的资源关系；关联不自动代表共同根因 |
| suggestedActions | 仅声明安全动作标识，如查看证据/打开对象；实际执行仍通过既有明确调用及用户操作 |

同一origin、problemType、目标与作用域代次组成聚合键；错误文本不参与主键。核心只按已声明规则和真实资源关系投影，不用字符串相似度推断根因。一个连接影响多个插件时，可以关联多个问题并列出共同资源，保留各自责任和结果。

恢复必须有对应所有者的恢复事件或可验证状态，例如核心确认新连接ready、插件报告同代次重试成功。等待超时、用户确认、隐藏提示、重启App都不等于恢复。旧代次的迟到成功不能解决新问题；目标删除/插件卸载可标“对象已结束，恢复未验证”，保留最后已知情况。启动后暂无法验证的open问题带stale状态说明，不能声称仍在实时故障。

## 3. 公共能力与通知策略

建议 `issues.query/get/acknowledge`；状态变化以核心事件记录，最新问题列表可用专属state契约，逐次变化历史用[F-CORE-019](history.md)。ack带expectedRevision，重复同一确认幂等、并发冲突返回CONFLICT。所有已启用插件平等使用公开接口，来源真实记录；不新增插件能力授权。公开ack不会修改问题是否已恢复，插件不能覆盖其他所有者的恢复事实。

问题投影与处理检查点在同一事务提交，重启后可以幂等重放未处理事件。先存事实再更新投影；查询返回projectedThrough和pending说明，投影落后不能伪装没有问题。事件缺口会降低coverage。投影失败由独立健康状态暴露，不递归制造新的故障事件风暴。

建议第一次发生、优先级升高、恢复和新episode产生通知意图；同一episode重复事件只更新计数，至少60秒的合并窗口内不重复提醒。用户已确认后，普通重复不重新提醒，升级或新episode可以再次提醒。历史回放/启动重建投影不重发已发通知；使用issueId+episodeId+transition生成幂等通知键。核心提供事实及提示意图，外壳决定最终可见呈现，具体UI另设计。

建议每来源最多200个活跃聚合键、全App2000个；达到限额时继续保存原始事件并给出aggregationLimited，不无限生成问题对象。事件留存期到期后问题只保留有界摘要、最近证据引用和expired标记；数量与过期规则见存储规格，不永久固定全部事件。

## 4. 验收与测试流程

AC-01聚合不串源且可追溯；AC-02确认/恢复/再发生准确；AC-03通知有界且投影可恢复。

环境：隔离SQLite、可注入事件与真实插件/连接生命周期；通知先用数据消费者验证，不冒称原生通知UI已验证。拟建投影和订阅测试，当前入口不存在。适用r1，结果归T-016。

| 用例 / 验收 | 准备和操作 | 预期 |
| --- | --- | --- |
| IS-01 / 01 | 同服务器同问题连续100次；另一服务器、另一插件发同错误码 | 计数正确；仅同聚合键合并；来源和目标独立，原始证据可查 |
| IS-02 / 02 | 确认open问题后再失败，再成功恢复，随后再次失败 | 确认不改变open；同episode不重复普通提醒；恢复有证据，再发生新episode |
| IS-03 / 01、02 | 连接代次变化后送旧恢复事件；多个插件共享连接断开；删除目标 | 旧恢复不解新问题；列共享资源关联但不伪造根因；结束与恢复区分 |
| IS-04 / 03 | 事件提交后、投影事务前/后终止进程，再启动；重复投递同eventId | 投影和计数幂等；pending/stale可见；已发送提示意图不重播 |
| IS-05 / 02、03 | 两消费者并发ack、过期revision、快速升级和关闭订阅 | 冲突/幂等结果明确；升级可重新提示；订阅关闭释放且无迟到污染 |
| IS-06 / 01、03 | 超过每源/全局聚合键预算、清理关联事件、使投影存储不可写 | 有界退化、原事件独立留痕、缺失证据和健康异常可见，不递归刷错 |

清理：停止事件生产、取消订阅、释放真实连接和测试App，恢复注入；仅保留脱敏计数/投影证据。UI/系统通知的功能流程在后续界面规格建立后补充，不在本稿虚构完成。
