## 1. 目标与不变量

明确什么已保存、保存多久、哪里有缺口、存储失效时业务如何继续。已有P-14逐次调用审计保持；新运行诊断不能靠占满队列或磁盘使清理/退出失效。建议核心统一存储服务，独立观测SQLite库，与服务器/凭据业务库分离；物理布局与schema已由本轮代码方案固定，确认前不创建。

## 2. 审计和事件的一致性

建议将调用审计纳入同一观测存储服务，由不可变call.started/call.finished事实生成兼容calls.list投影；一次调用只有一个权威callId。事件与必要投影在同一个观测事务提交，禁止业务先写一套calls再尽力复制另一套事件却宣称两者完全一致。普通领域事件仍由所有者在真实提交/结果之后报告。

公开调用仍先完成审计开始持久化再执行；开始记录不可写时返回LOG_UNAVAILABLE并不执行新业务副作用。操作已执行但终态记录失败时保持RESULT_UNKNOWN/可查询回执语义，不能自动重试业务。关闭、停止、取消、退出及存储健康查询沿用并明确扩展现有清理豁免路径，写入失败仍可释放资源，同时用独立有界健康缓冲说明缺口；豁免不等于故意跳过正常审计。

普通log、插件附加事件、快照/指标写入失败不扩大为拒绝业务动作，返回明确未持久化回执并更新健康。关键业务审计不能通过debug开关或采样关闭。观测查询/上报本身也逐次审计，内部写入/投影不递归创建调用。

业务库、远端和观测库之间没有通用跨系统事务。崩溃可能留下“操作开始、结果未知”，或业务已提交而附加领域事件未提交；恢复按业务回执/修订核对并记录reconciled事件及来源，不伪造原始完成时间、不重放副作用。不承诺每个UI动作和远端字节绝不丢失。

## 3. 建议的默认留存和容量

以下为本次代码方案的留存基线，尚待最终实施确认；当前T-019调用审计已经是30天，旧r1的7天说明不再是当前实现。

| 类别 | 建议时间 | 空间与规则 |
| --- | --- | --- |
| 用户操作、调用审计、关键领域/生命周期事实、问题变化 | 30天 | 256MiB预算，其中64MiB优先保留给审计；到时间或空间上限先清理可清理的最老记录 |
| 普通运行日志 | 7天 | 128MiB；trace/debug默认关闭，显式开启后24小时自动恢复，细节最多留24小时 |
| 通信历史 | 专用5秒桶24小时、分钟桶7天、小时/摘要30天 | 96MiB；由F-CORE-024维护聚合与覆盖，不重复计入通用指标 |
| 持久快照、1分钟通用指标桶、证据 | 7天；空间先到可提前轮转 | 32MiB，含包分块/预留；当前不实施问题摘要/活跃问题服务 |
| 紧急启动/写盘故障通道 | 最近一次及有限历史 | 独立最多8MiB轮转；不可用时只留内存并提供原生/健康提示，不能声称已落盘 |

正常在线预算合计512MiB，含索引和WAL/临时写入预算；维护在达到90%之前启动，单次写入预留所需空间，不能靠未checkpoint的WAL绕过上限。活动调用和短期证据固定占用也计入；无法腾出所需保留空间时按类型拒绝或降级，不无限增加磁盘。具体SQLite分段/回收方式与磁盘峰值验证在代码方案固定。

当前通信profile沿用T-019的独立96MiB分区，通用诊断独立32MiB，在线总额仍为512MiB。[F-CORE-024](../communication-history.md)定义5秒桶24小时、1分钟桶7天、1小时汇总与连接/测速摘要30天的专用例外；通用插件指标及其他诊断的原7天规则不改变。源桶仅在成功生成汇总后淘汰，时间/空间任一先到轮转并报告真实起点；不得把多级粒度重复相加或以历史失败阻塞已建立业务I/O。通信实时32MiB与测速16MiB等新增内存须在代码稿和既有队列预算合并核算，不假定属于原8MiB采集环。CH-04/07/08及CM-10/11验证子额度、失败/清理/重建，既有ST流程仍适用。上述通用采集增量尚未实施；既有通信实现/验证以T-019结果为准，本稿不增加主动测速范围。

显式导出的用户文件和数据库版本备份不计入上述在线预算，也不自动删除，界面/API报告分开占用。自动诊断包计入diagnostics的32MiB预算。保留不足30天时报告实际起点，不能只显示配置天数。未结束调用的最小状态在容量内受保护；崩溃恢复后标中断，不能永久阻止轮转。

现有writer采集总内存8MiB，内含审计/控制保留1MiB，紧急内存环1MiB另计；SDK信用/目录/上下文/快照/指标/feed/任务及查询缓冲的完整账目见代码方案§6，受控额度合计56.5MiB（含复用额度），不是整个App RSS上限。普通生产者超额显式拒绝/过滤并累计drop计数，关键事件使用保留通道也不承诺磁盘故障时不丢。正常退出最多2秒排空已接收数据；未完成回执仍不能称persisted，启动报告非正常结束及可知缺口。

## 4. 字段策略、查询与清理

使用事件类型字段白名单与结构校验，禁止将完整参数、异常对象、环境变量或console对象序列化入库。稳定错误码、对象标识、数量、长度、耗时和配置修订优先；配置变更记录变化字段名与修订，不保存密码等新旧值。高敏内容在采集前排除，导出再次应用同一策略。字符串限长与模式遮盖只是补充，不能声称任意自由文本都已自动安全脱敏。

策略对所有来源统一开放并留痕，来源绑定和描述命名空间用于正确性，不建立插件权限审批。按P-14允许插件使用公开诊断能力，因此这不是防范已启用插件恶意读取/删除的安全审计库，不声称不可篡改或合规取证。

本次管理方法为 `observability.v2.health.get`、`observability.v2.policy.get/set`、`events.v2.cleanup.start/get/cancel`；旧health/policy仅兼容投影。health独立于故障库返回active/degraded/unavailable、最近写入/错误、持久与丢弃计数、保留范围、队列/磁盘/备份占用、storeEpoch和策略版本；自身正常请求仍审计，失败走豁免故障环。

cleanup接受明确截止范围/来源，返回删除数量和新有效范围；不能删除仍活动调用的最小执行状态，不能接受文件路径。清理记录本身最后保存为管理事实，策略变化同样留痕。分页游标、问题证据和包引用受影响时显示过期/缺口。取消清理停止后续批次，已完成删除不回滚，结果报告部分完成。未确认清理与导出界面前，不新增UI动作。

## 5. 启动、重启及版本重建

历史T-019 r3代码基线（其后的收束结果及当前T-016观测2方案优先）：[代码方案r1 §6](../../technical/communication-monitor-implementation.md)固定core schema5、观测schema1及facts256/logs128/traffic96/diagnostics32 MiB分区；观测累计在线512MiB（含索引/WAL/临时证据），紧急8MiB单列，不能与旧core审计双写。call事实/兼容投影同事务，跨库问题投影+checkpoint同事务但不宣称跨库原子；每库main80%/WAL回收20%、增量vacuum与预算测试。统一启动日志/备份协调及旧日志v1恢复由F-CORE-007 r6承接；当前旧服务器/凭据/信任/设置/调用升级时不自动迁入新库。ST回归选取与MCODE-07～09/14由T-019维护，本增量不是已运行验证。

初始化顺序建议：取得独立数据根和进程锁 → 打开有限紧急通道 → 校验各库版本 → 观测服务可用 → 核心/插件启动。早期事件附启动ID与稳定记录ID，主库可用后幂等归档为imported-emergency，注明原采集/归档时间；全部介质不可写时保留可见失败，不能静默退出。

遵循P-52：结构版本不一致时提示、备份并全新建库，不自动迁移。当前调用审计已经在观测facts；本次schema1→2时连同其他观测历史备份，不自动导入新库。同版本core5不重建，不重新执行旧T-019从core调用表切换的过程。存储重建产生新storeEpoch和显式历史边界，旧游标失效。

建议业务库单独重建而观测库版本相同时保留诊断历史，以记录重建过程；旧serverId标记历史/已失效，不关联同名新服务器。观测库结构不一致同样完整备份后重建，旧证据保留在备份但不在线查询。若一次版本变化涉及多个相关库，必须由启动协调器按同一备份清单和恢复记录处理，失败保留旧套、中断不混用。现有dataset协调器已实现成员集合恢复，本次schema2与观测独立重建的回归见ST-10、OCODE-07和[F-CORE-007](../startup-settings.md)；不从既有实现推断新版本验证已通过。
