# 统一滚动条与浏览器默认行为治理

2026-11-06，规划与插件选型。源码已实施，实际结果和未验证范围见 [实施记录](implementation-desktop-consistency.md)；下文保留选型依据与验收目标。

## 目标

SoDeck 应在所有窗口中表现为同一个桌面工具：滚动条跟随应用主题，右键展示应用操作，键盘执行文本编辑、终端或应用功能。WebView 的刷新、打印、页面查找、缩放、历史导航和开发者工具不能作为浏览器默认功能直接暴露。

本次包含两个完整问题：统一滚动条，以及由核心统一治理浏览器默认行为。保留现有工作台布局和三种主题，具体文件与终端操作继续属于业务插件。

## 现状与证据

- `src/ui.css` 已是核心和外置插件共同使用的控件样式，`src/theme.ts` 向插件发送主题变量。统一滚动条可以复用这条路径。
- 核心多个列表、表单、消息、日志和设置区域使用 `overflow: auto`，没有统一滚动条规则；文件树单独设置 `scrollbar-width: thin`，两级标签栏另有隐藏滚动条的处理。
- 文件、终端和网络隧道页面运行在独立 iframe。父页面的 CSS 和键盘事件不会自动覆盖 iframe。
- xterm 6.0.0 有自己的滚动条实现，公开主题接口包含 `scrollbarSliderBackground`、`scrollbarSliderHoverBackground` 和 `scrollbarSliderActiveBackground`。只写原生滚动条 CSS 不足以覆盖终端。
- 主窗口来自 Tauri 配置，拆出的窗口由 `src-tauri/src/windows.rs` 创建。当前没有统一的浏览器默认行为策略，也没有接入 prevent-default 插件。
- 本机正在运行的安装版显示为 0.8.4；实际截图已看到“返回、刷新、另存为、打印、更多工具”菜单，同时文件业务菜单仍显示。开发者工具子菜单和浏览器默认快捷键本轮没有逐项实测。
- 用户按物理 Esc 停止了 Computer Use，已停止界面控制；后续仅进行源码和公开插件资料检查。

## 插件选型

| 候选 | 能解决的问题 | 核对结果 | 建议 |
| --- | --- | --- | --- |
| [tauri-plugin-prevent-default](https://github.com/ferreira-tb/tauri-plugin-prevent-default) | 集中禁用默认右键和浏览器快捷键；Windows 可直接配置 WebView2 原生行为 | 6.0.1，MIT，2026-10-05 发布；要求 Tauri ≥ 2.12、Rust ≥ 1.90，与项目 Tauri 2.12.5 / Rust 1.99.1 匹配 | 作为默认行为治理的实现基础，实施时固定 `=6.0.1` |
| [OverlayScrollbars](https://github.com/KingSora/OverlayScrollbars) | 自定义滚动条尺寸、颜色、轨道和显示状态 | 2.17.0，MIT，2026-10-20 发布；有原生 JavaScript 版本；需要逐容器初始化，不能自动覆盖子容器和 iframe | 保留为滚动条备选，先使用现有共享 CSS 与 xterm 主题接口 |

prevent-default 是集成到核心的 Tauri 依赖，随核心安装包工作，不是用户安装的 SoDeck 业务插件。它不涉及插件权限、授权或市场。

没有发现一个能同时接管 WebView 默认行为、全部 DOM 滚动容器和 xterm 滚动条的现成插件。推荐组合是 prevent-default 统一行为、共享样式统一外观；若平台实测证明 CSS 无法达到明确的视觉要求，再评估 OverlayScrollbars。

选型阶段未增加生产依赖；后续实施固定加入 prevent-default 6.0.1。它的替代方案是核心自行维护初始化脚本和各平台 WebView 适配；现成插件已有快捷键生成和 Windows 原生接口，维护成本更低。OverlayScrollbars 会增加容器初始化、销毁和布局兼容工作，目前尚不足以证明需要这项依赖。

## 默认行为统一策略

### Windows 优先关闭原生浏览器功能

启用 prevent-default 的 `platform-windows` 功能，通过 `PlatformOptions` 统一配置：

- `browser_accelerator_keys(false)`：关闭浏览器默认快捷键。
- `default_context_menus(false)`：关闭默认浏览器右键菜单。
- `dev_tools(false)`：常规运行不提供开发者工具。
- `zoom_control(false)`、`pinch_zoom(false)`、`swipe_navigation(false)`：控制页面缩放与历史导航，系统显示比例仍然有效。

[WebView2 官方说明](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2settings.arebrowseracceleratorkeysenabled)明确区分浏览器快捷键与文本编辑快捷键：关闭浏览器 accelerator 不关闭复制、剪切、粘贴、全选、撤销和 Home/End/PageUp/PageDown。该原生接口适合保留终端收到的按键，同时取消浏览器的默认动作。

只设置与本任务相关的选项，插件支持的自动填充、脚本、消息桥等其他开关沿用当前行为。原生配置通过插件的 WebView 创建回调应用于主窗口和后续拆出的窗口。

### Linux / macOS 使用同一份明确的快捷键策略

复用插件生成的快捷键拦截脚本，按平台补齐快捷键组合，并覆盖顶层页面和子 iframe。事件只取消浏览器默认动作，应用和插件的业务处理仍可接收事件。

| 类别 | 应取消的默认行为 | 需要保留的业务行为 |
| --- | --- | --- |
| 右键与菜单键 | 浏览器菜单、检查元素、保存网页、打印等 | 工作区菜单、文件操作菜单、终端菜单、文本编辑菜单 |
| 刷新 | F5、Ctrl/Command+R 及强制刷新 | 终端接收对应控制键或功能键；文件刷新通过自己的操作执行 |
| 查找与浏览 | 浏览器查找框、F3、光标浏览、历史前进后退 | 页面已有搜索、输入框编辑、终端移动与搜索按键 |
| 打印、打开、源码、下载 | 浏览器打印、打开网页文件、查看源码和下载页面 | 应用文件选择、文件传输、业务命令 |
| 缩放 | 浏览器页面缩放、重置缩放及导航手势 | 系统 DPI；终端字体等业务设置按自身设计处理 |
| 开发者工具 | F12、Ctrl+Shift+I/C，以及 macOS 对应组合 | 应用与插件的业务按键；常规开发运行采用同一策略 |
| 编辑与焦点 | 不禁用 | Ctrl/Command+C/X/V/A/Z、Tab、Shift+Tab、方向键、输入法和选择 |

上表描述默认动作，不把按键从终端或业务插件中直接吞掉。终端 Ctrl+R 历史搜索、Ctrl+P 上一条命令、Ctrl+U 清行，以及 F3/F5/F12 等功能键是重点回归项目。

### 插件不能直接使用默认配置

核对 6.0.1 源码后，需要明确处理以下细节：

1. `init()` 等价于全部 flags，其中包括 `FOCUS_MOVE`，会取消 Shift+Tab 默认焦点移动。必须排除这一项，并按平台选择实际需要的 flags。
2. 默认 `DEV_TOOLS` 只列 Ctrl+Shift+I，F12 等组合需要补齐或由原生设置关闭。
3. 默认 flags 没有完整覆盖缩放、历史导航和 macOS Command 组合；这些属于统一策略的补充部分。
4. `debug()` 会在调试构建中放开默认右键、开发者工具和刷新，不符合正常运行的目标。开发调试使用显式诊断方式，不恢复整套浏览器行为。
5. 插件默认调用 Tauri `js_init_script`。Tauri 在 Windows 会注入子 frame，但 Linux / macOS 默认只注入主 frame。需要复用生成脚本，通过核心的 all-frames 初始化路径补齐覆盖，不能仅注册插件就宣称五目标全部完成。
6. 插件 JavaScript 只调用 `preventDefault()`，不停止事件传播；业务菜单可继续处理右键。但某些控件会读取 `defaultPrevented`，必须通过实际业务回归确认兼容性。
7. Windows 原生设置调用在上游忽略返回错误，注册成功不足以证明设置生效。应验证实际设置和实际包行为。

实施首先验证插件的手动脚本注入与 Tauri all-frames 路径，覆盖自动创建的主窗口、动态窗口和子 frame。适配代码集中在核心，使用上游插件公开 API，不复制一套快捷键实现到每个业务页面。

## 右键的产品行为

- 空白、标题和工具栏区域没有默认浏览器菜单。
- 工作区标签、文件树和终端使用已有业务菜单，统一控件外观、屏幕边界定位、Esc 关闭和焦点返回。
- 输入框和文本编辑器提供剪切、复制、粘贴、全选等有效操作；只读文本提供复制。有选区时保持选区，不能为显示菜单而丢掉要复制的内容。
- 密码框沿用密码输入的限制，不自动把敏感字段变成可复制的普通文本。
- 普通快捷键、中文输入法、终端鼠标跟踪模式和 Shift+右键继续遵守各自业务约定。

通用文本菜单复用现有原生剪贴板能力和共享控件；终端与文件操作继续由插件实现。旧插件的业务菜单保留；新增通用文本菜单可随对应插件更新交付，不改变 UI v1 主版本。

## 滚动条统一方案

### 统一视觉约定

- 浅色、深色、多巴胺使用同一套尺寸和形态，颜色跟随各自主题。
- 采用窄、圆角滑块和低存在感轨道；默认可辨认，悬停或拖动时增强。普通滚动区域不出现方向箭头和突兀的系统灰白轨道。
- 建议普通轨道约 10px、滑块视觉约 6px；精确尺寸需根据 WebView 后端支持实测。标准 CSS 的宽度枚举与 WebKit 自定义规则按支持情况分支，避免标准属性覆盖自定义规则后失去预期样式。
- 内容没有溢出时不出现滚动条；横向只在确实需要时出现。短菜单不得因描边伪元素产生滚动范围。
- 不用只在悬停时出现的极细滑块作为唯一操作入口；保留滚轮、触控板、拖动和键盘滚动。
- 高对比度模式使用系统颜色或系统滚动条。主题切换不改变内容几何、终端列数或滚动位置。

### 统一落点

1. 在 `src/themes.css` 定义轨道及滑块默认、悬停、按下的语义色，`src/theme.ts` 增量发送对应变量。
2. 在现有 `src/ui.css` 定义通用滚动条规则。独立插件打包继续复制共享样式，避免逐页面写不同颜色和尺寸。
3. 盘点核心服务器列表、详情、设置、日志、消息、表单、长菜单，以及文件树、编辑器、传输任务、网络列表和弹窗，检查纵向与横向溢出。
4. 两级标签栏保留现有滚动与定位方式，明确隐藏轨道的例外；不能被全局规则重新显示为大滚动条。
5. 终端使用 xterm 公开主题接口适配滑块状态，必要的外观样式放在终端插件。不修改 vendor 文件、不外包一层通用滚动容器，不替换终端的缓冲区滚动机制。
6. 新主题字段是 UI v1 增量字段，旧插件可忽略。核心与三个官方插件分别升级、分别打包，核心安装包仍可独立工作。第三方自绘或冻结样式的插件需要遵守共享外观约定，不能声称核心 CSS 已自动覆盖它们。

OverlayScrollbars 仅在原生 CSS 的平台实测无法满足已确定的外观要求时进入下一步评估。届时先验证文件树、textarea 和动态弹窗的布局、焦点、滚动恢复、初始化闪烁与销毁，再决定是否引入；xterm 仍使用自己的实现。

## 实施顺序与验收

本轮按用户要求，将桌面一致性与仓库当前的组件设置、在线更新改动合并为一次提交。实现顺序仍先完成浏览器默认行为，再处理统一滚动条。

### 第一步：插件与核心覆盖验证

- 固定 prevent-default 版本，接入 Windows 原生选项及其他平台脚本策略。
- 证明主窗口、拆出的窗口、插件 iframe 和重挂载后都生效；补齐主窗口配置与动态窗口的一致策略。
- 先稳定复现浏览器默认动作，再增加回归。使用隔离的测试窗口和数据，不在用户真实终端中尝试刷新或发送测试控制键。

验收：右键、F5、Ctrl/Command+R/P/F、F12、缩放和前进后退不会执行浏览器动作；业务菜单、文本编辑、Shift+Tab、输入法和终端按键有效。

### 第二步：右键日常操作闭环

- 补齐核心与官方插件的通用文本菜单，使用同一组控件和已有剪贴板能力。
- 检查菜单选择、禁用状态、窗口边界、键盘菜单键、Esc 以及焦点返回。

验收：取消浏览器菜单后，服务器表单、文件路径、文本编辑器、日志选区和终端仍能完成常用复制粘贴。菜单操作不误作用于已经关闭或切换的视图。

### 第三步：统一滚动条

- 落实主题变量、共享规则与 xterm 适配，移除重复或冲突的局部滚动条样式。
- 检查所有已盘点容器，以及两级标签栏和短菜单例外。

验收：三主题、1100×720 / 720×480、125% / 150% 显示比例下外观一致；长列表可到达末项，横向滚动可用，固定标题/页脚不被遮挡；切主题、移窗和重挂载保留滚动位置与终端几何。

### 验证与交付

- 实施后运行 `npm run check`、`npm run scripts:test`、`npm run test`、`npm run build`，插件样式变化另运行相关插件检查及独立打包入口。
- 扩展现有工作区、正式前端产物和终端输入回归；页面测试验证事件、焦点、菜单和滚动，原生包验证 WebView 默认行为。Chromium 页面测试不能替代 WebView2 / WebKit 的实际菜单和快捷键验证。
- Windows x86_64 / ARM64、Linux x86_64 / ARM64、macOS ARM64 分别验证原生产物启动、退出及本次交互；核心与外置插件继续独立打包和发行，不增加发布批次或联动门禁。
- 同步 README、产品需求、架构说明和插件 API 的实施结果；规划不写成已交付功能。
