# 远程工作台代码整改方案

> 状态更新：Hello 和组件交互示例现已退役，源码、官方来源和发行配置已删除；本文有关保留或发行示例的描述属于历史方案。宿主回归改用仅测试夹具，真实业务由终端、文件、网络隧道插件提供。

状态：2026-11-05 已完成控制通信、混合连接，并继续实现真实终端、文件与统计。当前结果和剩余验证见 [实施记录](implementation-remote-plugins.md)；本文的批次清单仍为原方案，不能视为所有验收均已完成。

## 1. 整改目标和取舍

保留已完成的桌面壳、服务器目录、主题、在线更新、多窗口工作台和组件容器，在现有工程上增加业务。整改的目的是让新业务有明确落点，不把所有网络与任务代码追加到 `AppCore`、桌面命令或组件宿主里。

不重写前端框架、不引入数据库、不搭建多协议扩展框架、不一次性拆出几十个 crate。模块按变化原因和资源所有权划分，而不是按文件行数机械拆分。核心依然是一个发行程序，插件依然是独立进程和独立发行包。

初稿只制定方案；用户批准后开始按批实施。第一批未安装新生产依赖，插件模块按下文记录迁移，保留原有尚未提交的组件 UI 改动，每批保持可运行。

## 2. 当前代码与实际改造原因

下列是源码静态检查结论，说明新业务接入前需要调整的地方，不宣称已复现尚未实现的 SSH 业务缺陷。

| 现有位置 | 现状 | 本轮整改 |
| --- | --- | --- |
| `src-tauri/src/main.rs` | 组合 Tauri、命令、退出和包内烟测入口 | 逐步把命令和桌面退出适配移到 desktop；main 保留装配与注册 |
| `src-tauri/src/core.rs` | AppCore 持有目录、插件、UI、工作台和存储，较多跨模块流程直接实现为其方法 | 保留公共门面，将新能力放入独立服务；跨服务收尾集中在生命周期协调层 |
| `src-tauri/src/plugins.rs` | 清单读取、进程监督、JSON 行帧、请求匹配、核心 API 分派集中；监督循环同步调用 plugin_request | 分出协议/进程/路由边界，让接收循环不等待业务完成，避免双向调用互等 |
| `src-tauri/src/servers.rs` | 完成资料、凭据、路径校验与持久化；内部模型私有，界面只得到脱敏投影 | 保留 CRUD 和磁盘格式，增加仅核心内部可用的连接资料快照接口 |
| `src-tauri/src/workspaces.rs` | Context 和窗口归属已稳定；validate_owned 经 validate_context 同时要求 connected | 拆分视图身份检查和在线会话检查；断线后允许本地草稿、导航、关闭等适用操作 |
| `src-tauri/src/workspaces.rs` 的 reconnect | 更新工作台 Context；组件视图另外持有自己的 Context | 统一协调新 Context 发布、旧资源失效和组件重新绑定，不能只更新顶层标签 |
| `src-tauri/src/component_ui/host.rs` | ui.mount/event 同步调用插件；UI 事件最多 24 KiB | 保留小事件，增加任务和独立数据桥；正文、PTY、快照不塞事件 |
| `src-tauri/src/component_ui/close.rs` | 保存逐页同步请求，随后根据 dirty 判断并 dispose | 支持异步保存任务、草稿 flush、关闭取消及保存结果未知；保存成功前不移除视图 |
| `src-tauri/src/windows.rs` | 关闭工作台/窗口主要移除 UI 与归属；尚无真实网络资源 | 统一接入资源和会话关闭；窗口移动只改变展示，不触发断连 |
| `src/components.ts` | iframe 持有与 surface 校验已有实现；事件串行 Promise，flush 只等待这条链 | 分离控制桥和数据桥，flush 等待插件确认的草稿版本与流序号，而不是只等 invoke 返回 |
| `plugins/ui-example` | 同一个示例进程提供文件/终端/转发占位，草稿由小事件整段传输 | 保持测试示例；正式 terminal/files 新建独立插件，不在示例中累积生产功能 |
| `scripts/package-plugin.mjs` | 独立构建 Rust 程序并复制已存在的 ui 目录 | 为真实插件增加显式、可复现的 UI 构建步骤；核心构建不调用它 |

现有测试、单实例数据目录、修订检查、服务器备份、更新签名和独立发布流程继续复用，不因新增 SSH 重做。

## 3. 目标目录和职责

下面是最终建议落点，不要求在第一批就创建所有空目录。仅在对应批次有代码时建立文件；小模块先用一个文件，复杂后再自然拆分。

```text
src-tauri/src/
  main.rs                         # 桌面装配和命令注册
  core.rs                         # AppCore 服务装配、现有兼容门面
  model.rs                        # 现有应用状态/插件记录；不汇总全部新类型
  desktop/
    commands.rs                   # Tauri 入参/返回和异步适配
    lifecycle.rs                  # 桌面窗口/退出请求与核心协调的接点
  plugins/
    mod.rs                        # 现有接口的兼容出口
    manifest.rs                   # 清单基本检查
    process.rs                    # 启动、监督、进程树停止
    rpc.rs                        # 控制帧、双向请求匹配、超时和有界队列
    dispatch.rs                   # 插件 API 到核心服务的薄路由
  servers.rs                      # 现有资料/凭据 CRUD 与持久化
  servers/connection_profile.rs   # 核心内部快照、节点引用和身份比对
  workspaces.rs                   # 工作台、Context、窗口归属和布局
  lifecycle.rs                    # adopt/reconnect/close 的跨服务协调
  resources.rs                    # 资源归属、作用域状态与取消索引
  tasks.rs                        # 有限任务状态、进度、取消和等待
  streams/
    mod.rs                        # 流句柄、有序分块、窗口额度与取消
    plugin_pipe.rs                # 核心和插件进程的数据通道
    view_pipe.rs                  # 核心资源与 UI surface 的数据绑定
  connections/
    mod.rs                        # 尝试、已建连接、状态和调用入口
    route.rs                      # 扁平路径快照，顺序执行与逆序回收
    ssh.rs                        # SSH 库适配、direct-tcpip、保活
    socks5.rs                     # 已有字节通道上的 SOCKS5 协商
    host_keys.rs                  # 路径范围内的 SSH 主机信任
  terminal.rs                     # 核心 PTY 原语；不实现终端渲染
  remote_files/
    mod.rs                        # 文件原语、远端路径和错误模型
    sftp.rs                       # SFTP 实现、句柄和服务端扩展
    writes.rs                     # 暂存、版本检查、提交和结果待确认
  local_files.rs                  # 本地目标句柄、临时文件、跨平台替换
  transfers.rs                    # 两端流复制、进度及取消
  network_metrics.rs              # socket/业务计数、分层聚合、采样
  component_ui/                   # 继续使用现有模型和 layout/host/close
  windows.rs                     # 保留原生窗口与拖动命中逻辑
  storage.rs                     # 继续使用 JSON、日志和现有写入工具
  platform.rs                    # 进程/系统差异适配；必要时才拆子模块
  updates.rs, desktop_updates.rs  # 沿用独立在线更新
  validation.rs                  # 保留显式包内烟测入口

crates/plugin-protocol/            # 核心和两个真实插件共享的线协议类型
plugins/terminal/                  # 正式终端进程、UI、版本、锁文件
plugins/files/                     # 正式文件进程、UI、版本、锁文件
plugins/ui-example/                # 保留宿主测试
packages/plugin-ui-bridge/         # 第二个真实插件接入时提取的小型 UI 桥
```

`terminal.rs` 与终端插件不是重复实现：前者持有远端 PTY，后者持有终端页面、渲染和交互。`remote_files` 与文件插件也不是重复实现：前者持有远端文件句柄、读写和可靠提交，后者持有目录页面、草稿、冲突选择和下载列表。

不预先建立 Repository/UseCase/Service 三套同构目录、动态服务容器、全局事件总线或通用任务调度平台。长期运行的真实连接不是普通任务结果；PTY/文件句柄由对应服务持有，tasks 只记录操作进度与结局。

## 4. 依赖方向和公共协议

依赖方向固定为：桌面命令/插件路由 → 核心能力入口 → 对应服务 → SSH/SFTP/本地 IO 实现。UI 容器调用视图协议，不依赖 terminal/files 业务；connections 不导入插件业务；metrics 不反向调用连接或插件执行操作。

跨模块协调由 lifecycle 完成。AppCore 继续负责创建服务和提供现有入口，但新服务不拿 Arc<AppCore> 到处查所有状态，而是接收具体依赖，例如 Connections、Resources、计量句柄和现有日志/事件回调。保留当前实现的兼容门面可逐步迁移，不必先把所有旧方法重写。

`crates/plugin-protocol` 只放线协议需要的内容：Context、公开资源 ID/任务 ID、版本/能力说明、各服务公开请求/响应及稳定错误。不得包含 SSH 句柄、服务器保存密码、数据库式业务模型、插件草稿或 Tauri 类型。

核心和两个真实插件都通过本地 path 依赖该小 crate；它是编译期源依赖，发行包仍为各自独立程序。各组件保留自己的锁文件，不为了共享类型建立一个强制所有组件一起构建的根 workspace。非 Rust 插件仍可按文档实现 JSON 协议，不强制使用 Rust crate。

Context 可在 workspaces 中保留原有 public re-export，使现有测试和调用路径继续工作。共享协议只在核心与首个真实插件开始共用时建立，UI 桥则在终端/文件两种真实用途明确后提取；不复制整个示例代码形成三个不同版本。

Rust/TypeScript 的少量线协议类型先手写并用共同 JSON 样本做契约测试，不引入大规模代码生成工具链。API v1 向后兼容增加方法与可选字段，未知方法/能力清楚报错；新增业务插件声明最小核心版本，旧 Hello 插件不改包也能继续运行。

## 5. 核心状态、资源和锁

### 5.1 状态各存一份

| 状态 | 唯一持有位置 | 其他模块取得什么 |
| --- | --- | --- |
| 服务器/代理/保存凭据 | ServerStore | 核心内部连接快照或脱敏目录投影 |
| 连接尝试及实际 SSH 链 | Connections | attemptId、session 句柄、状态投影 |
| 工作台/窗口/组件视图归属 | Workspaces/ComponentUi | 固定 Context、viewId、surfaceId |
| PTY/远端文件句柄 | Terminal/RemoteFiles | terminalId/fileId/streamId，不暴露库类型 |
| 资源归属及作用域状态 | Resources | owner 索引、有效性检查、取消入口 |
| 操作进度与结局 | Tasks | taskId、进度、结构化结果/错误 |
| 终端渲染/屏幕快照 | 终端插件 | 核心只转交有界数据和序号 |
| 文件基线/草稿/冲突选择 | 文件插件 | 核心只取提交字节及 expectedVersion |
| 字节累计及速率 | NetworkMetrics | 只读统计快照 |

业务资源所有权建议使用一个简单的 `ResourceOwner` 结构，包含真实 pluginId/pluginInstanceId、创建时 Context、可选 viewId/taskId。资源表索引作用域、取消信号及状态，不把所有资源装进可随意 downcast 的 Any 大仓库。没有插件归属的建链资源归核心，不能伪造一个插件来源。

每个作用域有 open/closing/closed 的最小状态。关闭时先标 closing 阻止新建并摘取待释放项，再在锁外发取消/关闭并等待；最后确认结束并移除。避免刚扫描完资源又有新任务进入而泄漏。每个清理入口幂等，插件失效后的迟到回复不能复活资源。

### 5.2 分离两类有效性检查

现有 validate_owned 把界面操作和在线要求绑在一起，需要分为：

1. **视图仍属于这个窗口和插件实例吗？** 用于本地编辑、布局、切换页面、导出草稿和关闭。工作台断线时仍可成立。
2. **远端操作的 Context 和资源仍是当前有效连接吗？** 用于 PTY 输入、读文件、保存、下载。必须校验 connectionId/generation 及资源归属。

断线不是绕过身份检查的理由；本地操作也必须检查当前 surface 和作用域。已经关闭、已更换插件进程或旧窗口表面的消息一律拒绝。

### 5.3 锁和异步边界

保留现有目录提交串行机制。新服务的注册表锁只做查找、插入和摘除；拿到 Arc 句柄后立即释放锁，再等待网络、插件、用户输入或取消完成。不能持有 std::sync::MutexGuard 跨 await，也不能在日志/事件回调里继续持有服务锁。

网络、流和业务操作运行在应用已有异步运行环境中，不再为每个文件块新起线程或运行时。同步磁盘及既有阻塞兼容入口通过明确边界适配。监督循环、连接任务和每个数据流分别可取消、受并发/缓冲上限控制。

跨工作台、UI 与会话的提交顺序在 lifecycle 内固定；涉及多个注册表时短锁提交，并以操作 token 复核，避免网络完成后用旧快照写入。服务不互相循环调用获取锁。

## 6. 四个必须改造的跨模块流程

### 6.1 认证成功交给工作台

`servers.connection_snapshot` → `connections.connect` 建立链 → 复核 attemptId/档案身份 → lifecycle 接纳会话 → 现有工作台创建/激活 → 初始化已启用组件。

在建链前对同一 serverId 去重，建链后仍复核归属。现有 accept_connected 在已有工作台时直接返回已有对象，未来不能让未接纳的新 SSH 句柄游离；采用持有关闭责任的待接纳会话，接纳成功才转移给工作台，任何失败或重复都释放它。

没有业务插件时仍可连接并显示工作台状态。插件启动失败不把已经可用的连接伪装成失败。

### 6.2 断线和重连

断线先让连接服务标记该 generation 无效、取消相关远端资源，再更新工作台状态并通知组件。UI 视图和文件草稿继续存在，终端保留画面。断线事件只由核心确定，不让插件各自猜测服务器是否在线。

重连成功后，由 lifecycle 在同一个短提交中更新工作台和视图的当前 Context，撤销旧 surface 的远端写入绑定，再发送新状态。旧 PTY/文件句柄不直接改 ID 继续用，必须重新建立。

文件草稿还需要单独的 DocumentOrigin：原始目标身份/路径身份、资源路径、文件基线。不能因为视图换到新 Context，就把旧服务器的草稿自动保存到后来修改过地址或路径的服务器。目标身份发生变化时保留旧草稿但暂停远端保存，要求明确重新打开/确认目标；同一目标重连仍需重新校验远端版本。

### 6.3 窗口移动和终端显示迁移

保留现有“目标就绪后交接窗口归属”的方案；增加数据桥的序号屏障和挂载切换。源表面在输出序号 N 形成终端插件快照，后续输出由核心有界缓冲；目标恢复快照并应用 N 之后的数据，目标确认后才移交输入与尺寸权。

只能有一个可写输入表面，输入必须绑定可写表面代次。目标未就绪或快照失败时回到源，不新建 shell；正常切换不重复发送用户输入。终端高频输入不经过会触发全局 UI 刷新的普通 event 链。

文件编辑迁移依赖草稿版本确认，而不依赖旧 textarea 的完整文本碰巧先到达。断线、移窗、渲染重挂载三种代次分别管理，不用一个 generation 混代。

### 6.4 保存、关闭、退出和升级重启

关闭顺序为：确定待关闭集合 → flush 数据/草稿到已确认序号 → 冻结这组视图的新编辑 → beforeClose 汇总 → 用户决定 → 保存任务完成或明确放弃/取消任务 → 释放视图业务资源 → 释放会话链 → 移除工作台/窗口。

“冻结”需要允许本次保存、数据 drain 和收尾，不能一刀切拒绝所有插件 API。保存期间新编辑要么被界面明确禁止，要么产生新草稿版本并阻止按旧版本关闭，不能悄悄遗漏。取消关闭解除冻结；关闭多个文件时前面已成功保存的内容不回滚，失败页面及未完成草稿继续保留。

`ui.save` 兼容旧同步结果，并允许返回本插件的 pending taskId；关闭层订阅或查询状态，不延长所有 RPC 到几分钟。outcomeUnknown 不等同成功；断线时保存无法完成应保留页面并允许用户放弃或导出草稿。

disposeView 只是插件收尾请求，核心还必须按 view/plugin/workspace 作用域回收真实资源，不能把清理正确性依赖于插件一定回复。关闭终端页不关闭工作台连接；关闭文件插件不终止终端；移空窗口回收不影响已经移走的工作台。

应用退出和核心升级都调用同一生命周期协调，先处理保存和运行中的下载，再停止插件、回收剩余连接并退出。不在 Windows 关闭回调、主窗口按钮和 updater 中各写一套网络清理代码。

## 7. 插件 RPC 和数据通道整改

### 7.1 plugins.rs 的迁移

第一步只按职责搬代码并保留 mod.rs 的 read_manifest/Instance/supervise 等内部出口，先保证旧测试和行为不变。随后改 rpc：

- 接收循环只分类 frame、匹配响应并把新请求放入有界工作队列，不直接等待远端服务。
- 写入有单一顺序出口，响应可以按 requestId 乱序完成；调用方按 ID 匹配。
- pending 表按插件进程实例隔离；停止、超时、取消、进程退出都结束对应等待。
- 长任务立即返回 taskId；短请求保留现有有限超时，未知方法、参数错误、执行失败使用不同稳定错误。
- 错误增加 code/stage/retryable 等必要信息，中文说明只用于展示；不靠匹配错误文案判断协议错误类型。
- 限并发且控制队列为响应/停止保留通路，压力下能响应取消，不把无界 spawn 当作异步设计。

必需集成用例：核心正在等待插件 ui.mount 时，插件反向调用 sessions.get/terminal.open，双方仍可处理响应；另一个插件和退出请求也能继续响应。新插件进程必须有持续读取的客户端，不沿用示例“处理完本次请求才读下一行”的阻塞结构。

### 7.2 大数据不扩容控制帧

保持控制 RPC 的 64 KiB 和普通 UI 事件的 24 KiB 上限，新数据通道承载正文和终端字节。本机回环 TCP 的连接设置、分帧/序号/额度/结束由 streams 管理；端口随机且绑定回环、连接绑定实例会话标识。

宿主数据桥按 viewId/surfaceId 绑定流，通过有界分块和确认传给 iframe；不把通用 TCP 端口交给页面，不通过全局 Tauri 广播传正文，不用 setTimeout 轮询完整文件。二进制传输和平台 WebView 行为在最早真实终端中验证，失败时在桥实现内定向适配。

多个任务的流可共享该进程的数据连接，但每流及总连接都有限额，避免一个大下载让终端无法输入。复制文件时核心可直接连接远端流和本地 sink，不为让插件“经过数据”而拷贝整份文件来回。

| 位置 | 调整 |

## 9. 带宽埋点的代码安排

带宽从连接与资源创建时就建立归属，不到页面完成后再靠插件自报估算。

| 埋点位置 | 计数 | 汇总方式 |
| --- | --- | --- |
| 首站 TCP 外层包装 | 实际成功读写 socket 字节 | 每目标链传输总量；应用远程总量只加这一层 |
| 路径节点嵌套流 | 节点通道承载字节/估算 | 路径详情，不再次加到总量 |
| PTY 通道输入/输出 | 插件终端业务字节 | serverId + pluginId + direction |
| SFTP 文件内容读写 | 查看、校验、保存、下载实际内容 | 按真实资源 owner 计入文件插件，失败和重试不抹掉已消耗量 |
| 目录/属性请求边界 | 能测的协议字节或明确估算 | quality 标识，不能用 UI JSON 大小冒充 |
| 本地桥/终端重放/草稿同步 | 不计远程字节 | 流量计量应位于远端 IO 一侧，避免重复 |

每个 IO 包装先做计数，NetworkMetrics 只取计数快照、算速率和聚合；不持有会话去主动探测网络。计数热路径不写日志、不序列化 JSON、不获取全局大锁，不保存正文。每秒按单调时钟采样，按本轮设计做约 3 秒平滑和有标识的插件传输分摊。

连接级和本次运行服务器/pluginId 累计分开；generation 变更不把历史任务重复累加。结束资源只留下有限聚合，插件退出后累计不消失。累计整数使用不会在 JavaScript 丢精度的协议表示。

按依赖顺序推进，重构与真实功能穿插验证；每批一个完整主题，批次可包含多个小提交，不先做漫长的纯搬文件工程。

| 批次 | 具体整改 | 交付判断 |
| --- | --- | --- |
| 0. 固定现状基线 | 检查现有未提交 UI 改动，运行现有检查并记录；保持功能设计/整改计划入口清楚 | 当前目录、更新、UI/窗口行为有可追溯结果，不覆盖用户改动 |

第 2 批的 Resources 只做到连接取消和归属需要的最小程度，第 3 批由真实 PTY 引出流与基本长任务，第 4/5 批由文件业务验证复用，再补提交结果待确认等任务状态。最终的跨流程收尾在第 5 批统一，但前面的每批已经实现对应资源的关闭，不能把泄漏修复全部推到最后。

每批运行与改动相关的格式/类型/构建及测试，必要时扩展现有 npm 入口；检查通过且没有新问题时不反复全量重跑。五目标构建风险在新依赖第一次进入时就验证，最终实际包验收不以交叉编译代替。

## 13. 必须保持的代码约束

- AppCore/main/桌面命令不承载 SSH 协议循环、终端渲染或文件草稿业务。
- 插件不引用核心内部代码、不保存重复服务器凭据、不互相直接调用。
- 所有远端操作都带明确资源归属和有效 Context，不按当前活动标签选目标。
- 不用放宽消息大小、拉长全局超时或关闭错误检查代替数据通道和任务设计。
- 不持锁等网络/插件/用户，不让接收循环等待它自己才能接收的响应。
- 视图有效与连接在线分开；本地草稿不因断线被禁止编辑。
- 旧资源不在重连时换个 ID 假装复活，旧目标草稿不随档案修改静默换服务器。
- 关闭决定完成前不断开保存所需连接；决定完成后清理不依赖插件一定成功回复。
- 带宽从远端 IO 计量，不按 UI 重放或文件成功大小倒算，不把每层跳板相加。
- 不改变已确定的简单分发方式，不引入权限系统或与本轮无关的大型框架。
