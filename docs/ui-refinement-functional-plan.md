# UI 功能优化规划

日期：2026-10-20。状态：待实施的功能规划。本轮只新增本文档，业务代码未修改。

本规划承接本轮审查的 8 项问题，以当前工作区代码为依据，遵循 apple-design 的反馈、用户控制、一致性、可恢复性和可访问性要求。浏览器预览覆盖首页与设置；监控订阅失败的状态冲突已通过当前状态管理代码复现；其他结论来自组件实现核对，进入实施时补齐对应桌面交互复现。

## 1. 决策与范围

采取“局部优化为主、两处小范围重构”的方式。两处重构分别是监控状态管理，以及 Docker 表单与确认流程。按完整用户流程组织改动，让每一批都能独立验收。

| 原问题 | 处理方式 | 用户可见结果 | 优先级 |
| --- | --- | --- | --- |
| 1. 监控失败仍显示正在采集 | 局部重构状态表达 | 状态真实，旧数据清楚标记，可直接重试 | P1 |
| 2. 文件菜单未随下载弹窗关闭 | 局部修复 | 键盘只作用于当前弹窗，关闭后回到原文件 | P1 |
| 3. 创建容器意外丢失输入 | Docker 流程局部重构 | 有修改才提示放弃，返回编辑保留输入 | P1 |
| 4. Docker 表单错误离字段太远 | 随表单流程优化 | 字段旁提示，提交时定位错误 | P2 |
| 5. 长表单操作区被滚走 | 局部布局优化 | 标题与操作区可见，正文独立滚动 | P2 |
| 6. 创建阶段缺少重试次数 | 功能补齐 | 创建与编辑采用一致的重启策略输入 | P2 |
| 7. 缺少恢复跟随系统入口 | 局部功能扩展 | 可选择系统、浅色、深色，并跨窗口同步 | P2 |
| 8. 确认过期需要退出重来 | Docker 确认生命周期局部重构 | 原窗口重新检查，阅读最新后果后再确认 | P2 |

P1 表示直接影响状态判断、键盘操作或输入保留，P2 表示完成同一流程所需的体验与功能改进。优先级不等于必须拆成 8 个独立改动。

沿用现有三栏工作区、导航、字体与颜色变量、原生 dialog、按钮按下反馈和辅助功能设置。重构限于上述两个领域；共享组件只提取本次实际重复的结构，避免引入新的全局表单框架或弹层管理系统。现有日志相关未提交工作独立推进，不纳入本轮实现。

## 2. 监控：明确连接、订阅和数据三个层次

### 功能行为

- SSH 是否连接、监控订阅是否建立、单项指标是否有有效采样，分别表达。
- 首次等待订阅显示“正在连接监控”；订阅成功但还没有首个样本显示“等待首次采样”。
- 正常收到数据时显示最新数值与更新时间。
- 订阅失败时显示“监控暂不可用”和具体原因，提供“重试监控”。CPU、内存、网络不能继续显示正在采集。
- 失败前有数据时保留数值与历史，并标明“上次采样”；首次失败时显示占位状态，不伪造零值。
- 单项指标失败时只标记受影响指标，其他有效指标继续显示。
- SSH 断开时显示断开状态，监控重试入口应与 SSH 恢复路径保持一致。
- 重试只创建一个有效订阅；旧请求迟到的结果不能覆盖新状态。

### 重构边界

在现有 MonitorStore 中显式管理订阅生命周期，保留单项指标状态和现有请求代次隔离机制。集中生成标题、指标卡、摘要栏和独立监控窗口使用的状态文案。不能简单把 connected 改成 false：监控订阅失败并不等价于 SSH 断开，现有其他消费者也依赖该字段。

共享监控订阅还承载 Docker、挂载和流量数据；实施时检查这些消费者的不可用与过期数据表达，避免把资源卡修正确后留下其他面板假正常。

主要落点：src/resourceMonitoring.ts、src/resourcePresentation.ts、src/ResourcePanel.tsx、src/ResourceStatus.tsx、src/MonitorProvider.tsx，按实际依赖补齐受影响摘要组件。

### 验收

首次订阅失败、已有采样后失效、单项失败、重试成功、连续点击重试、重试中断开及旧响应迟到均有一致状态。同一时刻不能同时宣称监控失败和正在采集。监控故障不改变终端实际连接状态。

## 3. 文件操作：明确菜单到弹窗的交接

### 功能行为

选中文件并从菜单进入下载时，菜单关闭；下载弹窗获得初始焦点。方向键只操作弹窗内控件。Esc 只退出当前层，关闭后焦点返回原文件行；原行消失时返回文件树的可用焦点。

### 优化边界

首先修正下载入口的菜单关闭时机；菜单键盘监听只在该菜单实际拥有交互焦点、且没有前台模态层时生效。下载弹窗补全可访问名称和焦点恢复。核对同一 FilePanel 中其他“菜单进入弹窗”的入口，复用这一交接规则。

主要落点：src/FilePanel.tsx。当前需求可以在文件面板范围内完成。

### 验收

覆盖鼠标右键、键盘菜单键或 Shift+F10 打开菜单；以 Enter 进入下载；操作同名文件处理选项；Esc 退出并回到文件树。菜单不残留，不吞掉弹窗按键，不把焦点送到不可交互的背景菜单。

## 4. Docker：完整整理编辑、预览与确认流程

问题 3、4、5、6、8 共同属于这条流程。先统一生命周期，再实现字段与布局，避免多个 busy、preview、dirty 状态分别决定互相矛盾的行为。

### 4.1 编辑与草稿

流程为“编辑 → 校验与预检 → 查看后果 → 确认提交 → 后台任务”。查看后果时提供明确的“返回编辑”；退出整个流程用“取消”。返回编辑保留全部字段、动态行和合理的焦点位置。

关闭按钮、取消和 Esc 进入同一退出判断：未修改直接关闭；已修改提示“放弃创建设置？”，默认聚焦“继续编辑”，另一操作为“放弃修改”。返回编辑本身不会触发放弃提示。

草稿保存在该次流程的内存中。首次范围不包含跨重启恢复，也不将环境变量和命令自动写入浏览器持久存储。会话或引擎变化时使原预览失效，并提示用户重新检查；已有输入应尽可能留在可编辑状态。提交成功后再清理流程草稿。

提交结果不明时进入待核对状态，利用已有任务查询与请求去重机制确认结果。不能把结果不明当作普通表单失败，再生成一次新提交。

### 4.2 字段校验

- 本地格式错误在字段失焦后显示；已报错字段随着修改重新校验。
- 点击预览时校验全部字段，展开包含首个错误的分组，将其滚入可视区域并聚焦。
- 错误信息贴近字段，并用 aria-invalid、aria-describedby 建立关联。
- 环境变量指出具体行和原因，例如“第 3 行缺少变量名”“第 5 行变量名重复”。
- 远端权限、引擎失效和预检失败保留在流程级错误区域。
- 不在首次打开时让空白必填项全部报错；不因短暂输入中间态打断输入。

创建与编辑共用 Docker 字段校验和重启策略字段的规则，服务端继续负责最终校验。

### 4.3 长表单结构

沿用 DialogHeader，采用固定标题区、中间独立滚动区、固定操作区。常用字段与高级设置分组，沿用现有可展开结构。错误定位必须能展开相关分组，避免焦点落进折叠内容。

以窄窗口、短窗口和字体放大检查：操作区始终可达；焦点和错误提示不会被固定区域遮挡；动态添加的端口、挂载行可滚动定位。维持系统字体、现有间距变量和明确的按下反馈；如添加过渡，尊重减少动态效果设置，并允许用户连续操作。

### 4.4 重启策略

创建与编辑采用相同规则：选择“仅失败时重启”后显示“最大重试次数”，0 表示不限次数；有效范围与现有编辑界面和服务端保持一致。切换其他策略时隐藏该字段并按对应策略提交，切回时可以恢复本次编辑输入。预览中明确展示最终生效的策略和次数。

### 4.5 预览过期与重新检查

到期后保留目标与后果说明，显示“预览已过期，请重新检查”；提供“重新检查”，使“确认执行”暂不可用。重新检查只生成最新预览，用户阅读后再次确认。最新后果与旧内容有变化时给出明确提示。

刷新失败保留当前上下文和输入，提供重试与返回；不会自动提交。前端定时器用于即时反馈，服务端过期或对象变化的拒绝也进入同一恢复路径。

提交前的新预览替换旧预览标识和对应的尚未提交请求。已提交但结果不明的请求保留原 requestId，走已有核对或同请求重试路径，不进入重新创建操作的分支。

各操作的刷新方式必须尊重其输入来源：

| 操作类型 | 重新检查方式 |
| --- | --- |
| 常规容器、镜像、Compose、资源操作 | 使用原目标与动作参数重新预检 |
| 创建容器 | 使用本次表单完整输入重新 prepareCreate |
| 导入、导出、复制文件 | 使用原先由本机选择器确认的输入重新预检 |

目前 prepare_docker_transfer 会重新打开文件选择器，因此仅给通用确认弹窗加一个“刷新”按钮不足以完成最后一类操作。实施时需补充一个受当前会话、窗口和引擎归属约束的草稿重新检查入口，或使用现有接口提供明确的“重新选择文件”动作。推荐实现原草稿重新检查；如果草稿或来源已不可恢复，显示重新选择入口。草稿保留数量和清理策略也需一起定义，避免每次刷新无限积累失效草稿。

### 重构边界

创建流程拥有草稿、步骤、校验和预览状态；展示组件负责表单分组和布局。DockerConfirmDialog 提供统一的过期、刷新、提交和错误呈现，调用方提供相应的重新检查能力。复用现有 Docker 操作提交与任务系统，维持请求去重和目标归属校验。

主要落点：src/docker/CreateContainerDialog.tsx、ContainerSettingsDialog.tsx、DockerConfirmDialog.tsx、DockerTransferDialog.tsx、useDockerActions.ts、docker.css，以及确认弹窗的调用方。新增模块按实际职责拆出 Docker 表单校验、重启策略字段和流程状态；是否抽公共弹窗外壳以本批至少两个实际使用点为准。传输预览续查可能涉及 src/dockerApi.ts 和 src-tauri/src/docker/commands.rs、tasks.rs 的小范围扩展。

### 验收

有修改退出与无修改退出；预览返回保留输入；错误字段自动展开和定位；长表单全键盘完成；创建与编辑重启策略一致；前端及服务端过期；刷新后后果变化；来源或引擎变化；刷新失败保留输入；重复点击只产生一次提交；结果不明不会创建第二次操作。传输重新检查不能无提示更换文件或目标位置。

## 5. 外观：补全偏好设置

将现有顶栏双按钮整理为紧凑的“外观”菜单，提供“跟随系统／浅色／深色”。系统设置中提供相同选择，两处共用一个偏好状态。无历史偏好默认跟随系统，已有手动选择继续保留。

内部区分用户偏好和实际颜色：偏好有 system、light、dark 三种，实际颜色仍只有 light、dark。即使系统当前为浅色，从“浅色”切到“跟随系统”时，选中状态也必须立即更新。终端和其他只需要实际颜色的消费者继续使用解析后的颜色值。

跨窗口同步包括主窗口、独立窗口和后续新开的窗口。仅在跟随系统时响应系统主题变化。

主要落点：src/theme.ts、src/ThemeSwitcher.tsx、src/SystemSettingsDialog.tsx，以及现有菜单和样式资源。

验收覆盖旧偏好兼容、无偏好默认值、系统主题切换、相同颜色下偏好变化、跨窗口同步和键盘选择。

## 6. 实施批次与完成标准

| 批次 | 内容 | 相对规模与主要风险 | 完成标准 |
| --- | --- | --- | --- |
| A | 文件菜单交接 + 监控状态 | 文件修复小；监控中等，需兼顾共享订阅消费者 | 不再显示矛盾状态，菜单不干扰弹窗 |
| B | Docker 草稿、校验、布局、重启策略 | 中等，重点是状态切换与草稿生命周期 | 完整创建流程不会误丢输入，字段与操作区可达 |
| C | Docker 预览过期恢复 | 中等，涉及不同预检入口和请求去重 | 原地恢复且不产生重复操作，所有调用方行为一致 |
| D | 外观偏好补全 | 小，重点是偏好与实际颜色及多窗口同步 | 可恢复跟随系统，全部窗口行为一致 |

A、B 优先落地。C 接在 B 的流程整理之后。D 独立，可按交付节奏插入，但不阻塞前三批。

每批使用现有 Vitest 和 Playwright 基础设施：状态转换、字段规则、预览与请求关系用有针对性的自动化验证；键盘、焦点、滚动和多窗口用对应界面场景验证。保留 macOS、Windows 各自平台行为，在目标桌面 WebView 中复测浏览器模拟未覆盖的部分。

每批验收后再扩大下一批。整体完成以 8 项行为均有可验证结果为准；不把新增组件数量或整体视觉变化当作完成指标。
