# 第六阶段：SOCKS5 协议库接入计划

本计划承接[基础逻辑整改计划](plan-standard-library-adoption.md)的第六阶段，更新于 2026-11-07。核心客户端、网络插件服务端和检查器已接入固定版本报文库，核心 API 与发行版本保持原有约定；实际验证、代码规模和平台待验收项统一见[实施记录](implementation-standard-library-adoption.md)。下文保留设计与验收要求，尚未验证的目标不能按计划声明视为完成。

## 1. 决定与收益

采用 **`socker = "=1.0.0"` 的纯报文编解码接口**。核心与网络插件分别声明依赖，使用同一版本；不采用其 `socker-tokio`、`socker-compio` 运行时包装。

库负责 SOCKS5 握手、方法选择、RFC 1929 认证、CONNECT 请求和响应的报文结构、地址编码与解码。SoDeck 负责选择认证方式、决定支持哪些命令、读取多少字节、超时取消、远端连接和通道清理。业务数据继续由核心转发。

选择这一层次的原因是三个实际调用处的 IO 不同：核心使用 Tokio Stream，插件服务端使用同步 RPC，检查器使用 `std::net::TcpStream`。纯报文库可直接接收字节，不要求改写这些 IO，也不会默认接受另一种认证方式。

收益是删除三处分别维护的报文拼装、IP/域名/端口解析，以及数字状态码的隐含含义。保留少量按帧读取和产品策略，代码更容易说明和验证。当前纯协议生产代码约 210 行：核心 86 行、插件服务端 107 行、检查器报文协商 17 行；`manager.rs` 和核心网络转发不计入可删除的协议代码。**不承诺减少一半代码**，最终统计须包含新增辅助函数和适配代码，不能只计算库调用处。

### 依赖、维护与替代方案

2026-11-07 核对发行包和上游仓库：

- `socker 1.0.0`：2026-08-15 发布，MIT-0 许可，最低 Rust 1.97；项目当前固定 Rust 1.99.1 可编译。仓库未归档，默认分支最后提交为 2026-08-15；当时约 450 次 crates.io 下载、GitHub 0 star，属于较新的小项目，不能称为成熟的大规模验证方案。
- 该版本唯一直接依赖是 `caret 0.10`，用于保留已定义和未知的协议数值；隔离验证锁定到 `caret 0.10.1`。没有 Tokio、socket、DNS、平台 FFI、后台任务或异步运行时依赖。实施时核对两个 Cargo.lock 的实际新增包及许可证，固定发行版本，不使用 Git 分支依赖或本地 fork。
- 维护风险通过限定为报文层、固定版本、保留 SoDeck 行为测试及独立互操作验证来控制；依赖升级仍需运行这些回归。即便不再更新，已经接入的确定版本也不必自动升级，但后续协议缺陷的修复响应可能较慢。

| 替代方案 | 本阶段判断 |
| --- | --- |
| `tokio-socks 0.5.3`、`fast-socks5 1.0.0`、`async-socks5 0.6.0` | 完整客户端配置密码时也提供免认证，不能直接保持核心现有选择；插件服务端的 RPC 适配也会增加代码 |
| `socks-http-kit 0.1.1` | 接口接近现有流，原型有简化空间，但高层客户端丢失具体连接失败 REP；服务端对只有未知认证方法的问候不发送拒绝报文。此次不采用该高层接口 |
| `socks5-protocol 0.3.5` | 隔离复现确认认证选择函数把匹配项下标当作认证值，暂不采用 |
| `rama-socks5 0.4.0` | 有异步和同步协议接口，来自使用规模更大的 Rama 项目；同时带入多个 Rama 网络组件，当前仅替换握手不需要这些能力 |
| `socks5-proto 0.4.1`、`socks5-impl 0.10.3` | GPL 许可，当前项目未声明可直接确认兼容的分发条件，不作为本阶段默认依赖 |
| 继续使用现有实现 | 无新增依赖、已有运行证据，但三处继续维护协议格式；作为此次变更无法通过验收时的代码回退方案 |

公开来源：[socker 发行包](https://crates.io/crates/socker/1.0.0)、[上游仓库](https://github.com/loncothad/socker)。采用它是接口与架构的选择，不能据此断言整体稳定性已经提高。

### 已完成的选型验证

Windows x86_64、Rust 1.99.1 的临时项目中，发行源码的 37 项上游测试通过；另外 9 项兼容性用例通过，覆盖唯一认证方式编码、认证按字节计算及空密码、三种地址请求的每个截断边界、后续正文保留、全部 256 个原始 REP、绑定域名字节、版本/保留字节/地址类型错误、未知方法和命令、最大域名读取范围及越界编码。

验证也明确了库与产品策略的边界：库允许空认证方法列表、空域名字节及零端口，允许解析未知命令和认证方法；SoDeck 必须保留自己的拒绝规则。这些是选型时的隔离接口验证；正式接入后的真实链路、RPC、弱网络及发行包结果见实施记录。

## 2. 必须保持的可验收行为

| 部分 | 本阶段完成后必须满足 |
| --- | --- |
| 核心连接链 | SOCKS 协商借用已有 TCP 或 SSH direct-tcpip Stream；只有连接链第一站由本机建立物理 TCP，下一站域名继续交给代理解析；SSH/SOCKS 混合顺序与逐站凭据不变 |
| 核心认证 | 无凭据只提供免认证；配置账号密码只提供账号密码。代理选成免认证或未提供的方法必须失败，不能发送 CONNECT 后才发现降级 |
| 核心诊断 | 保留 `socksAddress`、`socksCredentials`、`socksAuthentication`、`socksProtocol`、`socksConnect` 分类，连接失败保留原始 REP 数值；真实 IO 错误沿用原有分类 |
| 插件入口 | 继续仅支持免认证 CONNECT；拒绝 BIND、UDP、未知命令及不支持的认证方式；默认本机回环绑定与现有指定地址参数不变 |
| 插件目标连接 | 仍通过 `net.tcp.open` 复用核心会话，远端解析目标域名；插件不建立 SSH、不保存另一套认证资料、不转发正文 |
| 数据边界 | 分片、同次发送多帧、请求紧跟正文都正确；插件仅按当前帧需要读取，业务数据留在核心；成功回复在正文前到达 |
| 检查器 | 经过实际本地 SOCKS 入口检查目标 TCP 可达性；完整读取 IPv4、IPv6和域名绑定地址响应，不扩大为应用协议健康检查 |
| 生命周期 | 原有取消、超时、资源限额、半关闭、计量和插件停用清理继续生效；超时或拒绝不产生后台遗留任务 |

核心目标域名保持非空、ASCII/Punycode、最长 255 字节；用户名非空，用户名和密码各最长 255 字节，保留现有空密码行为。本阶段不改变配置产品规则。

插件目标域名继续拒绝空值、控制字符、空白字符及无效 UTF-8，目标端口不能为零。绑定地址是代理返回的附带信息，与目标校验分开：零绑定端口、空域名字节及现有可消费的非 UTF-8 绑定域名字节不能被误当成目标配置错误。

## 3. 核心客户端如何修改

修改 `src-tauri/src/connections/socks5.rs` 和对应连接测试。保持 `connect(&mut Stream, host, port, credentials)` 的调用方式；`route.rs` 继续持有连接阶段、取消和超时，认证资料仍由核心提供。

1. 在开始协商前检查目标与凭据，构造 `Address`。IP 字面量转换成 IP 类型，域名保留字节；不调用本地 DNS。无效参数在写出网络数据前明确失败。
2. 通过 `ClientGreeting::encode` 只编码选定的一种认证方法，再用当前 Stream 的 `write_all` 写出。读取两字节 `ServerChoice` 并解码；比较选定方式，不接受库能表示的其他方式。
3. 需要账号密码时，通过 RFC 1929 `Request::encode` 写出认证；读取两字节认证 `Response`，检查版本与成功状态。不输出包含用户名、密码的请求对象或原始字节日志。
4. 通过 `Request::encode` 写出 CONNECT 请求，删除手工地址类型、域名长度、IP 字节和端口拼装。
5. 响应先精确读四字节前缀。版本与保留字节错误为 `socksProtocol`；非零 REP 立即返回原有 `socksConnect` 及数值，不因对端没有继续发送绑定地址而额外等待。成功时按地址类型读取剩余帧，再由 `Response::decode` 解码，要求消费长度等于取得的完整帧。

按帧读取保留一个局部小函数，不建跨协议 IO 框架或新的共享 crate。两字节响应与变长 CONNECT 响应分别处理；读取上限是当前帧的剩余长度，不使用可能预读正文的 `BufReader`。

核心协商仍受 `Attempt.wait` 的 30 秒阶段超时和取消控制，不给库增加一套独立超时。成功后原 Stream 继续用于下一站，不能替换为库自行连接的 socket。

库错误按所在阶段映射：方法选择和认证子协议响应无效继续属于 `socksAuthentication`，CONNECT 响应格式无效属于 `socksProtocol`；读取 EOF、网络断开等 IO 失败走原有 IO 错误路径。不能把所有解码错误统一成一个新的通用提示。

## 4. 插件服务端如何修改

修改 `plugins/network-proxy/src/socks5.rs`。继续使用 `Read / Write / Connect / Reject` 动作连接现有 `manager.rs`；状态精简为问候、请求及完成，缓冲只保存当前帧。

### 精确读取与解码

库的 `decode` 返回 `Partial` 或带消费长度的 `Complete`，但不会告诉调用方下一次读多少。SoDeck 保留很小的帧长度计算，用于 RPC 调度；不要在每个 35ms tick 只读一个字节。

| 帧 | 首次读取 | 知道前缀后的完整长度 |
| --- | --- | --- |
| 客户端问候 | 2 字节 | `2 + NMETHODS`，最大 257 字节 |
| IPv4 请求或响应 | 4 字节 | 10 字节，随后读取剩余 6 字节 |
| IPv6 请求或响应 | 4 字节 | 22 字节，随后读取剩余 18 字节 |
| 域名请求或响应 | 4 字节，再读长度字节 | `7 + 域名字节数`，最大 262 字节；255 字节域名的请求读量为 4、1、257 |

网络可能返回少于请求量的数据；累计到当前需要长度前返回 `Read(剩余量)`。完整帧调用库解码并校验消费长度。`next()` 只返回当前剩余量；不通过扩大 `maxBytes` 试图提高吞吐，也不吸收正文后再另建缓存移交流程。

### 产品策略与动作

- 问候解码后只选择免认证。只有未知/私有方法或账号密码时，也明确发送 `[5,255]` 并结束；空方法列表及错误版本按无效协商关闭。
- 请求前缀仍用于及时拒绝：非法版本/保留字节拒绝，非 CONNECT 返回 REP 7，未知地址类型返回 REP 8，无须等待不支持命令的完整正文。
- 合法完整请求由库解析为地址与端口；再执行现有目标校验。删除 `kind`、临时 `host` 以及分别拼装 IPv4/IPv6/域名和端口的状态。转换成 `Connect(host, port)` 后，目标连接交回 manager。
- 成功和失败响应使用库 `Response::encode`，以有名称的 `Reply` 替代裸状态码。保留当前 IPv4 `0.0.0.0:0` 绑定地址响应；不增加 BIND、UDP 或服务端账号密码功能。
- 目标连接错误仍保持现有 REP 映射：连接拒绝 5、超时 6、其他错误 1；命令不支持 7、地址不支持及现有目标校验拒绝 8。无效 UTF-8 等其他解析失败遵循对应阶段错误处理，不修改核心 RPC 的错误结构。

### manager 的修改边界

`manager.rs` 仅调整协议动作和响应构造。保留接受通道、读取、目标连接状态轮询、日志和关闭流程；成功时继续先排队写入响应，再调用 `net.stream.splice`，依赖核心命令队列顺序保证响应先于正文。

补足按协商阶段处理异常：已经发送方法拒绝或请求拒绝后，不再发送第二个错误帧；问候未完成时的 EOF、超时和解析错误关闭通道，不发送 CONNECT 阶段响应。实施前先用现有 manager 复现和记录此类输入的行为，再按定义建立回归，不能只测试纯解析器。

不新增把 RPC 包装成 `AsyncRead/AsyncWrite` 的适配器。`Client.call` 自身是同步调用，当前超时 4 秒；不能把它放进异步 `poll_read`，也不能在持有 App 锁时等待网络帧。继续使用核心 `pending` 状态返回下一轮 tick。

## 5. 同步检查器如何修改

修改 `plugins/network-proxy/src/checks.rs`，复用插件 `socks5.rs` 内的帧长度、编码与响应解码辅助函数。服务端请求与客户端响应已有两个真实用例，可以在插件内共用地址帧长度处理；不把检查器搬进核心，不引入另一个运行时。

1. 保留单独的检查工作线程及 `std::net::TcpStream`，从真实本地入口发起连接。
2. 用库编码免认证问候与 CONNECT 请求，方法响应只接受免认证；删除检查器中的手工域名和端口拼装。
3. 把固定读取 10 字节改为按前缀读取完整响应，用库解码并检查原始 REP；保留检查结果的现有意义与 UI 返回结构。
4. 保留连接 2 秒、写入 2 秒、读取 12 秒的配置。变长响应以一次逻辑响应的 12 秒绝对截止时间为限，每次实际 read 前计算剩余时间；不能每读一个字段就重新给 12 秒，也不能让慢速逐字节输入无限延长检查。方法响应与 CONNECT 响应各有自己的读取截止时间。
5. EOF、非法版本、非零保留字节、未知地址类型与截断响应明确失败。非零 REP 前缀可立即报错；成功响应必须读完地址和端口，正文不被当成响应尾部。

当前固定 10 字节与自有服务端响应相符，不把此改动描述为已确认的用户故障。新增测试使用独立手工报文模拟三种绑定地址及慢速/截断响应，证明读取边界和截止时间。

## 6. 超时与弱网络验证

协议库不处理 TCP 重传，也不接管 SSH 或正文转发。它能减少报文处理差异；高延迟和丢包是否可用，还取决于现有截止时间和底层传输。

本阶段先保持现有超时：核心连接链每阶段 30 秒，插件接受客户端后的协商与目标连接总期限 14 秒，核心目标连接 10 秒、协商资源保护 15 秒，检查器按上一节配置。不统一拉长超时，不增加业务数据重试或自动重放。测试若发现有效慢网络稳定触发不合理失败，先记录具体阶段和原因，再对该行为给出定向调整，不能以放宽所有测试时间代替分析。

### 两类不同的测试

跨平台夹具控制字节发送时机：逐字节输入、100ms 间隔、阶段间暂停、永久停止发送、阶段中取消。它验证分帧和截止时间，**不冒充丢包测试**。

真实丢包在 Linux 原生 runner 的隔离 network namespace/veth 中使用 `tc netem`，仅影响测试链路；正常结束和失败退出都清理该 namespace。明确安装 iproute2、记录内核与 tc 版本。不在开发机现有 SSH 或系统默认网卡上改网络参数。

| 场景 | 每个方向增加的延迟与抖动 | 每个方向丢包 | 验证重点 |
| --- | --- | --- | --- |
| 基线 | 0ms | 0% | 合法场景全部成功，作为修改前后对照 |
| 常见远程连接 | 50ms ± 10ms | 0% | 约 100ms 额外往返延迟下，混合连接和代理协商全部成功 |
| 跨区域链路 | 150ms ± 30ms | 1% | 重传后能完成的连接数据一致；记录建立成功率和耗时 |
| 较差链路 | 300ms ± 50ms | 3% | 约 600ms 额外往返延迟下的握手、正文、超时及清理 |
| 严重抖动与丢包 | 500ms ± 100ms | 5% | 明确失败和资源恢复，不要求每次建立成功 |
| 黑洞/连接断开 | 有限时间内全部阻断或关闭对端 | 100%/断开 | 在既有期限内结束；取消、停用与会话断开可清理 |

在本地客户端到入口、核心连接链的网络段分别施加干扰；不把 RPC 调用超时当成远程 TCP 超时。对受影响段做单站 SOCKS 与一条 SSH/SOCKS 混合链，避免仅测试本机回环入口后宣称远程链路已覆盖。

基线和无丢包配置每组至少 10 次；有丢包配置每组至少 20 次，修改前后使用相同拓扑和参数。记录成功次数、阶段耗时、失败分类和数据校验；工具支持固定随机种子时记录并复用。单次随机波动复跑后判断，稳定复现的新失败必须查明。成功率下降不能单靠提高截止时间掩盖，也不承诺库接入后成功率一定上升。

成功转发至少覆盖现有 128 KiB 负载、双向同时传输、请求紧跟 `tail`、客户端和远端分别半关闭。对更大负载逐字节比较或校验哈希；成功结果必须无丢失、无重复、无额外协议字节。超时不得误报成功，不能有无限等待。

核心接收到关闭/取消后，五秒内监听应停止接收、活动流和待连接资源应释放，连接名额可重新使用；允许按既有规则短期保留已关闭的诊断记录。插件异常退出、停用、会话断开和超时都验证此行为。

## 7. 回归与独立互操作

### 行为测试

- 核心：免认证、密码成功/失败、拒绝认证降级、逐站凭据、非 ASCII/长度边界、IPv4/IPv6/域名目标、三类绑定地址、完整帧后的正文、REP 1–8 和未知 REP 数值、非零 REP 的截断尾部、非法版本/RSV/ATYP、协商取消与阶段超时。
- 插件：逐字节和各种分片问候/请求、没有可接受方法、未知方法与免认证混合、BIND/UDP/未知命令、空域名/无效 UTF-8/空白/控制字符/零端口、最长域名、精确 `next()`、完成后再次 feed、错误阶段仅发送一次合法响应或直接关闭。
- 检查器：真实入口可达、目标拒绝、三类绑定地址、每个边界 EOF、慢速输入和绝对截止时间；失败输出仍用于当前规则的检查结果。
- 通道：复用 `network_roundtrip`，检查握手与 `tail` 连发、128 KiB 正文和半关闭；补足双向传输、目标连接中取消、插件退出及已建立转发清理。
- 资源上限：16 个待协商、64 个活动客户端和已有队列/预算继续有效；关闭部分连接后可以建立新连接。不为库接入扩大核心资源限制。

### 独立实现互操作

核心客户端使用 `fast-socks5 1.0.0` 的独立测试服务端验证免认证与密码模式；仅作为测试依赖，不能进入生产路径。异常报文和降级行为使用手工报文夹具，以免另一个库的默认行为掩盖断言。

真实网络插件入口使用 curl 的 `--socks5-hostname`，目标服务只在测试远端可解析，验证代理端 DNS；另测 IP 字面量和目标连接失败。固定测试工具 curl 8.21.0，版本、安装来源和下载校验值在测试工具安装入口声明；已有对应版本可复用，缺少工具明确安装或报告，不把未执行用例显示为通过。实施已运行上述互操作，实际平台和结果见[实施记录](implementation-standard-library-adoption.md#第六阶段验证与实际包)。

curl 检查的 HTTP 请求只用来确认经过真实入口的数据到达独立测试服务；插件产品内的检查器仍只检查 TCP 可达性。不能只让生产库同时扮演测试两端互相验证。

实施采用 `npm run network:netem`，在私有 Linux network namespace 的回环接口施加干扰，覆盖夹具的全部 TCP 段。它未实现上文按 veth 分别控制入口段与远端段的拓扑；这一差异及当前环境的随机种子支持情况必须在实施记录中明确，不能将多段叠加结果换算为单条互联网链路的成功率。

## 9. 验证命令与发行验收

实施运行已有 `npm run check`、`npm run scripts:test`、`npm run test`、`npm run network:test`；插件运行 `cargo fmt --manifest-path plugins/network-proxy/Cargo.toml -- --check`、`cargo test --manifest-path plugins/network-proxy/Cargo.toml --locked`。新增定向用例并入这些入口，额外弱网络脚本在创建后才写入工作流。

核心执行 `npm run build -- --locked`，网络插件执行 `npm run plugin:build -- --plugin network-proxy`。复用当前 GitHub Actions 原生目标和工具链，只添加本阶段确实需要的测试与工具安装；核心发行构建不依赖业务插件打包，组合网络验收单独运行。未收到发布指令前，不创建标签或 Release。

| 正式目标 | 受影响组件验收 |
| --- | --- |
| Windows x86_64 | 核心包与网络插件包分别构建；包内程序启动/退出，真实 SOCKS 入口与混合连接 |
| Windows ARM64 | 使用原生 ARM64 产物，在 ARM64 系统运行同一验收 |

## 10. 完成条件、风险与回退

本阶段完成必须同时满足：三处使用固定 socker 版本；自写报文/地址处理已实际移除；全部策略和边界回归通过；独立互操作及弱网络结果可复核；两个受影响发行组件完成五目标原生包验收；生产依赖与锁文件一致；实施记录说明净代码变化、实际验证和已知限制。

主要风险为新库使用规模小、库默认宽容策略漏补、按帧读取不准确造成正文消费、错误阶段重复回复，以及检查器变长读取延长超时。每项都对应上述测试与实现边界，不能只凭上游测试通过宣布完成。缺少目标平台环境时如实记录待验收，不能外推完成。

回退范围仅为本阶段的核心协议、网络插件协议/检查器及相应依赖锁文件变化，保留已有其他阶段改动。生产只有一种实现路径，不长期保留双实现或运行时开关；未通过验收的替换不进入发行包。完成后的事实证据写入[基础逻辑复用实施记录](implementation-standard-library-adoption.md)，此计划不追加逐次运行日志。
