# 工作台侧边工具入口与停靠：功能设计

设计日期：2026-11-10。状态：工作区源码已实施，尚未发布；实际验证及平台边界见[实施记录](implementation-tool-docking.md)。本文补充[工作台分屏与多窗口设计](plan-workbench-layout.md)，集中定义侧边按钮、工具位置及拖动的一致行为；现有分屏、移窗与业务生命周期继续沿用既有体系。具体核心/插件边界、数据迁移和代码落点见[代码整改方案](plan-tool-docking-coding.md)。

## 1. 需求理解与设计结论

用户明确要求：终端不出现在侧边；按钮可以左右拖动；组件在右边，按钮就在右边，按钮在左边，页面也应在左边。

据此推断，侧边按钮应是**工具所在位置的入口**。按钮和工具面板共同表示一个停靠位置，不能分别移动，也不能让按钮按插件的默认位置排列、面板却按另一套布局显示。用户应能通过按钮的位置预测内容在哪里打开。

这里的“页面跟随”指按钮对应的工具面板。例如把文件按钮移到右侧后，文件目录树在右侧打开；双击文件产生的编辑页仍属于中央标签组。终端同样属于主区域页面，仍支持左右/上下分屏、排序和独立窗口。

本方案选择以下共同规则：

1. **侧边只放工具入口。** 文件目录树、Docker 总览、系统状态和网络隧道可以停靠；终端、文件编辑器和容器详情等中央页面不进入侧边工具条。
2. **按钮与面板共同移动。** 拖按钮、拖面板标题或使用“移到左侧 / 移到右侧”，结果一致。
3. **工具在当前窗口停靠哪边，入口就在那边。** 两侧不会同时保留同一个工具的普通按钮；展开工具必须有同侧可见入口。
4. **每侧同一时间展开一个工具。** 同侧切换、收起和移动保留原实例与业务状态。
5. **拖动调整当前服务器的工作台并保存。** 其他服务器不突然重排；新服务器继续使用已保存默认值与插件推荐值。这是本方案对未指定记忆范围的建议。

## 2. 界面结构与入口职责

```text
服务器标签与全局操作
┌────────┬──────────────┬────────────────────────┬──────────────┬────────┐
│左工具条│左侧工具面板  │ [终端 1 ×] [配置文件 ×] ＋│右侧工具面板  │右工具条│
│ 文件   │（可收起）    ├────────────────────────┤ Docker       │ Docker │
│        │              │ 当前服务器的页面与分屏 │（可收起）    │ 状态   │
│        │              │                        │              │ 隧道   │
│ …      │              │                        │              │ …      │
└────────┴──────────────┴────────────────────────┴──────────────┴────────┘
连接状态与传输速率
```

| 功能 | 入口与显示位置 | 本次规则 |
| --- | --- | --- |
| 终端 | 主区域标签栏的「＋」、已有终端标签 | 删除左右工具条和“更多工具”中的终端入口；新建、切换、关闭及默认初始化沿用现有行为 |
| 文件目录树 | 左或右工具条，同侧面板 | 按钮与目录树一起换边；打开文件仍进入当前工作台的中央编辑页 |
| Docker 总览 | 左或右工具条，同侧面板 | 原实例和选择状态随位置移动；容器详情、日志继续使用插件已有页面 |
| 系统状态 | 左或右工具条，同侧面板 | 移动和收起不改变采集与暂停策略 |
| 网络隧道 | 左或右工具条，同侧面板 | 移动和收起不启停规则，也不重新建立连接 |
| 消息、设置、服务器管理 | 现有全局入口 | 保持与服务器工具条的职责区分 |

不修改各插件的首次展开/创建策略。关闭最后一个终端后保留主区域空态及「＋」，不会自动补建终端。没有可用终端插件时，「＋」沿用既有默认动作与不可用原因，不生成假终端。

## 3. 点击与按钮状态

| 工具状态 | 按钮显示 | 点击结果 |
| --- | --- | --- |
| 已停靠、当前收起 | 所在侧普通按钮 | 在该侧展开原工具；尚未创建时按现有流程创建一次 |
| 已停靠、当前展开 | 所在侧选中按钮 | 收起面板，按钮恢复普通状态 |
| 同侧另一个工具正在展开 | 待切换工具为普通按钮 | 收起原面板、展开点击的工具；原实例继续存在 |
| 界面正在首次准备 | 同侧入口显示等待状态 | 不重复创建；失败显示原因并允许沿用原请求处理重试 |
| 插件异常或工具不可用 | 同侧入口带错误/不可用提示 | 显示原因和现有恢复入口；不创建替代实例 |
| 工具放入主区域或其他窗口 | 不在两侧保留普通停靠按钮 | 从“更多工具”定位或显式停靠，见第 6 节 |

选中表示“这个工具面板当前在这一侧实际展开”。中央页签被选中、工具曾经打开过、后台任务正在运行，都不能让侧边按钮变成选中状态。

按钮使用现有图标、主题和统一命中尺寸，左右镜像一致；展开强调靠近对应面板。悬停或键盘聚焦显示工具名称，鼠标按下并达到拖动阈值后显示拖动反馈。错误和等待状态同时提供文字，不能只靠颜色。

固定状态继续表示用户希望常驻工具条。**未固定工具在展开时临时显示同侧按钮**，收起后才回到“更多工具”。高度不足时优先保留当前展开工具及底部更多入口，其他按钮进入溢出列表。

## 4. 拖动与共同移动行为

### 4.1 可拖动对象与落点

- 工具按钮可以拖到另一侧，也可在同一侧上下排序。两侧工具条的空白区域都接受落点，目标侧收起时也可拖入；底部“更多工具”不是可排序工具。
- 面板标题的名称/空白区域可以拖动，菜单和收起按钮保持普通点击。拖到侧边工具条执行同一停靠操作；已有工具放入主区域和拆窗的入口继续可用。
- 拖动中显示工具名称、目标侧和排序插入线；从源侧到目标侧只预览，不实时移动实际面板或反复触发布局保存。
- 建议按下后移动超过 6 CSS px 才进入拖动；普通点击仍执行展开/收起。开始拖动后抑制本次点击，不能松手后又把刚移动的面板收起。
- 拖工具按钮到中央、窗口外或无效区域，松手取消。本次不通过拖侧边按钮创建浮窗；实际工具页面仍通过既有页面/面板迁移入口拆出。

### 4.2 松手后的结果

| 操作前 | 成功松手后 |
| --- | --- |
| 展开的 Docker 从右拖到左 | 右按钮移除，左侧目标位置出现选中按钮，原 Docker 面板在左侧展开 |
| 左侧原来展开文件目录树 | 文件按钮仍在左侧，目录树收起且状态保留；左侧改为显示 Docker |
| 收起的文件从左拖到右 | 文件按钮移到右侧，文件仍收起；右侧正在展开的工具保持不变，不创建文件实例 |
| 在同侧调整按钮顺序 | 只改变排序，不切换面板、不改变焦点和展开状态 |
| 拖动面板标题到另一侧 | 与拖动对应按钮的结果完全相同 |
| 菜单选择“移到左侧 / 移到右侧” | 与跨侧拖动一致，插在目标侧末尾；不另走只改面板的路径 |

跨侧移动当前展开工具后，源侧直接收起，不自动展开另一个工具；目标侧原工具只收起。目标侧使用其已有宽度，中央布局按现有最小尺寸规则重新计算。

移动只变更停靠、排序和可见性；`viewId`、插件实例、服务器 Context、草稿、文件选择、终端/隧道资源保持。源工具从未创建时，移动只保存它的入口位置，不能为了移动启动插件业务。

### 4.3 取消、并发与失败

- Esc、指针取消、窗口失焦、切换服务器或在无效位置松手：清理预览并保持原位置、排序、焦点与面板状态。
- 拖动期间工具关闭、插件失效或目标工作台进入关闭/迁移：提交时重新检查，拒绝过期操作，恢复源位置并提示原因。
- 指针经过插件 iframe 时仍持续接收拖动与松手；不用插件页面自行实现宿主拖放。
- 同一次松手只提交一次；拖动待处理期间不给同一工具发第二次布局操作。请求结果不明确时查询原操作，不用新请求重复搬动。
- 核心拒绝移动时，按钮和面板都保留原位置；不能只移动其中一个。
- 已提交布局但记忆写入失败：当前布局继续有效，明确提示“布局已调整，但未能保存，重启后可能恢复原位置”，重试只保存当前布局，不重做移动。

键盘或不方便拖动时，按钮右键菜单提供“移到左侧 / 移到右侧”“上移 / 下移”和现有固定/取消固定操作；无可移动方向时禁用。拖动成功后焦点跟随原工具，取消后返回原触发对象；隐藏内容不能继续持有输入焦点。

## 5. 位置与记忆由谁决定

核心维护工具在当前工作台的布局。前端把按钮与实际面板从**同一份布局快照**绘制出来，插件只提供视图类型、图标、标题和推荐位置。

入口位置的读取顺序：

1. 已有逻辑工具：读取实际所在的工作台和停靠/中央位置，包括当前收起的工具。
2. 尚未创建的工具：读取当前服务器、当前布局槽保存的入口位置与排序。
3. 没有保存位置：读取已有本机默认偏好；再回退到插件推荐值。

不能先按 `preferences.side` 放按钮，再通过另一份 `host.left/right` 放面板。跨侧移动、面板菜单、从中央重新停靠、返回来源、窗口关闭后的工具回收，都必须更新或投影成相同的位置事实。

| 数据 | 范围与保存方式 |
| --- | --- |
| 工具实际停靠侧、入口顺序、中央/独立窗口位置 | 当前服务器及其工作台布局槽，复用 `workbench-layout.json` |
| 左右宽度、布局结构与工具展开意图 | 复用既有工作台布局记忆；紧凑显示不覆盖保存意图 |
| 用户固定入口与新工作台推荐偏好 | 继续使用既有 `ui-layout.json`；展开时的临时按钮不改固定偏好 |
| 当前实例、连接、命令、正文和任务 | 原有运行期/插件业务状态，不因布局保存而自动恢复 |

布局保存记住稳定工具定义，不写入运行期 viewId、会话身份或业务正文。同一服务器拆出的工作台保留各自布局槽；切换服务器或重开后按钮与恢复的实际工具位置一起恢复。重开仍不自动连接服务器或执行终端命令。

## 6. 主区域、独立窗口与更多工具

保留已有工具放入主区域和独立窗口的能力。空间承诺明确为：**普通侧边按钮表示当前窗口这一侧停靠的工具**。当工具离开侧栏，其导航改用中央标签、独立窗口或“更多工具”，避免用左侧选中按钮表示右边或其他窗口的内容。

两侧底部的“更多工具”共用工具清单，显示名称及位置，例如“左侧 · 收起”“右侧 · 展开”“主区域”“其他窗口”。清单不混入终端等中央页面定义，也不将另一侧工具复制成常驻按钮。

- 点击工具名称：打开/定位已有位置；在主区域的激活原标签，在其他窗口的显示并聚焦原窗口，均不隐式搬回。
- 当前窗口的中央工具可通过“停靠到左侧 / 停靠到右侧”显式停靠，按钮与工具一起进入选定侧。其他窗口的工具先定位到原窗口，再从其工具菜单移窗或返回来源；跨窗继续使用原有准备、交接和失败回滚流程，已有实例只移动、不复制。
- 未固定或溢出的侧栏工具从这里打开，展开期间获得同侧临时按钮。缺失插件保留原有布局信息和不可用原因，插件恢复后沿用保存位置。
- 清单为空显示“没有可用工具”；菜单靠近触发位置，底部向上展开，搜索、纵向溢出及 Esc 焦点返回沿用现有规则。

## 7. 最小实施范围与兼容

| 位置 | 需要解决的完整问题 |
| --- | --- |
| [components.ts](../src/components.ts) | 工具入口改从实际位置投影；排除中央页面的 `locateEntry`；按钮/面板标题拖动、预览、菜单、溢出与更多清单使用同一规则 |
| [components.css](../src/components.css)、[workspaces.css](../src/workspaces.css) | 两侧一致的按钮状态、落点与插入反馈；保留现有主题、尺寸和 iframe 表面层 |
| [component_ui/layout.rs](../src-tauri/src/component_ui/layout.rs)、[workbench_layout.rs](../src-tauri/src/workbench_layout.rs) | 将入口位置/排序与实际工具布局共同处理，覆盖尚未创建、隐藏、中央及返回来源等状态 |
| [workbench_memory.rs](../src-tauri/src/workbench_memory.rs) | 在既有记忆格式中保存工具入口顺序与未创建工具的位置；兼容已有停靠与默认偏好 |
| [布局测试](../scripts/test-workbench-layout.mjs)、[交互测试](../scripts/test-workbench-interactions.mjs) | 验证真实核心快照、拖动结果、焦点和 iframe 不重建，覆盖第 8 节 |

宿主按已有 `container: sidebar` 识别侧栏工具，对 `editor/dialog` 不生成工具按钮。旧插件声明的 `locateEntry` 不再让中央页面出现在侧边；官方终端随独立插件更新清理该推荐字段，旧版终端在新核心上也必须符合新入口规则。实际需要改动的插件清单及测试夹具在实施时同步核实，不能只改终端 ID 特例。

旧布局若按钮偏好与实际停靠冲突，优先实际停靠；中央页旧固定入口忽略，不删除已有页面、插件数据或默认新建配置。当前只增加宿主布局行为，不要求插件更换 RPC 主版本，不增加生产依赖或新的布局框架。

## 8. 可验收行为与交付范围

| 编号 | 操作 | 必须看到的结果 |
| --- | --- | --- |
| D01 | 新连接、切换服务器、终端位于任意中央组/独立窗口 | 左右工具条及更多工具均无终端；标签栏「＋」仍按现有规则新建 |
| D02 | 把已展开 Docker 从右拖到左，再拖回 | 每次只有同侧一个按钮和面板；实例、选择与原 iframe 保持 |
| D03 | 把未创建/收起的工具拖到另一侧 | 只变位置，不创建实例、不抢占目标侧面板；之后点击在新侧打开 |
| D04 | 目标侧已有文件树，移入展开的 Docker | Docker 展开、文件树收起；文件导航与后台任务保持 |
| D05 | 同侧上下排序、原位松手、微小移动点击 | 排序不切页；原位无操作；点击不会误拖，拖后不会追加收起 |
| D06 | 拖标题、按钮及菜单移侧 | 三种入口产生相同布局、按钮位置和展开结果 |
| D07 | Esc、失焦、指针经过 iframe、无效松手、切换服务器 | 手势有明确结束，取消不修改布局，无残留预览或错位 |
| D08 | 拖动时关闭/迁移、重复提交、核心拒绝和保存失败 | 旧请求不覆盖新状态；布局与保存失败按第 4.3 节处理 |
| D09 | 工具移入中央、拆窗、返回与回收 | 普通侧边按钮只出现在实际侧栏；更多清单定位原实例，显式停靠才搬回 |
| D10 | 切换服务器、移窗、重启恢复旧/新布局 | 各工作台位置与排序保持，其他服务器不被重排；旧冲突以实际停靠为准 |
| D11 | 未固定工具展开、20 个工具、短窗口与三主题 | 活跃同侧入口可见；其他工具可从更多找到；无双侧选中或不可达入口 |
| D12 | 文件选择/草稿、系统采集与运行中的隧道随工具移动/收起 | 状态与资源连续，无复制实例、重复连接或意外停止 |

实施后运行相关 `npm run check`、`npm run scripts:test`、`npm run test`、`npm run layout:test`、`npm run interactions:test` 及 `npm run build`；插件声明变化时执行 `plugin:check` 和对应独立插件构建。回归接入现有入口与工作流，不在设计阶段添加不存在的命令。

五个正式系统与架构分别验证原生构建、打包及实际包启动退出；Windows、Linux、macOS 的真实拖动、窗口失焦、键盘菜单和缩放分别记录。浏览器示意不能替代 Tauri 插件 iframe、真实资源或原生设备验收。

本文保留功能方案与可操作示意，源码整改、独立构建和实际平台证据统一维护在[实施记录](implementation-tool-docking.md)，不借用历史通过结果。核心与插件版本未升级，尚未发布。
