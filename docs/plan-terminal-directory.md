# 终端目录自动识别与文件跟随方案

2026-11-09。状态：实现与验收见[实施记录](implementation-terminal-directory.md)。本方案补充[组件通信设计](plan-component-communication.md)中尚未解决的默认 shell 集成，不重做共享状态基础设施。现行行为仍以[使用指南](usage.md)和[实施记录](implementation-component-communication.md)为准。

## 1. 对需求的理解

用户截图中，终端已经从 `/home/dw` 切到 `/mnt/data`，文件侧栏仍停在 `/home/dw`，“跟随终端”看起来已经开启。

据此推断，用户希望的是：**连接服务器后，终端与文件面板自然协作；终端换目录，文件面板自动定位；无需配置 shell、主机名或理解目录报告协议。不能跟随时，界面直接说明原因。** 这是一套默认可用的工作流，不只是增加一个能取到路径的接口。

本次采用以下产品判断：

- 使用场景是运维工作台，优先可靠、少操作、可恢复；沿用现有面板、主题和目录树，不重新设计视觉风格。
- 以当前活动终端为跟随对象。文件面板手动浏览不会改变终端，也不会因为终端反复报告同一路径而被拉回。
- 自动识别失败不影响连接、终端输入或文件浏览；无法确认时保留文件面板原位置并解释状态。
- 本轮首先完整解决截图代表的 Linux 登录 shell 场景；客户端五个正式平台与远端 shell 的支持范围分开验收。

代表性验收：一台未配置 SoDeck、未添加目录报告脚本的 Ubuntu 服务器，首次连接后执行 `cd /mnt/data`，提示符返回后文件侧栏自动展开并定位到该目录。

## 2. 现在是什么方式，为什么看起来不稳定

当前链路如下：

```text
远端 shell 自行输出 OSC 7 目录报告
  → 终端页面的 xterm 解析报告并校验手工配置的主机名
  → 核心保存 terminal.location.v1
  → 文件插件读取活动终端位置
  → 当前文件服务验证目录后定位目录树
```

OSC 7 是一类通常不会显示在终端画面里的控制序列，用来告诉终端当前目录。普通提示符里显示了 `/mnt/data`，并不代表 shell 发出了这种报告。

| 已确认的实现 | 对使用体验的影响 | 证据 |
| --- | --- | --- |
| 核心只申请 PTY 并启动登录 shell，没有自动安装目录报告钩子 | 普通 SSH 连接成功不等于能识别目录 | [核心终端](../src-tauri/src/terminal.rs)的 `run` |
| `directoryReportHost` 默认空字符串；空值直接拒绝报告 | 新安装默认不能上报，即使 shell 恰好支持 OSC 7 | [设置声明](../plugins/terminal/release.json)、[目录解析](../plugins/terminal/ui-src/location.js) |
| 报告 URI 的 hostname 必须与配置值一致；连接 IP、显示名和 shell 主机名可能不同 | 填了服务器地址也可能没有效果 | [目录解析](../plugins/terminal/ui-src/location.js)的 `parseOsc7` |
| 该字段属于跨服务器共享的终端组件设置 | 一台机器配好后，另一台不同 hostname 的机器仍可能失败 | [组件设置设计](plan-component-settings.md)、终端设置声明 |
| 文件按钮默认开启，按钮只表达保存的偏好，没有表达报告是否可用 | 无报告时按钮仍可点击且显示开启，实际不导航，也不说明缺少什么 | [文件共享状态](../plugins/files/ui/shared-state.js) |
| 真实联动测试先写入 hostname，再向测试 shell 手工添加报告钩子 | 已有测试证明配置后的联动，没有覆盖首次连接默认体验 | [组合测试](../scripts/test-component-communication.mjs) |

本次在现有代码层复现了两个确定行为：合法的 `file://dw/mnt/data` 在主机名留空或填成连接 IP 时被拒绝；没有目录记录时，“跟随终端”的 `aria-pressed` 仍为 `true`、按钮可用，但导航次数为 0。匹配 `dw` 时解析成功。

这能解释截图中的现象，但尚未连接用户那台服务器核对其 shell、插件版本和配置，因此不把截图的具体触发条件认定为已远程复现。

## 3. 方式比较与推荐

SSH 的 PTY 是终端字节流，没有一个通用的“查询这个交互式 shell 当前目录”请求。要么由真实 shell 报告，要么取得服务端对应进程的信息。

| 方式 | 优点 | 关键问题 | 决定 |
| --- | --- | --- | --- |
| SoDeck 自动为当前 shell 安装目录报告钩子 | 知道实际 shell 的目录；不依赖提示符长相；目录变化后及时上报；无需不断查询 | 需要按 shell 适配启动与钩子，保留用户配置行为 | **作为默认方案** |
| 读取 Linux `/proc/<pid>/cwd` | 得到指定进程的实际目录，较少受提示符影响 | 仍需可靠获得该 PTY 的 shell PID；父 shell 与前台子 shell 不一定同目录；受进程可见性、权限和命名空间影响；持续读取需要调度；不通用于其他远端系统 | 本轮不增加第二套自动路径；若后续有无法使用钩子的真实需求，再做 Linux 专项 |
| 保持手工 OSC 7 配置 | 实现改动少，可兼容已有用户脚本 | 配置成本与全局 hostname 问题仍在 | 保留高级兼容，不作为默认使用要求 |
| 在另一条 exec 会话执行 `pwd`，或读取 SFTP 初始目录 | 容易实现 | 读到的是另一进程/文件服务的目录，不是用户正在操作的 shell | 不采用 |
| 从提示符或输入的 `cd` 推断 | 不要求 shell 配合 | 自定义提示符、命令失败、函数、软链接、`cd -`、子 shell 都会产生误判 | 不采用 |

推荐的本质是**让 SoDeck 自动完成 shell 集成，并把“已开启”与“已经生效”分清楚**。更换 OSC 7 编码本身不会消除配置门槛；放宽 hostname 检查也不能建立可靠的文件系统对应关系。

## 4. 用户应该看到的行为

### 4.1 正常流程

1. 用户连接服务器，新终端默认尝试自动识别；无需填写主机名或改远端配置文件。
2. 第一次可信目录报告到达后，文件面板自动定位登录目录，不要求用户先输入一次 `cd`。
3. 执行 `cd`、`pushd`、函数内切换目录等操作，shell 回到可输入状态时报告实际结果；切换失败则保持原目录。
4. 文件面板展开祖先与目标目录、选中目标并滚动到可见位置，保留其他树分支。焦点继续留在终端，不打断输入。
5. 切换到终端 2 时跟随终端 2；后台终端输出不能抢走位置。切到编辑器时暂停跟随。

“当前目录”定义为受集成 shell 最近一次在提示符就绪时确认的目录；运行中的任意程序、嵌套环境不自动视为同一个 shell。

### 4.2 跟随状态与反馈

保留工具栏“跟随终端”开关，按下态只代表用户的偏好。利用文件侧栏现有底部状态区域增加一行简短运行状态，不继续挤压截图中已经较满的工具栏。正常使用不弹消息；较长说明通过状态详情展开，不能只靠颜色或悬停表达。

| 实际情况 | 建议文案 | 行为与恢复 |
| --- | --- | --- |
| 尚在启动、等待首个有效报告 | `正在识别终端目录…` | 保留位置；长时间无报告时改为未就绪并给出原因，不能无限转圈 |
| 已取得并成功定位活动终端目录 | `跟随：终端 1` | 后续有效目录变化才定位 |
| 用户手动浏览了别的目录 | `已手动浏览，下次切换目录时跟随` | 不因重复提示符回跳；可在状态详情“定位到终端目录”一次性返回 |
| 活动 shell 正在执行命令 | `终端忙碌，保留当前位置` | 内部暂停自动定位；短命令不立即切换文案，避免闪烁 |
| 中央活动页不是终端 | `已暂停：当前不是终端` | 返回终端时定位其当前有效目录 |
| 首次集成失败或 shell 暂不支持 | `当前终端无法自动识别目录` | 详情说明失败阶段及实际 shell；普通终端继续可用；修正配置后新建终端重试 |
| 缺少所需核心/插件能力 | `当前版本不支持自动目录识别` | 详情指出需更新的组件，复用既有更新入口 |
| 已报告目录但文件服务无权访问/无法对应 | `无法浏览终端目录` | 保留原位置；详情显示目标目录与原因，并允许重试定位；不自动提权 |
| 终端退出或服务器断线 | `已暂停：终端已退出` / `已暂停：连接已断开` | 旧目录只作历史信息；重连后按现有规则新建终端 |
| 用户关闭跟随 | `手动浏览` | 保存已有全局文件偏好；重新开启时立即定位当前有效目录 |

详情里的“定位到终端目录”只在有可验证报告时可用。它读取当前事实并重新尝试文件定位，不向终端输入 `pwd`、回车或任何补偿命令。

### 4.3 不打断手动操作

- `cd` 后跟随；在同一目录反复按回车、执行 `ls` 或输出大量内容，不把用户手动浏览的位置拉回。
- 运行命令导致的短暂忙碌不能清空“最近处理过的目录”标识；否则每次普通命令结束都会误触发回跳。
- 文件侧栏隐藏时不请求导航，显示后读取最新有效目录。终端隐藏或移窗不应重启 shell 或重复集成。
- A→B→C 连续切换时只提交最新定位，旧目录请求即使最后返回也不能覆盖 C；手动导航会取消尚未完成的自动定位。
- 维持单向跟随。点文件夹不会偷偷向正在运行的终端发送 `cd`。从文件目录新建终端可另做完整功能，不并入本次。

## 5. 实现方向与责任边界

### 5.1 在创建终端时集成

终端插件为支持的 shell 准备随插件发行的轻量启动脚本，在新 PTY 的启动路径里完成集成。正常使用不需要远端安装 Agent，不要求 root，不联网下载脚本，不永久改写 `.bashrc`、`.zshrc` 等用户文件。

核心当前只支持默认登录 shell，需要补充一个可选、版本化的通用 PTY 启动能力，建议能力名为 `terminal.launch.v1`：由 `terminal.open` 接收插件提供的启动命令，旧调用继续启动默认 shell。SSH 适配层在同一 PTY channel 上执行启动命令；后续传输实现只需要实现相同启动语义。插件不直接操作 SSH channel，也不保存认证资料。

启动脚本、shell 类型识别和报告解释属于终端插件；核心只管理启动、字节流、资源、超时与取消。识别环境可以复用 `session.exec.v1`，但不能把那条 exec 的 `pwd` 当成交互终端目录，也不依赖系统状态插件必须存在。

实施前先用真实 Bash/Zsh 验证启动方案，必须同时满足：

- 启动用户原有 shell，保留约定的登录/交互行为；不能为目录识别把用户从 Zsh 换成 Bash。
- 用户启动配置按正确顺序执行且不重复；主题、已有钩子、命令历史、`$?` 和终端控制行为保持。
- 钩子在用户配置完成后接入，链式保留现有 `PROMPT_COMMAND`、Zsh hook 等；不能覆盖原函数或直接替换提示符。
- 不依赖远端额外安装 Python、Node.js 等运行时。若某 shell 需要临时脚本，使用当前用户专属临时位置，退出清理；强断残留的清理只处理本插件可确认归属的文件。
- 识别和准备有界、失败回退普通终端；shell 一旦已交给用户，就不能为“重试识别”重新执行启动流程、重放输入或杀掉正在运行的程序。

这是实现需要先证明的部分，不把“加一条 PROMPT_COMMAND”当成完成自动集成。

### 5.2 报告真实目录与活动状态

受控集成在首次提示符和每次后续提示符就绪时报告实际目录；同时报告命令开始/提示符就绪，使文件面板知道什么时候可以认为目录对应当前 shell。

报告绑定完整 Context、terminalId 和本次集成实例。协议可以沿用 OSC 控制序列承载，但 SoDeck 自动集成应使用明确的会话标记和有界消息格式，区分自身报告与远端应用偶然输出的 OSC 7；不要把所有匹配主机名的输出都当作同一来源。

会话标记用于避免串台和旧报告误用，不是插件权限、远端身份认证或文件系统一致性的证明。对路径进行正确的 URI/载荷编码，支持中文、空格、`%`、`#` 等字符；非法/过长输入有明确失败状态，不无限积累缓冲。

当前文件服务默认视角与登录 shell 视角一致，才允许映射。继续复用 `files.location.v1` 的 realpath/stat 检查。**“这个路径在文件服务中存在”只能证明可访问，不能证明它和容器内同名路径是同一个目录。** SFTP chroot、受限账户等视角不能确认时应降级，不能仅移除 hostname 校验就发布 `session-default`。

### 5.3 嵌套环境的诚实边界

第一轮自动集成只承诺本次启动的受控登录 shell。进入 `ssh`、`docker exec`、`sudo -i`、未集成的子 shell、tmux/screen 时，外层 shell 已在执行命令：保留文件面板位置，不接受这些环境碰巧输出的同名目录报告；返回外层提示符后自动恢复。

钩子需要绑定实际受控 shell，避免子进程继承后冒充外层就绪。对 `exec` 替换 shell、钩子被用户配置移除等情况显示失去识别，不能继续把上次目录当作当前目录。这里不承诺识别所有嵌套程序名称；无法确认时使用“终端忙碌/目录未就绪”的准确状态。

自动跨容器、跨主机和跨文件系统映射不在本轮范围；如果以后要支持，应由对应会话/文件能力明确提供映射，而不是靠 hostname 或字符串猜测。

### 5.4 复用现有共享状态与生命周期

| 对象/职责 | 唯一管理者 | 生命周期要求 |
| --- | --- | --- |
| PTY、启动任务和底层连接资源 | 核心 | 创建即登记归属；关闭、断线、插件退出取消并释放；迟到结果不能恢复已关闭资源 |
| shell 集成、报告可信度与活动状态 | 终端插件 | 每个终端只集成一次；识别失败可降级；移窗不重复启动；配置关闭即使报告失效 |
| 当前终端位置事实 | 终端插件写入现有 StateHub | 复用终端/Context/输出位置去重；退出、断线、输出缺口与上下文变更使事实失效 |
| 跟随偏好、目标目录与导航请求 | 文件插件 | 偏好与运行状态分离；仅活动终端触发；每次提交结果复核 Context 与导航序号 |
| 视图和状态文案 | 对应插件页面 | 重挂载先读最新事实；恢复屏幕快照不重新发布历史报告 |

继续使用 `terminal.location.v1` 的 `known/unknown` 和现有位置字段，按兼容规则增加可选活动状态、原因码等信息；新字段缺席时按旧数据处理。忙碌期间不把旧路径作为新的已知报告，文件插件单独保留上次成功处理的目录以避免重复定位。若实现证明必须改变旧字段语义，则另起主题主版本，不能悄悄破坏旧消费者。

故障原因使用稳定原因码；界面显示普通语言，诊断详情显示 shell、报告来源、最近确认时间、失败阶段。普通日志用于排查，不自动变成消息中心警告，也不记录完整终端输入。

### 5.5 兼容与支持范围

- 首次完整交付以远端 Linux Bash、Zsh 为范围，两者都通过自动启动与用户配置兼容验收后才声明支持。截图中的 Ubuntu/Bash 是第一优先验证环境。
- Fish、PowerShell 和其他远端 shell 在后续有对应适配与真实验证后启用；第一轮明确显示支持边界，普通终端继续可用。客户端 Windows/Linux/macOS 不决定远端 shell 类型。
- 五个客户端正式目标仍然分别构建、打包并验证实际包；不能把“远端第一轮支持 Linux shell”理解为只做 Linux 客户端。
- 新插件先检查可选启动能力。旧核心维持原普通终端/手动报告能力，并准确说明缺少自动识别；新核心必须支持旧插件不传启动参数的行为。
- 新自动路径不要求 hostname，也不复用旧全局 hostname 作为自动识别身份。已有手工 OSC 7 配置保留兼容读取与高级入口；同一终端明确选择一种报告来源，不混用两个来源抢写。
- “跟随终端”已有偏好继续保留；终端集成设置调整只作用于新终端，现有会话不进行运行中补注入。核心与插件继续独立版本、独立分发，不新增生产依赖和远端安装流程。

## 6. 实施顺序与验收

### 第一步：建立首次连接的失败用例

在现有隔离 SSH 与三插件组合测试基础上，增加未配置 hostname、未配置报告脚本的真实 Bash/Zsh 场景。验收脚本只连接、输入用户命令并检查文件面板，不能通过测试专用代码帮产品安装钩子。保留现有手工 OSC 7 用例验证向后兼容。

### 第二步：补齐自动启动和可见状态

先验证真实 shell 的启动配置兼容，再接入通用 PTY 启动能力、报告与文件跟随状态。一次完成创建、首次定位、后续变化、失败降级、隐藏/移窗和退出清理；只让按钮增加说明不能算解决“首次连接可用”。

主要影响：[核心终端](../src-tauri/src/terminal.rs)、[RPC 分派](../src-tauri/src/plugins/dispatch.rs)、终端插件进程与 `ui-src`、[文件跟随控制器](../plugins/files/ui/shared-state.js)、相关设置元数据及测试夹具。`plugins/terminal/ui` 是构建产物，按既有脚本生成。

### 第三步：按行为验收后再独立交付

| 场景 | 必须看到的结果 |
| --- | --- |
| 干净 Ubuntu/Bash、Linux/Zsh，首次连接 | 无需手工配置；首个提示符确认目录；`cd /mnt/data` 后自动定位。在隔离测试网络下，收到有效报告到定位完成不超过 1 秒 |
| 两台不同 hostname 的服务器；分别以 IP/域名连接 | 各自自动识别，不修改全局 hostname，不相互影响 |
| 自定义提示符、已有提示符钩子、登录配置、历史设置 | 原行为保持；初始化不重复；最后命令退出状态不被报告脚本改写 |

| 手动浏览后执行 `ls`、按回车、运行长命令 | 同一路径不回跳，焦点留在终端；状态不过度闪烁 |
| 多终端、非终端活动页、快速 A→B→C、手动导航与自动导航并发 | 只跟随正确来源；旧异步结果不能覆盖当前选择、滚动和路径 |
| 容器、嵌套 SSH、`sudo -i`、tmux、`exec` 替换 shell | 不误认外层当前目录；退出返回受控 shell 后恢复；无法恢复时显示原因 |
| SFTP chroot、路径存在但视角不同、无访问权限 | 不用“路径存在”冒充相同文件系统；保留位置，给出准确原因 |
| 不支持的 shell、受限启动、钩子冲突、握手失败/迟到、格式错误 | 普通终端仍可使用；目录增强降级；不输入补偿命令、不无限重试 |
| 隐藏、移窗往返、输出追赶/缺口、断线重连、插件退出、取消关闭 | 不重复集成、不复活旧报告；释放订阅与资源；新 Context 重新建立识别 |
| 新旧核心/插件组合、保留旧手工配置 | 基础终端不回归；能力不足说明准确；旧配置不阻挡新自动路径 |
| 五个客户端原生包 | 对应架构程序启动/退出、真实插件加载、终端输入与目录跟随验证；记录实际远端 shell 和未覆盖范围 |
