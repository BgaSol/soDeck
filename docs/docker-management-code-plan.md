## 1. 建议采用的修改方式

保留现有 SSH 工作区、Docker 列表监控、容器日志和终端，在其上补齐三个部分：

1. **Docker 查询与操作模块**：结构化详情、类型明确的管理命令、独立执行连接。
2. **App 级 Docker 任务管理**：提交去重、并发约束、后台执行、多窗口同步、结果核对。
3. **现有侧栏内的功能组件**：容器操作与详情、镜像、Compose、创建表单、空间与资源。

按四批完成 P0–P2，每批保持 App 可构建、可使用、可单独验收。第一批是完整的日常容器管理流程；后续批次复用同一套基础设施。确认本方案后按此顺序实施，不需要把全部功能塞入一次代码提交。

不增加 Docker SDK、前端状态管理框架或动画框架。使用现有 Rust SSH、Tauri Channel、React、Lucide、主题变量与控件体系。服务器仍通过已有已验证 SSH 连接路径访问，使用当前账号权限。

## 3. 数据与执行链路

```text
DockerPanel 与功能组件
  ├─ MonitorProvider → MonitorManager → Docker 引擎／容器／镜像共享列表
  └─ DockerManagementProvider → DockerManager
       ├─ 详情和资源数据：按可见对象订阅，共享查询
       ├─ 管理任务：校验 → 占用操作范围 → 独立 SSH 执行 → 核对
       └─ 完成／失败／待确认 → Channel 更新 → 相关缓存失效与共享刷新
```

| `src-tauri/src/docker/model.rs`    | 引擎绑定、详情、能力、动作、预览、任务、结构化错误                |
| `src-tauri/src/docker/query.rs`    | 检测、列表、受控 inspect 查询和解析                               |
| `src-tauri/src/docker/executor.rs` | 独立 SSH 连接、双输出流读取、截止时间、提交阶段跟踪、有限输出缓冲 |
| `src-tauri/src/docker/tasks.rs`    | DockerManager、任务准入、去重、互斥、订阅、核对、生命周期         |
| `src-tauri/src/docker/commands.rs` | Tauri 命令、窗口／会话权限验证、参数和结果转换                    |

第二批增加 `images.rs`、`stats.rs`；第三批增加 `compose.rs`、`create.rs`、`store.rs`；第四批增加 `resources.rs`、`cleanup.rs`、`transfer.rs`。模块职责以最终代码体量为准，小功能不为拆分而拆分。

现有日志和终端继续调用兼容导出的容器目标／命令检查，不改写其采集、存档、PTY 与历史机制。

### 3.2 引擎和对象身份

新增内部 `EngineBinding`，由后端根据真实会话和监控状态生成。前端只保存可展示字段和不可自行构造的 `engineToken`。

绑定至少包含：已验证连接身份、监控实例代次、`engineGeneration`、Endpoint，以及探测可得的 daemon 标识和能力信息。daemon 标识用于辅助发现同一 Endpoint 下的引擎替换，不宣称能证明每一次守护进程重启。

每次提交均执行以下检查：

1. 用现有 `State.spec` 校验当前窗口对会话的所有权，同时校验窗口 generation 和 App 运行状态。
2. 用 MonitorManager 提供的方法核对当前引擎绑定；不直接暴露其内部锁和数据结构。
3. 后端确认目标仍是预期对象，容器使用完整 64 位 ID，名称只用于展示；镜像区分完整内容 ID 和 Tag 引用。
4. 建立执行连接后再检查引擎及对象前置条件，然后向固定 Endpoint 发出命令。

引擎变化后，旧任务保留原目标记录，新页面不接收旧目标的详情或列表更新。已提交任务不会因用户切换 context 而改投其他引擎。不可用的引擎显示过期数据和原因，写操作要求重新建立有效绑定。

### 3.3 查询与管理执行分离

现有 `remote_read` 继续承担有界查询。新增管理执行器复用 `connect_verified`，独占自己的 SSH session，不占用主终端，也不共享监控的 session。

- 使用非阻塞读写及操作 deadline，同时读取 stdout／stderr；处理已有连接初始化超时，避免长操作仍被底层短超时截断。
- 命令由 Rust 枚举和结构化参数生成，统一 shell 转义和字段校验；IPC 不接收任意 shell 命令。
- 保持固定 `docker --host` 目标及当前的 context 环境处理；需要当前实现尚不支持的 context TLS／SSH transport 时，明确返回能力不可用。
- 输出使用有界环形缓冲，清理控制字符并合并进度事件；UI 订阅慢或关闭不阻塞远端输出读取。错误摘要、命令展示和任务记录隐藏敏感值。
- 增加 `TrafficPurpose::DockerAction`，归入现有其他通信类别；Docker 查询仍归监控，文件字节流归传输。

停止宽限和客户端等待时间分开处理。Docker stop 可能在宽限后强制终止进程，也支持无限宽限；不能用当前 6 秒查询超时直接包住 stop。[D1] 默认尊重容器／引擎停止配置，能取得有限宽限时给等待期限留足额外时间；未知或无限宽限使用有界观察期限，超时进入“结果待确认”，不偷偷缩短远端宽限。

拉取和 Compose 使用各自更长的 deadline。初值在真实慢操作测试中固定，并集中放在操作策略中，不散落在组件或 IPC 函数里。

## 4. 任务机制与 IPC 契约

### 4.1 第一批接口

以下是接口职责，不是已新增的代码：

| 拟定 IPC                            | 输入要点                                                      | 返回／行为                                           |
| ----------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------- |
| `subscribe_docker_management`       | sessionId、窗口代次、Channel                                  | 返回订阅 ID；首帧包含引擎绑定、相关任务和 revision   |
| `update_docker_management_interest` | 订阅 ID、可见详情目标；第二批增加 stats 目标                  | 只采集正在查看的数据；多个窗口查看同一对象时共享采集 |
| `unsubscribe_docker_management`     | 订阅 ID                                                       | 幂等解除观察，不取消已接受的任务                     |
| `prepare_docker_operation`          | sessionId、engineToken、类型化动作和目标                      | 返回需确认的对象、影响、前置条件与短时有效 previewId |
| `submit_docker_operation`           | sessionId、engineToken、requestId、动作；需确认时附 previewId | 快速返回 operationId，执行结果通过订阅发送           |
| `reconcile_docker_operation`        | 有权限的订阅／会话、operationId                               | 只读取原目标的当前状态，不重放原命令                 |
| `list_docker_operations`            | 订阅 ID、游标                                                 | 打开操作记录时读取有界分页；用于重订阅恢复和核对     |
| `docker_operation_summary`          | 主窗口权限                                                    | 返回活动任务和待确认任务数量，接入退出流程           |

普通启停使用提交时预检查，不增加每次操作都要确认的弹框。删除、AutoRemove 等会改变后果的动作先获取预览；预览与对象、引擎、动作参数绑定。预览失效或影响范围变化时重新确认。

Channel 帧使用单调 revision、订阅 ID 和引擎绑定过滤旧消息。采用有限待发送帧与进度合并；需要背压时沿用现有转发模块的 ack 模式。初始快照和后续增量之间不能丢失刚接受的任务。

### 4.2 任务与详情数据

`DockerOperation` 至少包含 operationId、requestId、原始目标、动作、阶段、创建／提交／结束时间、命令结果、观察结果、错误、允许的后续动作及 revision。

`ContainerDetail` 第一批包含状态、健康状态、退出码、OOM、错误摘要、重启策略／次数、AutoRemove、停止配置、创建／启动／退出时间、端口、网络、挂载。每份详情带完整目标身份、更新时间和过期状态。

第一批的常规 inspect 查询只提取需要的字段，避免把环境变量等完整配置送入共享监控。健康失败输出限长处理。列表沿用现有不健康检测返回的对象 ID，不能把“未出现在不健康集合”推断成“已确认健康”。

第二批的环境变量、配置、原始 inspect 通过当前详情窗口的显式读取取得；默认隐藏敏感值，揭示结果只发给请求窗口。离开详情／迁移后重新隐藏，不进入广播任务记录、持久化快照或调试日志。

### 4.3 任务状态与结果判定

```text
已接受 → 校验中 → 执行中 → 核对中 → 已完成／失败／结果待确认
               └─ 尚未提交时可中止
```

“命令结果”与“当前对象状态”分别存储，避免把服务当前运行误当成操作证据：

| 情况                                         | 处理                                                               |
| -------------------------------------------- | ------------------------------------------------------------------ |
| 提交前发现目标已被删除、状态已变化、权限不足 | 返回明确前置条件错误；不发出写命令                                 |
| 启动前已经运行／停止前已经停止               | 返回“无需执行，当前已是目标状态”；不补发命令                       |
| 收到明确退出码 0                             | 记录命令完成，立即核对详情及共享列表；健康状态单独显示             |
| 命令完成但查询失败                           | 保留已知的命令结果，显示“执行完成，当前状态待刷新”；不改报操作失败 |
| 命令明确失败                                 | 保留失败阶段和可用诊断；仍刷新可能发生变化的对象                   |
| 请求可能已发送，但连接中断或等待超时         | 标记结果待确认；禁止自动重试，提供只读核对                         |
| 核对发现容器正在运行                         | 只能说明当前状态；无法单凭这一点证明此前 restart 成功              |
| 多步骤操作部分完成                           | 分别记录各阶段／对象；保留已创建对象和已完成变更                   |

任务记录应区分“尚未发送”“已收到 SSH 执行接受”“执行结果未知”，但不能声称 SSH 接受就等于 Docker 已完成。在进程崩溃、网络不确定等情况下，不承诺跨重启的恰好一次执行。

结果未知时保留冲突提示。只读核对更新观察事实；没有完成证据时不自动重放或自动标成功。用户确需再次操作时，重新预检并明确确认这是一次新操作，同时提示原操作仍可能完成。

### 4.4 并发、缓存与生命周期

- 同一 App 运行期间，以连接身份和 requestId 原子去重；同 ID、不同参数返回冲突。清理可见任务记录不能顺带清除仍有效的去重标记。
- 同一引擎／容器的互斥动作只允许一个；冲突立即提示，不排队积压相反的启停意图。不同容器可以在有界并发内执行；日志和终端仍独立可用。
- 镜像动作按实体和引用锁定；Compose、范围清理首版采用同引擎管理写操作独占，减少跨容器／镜像／网络的竞争。读取不受此写锁限制。
- 网络 IO 不持有全局 State、配置库或任务表锁。任务准入和配置删除需要短时协调，防止检查结束后又接纳新任务。
- 同一验证身份的多窗口共享任务。不同服务器别名可能连接到同一 daemon，本轮不跨别名合并权限或锁，外部竞争仍由执行前核对及引擎错误处理。
- 任务有结果后失效受影响详情／列表缓存，调用 MonitorManager 定向刷新；短时间内多项完成合并刷新。没有活跃监控订阅时记录失效，下一次打开立即取新数据。

现有 Monitor Entry 要求存在活跃主会话，因此任务不能寄生在 Entry 上。DockerManager 放入 App State：接受任务后持有已验证连接上下文和独立取消令牌，关闭页面、迁移标签、关闭主终端只解除观察。任务结束后释放连接与凭据引用，保留不含凭据的结果元数据。

| App 场景                       | 接入行为                                                                                         |
| ------------------------------ | ------------------------------------------------------------------------------------------------ |
| 切换监控／Docker、关闭详情     | 停止不需要的详情采样，任务继续                                                                   |
| 分离／合并标签、窗口重载／关闭 | 校验新窗口所有权并重新订阅；旧窗口订阅和确认草稿失效，不重交命令                                 |
| 主终端结束                     | 已接受任务继续使用独立连接；新写操作需要有效的工作区会话                                         |
| 退出 App                       | 汇总活动／待确认任务；停止接单，未提交任务中止，已提交任务有界收尾；关闭连接不代表远端操作已取消 |
| 删除服务器配置／重置配置数据库 | 执行中任务对路由各跳配置构成占用；配置操作与任务准入串行核对                                     |
| 再次启动 App                   | 首版重新读取远端现状，不自动恢复或重放管理命令                                                   |

首版操作历史仅保存在本次 App 进程内，活动和待确认记录优先保留，已完成记录有界展示。退出文案须区分现有持久化文件任务记录与 Docker 内存记录，不能沿用“所有任务记录下次都可核对”的笼统表述。没有后台常驻或跨 App 退出继续跟踪的承诺。

## 5. 第一批：容器基本操作与排障详情（P0）

### 5.1 交付范围

| 功能     | 正式行为                                                                  |
| -------- | ------------------------------------------------------------------------- |
| 启动     | 已创建／已停止容器可启动；先检查对象和状态                                |
| 停止     | 运行中容器可停止，重启中容器按能力提供停止；展示操作阶段                  |
| 重启     | 第一批面向运行中容器；已停止容器使用启动入口                              |
| 删除     | 仅允许可删除的非运行对象，默认不带 force 或 volumes；删除前确认可写层影响 |
| 排障详情 | 状态／健康、退出码／OOM、重启、时间、端口／网络、挂载                     |
| 任务反馈 | 当前对象忙碌、后台任务摘要、记录、失败原因、结果核对                      |
| 列表完善 | 需要关注筛选、明确的不健康标识、状态与任务进度分开显示                    |

AutoRemove 容器退出时可能自动删除并影响匿名卷。[D2] 因此 stop／restart 的预检查识别该配置；显示单独的影响确认，不能套用普通“停止后可随时恢复”的文案。第一批不开放暂停容器的额外管理动作；日志可继续使用。

### 5.2 前端拆分

新增 `src/dockerApi.ts`、`src/dockerManagement.ts`、`src/DockerManagementProvider.tsx`，分别承担 IPC／类型、状态合并、工作区订阅生命周期。

`DockerPanel.tsx` 保留导航和页面编排；按需要抽出 `src/docker/` 下的 `ContainerList`、`ContainerDetail`、`ContainerActions`、`DockerConfirmDialog`、`DockerOperationStatus`。组件不各自建立列表轮询，也不以本地定时器模拟真实任务。

实施时必须保留：虚拟列表、稳定排序、搜索筛选、选中项、返回滚动位置、键盘访问和旧窗口快照恢复。行主体与更多按钮采用独立可交互元素，修正现有按钮式 option 不适合嵌套操作按钮的结构。

界面沿用已评审的间距、字重、颜色、圆角和侧栏宽度；只在当前侧栏切换列表／详情。对话框默认焦点放取消、关闭后归还焦点；减少动态效果设置继续有效。任务进度通过适量状态播报反馈，刷新不抢焦点。

第一批不显示尚未交付的项目、创建容器、CPU／内存采样和清理入口。

### 5.3 首批验收门槛

- 启动、停止、重启、删除完整通过真实 Docker 验证；停止时间超过现有查询上限仍正确工作。
- 双击和跨窗口同时操作不会重复执行；主终端仍可输入，其他容器的操作可独立反馈。
- 对象被外部删除或同名重建、引擎切换、断线、无权限、命令成功但刷新失败均有正确状态。
- 删除不自动升级为强制操作；AutoRemove 有对应行为和提示。
- 窗口迁移不重交任务；退出、配置删除和数据库重置考虑执行中的任务。
- 320／360／480px 侧栏、深浅主题、键盘、减少动态效果下符合现有 UI 设计。

## 6. 第二批：资源诊断、补充操作与镜像（P1）

在第一批基础上追加以下内容：

| 功能                                   | 代码改动与边界                                                                                       |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 暂停／恢复、重命名、强制停止、重启策略 | 增加类型化动作、状态检查及所需确认；force remove 若启用，使用独立预览和影响确认，不混入普通删除      |
| stats／进程                            | `stats.rs` 与管理兴趣订阅；初始按约 5 秒采样，同对象多窗口共享；详情不可见后停止                     |
| 配置详情                               | 独立按需读取 Entrypoint、Command、Labels、环境变量与 inspect；敏感数据只进入请求窗口的临时状态       |
| 镜像详情                               | `images.rs` 建立镜像实体和引用模型，补充摘要、Tag、平台与被哪些容器使用                              |
| 拉取                                   | 复用后台任务；逐层／阶段反馈，输出不提供总量时不虚构百分比；使用远端已有 Registry 认证               |
| Tag 与删除                             | 区分新增／移除引用及删除实体；目标 Tag 已存在时重新确认；普通删除不自动强制                          |
| 端口转发                               | 扩展 `ForwardOpenRequest` 与草稿初始化，传入服务器、宿主发布地址／端口和来源说明；保留现有未保存草稿 |
| 挂载文件定位                           | `SessionWorkspace` 复用现有 revealRequest 流程；只对已确认属于当前 SSH 主机的 Bind Mount 提供定位    |

镜像的多个 Tag 可以指向同一内容 ID，移除某个 Tag 与删除镜像内容是不同结果。[D3] 删除预览必须标明究竟操作哪个引用／实体；即使预览没有引用，执行前仍复核，并处理引擎侧的新引用冲突。

stats 明确 CPU 统计口径；缺失值显示不可用而非 0。累计 IO 与速率分开，重启或计数回退时重置速率基线。只保留当前查看需要的有限样本，不建设完整容器时序数据库。

端口联动使用已经发布到宿主的端口，并校验 TCP、IPv4／IPv6 与宿主归属；不把容器内部 IP 直接作为默认转发目标。不能确认引擎宿主属于 SSH 服务器时，保留显示／复制并说明原因。打开转发草稿不自动启动规则。

验收重点：同镜像多 Tag、停止容器仍引用镜像、鉴权失败／拉取中断、采样隐藏后停止、转发窗口已有未保存草稿、外部引擎路径和端口不被误认为当前主机资源。

## 7. 第三批：Compose 与创建容器（P1）

### 7.1 Compose 项目管理

新增项目类型、项目列表／详情、配置关联与更新确认组件；后端通过 `compose.rs` 管理探测、配置预检和项目动作。没有可用 Compose 插件时显示说明，已有容器／镜像能力继续工作。

项目关联记录包含稳定服务器配置标识、引擎定位信息、项目名、工作目录、有序 Compose 文件、env 文件路径和 profiles。持久化使用独立 `docker-management.sqlite` 与版本化迁移，不改变 `servers.db` 当前的不兼容重置策略。保留记录 revision，避免两个窗口互相覆盖关联设置。

关联仅保存路径和设置，不保存展开后的环境变量或认证信息。删除服务器配置时，如仍有关联记录则提示先解除关联；解除关联只删本地记录，不执行远端 down。下次连接发现引擎不同须重新核对关联。

| 操作           | 行为                                                                              |
| -------------- | --------------------------------------------------------------------------------- |
| 项目发现／关联 | 使用 Compose 列表与容器标签发现，允许从远端文件树选择配置；缺失信息由关联表单补齐 |
| 启动已有服务   | 只启动现有服务容器；需要创建时引导应用配置                                        |
| 停止／重启     | 保持与应用配置分开的动作和文案                                                    |
| 应用配置       | 预检配置、profiles、环境文件、服务及影响范围，确认后后台部署                      |
| 更新镜像       | 拉取 → 复核目标镜像／配置 → 确认应用 → 核对容器与健康；不得把拉取成功当部署成功   |
| 停止并移除项目 | 展示容器与网络影响，首版不附带删除卷／镜像／孤立服务                              |
| 项目日志       | 按服务／副本打开现有容器日志窗口；重建后使用新容器 ID，保留旧日志档案             |

Compose restart 不应用配置文件变更。[D4] 界面和命令层都须区分 restart 与 up。down 的资源范围与选项有关，外部卷／网络有独立规则；首版预览严格对应实际传递的选项。[D5]

预览记录配置指纹、关联 revision、服务集合和已解析镜像身份；提交前重新校验，变化则让用户复核。更新镜像后尽可能用已解析 digest／受控覆盖配置固定目标，避免预览后 Tag 移动使部署内容变化。高级参数按实际 CLI 能力探测启用，不仅比较版本字符串。

App 内采用同引擎写操作独占；对 App 外编辑配置和操作 Docker 不宣称事务隔离。配置复查与远端执行不是天然原子操作，执行后也要核对，部分成功按服务反馈。编辑器保存 Compose 文件不会触发自动部署。

### 7.2 从镜像创建容器

新增 `create.rs` 与 `CreateContainerDialog`，表单包含名称、发布端口、环境变量、Bind Mount／已有 Volume、网络、重启策略，以及折叠的命令和工作目录。

实现为“预览 → create → 记录完整 ID → start → inspect”，明确每一阶段。首版只使用已拉取镜像，按解析后的镜像 ID 创建，不在点击创建后隐式启动一轮未确认的镜像拉取。

- 表单与后端都校验端口、名称、路径、挂载模式和网络；环境变量键重复等问题在对应字段展示。
- Bind Mount 使用明确的挂载语义，缺失路径不偷偷创建；网络／Volume 在提交前重新检查。
- create 成功但 start 失败时保留容器，定位对象并提供诊断；不自动删除后重试。
- 创建请求带操作标识，丢失回包后按已记录 ID／创建标识核对，不能仅凭同名对象认领成功。
- 命令以可控参数表示；需要 shell 的行为由用户显式配置，不能把整段表单内容直接作为宿主 shell 执行。
- 环境变量通过仅当前远端用户可读的临时 env 文件传递，避免放进 shell 命令日志；记录清理状态并在失败／断线后处理残留。首版不接受该文件格式无法可靠表达的多行值。

创建和关联草稿不把敏感值写进工作区迁移快照。跨窗口迁移时保留安全字段，敏感字段清空并提示重新填写；已提交的后台任务不受影响。

验收重点：多配置文件顺序、profiles、缺失 env、配置变更、停止项目、服务副本重建、Down 后关联仍在、名称／端口冲突、创建后启动失败、临时文件清理。

## 8. 第四批：空间、卷、网络与批量维护（P2）

### 8.1 空间与资源

在引擎更多菜单增加“空间与资源”，后端 `resources.rs` 提供用量、卷和网络的列表／详情／引用关系；随后加入创建、删除和网络连接／断开。

管理命令继续复用引擎绑定、预览、任务和锁。网络使用完整 ID；Volume 以名称和可取得的创建信息复核，无法证明还是原对象时不继续使用旧删除预览。

### 8.2 分类清理与批量操作

`cleanup.rs` 负责候选计算、确认范围和逐对象执行。优先处理用户明确选择的对象；预览失效后不得把新增候选自动加入原确认。

Docker system prune 会覆盖多种资源，不能直接用它实现“只删除勾选对象”。[D6] 构建缓存等原生按类别清理没有统一的精确候选预览保证，因此单独展示规则与估算，并报告引擎实际返回的结果。未知释放空间显示未知，共享层不按逐行大小相加承诺释放量。

批量动作是父任务加逐项结果，允许部分失败，无整体回滚承诺。删除 Volume 始终独立选择和确认；任何删除失败不自动升级为 force。

### 8.3 容器文件与镜像导入导出

新增 Docker 数据通道适配器，对接现有传输任务展示和本地文件选择。明确数据起点／终点是本机、SSH 服务器还是容器。

Docker cp 可以使用 tar 流，镜像 save／load 也涉及二进制数据。[D7][D8] 这些数据走独立二进制通道，stderr 单独读取，不经过文本命令缓冲，也不把 SFTP 当成容器文件系统。

文件处理复用现有任务的重名、覆盖、取消和进度模式；若涉及本机解包，检查路径穿越、链接和目标边界。只有已知总量时才显示百分比；取消不能宣称远端所有写入已撤回。

验收重点：使用关系变化、预览范围变化、卷数据删除、受保护／内置网络、批量部分失败、大文件背压、断线、中止、tar 异常路径、导入后镜像引用变化。
